# 设计说明

## 1. 完成到哪一步

当前完成的是一个可运行的校园商品前端：

- 商品列表从 Mock API 拉取并渲染，支持前端标题过滤、缺货区分和长标题省略。
- 可以在列表页发布商品，完成前端校验、元转分、成功提示、表单重置和列表刷新。
- 可以在商品卡片直接上架/下架，并对同一商品的连续操作加锁。
- 可以选择购买数量并下单；下单后跳转订单页并重新拉取订单列表。
- 待支付订单可以发起支付宝/微信支付，使用每秒轮询确认状态。
- 商品详情页支持直接访问、返回列表和“商品不存在”提示。
- 已加入 Vitest 单元测试，覆盖金额转换、金额展示兜底和标题清洗。

一句话概括：**我完成了一个能浏览、发布、上下架商品并选择数量下单、支付的前端，同时把金额和标题清洗这类高风险规则固化为单元测试。**

## 2. 我是怎么拆的

| 顺序 | 我做的事 | 为什么排在这个位置 |
|---|---|---|
| 1 | 先读 `mock/server.mjs` 和商品/订单数据，确认返回结构 | 先知道 `data.items`、金额单位和状态枚举，避免把分当元或把对象当数组 |
| 2 | 编写 `src/utils/money.js` 与测试 | 商品展示、发布表单和订单金额都依赖元/分转换，这是贯穿链路的基础 |
| 3 | 编写 `src/api/index.js`，集中基础地址和错误解析 | 所有页面都需要同一套请求行为，先统一可避免重复 fetch 代码 |
| 4 | 做商品列表、卡片和发布表单 | 先验证读取、过滤、发布和刷新闭环，再做写操作与订单链路 |
| 5 | 接入商品上下架 | 该功能只修改单个商品状态，适合在列表链路稳定后补充，并用 ID 级锁防止连点 |
| 6 | 做下单、数量选择和订单列表 | 下单依赖商品 ID 与库存，订单页依赖订单接口；数量选择放在链路稳定后补齐 |
| 7 | 做支付轮询和详情路由 | 支付依赖订单状态，详情依赖商品详情接口，两者都需要额外处理异步生命周期和不存在情况 |
| 8 | 补 Vitest 并做浏览器全链路验证 | 构建通过不代表边界正确，测试和实际点击分别覆盖确定性规则与交互状态 |

这个顺序的核心是先定数据契约，再定公共工具，最后做页面和异步交互。支付放在后面，因为它依赖订单号；详情页也放在后面，因为它需要单独处理直接访问和 404。

## 3. 程序分成哪几块

| 文件或模块 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `src/utils/money.js` | 元转分、分转元、价格展示 | 金额规则必须一致，不能让每个组件自己除以 100 |
| `src/utils/product.js` | 商品标题清洗与兜底 | 异常标题会在列表、订单和详情多处出现，集中处理避免规则漂移 |
| `src/api/index.js` | API 地址、fetch 封装、业务错误解析 | 更换端口时只改常量；HTTP 错误与 `{ code, message }` 错误也能统一处理 |
| `ProductListView.vue` | 拉取商品、搜索过滤、互斥状态、上下架请求锁、页面组合 | 页面只负责列表状态和编排，卡片细节交给子组件 |
| `ProductCard.vue` | 单个商品展示、缺货样式、数量输入、购买与上下架事件 | 卡片可独立复用，父组件不需要关心标题省略和状态徽标 |
| `ProductForm.vue` | 表单状态、字段校验、提交锁和成功反馈 | 将一组输入和校验集中管理，避免列表页变成大文件 |
| `OrderListView.vue` | 订单加载、支付流程、轮询生命周期 | 定时器和订单状态更新是页面级职责，不能散落在卡片中 |
| `OrderCard.vue` | 单条订单展示、支付方式选择、按钮状态 | 只通过 props 和事件与父组件通信，支付控制仍留在页面层 |
| `ProductDetailView.vue` | 按 URL 参数自行请求商品、404 状态、返回入口 | 直接打开详情页不依赖列表传参，刷新和分享链接都能工作 |
| `router/index.js` | 三个页面的 URL 映射 | 页面切换、导航激活和详情 URL 由路由统一管理 |
| `App.vue` | 顶部导航、下单动作、全局 toast、订单刷新 key | 跨页面触发的下单动作和导航提示放在应用壳层，页面只发事件 |
| `money.test.js` / `product.test.js` | 验证金额和标题清洗的确定性规则 | 这些规则边界多，适合用快速、可重复的单测固定下来 |

如果后续增加“退款”和“优惠券”，最先需要扩展的是 API 层的请求语义和订单/支付状态模型，而不是继续把逻辑堆到订单卡片里。支付轮询目前只是订单页的一种动作，未来抽象成独立的支付服务模块会更合适。

## 4. 一次完整链路怎么走

### 商品浏览与筛选

```text
进入 /
  → onMounted 调用 getProducts({ pageSize: 50 })
  → API 返回 { code: 0, data: { items: [...] } }
  → 列表取 data.items
  → 标题通过 normalizeProductTitle() 清理
  → 输入关键词时在 computed 中按标题 includes 过滤
  → 无结果显示“没找到相关商品” + “清空筛选”
```

筛选只改变本地 `filteredProducts`，不会再次请求接口。`loading`、`error`、`empty`、`ready` 由同一个 `viewState` 计算，模板用 `v-if / v-else-if / v-else` 保证互斥。

### 发布商品

```text
填写表单
  → 提交前 validateForm()
  → 校验失败：字段下方显示错误，不发 POST
  → 校验通过：yuanToFen('19.9') = 1990
  → POST /api/products，price 是整数分
  → 成功：toast + 5 个字段重置
  → emit('created')
  → 父组件重新 getProducts({ pageSize: 50 })
```

`submitting` 在请求一开始设为 `true`，直到 `finally` 才恢复；按钮同时 disabled 并显示“提交中…”。这是发布链路的防重复请求锁。

### 商品上下架

```text
点击“上架 / 下架”
  → ProductCard emit('toggle-status', product)
  → ProductListView 计算 nextStatus
  → 将商品 ID 加入 statusUpdatingIds
  → PATCH /api/products/:id/status
  → 成功：用响应 status 更新对应商品，提示“已上架 / 已下架”
  → 失败：显示后端 message
  → finally：移除该商品 ID 的锁
```

锁是 `Set<string>` 而不是单个布尔值，因为不同商品可以独立操作，同一商品不能被重复点击。请求完成后如果组件已卸载，通过 `cancelled` 检查不再更新状态。

### 数量选择与下单

```text
商品卡片选择 1~stock 的数量
  → ProductCard emit('buy', { product, quantity })
  → App.vue handleBuy(payload)
  → 校验 product.id 和正整数 quantity
  → creatingOrder = true，所有购买按钮锁定
  → POST /api/orders，body = { productId, quantity }
  → 后端创建订单并扣减库存
  → ordersRefreshKey += 1
  → router.push({ name: 'orders' })
  → OrderListView 挂载后 getOrders()
  → 从 data.items 渲染，新订单按 id 倒序显示
```

商品卡片在库存变化时会用 `watch(stock)` 把数量钳制在合法范围；详情页同样处理。最终库存是否足够仍以后端为准，前端范围限制只用于减少无效请求。

### 支付轮询

```text
选择 alipay / wechat
  → 点击“去支付”
  → payingOrderId = order.id，相关按钮“支付中…”并 disabled
  → createPayment({ orderId, method })
  → 得到 paymentId
  → 每 1000ms getPayment(paymentId)，最多 10 次
  → processing：继续保持支付中
  → paid：stopPolling + 订单状态改为 paid + 成功提示
  → 达到上限：stopPolling + “支付状态未确认，请稍后在订单列表查看”
  → 离开页面：onUnmounted 设置 cancelled = true 并 clearInterval
```

支付期间 `payingOrderId` 同时承担三件事：标记当前订单、锁定全部支付按钮、驱动“支付中…”文案。已支付订单由 UI 永久禁用；接口层仍然保留重复支付 409 保护，避免绕过 UI 重复请求。

## 5. 防重复提交怎么设计

本项目有三类位置不同的请求锁，不能用一个“全局忙碌”粗暴覆盖全部操作：

| 场景 | 锁 | 作用范围 |
|---|---|---|
| 发布商品 | `ProductForm.submitting` | 防止同一表单重复 POST |
| 上下架 | `ProductListView.statusUpdatingIds` | 只锁正在 PATCH 的商品，其他商品仍可操作 |
| 下单 | `App.creatingOrder` + `orderingProductId` | 创建订单期间锁定全部购买按钮，避免重复订单 |

这三类操作请求语义不同，所以锁粒度也不同。上下架需要按商品 ID 隔离；下单需要全局串行，因为一次点击成功后马上会跳转页面。

## 6. 一个取舍

**商品搜索选择了前端过滤，没有每次输入都请求服务端。**

- 可选方案：前端拿到 50 条商品后按标题过滤 / 每次关键词变化都调用 `GET /api/products?keyword=...`。
- 当前选择：前端过滤。
- 原因：本项目的验收重点是页面状态和标题过滤，商品量由 `pageSize: 50` 控制，前端过滤响应即时、实现简单，也不会出现输入过快导致的请求竞态。
- 代价：商品超过当前页时，前端搜索只能搜到已加载的数据；商品规模变大后需要改成服务端搜索、分页和防抖。

支付状态选择了轮询，而不是 WebSocket 或 SSE。轮询更符合 Mock 服务的简单模型，容易观察 `processing → paid`，也便于验证最多 10 次和卸载清理；代价是支付期间会周期性产生 `GET /api/payments/:id` 请求。生产系统若支付量较大，可以改为推送或更长的退避间隔。

## 7. 卡得最久的问题

**现象：支付开始后离开订单页，定时器如果只清一次，仍可能留下已发出的请求或旧回调，页面切换后还会继续查询支付状态。**

一开始容易只想到“在 `onUnmounted` 里 `clearInterval` 就够了”，但支付请求是异步的：请求可能已经在途，回调返回时组件已经销毁；同时旧轮询和新轮询如果共用同一个 token，也可能出现状态互相覆盖。

最后的处理顺序是：

1. 组件卸载时先把 `cancelled = true`，再调用 `stopPolling()`。
2. `stopPolling()` 先自增 `pollToken`，让已经发出的旧回调失效，再清除唯一的 `pollTimer`。
3. 每次 `getPayment()` 返回后检查 `cancelled` 和 token，不满足就直接返回，不更新状态。
4. 使用 `requestInFlight` 避免上一次请求还没返回时又启动下一次请求。
5. 离开页面后观察 Network 5 秒，确认没有新的 `GET /api/payments`。

这个问题比单纯写“每秒调用一次”更关键，因为验收关注的是组件销毁后的异步副作用，而不只是接口能否返回。

## 8. 测试与验证

### 已提交的自动化测试

`npm test` 使用 Vitest，当前 2 个测试文件、15 个用例：

- `yuanToFen` 覆盖 `0.01`、`19.9`、`12.5`、`1`、`100`、浮点误差和非法输入。
- `fenToYuan` / `formatPrice` 覆盖 0、两位小数、大额展示和 NaN 兜底。
- `normalizeProductTitle` 覆盖 script 标签、HTML 标签、控制字符、零宽字符、正常长标题和空值兜底。

### 临时浏览器验证

使用临时 Playwright 脚本做过一次全链路检查，验证了：

- 列表 24 条、搜索空态、表单字段错误和发布成功刷新。
- 上下架快速连点只产生 1 次 PATCH。
- 数量 2 下单请求和订单列表金额一致，快速连点只产生 1 次 POST。
- 支付过程中 `processing` 不提前成功，最终 `paid`。
- 离开订单页后 5.2 秒内新增支付查询为 0。
- 详情页直接访问和 404 状态。

临时脚本不在仓库中；正式交付时可将其中关键流程迁移为 Vue Test Utils 或 Playwright E2E 套件。

## 9. 没做的事和已知问题

| 项 | 状态 | 原因 |
|---|---|---|
| 下单后列表库存即时回写 | 未做 | 下单成功后跳转订单页；返回商品列表时会重新请求，但不在原列表实例上原地扣减 |
| 分页、服务端搜索 | 未做 | 当前数据量小，先完成本地筛选和核心交易链路 |
| 登录鉴权、图片上传、富文本 | 未做 | 题目未要求，且会扩大安全和数据模型范围 |
| 完整 E2E 测试套件 | 未提交 | 已提交金额和标题清洗单测，临时浏览器脚本不放入仓库 |
| Mock 数据持久化 | 不做 | 题目要求不修改 `mock/`，数据只在内存中，重启会复原 |
| 生产环境 History fallback | 未配置 | 当前主要用 Vite 开发服务器；部署静态服务器时必须配置回退到 `index.html` |
| 标题数据源清理 | 展示层处理 | 不改原始数据，避免修改题目提供的 Mock；展示层只显示清洗后的纯文本 |
