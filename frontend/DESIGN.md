## 2. 我是怎么拆的（最重要）

## 3. 我的程序分成哪几块

| 文件 / 模块                                                    | 负责什么                                | 为什么单独拆出来                                                   |
| ---------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------- |
| `main.js`                                                  | 组合根 + 两个视图状态机（商品 / 订单）              | 只有一个地方决定「现在画加载态、错误态、空态还是数据」，互斥由结构保证                        |
| `api.js`                                                   | 所有 HTTP 请求、统一响应包解包、错误转 `ApiError`   | 换端口只改一处；业务错误统一带上 `status`/`code`，调用方直接显示 `message`         |
| `money.js`                                                 | 分↔元换算、`¥xx.xx` 格式化、单价 × 数量          | 金额是全场唯一口径，必须能脱离 DOM 单测                                     |
| `text.js`                                                  | 展示层清洗（mock 里埋了 `<script>` 标题）       | 安全（一律 `textContent`）和「看到的字」分开：清洗只去噪，不改数据                   |
| `product-status.js` / `order-status.js`                    | 状态枚举 → 文案 / 样式 / 目标状态               | 徽标和按钮都从这一份推导，不会出现「徽标说在售、按钮说上架」                             |
| `product-list.js` / `order-list.js`                        | 两张表格（纯渲染，入参决定一切）                    | 视图不碰请求，才能做到「同一份 state 随时重画」                                |
| `search-box.js`                                            | 搜索输入（防抖 + 回车 + 清空）                  | 三个入口收敛成一个 `onSearch`，重复词的去重也压在这一层                          |
| `publish-form.js` / `purchase-form.js` / `payment-form.js` | 三个弹窗：发布 / 购买 / 支付                   | 各自有独立的校验与提交状态，只通过回调把结果抛给 `main.js`                         |
| `payment-poller.js`                                        | 支付轮询状态机（间隔、上限、停止）                   | 唯一一处「什么时候查、查到什么算成功」；`fetchPayment` 可注入，能直接单测               |
| `toast.js`                                                 | 全页唯一提示条                             | 三个面板 + 列表操作都要提示，各建一条会在同一位置叠起来                              |
| `dom.js`                                                   | `createElement` 封装，显式禁止 `innerHTML` | 商品 24 的标题就是 `<script>alert('xss')</script>`，把「别拼字符串」落成代码约束 |
| `styles.css`                                               | 全部样式                                | 与逻辑分离，改版式不动 JS                                             |
| `tests/*.test.js`                                          | 纯函数与接口层的单测（81 条）                    | 不依赖 DOM，跑得快，改完先看它                                          |

**如果再加「退款」和「优惠券」，最先乱的是这里**：`main.js` 里的 `orderState / payingOrderIds / settledOrderIds` 会继续膨胀，订单表的操作列会变成一串 if。届时应该把「订单」提升成一个自己的 store（`orders-store.js`：数据 + 支付中/已支付/已退款 + 允许的 action），视图只订阅它——现在 `order-status.js` 已经是个小号版本。

## 4. 一次完整链路是怎么走的（支付，L2-10）

```text
订单行点「去支付」
  → 弹窗显示订单号 / 商品 / 应付金额 ¥xx.xx（直接用接口返回的 totalAmount，单位是分）
  → 选支付方式（默认支付宝，另一个是微信）
  → POST /api/payments { orderId, method }
      ├─ 200 { paymentId, status: "processing" }
      │    → onStart：这一行按钮变「支付中…」并 disabled（payingOrderIds 加锁）
      │    → 1 秒后开始 GET /api/payments/{paymentId}，每 1 秒一次，最多 10 次
      │        ├─ processing → 只更新「支付中…（第 n 次确认）」，不报成功
      │        ├─ paid → toast「支付成功：订单号，金额」
      │        │        → 行徽标变「已支付」+ 按钮永久禁用（settledOrderIds）
      │        │        → 重新拉订单列表（服务端状态为准）
      │        └─ 10 次仍 processing → 停轮询，提示「支付状态未确认，请稍后在订单列表查看」，解锁该行
      └─ 409「订单已支付，请勿重复支付」→ 弹窗里原样显示后端 message，按钮恢复

关闭弹窗 / ESC / 点遮罩 / 页面 pagehide
  → poller.stop()：清掉下一个定时器 + abort 正在飞的那个 GET + 丢弃晚到的结果，并解锁该行
```

> 下单链路同构：点「购买」→ 数量校验（正整数）→ `POST /api/orders`（quantity 是数字）→ 201 用返回的 `totalAmount` 展示 → 重新拉商品和订单 → 库存减少、新订单高亮。不再重复画。

## 5. 一个取舍：我选了 A，没选 B

- **可以在哪两个方案里选**：每次操作整表重渲染（单一 state） / 细粒度改 DOM 或引入 Vue、React
- **我选了**：整表重渲染。`render()` / `renderOrders()` 里只有一条路径——加载态 → 错误态 → 空态 → 数据。
- **因为**：状态来源只有一个（`state.items` / `orderState.items`）。「徽标和按钮对不上」「加载中和空态同时出现」「支付成功后按钮又变回可点」这类问题在结构上就不可能出现；上下架、下单、支付之后只要改 state 再 render，不需要手写 DOM 同步。
- **代价是**：每次操作都重建节点，滚动位置和焦点会丢（补了 `focusRow` + `scrollIntoView` 的一部分），上千条数据时性能会明显下降；另外「支付中 / 本会话已支付」这种不在接口数据里的状态必须由页面层记住，一刷新就没了——所以才有 `payingOrderIds` / `settledOrderIds`。

## 6. 我卡得最久的一个问题

- **现象**：单测报 `expected +0 to be null`——单价字段缺失时，购买弹窗的预估总价显示 `¥0.00`，而不是「—」。
- **我一开始以为**：是测试写错了（字段缺失应该抛错，测试却断言返回 null）。
- **试过什么**：① 在 `estimateTotal` 里判 `!unitCents`——但 0 分也是合法输入，会被误伤；② 在视图层判 `total === 0` 就显示「—」——治标，而且会把真正的 0 元也藏起来。
- **最后靠什么定位的**：把断言原文读了两遍。`+0` 说明函数没抛错、而是返回了 0，于是去控制台单独验 `Number(null)`、`Number('')`、`Number.isInteger(0)`。
- **真正的原因**：`Number(null)` 和 `Number('')` 都是 0，`Number.isInteger(0)` 为 true，所以「字段缺失」被当成了「0 分」，一路算出一个看起来完全正常的 `¥0.00`。
- **怎么修的**：`multiplyCents` 先显式挡掉 `null / undefined / ''` 再转数字，并补两条用例（这两种输入必须抛错）。同类风险继续由展示层的 `formatCnySafe` 兜住。
