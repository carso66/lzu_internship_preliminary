# 设计说明

## 1. 完成到哪一步

当前完成的是一个可运行的校园商品前端：

- 商品列表从 Mock API 拉取并渲染，支持前端标题过滤、缺货区分和长标题省略。
- 可以通过独立页面 `/products/new` 上架商品，完成字段校验、元转分、成功提示、表单重置，并展示新商品 ID 与详情入口。
- 可以在商品卡片直接上架/下架，并对同一商品的连续操作加锁；下架商品在列表和详情页都禁止购买。
- 商品列表优先识别明确同款；没有明确同款时，按标准商品类型或具体分类把相近购买意图归为一组。组内仍显示商品编号和卖家名称，缺少 `sellerId` 时只说明无法判定卖家归属。
- 顶部可切换游客、买家、卖家和管理员演示角色；上下架前通过 `canManageProduct()` 判断前端管理权限，无权限时不发请求。
- 可以选择购买数量并下单；全局入口会再次校验正整数、库存异常和库存上限。
- 待支付订单可以发起支付宝/微信支付，使用每秒轮询确认状态。
- 商品详情页支持直接访问、返回列表和“商品不存在”提示；未知路径进入统一 404 页面。
- 路由通过 `meta.title` 和 `router.afterEach()` 更新浏览器标题。
- API 默认走同源 `/api`，可由 `VITE_API_BASE_URL` 覆盖，并由 Vite 代理到 Mock。
- 商品和订单列表通过请求 ID 防止旧响应覆盖新状态，卸载时使在途请求失效。
- 已接入 Vitest、ESLint、Prettier 和 GitHub Actions CI，`npm run check` 串联全部检查；边界与错误测试已扩到 8 个测试文件、89 个用例。

一句话概括：**我完成了一个能浏览、在独立页面发布、按商品归属控制上下架入口并选择数量下单、支付的前端，同时把金额、标题、数量、表单、权限、API 请求封装和路由匹配固化为单元测试，并补齐了 404、动态标题和工程化检查。**

| 10 | 拆出独立上架页并补路由边界测试 | 导航和页面职责更清晰；静态 `/products/new` 与 `/products/:id` 的匹配顺序必须由测试锁定 |
| 11 | 补卖家信息展示、商品编号和前端权限判断 | 同名商品不能靠标题或卖家名识别；卖家归属只能按 `sellerId` 判断，并明确前端权限不替代服务端授权 |
| 12 | 增加相似商品分组与组级权限摘要 | 聚合改善浏览效率，但商品身份、卖家、库存和权限必须独立；权限变化需要页面级、组级和单件商品三处同步呈现 |

这个顺序的核心是先定数据契约，再定公共工具，最后做页面和异步交互。支付放在后面，因为它依赖订单号；详情页也放在后面，因为它需要单独处理直接访问和 404。文档审计放在最后，是因为完成状态、测试数量和已知边界必须以最终代码为准。

## 3. 程序分成哪几块

| 文件或模块 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `src/utils/money.js` | 元转分、分转元、价格展示 | 金额规则必须一致，不能让每个组件自己除以 100 |
| `src/utils/product.js` | 商品标题清洗与兜底 | 异常标题会在列表、订单和详情多处出现，集中处理避免规则漂移 |
| `src/utils/productForm.js` | 商品表单校验、码点计数、分类常量 | 标题/价格/库存/分类/描述规则集中一处，组件与单测共用同一套逻辑 |
| `src/utils/quantity.js` | 购买数量与库存校验 | 输入框的 `min/max` 不是可靠校验，卡片、详情和全局下单入口需要同一套错误文案 |
| `src/utils/permissions.js` | 角色常量、演示会话和商品管理判定 | 游客、买家、卖家和管理员的权限边界必须集中定义；卖家归属只按用户 ID 与 `sellerId` 精确匹配 |
| `src/utils/productGroups.js` | 相似商品展示聚合、卖家信息与价格库存摘要、组级权限三态 | 聚合规则和权限摘要必须可单测；组只用于展示，不能变成新的权限资源 |
| `src/api/index.js` | API 地址、fetch 封装、业务错误解析 | 默认 `/api` 由 Vite 代理，环境差异通过 `VITE_API_BASE_URL` 覆盖；错误解析也只保留一份 |
| `ProductListView.vue` | 拉取商品、搜索过滤、互斥状态、上下架权限预检、请求锁和请求竞态保护 | 页面只负责列表状态和编排，不再承载发布表单；无管理权限时不发 PATCH |
| `ProductCreateView.vue` | 独立上架页、成功反馈、详情入口和继续上架 | 发布流程与列表浏览解耦，导航可单独高亮上架页 |
| `ProductGroupCard.vue` | 聚合组折叠、组头摘要和组级权限展示 | 把“组的概览”和“单件商品的操作”分开，避免聚合后丢失卖家与权限差异 |
| `ProductCard.vue` | 单个商品展示、商品编号与卖家名称、缺货/下架样式、数量输入、购买与上下架事件 | 卡片可独立复用；无管理权限时显示明确提示并禁用上下架按钮 |
| `ProductForm.vue` | 表单状态、五字段校验、描述字数、提交锁和组件内成功提示 | 将一组输入和校验集中管理，页面只消费 `created` 事件 |
| `OrderListView.vue` | 订单加载、请求竞态保护、支付流程、轮询生命周期 | 定时器和订单状态更新是页面级职责，不能散落在卡片中 |
| `OrderCard.vue` | 单条订单展示、支付方式选择、按钮状态 | 只通过 props 和事件与父组件通信，支付控制仍留在页面层 |
| `ProductDetailView.vue` | 按 URL 参数自行请求商品、404 状态、下架禁购、返回入口 | 直接打开详情页不依赖列表传参，刷新和分享链接都能工作 |
| `NotFoundView.vue` | 未匹配路径的统一 404 页面和返回入口 | 路由兜底不应复用业务页面，避免用户看到空白页 |
| `router/routes.js` | 业务页面与 404 路由表，静态路径先于动态参数路径 | 路由表可被单测直接导入，避免页面组件和浏览器 history 干扰匹配测试 |
| `router/index.js` | 路由实例、滚动复位、`meta.title` 和浏览器标题 | 页面切换、导航激活、详情 URL 和标题更新由路由统一管理 |
| `App.vue` | 顶部导航、全局数量/下架校验、下单动作、全局 toast、订单刷新 key | 跨页面触发的下单动作和导航提示放在应用壳层，页面只发事件 |
| `money.test.js` / `product.test.js` / `quantity.test.js` / `productForm.test.js` / `permissions.test.js` / `productGroups.test.js` / `api/index.test.js` / `router/index.test.js` | 验证金额、标题清洗、数量、表单校验、商品归属、聚合权限摘要、API 请求封装和路由优先级 | 这些规则和错误分支边界多，适合用快速、可重复的单测固定下来 |

当前测试仍是单元测试（工具函数、表单校验、商品归属、聚合摘要、API 请求封装和路由匹配），不是组件级测试或端到端测试。组件交互和完整交易链路主要依靠此前临时浏览器验证记录，交付时应继续明确这一边界。

如果后续增加“退款”和“优惠券”，最先需要扩展的是 API 层的请求语义和订单/支付状态模型，而不是继续把逻辑堆到订单卡片里。支付轮询目前只是订单页的一种动作，未来抽象成独立的支付服务模块会更合适。

## 4. 一次完整链路怎么走

### 商品浏览与筛选

```text
进入 /
  → onMounted 调用 getProducts({ pageSize: 50 })
  → 每次加载递增 loadRequestId，只允许最新请求回写
  → API 返回 { code: 0, data: { items: [...] } }
  → 列表取 data.items
  → filteredProducts 先按标题 includes 过滤
  → buildProductGroups(filteredProducts, session) 优先识别明确同款，再按标准类型或具体分类归组
  → 渲染 ProductGroupCard；多商品组默认折叠，单商品组默认展开
  → 组内逐件渲染 ProductCard，卖家、库存、状态和权限不合并
  → 无结果显示“没找到相关商品” + “清空筛选”
```

筛选只改变本地 `filteredProducts`，不会再次请求接口；聚合结果由 `productGroups` computed 派生，不写回商品数组。`loading`、`error`、`empty`、`ready` 由同一个 `viewState` 计算，模板用 `v-if / v-else-if / v-else` 保证互斥。组件卸载或发起新请求后，旧响应会因请求 ID 不匹配而被丢弃。

### 发布商品

```text
进入 /products/new
  → ProductCreateView 渲染 ProductForm
  → 提交前 validateForm()
  → 校验标题、价格、库存、分类和描述
  → 校验失败：字段下方显示错误，不发 POST
  → 描述可为空，最多 200 字，并实时显示 x/200
  → 校验通过：yuanToFen('19.9') = 1990
  → POST /api/products，price 是整数分
  → 成功：组件内 toast + 5 个字段和字段错误全部重置
  → emit('created', product)
  → ProductCreateView 展示新商品标题、ID、查看详情和继续上架
  → 不在此处刷新 ProductListView；之后进入列表页会重新请求
```

`submitting` 在请求一开始设为 `true`，直到 `finally` 才恢复；按钮同时 disabled 并显示“提交中…”。这是发布链路的防重复请求锁。

### 商品上下架

```text
点击“上架 / 下架”
  → ProductCard emit('toggle-status', product)
  → ProductListView 计算 nextStatus
  → canManageProduct(product, session)
  → 无权限：显示提示，不发请求
  → 有权限：将商品 ID 加入 statusUpdatingIds
  → PATCH /api/products/:id/status
  → 成功：用响应 status 更新对应商品，提示“已上架 / 已下架”
  → 失败：显示后端 message
  → finally：移除该商品 ID 的锁
```

锁是 `Set<string>` 而不是单个布尔值，因为不同商品可以独立操作，同一商品不能被重复点击。请求完成后如果组件已卸载，通过 `cancelled` 检查不再更新状态。`ProductCard` 的 `canBuy` 同时要求 `status === 'on'` 且库存大于 0，因此商品下架后数量输入和购买按钮都会禁用，但标题与详情链接仍保留。

### 相似商品、卖家信息与权限边界

- 商品唯一身份是 `id`，不是标题。展示层先按 `spuId` 识别明确同款，再按清洗后的标题匹配标准商品类型，最后仅在分类足够具体时按分类归组；无法可靠识别时每件商品独立成组。组内仍保留每件商品的编号、卖家名称、售价、库存和状态，不做静默合并。
- 组标题不由第一件商品或出现次数最多的标题决定：明确同款优先使用标准类型或共同标题前缀，标准类型和具体分类直接使用固定名称，无法识别时使用该商品清洗后的标题。
- 配件与主商品分开；只有当配件词与标题最前面的主商品词重叠时才排除类型，因此“耳机收纳盒”不并入耳机，而“耳机含收纳盒”仍归入耳机。
- `sellerName` 只是展示字段，不能用于权限判断。卖家管理权限只比较商品的 `sellerId` 与当前会话用户 ID；字段缺失、空白或只有同名卖家时一律拒绝。
- 数字 `42` 与字符串 `'42'` 视为同一用户 ID；展示名称不同不影响按 ID 判定归属。
- 组头的 `sellerCount` 表示按卖家编号或独立商品区分出的卖家信息条数，不因卖家名称相同而合并；`identifiedSellerCount` 只表示有卖家编号的不同卖家数量，不表示实名认证。
- 当前 Mock 的 24 件商品归为 20 组，其中“耳机”2 件、“备考资料”3 件、“教材”2 件，其余多为单件组。固定词表无法覆盖的商品保持独立，这是保守展示策略，也不是后端分类结果。

### 权限变化怎么展示

权限展示分三层，不能让组级摘要替代单件商品操作：

1. **页面级**：汇总当前可见商品的 `manageableCount / totalCount`，用 `全部可管理 / 部分可管理 / 仅浏览` 徽标和一段 `aria-live="polite"` 文本持续说明当前角色与覆盖范围。
2. **聚合组级**：每个组显示 `all / partial / none`。例如卖家只拥有组内 1/3 件商品时显示“部分可管理，可管理 1/3 件”，不能把整个组显示成可管理。
3. **单件商品级**：每张卡片仍根据 `canManageProduct(product, session)` 显示“上架 / 下架 / 无管理权限”，操作处理函数再次校验。

变化规则：

- 角色变化：角色与 `scope` 重新计算；分组键不必变化。
- 会话用户 ID 或商品 `sellerId` 变化：重新计算 `manageableCount` 和 `all / partial / none`。
- 上下架状态变化：管理权限不变，只改变可执行动作和购买/缺货状态。

演示入口位于顶部导航：选择“游客”或“买家”后应看到 `none`；选择“管理员”后应看到 `all`；选择“卖家”并输入编号后，只有商品 `sellerId` 与会话 ID 匹配时才进入 `partial` 或 `all`。当前 Mock 商品没有 `sellerId`，所以卖家模式实际仍为 `none`；`partial` 仅在测试夹具中验证，不能靠伪造页面数据制造“卖家归属已认证”的假象。
- 服务端返回 403：以服务端结果为准，显示错误并重新拉取或刷新权限状态；前端摘要不是安全边界。
- 权限徽标持续可见，不依赖一次性 toast；toast 只补充操作结果。

### 数量选择与下单

```text
商品卡片选择 1~stock 的数量
  → ProductCard emit('buy', { product, quantity })
  → App.vue handleBuy(payload)
  → 校验 product.id、下架状态，并调用 getQuantityError(quantity, stock)
  → 数量非正整数、库存异常或超库存时直接提示，不发请求
  → creatingOrder = true，所有购买按钮锁定
  → POST /api/orders，body = { productId, quantity }
  → 后端创建订单并扣减库存
  → ordersRefreshKey += 1
  → router.push({ name: 'orders' })
  → OrderListView 挂载后 getOrders()，请求 GET /orders?pageSize=50
  → 从 data.items 渲染，新订单按 id 倒序显示
```

商品卡片和详情页在库存变化时会用 `watch(stock)` 把数量钳制在合法范围；全局下单入口仍会再次调用 `getQuantityError()`，不能只信任输入框的 `min/max`。最终库存是否足够仍以后端为准，前端校验只用于减少无效请求。

### 支付轮询

```text
选择 alipay / wechat
  → 点击“去支付”
  → payingOrderId = order.id，相关按钮“支付中…”并 disabled
  → createPayment({ orderId, method })
  → 得到 paymentId
  → 每 1000ms getPayment(paymentId)，最多 10 次
  → processing：继续保持支付中
  → paid：stopPolling + 订单状态改为 paid + 成功提示
  → 达到上限：stopPolling + “支付状态未确认，请稍后在订单列表查看”
  → 离开页面：onUnmounted 设置 cancelled = true 并 clearInterval
```

支付期间 `payingOrderId` 同时承担三件事：标记当前订单、锁定全部支付按钮、驱动“支付中…”文案。已支付订单由 UI 永久禁用；接口层仍然保留重复支付 409 保护，避免绕过 UI 重复请求。

## 5. 防重复提交怎么设计

本项目有三类位置不同的请求锁，不能用一个“全局忙碌”粗暴覆盖全部操作：

| 场景 | 锁 | 作用范围 |
|---|---|---|
| 发布商品 | `ProductForm.submitting` | 防止同一表单重复 POST |
| 上下架 | `ProductListView.statusUpdatingIds` | 只锁正在 PATCH 的商品，其他商品仍可操作 |
| 下单 | `App.creatingOrder` + `orderingProductId` | 创建订单期间锁定全部购买按钮，避免重复订单 |

这三类操作请求语义不同，所以锁粒度也不同。上下架需要按商品 ID 隔离；下单需要全局串行，因为一次点击成功后马上会跳转页面。

## 6. 一个取舍

**商品搜索选择了前端过滤，没有每次输入都请求服务端。**

- 可选方案：前端拿到 50 条商品后按标题过滤 / 每次关键词变化都调用 `GET /api/products?keyword=...`。
- 当前选择：前端过滤。
- 原因：本项目的验收重点是页面状态和标题过滤，商品量由 `pageSize: 50` 控制，前端过滤响应即时、实现简单，也不会出现输入过快导致的请求竞态。
- 代价：商品超过当前页时，前端搜索只能搜到已加载的数据；商品规模变大后需要改成服务端搜索、分页和防抖。

支付状态选择了轮询，而不是 WebSocket 或 SSE。轮询更符合 Mock 服务的简单模型，容易观察 `processing → paid`，也便于验证最多 10 次和卸载清理；代价是支付期间会周期性产生 `GET /api/payments/:id` 请求。生产系统若支付量较大，可以改为推送或更长的退避间隔。

工程化校验选择了“一个命令跑完所有静态与构建检查”：`npm run check` 依次执行 ESLint、Prettier 检查、Vitest 和 Vite 构建，CI 也复用同一命令。代价是每次提交前耗时略长，但能减少“本地单测过了、格式或构建没过”的交付风险。

## 7. 卡得最久的问题

**现象：支付开始后离开订单页，定时器如果只清一次，仍可能留下已发出的请求或旧回调，页面切换后还会继续查询支付状态。**

一开始容易只想到“在 `onUnmounted` 里 `clearInterval` 就够了”，但支付请求是异步的：请求可能已经在途，回调返回时组件已经销毁；同时旧轮询和新轮询如果共用同一个 token，也可能出现状态互相覆盖。

最后的处理顺序是：

1. 组件卸载时先把 `cancelled = true`，再调用 `stopPolling()`。
2. `stopPolling()` 先自增 `pollToken`，让已经发出的旧回调失效，再清除唯一的 `pollTimer`。
3. 每次 `getPayment()` 返回后检查 `cancelled` 和 token，不满足就直接返回，不更新状态。
4. 使用 `requestInFlight` 避免上一次请求还没返回时又启动下一次请求。
5. 离开页面后观察 Network 5 秒，确认没有新的 `GET /api/payments`。

这个问题比单纯写“每秒调用一次”更关键，因为验收关注的是组件销毁后的异步副作用，而不只是接口能否返回。

商品列表和订单列表也存在同类风险：页面重新挂载或用户快速重复触发加载时，较早发出的请求可能最后返回。处理方式是每次加载递增 `loadRequestId`，在成功、失败和 `finally` 中都检查当前 ID，并在卸载时再次递增，确保旧请求无法覆盖新状态。

## 9. 后端接口添加建议

当前前端只对接 `mock/server.mjs`，以下内容是接入真实后端时的建议契约，**不代表后端已经实现**。现有接口路径、字段名和成功响应的 `data` 结构应尽量保持不变，先由后端补齐身份、归属、并发和幂等能力，再考虑扩展页面功能。

### 9.1 统一接口约定

| 项 | 建议 |
|---|---|
| 基础路径 | 保持 `/api`；部署到独立域名时通过 `VITE_API_BASE_URL` 覆盖 |
| 请求格式 | JSON；创建和支付请求使用 `Content-Type: application/json` |
| 成功响应 | 始终返回 `{ "code": 0, "message": "ok", "data": ... }` |
| 业务失败 | 返回非 0 `code`、可展示的 `message` 和 `data: null` |
| HTTP 状态 | `400` 参数错误、`401` 未登录、`403` 无权限、`404` 不存在、`409` 状态或库存冲突、`422` 业务校验失败 |
| 金额 | 全部使用整数分；订单金额由后端根据商品价格和数量计算，不能信任客户端传入的 `totalAmount` |
| 时间 | 使用 ISO 8601 字符串，例如 `2026-11-26T10:00:00+08:00` |
| 分页 | 统一使用 `page`、`pageSize`，返回 `{ items, page, pageSize, total }` |
| 认证 | 使用 `Authorization: Bearer <token>`；请求封装统一注入 token，页面不自行拼请求头 |
| 空响应 | 业务接口不要返回 `204 No Content`，否则当前 `request()` 无法解析 `code`，会被当作失败 |

前端现有的 `request()` 会优先读取 HTTP 错误响应中的 `message`，再检查响应体的 `code` 是否为 0。因此后端的参数错误、库存不足、重复支付和权限拒绝都应给出稳定、可直接展示的中文 `message`，不要把异常堆栈或数据库错误暴露给前端。

建议的通用错误体：

```json
{
  "code": 40301,
  "message": "只能管理自己发布的商品",
  "data": null
}
```

如果前端需要在字段下方显示错误，可增加可选结构 `data: { fields: { title: "标题不能为空" } }`；当前页面暂未使用该结构，接入时再统一扩展。

### 9.2 登录与会话接口

| 方法 | 路径 | 状态 | 说明 |
|---|---|---|---|
| `POST` | `/api/auth/login` | 建议新增 | 登录并返回 token 和当前用户 |
| `GET` | `/api/auth/me` | 建议新增 | 恢复页面时获取当前会话和角色 |
| `POST` | `/api/auth/logout` | 建议新增 | 注销当前 token |

登录请求字段应根据实际账号体系确定，例如 `{ "account": "...", "password": "..." }`。成功返回建议：

```json
{
  "token": "opaque-token",
  "user": {
    "id": "42",
    "name": "张三",
    "role": "seller",
    "sellerId": "42"
  }
}
```

约束：

- `role` 和 `sellerId` 必须由后端根据登录身份返回，前端切换器只能用于演示，不能作为生产授权依据。
- 卖家发布商品时，后端从 token 对应的会话写入 `sellerId`，不接受客户端在商品请求体中指定任意卖家编号。
- 管理员代卖家创建或修改商品时，必须显式记录操作者、目标卖家和操作原因，并写审计日志。
- 生产环境应移除或隐藏顶部的演示角色切换；`GET /api/auth/me` 返回什么身份，页面就展示什么权限。

### 9.3 商品接口

现有接口建议保留：

| 方法 | 路径 | 用途 | 后端必须补充的规则 |
|---|---|---|---|
| `GET` | `/api/products` | 商品列表 | 只返回允许公开展示的商品；分页、筛选参数做白名单校验 |
| `GET` | `/api/products/:id` | 商品详情 | 不存在返回 404；不要因查询参数错误返回 500 |
| `POST` | `/api/products` | 创建商品 | 卖家身份和 `sellerId` 从会话取得；校验整数分、库存和分类 |
| `PATCH` | `/api/products/:id/status` | 上架/下架 | 卖家只能操作自己商品，管理员可操作全部；`status` 只允许 `on/off` |

建议逐步补充的接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/seller/products` | 卖家管理自己的商品，避免把“我的商品”权限混入公开列表参数 |
| `PATCH` | `/api/products/:id` | 编辑标题、分类、描述、库存等；需要版本号或条件更新，防止覆盖并发修改 |
| `GET` | `/api/categories` | 返回后端分类树；前端接入后再取消表单中的分类硬编码 |

建议商品响应在现有字段基础上补充：

```json
{
  "id": "24",
  "spuId": "spu-1001",
  "sellerId": "42",
  "sellerName": "校园数码铺",
  "title": "降噪蓝牙耳机 Pro",
  "price": 19900,
  "stock": 12,
  "category": "数码",
  "categoryPath": ["数码", "耳机"],
  "standardType": "耳机",
  "status": "on",
  "description": "主动降噪，续航 30 小时。",
  "version": 3,
  "createdAt": "2026-11-26T10:00:00+08:00",
  "updatedAt": "2026-11-26T10:00:00+08:00"
}
```

`spuId`、`categoryPath` 和 `standardType` 用于稳定相似商品分组，但商品唯一身份仍然是 `id`。`sellerName` 只用于展示，不能参与权限判断；权限只比较后端返回的 `sellerId` 与会话用户 ID。当前 Mock 商品没有 `sellerId`、`spuId`，所以接入真实数据后需要重新跑卖家归属和聚合测试。

库存和状态写入必须由数据库事务或条件更新保证原子性，不能采用“先查库存、再单独扣减”的非原子流程。建议至少做到：

```text
库存：UPDATE product SET stock = stock - quantity
      WHERE id = ? AND status = 'on' AND stock >= quantity
状态：更新时校验 sellerId 和 version，冲突返回 409
```

### 9.4 订单与支付接口

现有接口继续使用：

| 方法 | 路径 | 用途 | 后端必须补充的规则 |
|---|---|---|---|
| `POST` | `/api/orders` | 创建订单 | 从会话取得买家；原子扣减库存；后端计算总金额 |
| `GET` | `/api/orders` | 订单列表 | 普通用户只能查看自己的订单；管理员可按权限查看全部 |
| `GET` | `/api/orders/:id` | 订单详情 | 校验订单归属，不能只凭订单 ID 返回 |
| `POST` | `/api/payments` | 创建支付单 | 校验订单归属和状态；重复请求返回同一结果 |
| `GET` | `/api/payments/:paymentId` | 查询支付状态 | 校验支付单归属；轮询接口不要产生新支付单 |

建议订单字段至少包含 `buyerId`、`sellerId`、`productId`、`quantity`、`unitPrice`、`totalAmount`、`status`、`createdAt` 和 `paidAt`。当前前端使用的订单状态是 `created/paid`，支付状态是 `processing/paid`；新增 `cancelled`、`failed`、`refunded` 等状态时，必须同时更新 `OrderCard.vue` 的状态文案、按钮禁用条件和 `OrderListView.vue` 的轮询终止条件。

创建订单和创建支付建议支持幂等键：

```http
POST /api/orders
Authorization: Bearer <token>
Idempotency-Key: <uuid>
Content-Type: application/json

{ "productId": "24", "quantity": 2 }
```

后端规则：

- 同一个用户、同一个幂等键和同一个请求体重复提交时，返回第一次创建的订单，不重复扣库存。
- 同一个幂等键但请求体不同，返回 409。
- 支付单幂等键建议由前端在用户点击支付时生成；用户重复点击不能生成两笔支付。
- 库存不足、商品下架、订单已支付和重复支付都应返回明确的 409，而不是 500。
- `POST /api/orders` 成功后返回订单实体；`POST /api/payments` 返回 `paymentId`、`orderId`、`amount`、`method` 和 `status`，保持当前前端字段名不变。

当前前端会在创建支付后每秒轮询，最多 10 次。如果后端引入异步支付回调，建议让 `GET /api/payments/:id` 成为只读状态查询，不要在查询接口里隐式创建新的支付单或重复扣款。

### 9.5 相似商品聚合接口的边界

当前聚合完全在前端完成，后端第一阶段不需要新增聚合接口。建议先通过商品响应补充 `spuId`、`categoryPath` 和 `standardType`，让前端现有 `buildProductGroups()` 能获得更稳定的数据。

只有在商品量变大、必须服务端分页后再考虑：

```http
GET /api/product-groups?keyword=耳机&page=1&pageSize=20
```

建议响应结构：

```json
{
  "items": [
    {
      "groupKey": "spu-1001",
      "title": "耳机",
      "reason": "spu",
      "itemCount": 3,
      "items": [
        { "id": "24", "sellerId": "42", "sellerName": "校园数码铺", "price": 19900, "stock": 12 }
      ]
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

聚合接口只能返回展示分组，不能把多个商品合并成一个可交易实体：

- 每个 SKU 仍然保留独立 `id`、`sellerId`、库存、价格和上下架状态。
- 组头可以显示最低价、最高价、商品件数和卖家信息数，但不能代替单件商品的购买或管理操作。
- 组级权限摘要只能由逐件权限计算得出，不能由组标题、卖家名称或 `groupKey` 推导。
- 后端分页时，同一 `groupKey` 的商品不能被拆到无法正确合并的多个页；否则应分页后再分组，或返回稳定的分组游标。
- 没有可靠 `spuId` 或分类信息时，宁可让商品独立成组，也不要为了“看起来聚合”而错误合并。

### 9.6 权限矩阵建议

如果继续沿用当前单角色演示模型，建议后端按下面的矩阵执行最终授权：

| 操作 | 游客 | 买家 | 卖家（本人商品） | 卖家（他人商品） | 管理员 |
|---|---|---|---|---|---|
| 浏览商品、查看详情 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 发布商品 | 拒绝 | 拒绝 | 允许 | 允许 | 允许 |
| 上架/下架 | 拒绝 | 拒绝 | 允许 | 拒绝 | 允许 |
| 创建订单、支付 | 拒绝 | 允许 | 拒绝 | 拒绝 | 允许 |
| 查看订单 | 拒绝 | 仅本人 | 拒绝 | 拒绝 | 允许 |
| 管理全部商品和审计 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 允许 |

说明：

- 上表是建议模型，不是当前前端已经具备的安全能力。当前前端只实现了商品管理权限演示，下单入口并未按角色做完整的服务端授权。
- `sellerId` 必须来自服务端会话；前端传入的角色、卖家编号和商品归属都不能作为可信依据。
- 卖家只能管理 `product.sellerId === session.userId` 的商品；`sellerName` 相同不算同一卖家。
- 管理员越权操作应写审计记录，至少包含操作者、操作类型、目标资源、变更前后值和操作时间。
- 如果产品允许“卖家也作为买家下单”，应把买卖能力拆成 `capabilities` 或独立权限，而不是继续依赖单一 `role` 字段。

### 9.7 前后端接入顺序

1. 先冻结响应包裹、金额单位、商品/订单/支付字段和状态枚举。
2. 实现登录、`GET /api/auth/me` 和统一 token 注入，替换前端 `DEMO_SESSION`。
3. 实现商品写入归属校验，确保卖家只能发布和管理自己的商品。
4. 实现订单原子扣库存、订单归属校验和支付幂等。
5. 在商品响应中补充 `sellerId`、`spuId` 和分类字段，再决定是否需要服务端聚合接口。
6. 更新 `src/api/index.js`、文档和测试，最后再做组件级和 E2E 验证。

### 9.8 后端接口验收条件

- 未登录访问写接口返回 401，普通用户越权返回 403，且错误 body 有可展示的 `message`。
- 卖家无法上下架他人商品；管理员可以操作，并产生审计记录。
- 同一幂等键重复创建订单不会重复扣库存，超出库存返回 409。
- 订单列表和支付查询不会返回其他用户的数据。
- 创建订单时伪造 `totalAmount` 或 `sellerId` 不影响后端计算结果。
- 商品下架后不能下单，重复支付返回 409。
- 商品响应包含稳定的 `id`；聚合前后单件商品的数量、库存、卖家和权限均不丢失。
- 前端 `npm run check` 通过，并补充至少一组真实后端接口联调记录。
