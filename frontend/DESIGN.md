# 设计说明（DESIGN）

---

## 1. 我做到了哪一步

- [x] L0：5 条全通
- [x] L1：4 条全通（下单 / 订单列表 / 金额 / 校验）
- [ ] L2：没做

**一句话**：我做了一个校园二手市集的前端，能发布、搜索、上下架、下单、看订单，但**还不能支付** —— 订单表里「待支付」永远不会变绿，原因见第 7 节。

有一点要说明：防重复提交（L2-11）我是**顺手做掉的**，不是选的 L2 项。因为我连点两次购买时第一次请求还没回来，会重复下单，所以加了 `submitting` 守卫，后来对照 README 才发现正好是它的四条验收。

## 2. 我是怎么拆的（最重要）

| 顺序 | 我做的事 | 为什么排在这个位置 |
|---|---|---|
| 1 | 先起 mock，`curl` 把 5 个接口各打一遍 | 才知道返回是 `{code,message,data}` 三层壳、商品数组在 `data.items` 而不是 `data`。靠猜会写成 `data[0]`，直接白屏 |
| 2 | 先写 `money.js` / `client.js` / `constants.js` | 金额换算和分类数组全站共用，先定死一份，避免"这个组件 19.9、那个组件 1990" |
| 3 | 先写**写死数据**的列表，确认能渲染 | 页面空白时能一眼分清是渲染错还是请求错。一上来就接接口，两个错会叠在一起 |
| 4 | 换成真实请求 + 加载态 | 第 3 步通了才值得接接口 |
| 5 | 发布表单（先能提交，再加校验） | 要先有表单才知道哪几个字段需要判 |
| 6 | 上下架、搜索空态 | 独立、不依赖别人，放一起做掉 |
| 7 | **下单排在订单列表前面** | 订单数据是下单产生的。先做列表只能看种子数据，验不出"新单出现在最上面" |
| 8 | 订单列表 | 最后做，因为它能回头验证金额口径和下单真的落库了 |

**顺序上踩的坑**：第 1 步我一开始跳过了，直接凭 README 的字段表开写，把 `data.items` 写成 `data`，页面空白查了十几分钟。回去补 curl 之后基本没再为"数据长什么样"卡过。

## 3. 我的程序分成哪几块

| 文件 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `api/client.js` | 发请求、剥 `{code,message,data}` 壳、`code!==0` 就 `throw` | 换地址只改一处；组件层永远只拿到干净业务数据 |
| `utils/money.js` | `fenToYuan` / `yuanToFen` | 金额口径最容易写歪，必须只有一份 |
| `constants.js` | `CATEGORIES` | 两个下拉都要用它，写两份以后加分类必漏一处 |
| `App.vue` | **唯一持有数据的地方** | 见下面的流向 |
| `ProductList.vue` | 渲染 + 转告事件，自己不判断 | 它不拥有 `products`，没权改 |
| `BuyPanel.vue` | 每张卡片的下单行 | 数量和按钮状态每张卡独立，不拆就 24 个商品共用一个 `quantity` |
| `PublishForm.vue` | 发布 + 本地校验 | 校验规则和字段绑死 |
| `OrderList.vue` | 订单表格，纯展示 | 只有 `defineProps`，一个 `emit` 都没有 |

数据的流向是**谁拥有数据，谁负责更新**：`BuyPanel → ProductList → App`，`App` 下面的组件没有一处自己调过 `api.listProducts()`。这条不是我设计的，是被第 6 节那个 bug 逼出来的。

**再加「退款」和「优惠券」，哪里最先乱？**

- **优惠券 → 金额计算散在三个地方**：`PublishForm` 的 `yuanToFen`、`BuyPanel` 的 `totalFen = price × quantity`、`OrderList` 的 `fenToYuan(totalAmount)`。真正的风险不是"要改三处"，而是前端算的必须和服务器一模一样 —— 前端减 5 元、服务器减 3 元，用户看到预估 ¥12.00 实际扣 ¥14.00。这种不一致比报错难查，因为它不崩，只是数字不对。
- **退款 → 订单状态写死在展示组件里**。`OrderList.vue` 里是一张 `const STATUS_TEXT = { created: '待支付', paid: '已支付' }`，加 `refunding` 要改它。更麻烦的是 `OrderList` 现在一个 `emit` 都没有，是纯展示组件，加"申请退款"按钮等于要把它从"只进不出"改成"能往上发事件"。

## 4. 一次完整链路是怎么走的

选下单：

```
卡片数量框输入 "3"
  → computed valid：/^\d+$/ 且 >0 ？
      ✗ 红字「购买数量必须是正整数」，合计显示 —，一个请求都不发
      ✓ totalFen = 199 × 3 = 597 分 → 显示 ¥5.97
  → 点「购买」：submitting=true，按钮禁用变「提交中…」
      （此刻再点第二下，if (submitting.value) return 直接忽略）
  → POST /api/orders { productId: 6, quantity: 3 }   ← 数字 3，不是字符串 "3"
  → 201：数量重置回 '1'（不重置用户以为没点上，再点就重复下单）
      → emit('ordered', {orderNo}) → ProductList 原样往上转一层
      → App：notice = 订单号 → await Promise.all([search(), loadOrders()]) 并发
  → 409：client.js 把后端 message 原样 throw → 红字「库存不足」
      → finally submitting=false（失败也要解禁）
```

`orderNo` 用的是服务器返回的，不是我前端拼的 —— 前端拼的单号和后端对不上是迟早要炸的。

## 5. 一个取舍：我选了 A，没选 B

### 取舍一：成功提示放 App，不放卡片

- **可以选**：A `BuyPanel` 自己显示绿字 / B 订单号带到 `App`，由 `App` 显示
- **我选 B**
- **因为**：下单成功必须重拉列表，重拉让 `loading=true`，`ProductList` 的 `v-if="loading"` 分支成立，**整个列表被销毁重建**，卡片里的本地状态活不过那一瞬。`App` 永远不销毁。
- **代价是**：事件链多穿一层，`ProductList` 纯粹在转告，看着有点绕。

### 取舍二：本地校验只判格式，库存够不够交给服务器

- **可以选**：A 只判格式 / B 库存 0 就把购买按钮禁用
- **我选 A**
- **因为**：我手上的 `stock` 是上一次拉列表时的快照，别人买完就过期了，我在前端拦的是"我以为的库存"。
- **代价是**：用户点了才知道买不了。

这条页面上**看得见**：已下架商品的「购买」按钮是可点的，看着像 bug，是我故意留的 —— 点下去返回 `409 商品已下架`，红字直接显示。禁用它就等于在 `BuyPanel` 里重写一遍后端规则。

## 6. 我卡得最久的一个问题

- **现象**：点「购买」，库存确实减了、订单确实生成了，但界面上那句「下单成功，订单号 SO…」不出来。而失败的红色提示一直好好的。
- **我一开始以为**：CSS 颜色不对，或者 `emit` 没触发。两个都是猜，没有一个先验证过。
- **试过什么**：
  1. **先 grep 了一遍文件，确认代码到底在不在。** 结果 `success` 这个标识符一个都没有 —— 问题根本不是"代码坏了"，是之前 AI 平台给的改动**压根没落进文件**。这一步我该一开始就做。
  2. 补上之后还是不出现。这次代码确实在文件里，所以是行为问题。
  3. 拿"红字能看到、绿字不能"这个差异当线索去查。这个差异不是我主动发现的，是对比失败路径时冒出来的，回头看它本来就是破案钥匙。
- **最后靠什么定位的**：**看 mock server 的控制台日志，不是看前端。** 日志里每次 `POST /api/orders -> 201` 后面紧跟一次 `GET /api/products`，这才反应过来是我自己在成功后调了 `search()`。
- **真正的原因**：**`v-if` 是销毁，不是隐藏。** `loading` 变 true → 整个列表（包括每个 `BuyPanel`）被卸载销毁 → 卡片里的 `success` ref 跟着没了，刚赋的值活不过这一瞬。三个现象一次全解释通：

  | 情况 | 会不会重拉列表 | 组件会不会销毁 | 提示能不能看到 |
  |---|---|---|---|
  | 下单成功 | 会 | 会 | ❌ |
  | 下单失败 | 不会 | 不会 | ✅ 红字正常 |
  | 发布成功 | 会，但表单不在 `v-if` 分支里 | 不会 | ✅ 绿字正常 |

- **修的方式**：提示移到 `App.vue` 的 `notice`，`orderNo` 通过事件带上去。原则是**谁不会被卸载，提示就放谁身上**。

（另一个低级错误：`<style scoped>` 我贴进 `<template>` 一次、贴进 `<script setup>` 一次，同一个错犯了两次。后来每次改完跑一遍 `npx vite build` 当语法检查，十几秒就能抓出来。）

## 7. 没做的事和已知问题

| 项 | 状态 | 原因 |
|---|---|---|
| L2-10 支付链路 | 没做 | 感觉有难度，也有时间问题。本身对这个前端的知识掌握一般，也想止步于此，先回头把项目内容弄懂 |
| L2-12 Vitest | 没做 | 没时间 |
| L2-13 响应式 / 路由 | 没做 | 没时间。商品列表是 `auto-fill` 流式列数，窗口窄会自动变单列，但没做断点适配，375px 下订单表格应该会横向溢出 |
| 分页 | 没做 | 种子 24 条，`pageSize` 传 50 一次拉完 |

### 三个已知问题，照实写

**① 「待支付」永远不会变绿 —— 这是预期，不是 bug。**
后端是被动结算：只有前端去 `GET /api/payments/:id` 且距发起超过 2500ms，服务器才在这次请求里把 `processing → paid` 并同步订单。我没做支付，所以没有请求会触发这个翻转。评审看到橙色徽标以为是 bug 的话：它确实不是 bug，是缺了 L2-10。

**② 故障注入打开时，空态那句话是错的。**
`ERROR_RATE` 让请求随机失败时，列表挂了页面显示"没找到匹配的商品" —— 这句话是错的，实际是请求失败不是没数据。因为 `search()` 的 `catch` 只做了 `console.error`，没把错误状态传到组件，也没有重试按钮。明确知道、没时间修。

**③ 标题框故意没加 `maxlength="50"`。**
加了就打不出 51 个字，L1-9「超长要拦下来」在页面上根本演示不出来。所以让它能超，靠 `validate()` 报错「标题最多 50 个字，当前 51 个」，把实际长度告诉用户而不是悄悄截断。
