# 设计说明（DESIGN）

## 1. 我做到了哪一步

- ✅ L1：4 / 4 条（下单、订单列表、金额处理、表单校验）

总结：**我做了一个单页的商品市集，能列表、发布、上下架、下单并查看订单，金额从输入到展示全程不出错，但支付轮询和商品详情路由还没做。**

## 2. 我是怎么拆的

| 顺序 | 我做的事                                           | 为什么排在这个位置                                                                   |
| -- | ---------------------------------------------- | --------------------------------------------------------------------------- |
| 1  | 先起 `mock/server.mjs`，读 `db.json` 的真实字段         | 不看真实数据就不知道该建什么结构。这一步还发现了题目埋的边界：超长标题、`<script>` 标题、`9999999` 分的大额、库存 0、已下架商品 |
| 2  | 先定金额口径，写 `money.js` 并单独跑边界值                    | L0-2、L1-8、L2-12 全靠它。口径定错后面每条都要返工，所以放在任何页面代码之前                               |
| 3  | 写 `api.js` 统一解包 `{code,message,data}`          | 题目明确要求业务错误要显示 `message`。集中一处，后面每个页面都不用重复处理 HTTP/业务码                         |
| 4  | 写 `server.mjs`：静态服务 + `/api` 代理 + 自动拉起/复用 mock | 先保证「一条命令能跑」，否则 F12 里会把跨域、端口写错和真正的代码 bug 混在一起排查                              |
| 5  | 列表渲染（L0-1），一次取 `pageSize=50`                   | 列表是唯一「读」链路，先验证请求→解包→渲染通了，再往上面加写操作                                           |
| 6  | 发布 + 校验 + 成功反馈（L0-2/3、L1-9）                    | 发布是写入口，依赖列表已就绪；校验放在发请求之前，才能做到「失败不发 POST」                                    |
| 7  | 上下架（L0-4）                                      | 和发布同属商品写操作，复用同一份 `state.products` 与渲染函数                                     |
| 8  | 加载态 / 空态 / 三个筛选条件（L0-5）                        | 这是对已有列表的状态补全，放最后才能验证「加载时空态不出现」的互斥                                           |
| 9  | 下单 + 订单列表 + 预估金额（L1-6/7/8）                     | 下单依赖商品列表里的 `id` 和 `price`，订单列表依赖下单产生的数据，所以必须在列表之后                           |
| 10 | 防重复提交 + Vitest（L2-11/12）                       | 都是对已有代码的加固：前者给下单按钮加状态锁，后者把已稳定的 `money.js` 固化成测试                             |

**关键判断**：把「金额口径」和「请求解包」放在页面之前，是因为它们被 4 条以上验收项共用；反过来若先堆页面，等发现 `19.99*100` 有浮点误差或 `message` 没显示时，要改的是每一处调用点。

## 3. 我的程序分成哪几块

| 文件 / 模块                | 负责什么                                                      | 为什么单独拆出来                                             |
| ---------------------- | --------------------------------------------------------- | ---------------------------------------------------- |
| `server.mjs`           | 静态文件服务、`/api/*` 反向代理、检测并自动拉起/复用 mock                      | 端口和跨域问题集中在一处；页面永远只写相对路径 `/api/...`，换端口只改环境变量         |
| `src/money.js`         | `toFen()` / `formatYuan()` / `estimateTotal()`            | 纯函数、零 DOM 依赖，所以能被 Node 直接 import 做单测；发布、列表、订单、预估四处共用 |
| `src/api.js`           | 拼 `/api` 前缀、统一 `fetch`、解包响应、把业务错误抛成 `Error`               | 换地址只改一处；业务 `message` 保证不会漏显示                         |
| `src/app.js`           | 状态（`products` / `orders` / `loading` / `filters`）、渲染、事件委托 | 状态集中，加载态与空态才能严格互斥                                    |
| `src/styles.css`       | 布局、徽标、灰化、375px 响应式                                        | 样式与结构分离；长标题省略、库存 0 灰化都是纯 CSS                         |
| `tests/money.test.mjs` | 12 条金额边界断言                                                | 金额是最容易翻车的地方，单独固化                                     |

**如果再加「退款」和「优惠券」，哪里会最先乱掉**：`app.js`。现在订单状态映射、金额预估、按钮禁用状态、商品行渲染都在这一个文件里；加了退款要改订单状态，优惠券要改金额计算，两处都会挤进 `buy()` 和 `renderOrders()`。下一步会拆出 `orders.js`（订单状态机）和 `ui.js`（纯渲染函数），让 `app.js` 只做编排。

## 4. 一次完整链路是怎么走的

选「下单」这条（最满意，因为它串起了校验、金额、事务结果和状态恢复）：

```
用户改数量 → input 事件用 money.js 算出「预计 ¥xx.xx」并就地显示
  → 点「购买」→ 立即 disabled + 文案「提交中…」（防重复提交）
  → quantity 是正整数？ ── ✗ → toast 提示，不发请求
  → POST /api/orders { productId: 3, quantity: 2 }   （quantity 是数字，不是字符串）
  → 201 → 比对 服务端 totalAmount === 前端预估（unitPrice × quantity）
        → toast 成功 + Promise.all(重新拉商品、重新拉订单)
        → 列表里库存减少，订单列表出现新订单（状态「待支付」）
  → 409 "库存不足" / "商品已下架" → toast 直接显示后端 message
  → finally：无论成功失败都恢复按钮（失败也能重试）
```

## 5. 一个取舍：我选了 A，没选 B

- **可以在哪两个方案里选**：原生 HTML + ES Modules（零构建、零运行时依赖） / Vue 3 + Vite
- **我选了**：原生方案
- **因为**：题目明说「选原生的不扣分」，而评审是**照着 SUBMISSION 的命令真的跑一遍**。当前网络下 `npm install` 有卡住/超时的真实风险，零依赖能保证 `npm start` 必定起得来；另外 `npm create vite` 会生成一堆样板文件，反而掩盖自己的判断。测试要用 Vitest 是唯一例外，但它只在 `npm test` 时用到，不影响启动。
- **代价是**：没有组件化和热更新，`app.js` 同时承担状态、渲染和事件绑定，功能一多就会变乱（见第 3 节）；样式全部手写，开发速度比用组件库慢。

**第二个取舍（金额换算）**：`toFen()` 用字符串按小数位拆成整数相加，没用 `Math.round(元 * 100)`。因为 `19.99 * 100 === 1998.9999999999998`，大金额下取整也不可靠。代价是输入格式被限制为纯数字字符串，不能接受 `¥19.99` 或 `1,999` 这类写法——对本题的金额输入框够用。

## 6. 我卡得最久的一个问题

- **现象**：VS Code 里的智能体（Continue）连上之后提问一直不回复，面板没有反应；但密钥、网关和模型名看起来都配好了。
- **我一开始以为**：密钥写错了、网络不通，或者模型名不对。于是反复检查配置、换更短的问题、把同一句话重发，都没用。
- **试过什么**：① 单独确认 API Key 和网关 `https://api.xytoken.xyb2b.com/v1` 能正常联通；② 换问题、重发同一句、反复重试；③ 换不同模型逐个试，发现有的能回、有的依旧空白。
- **最后靠什么定位的**：不再猜，先读 Continue 本地的 `devdata.sqlite`，看到这 22 次请求全部 `tokens_generated = 0`——请求发出去了、计费了、一个字也没产出；再用 `/v1/chat/completions` 拿同一段长问题逐个实测 9 个白名单模型的流式输出，统计每个模型 `content` 与 `reasoning_content` 的字数和首个正文帧，一次就定位到返回格式的差异。
- **真正的原因**：`glm-5.3` 这类推理模型把正文全写进 `reasoning_content`（思考）字段，`content` 为空，而 Continue 只渲染 `content`，所以面板什么都没有。换成实测能直接输出正文的 4 个模型（`qwen3.8-flash` / `deepseek-v4.1-flash` / `MiniMax-M3` / `deepseek-v4-pro`）后恢复正常。**这是工具链的显示格式问题，不是业务代码的 bug**；完整过程和反思写在 `AI_USAGE.md` 第 2、4、5 节。
