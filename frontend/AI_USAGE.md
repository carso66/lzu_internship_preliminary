## 2. 模型选型

在这一轮实现中，我把任务按“确定性实现”和“需要推理的边界问题”分开处理：

| 任务类型 | 我的选择原则 | 实际结果 |
|---|---|---|
| 写页面、组件、CSS 和简单校验 | 优先让助手按现有项目风格直接实现，减少重复劳动 | 商品列表、表单、订单卡片和详情页按现有结构完成 |
| 金额、错误解析、轮询清理 | 先要求解释边界，再检查具体代码和实际行为 | 没有只接受“看起来能跑”的实现，而是检查了整数分、非 2xx 和卸载后的请求 |
| 上下架、数量下单、防重复 | 先明确请求锁的作用范围，再做浏览器请求计数 | 同一商品 PATCH 和快速购买 POST 都通过请求计数验证 |
| 异常标题排查 | 先定位数据，再决定是否改数据源 | 发现是标题字符串中混入标签，最终在展示层清洗，不改 `mock/` |
| 最终验证 | 不只让 AI 写代码，还让它执行测试、构建和浏览器流程 | `npm test` 15/15 通过，`npm run build` 通过，并检查了主要交互 |

本轮对话没有明确记录使用过哪些平台模型，所以不把示例模型名写成事实。若平台日志显示使用了不同模型，应在提交前按记录更新本节。

## 3. 五个具体场景

### 场景 1：确认元转分为什么不能直接用 `parseInt` 或裸 `* 100`

- **我想干什么**：实现 `yuanToFen(yuan)`，保证 `0.01`、`19.9`、`12.5`、`1`、`100` 等输入都变成整数分。
- **我怎么问的**：要求比较 `parseInt`、直接乘 100 和 `Math.round(Number(x) * 100)` 的差异，并说明浮点误差。
- **它给了什么**：指出 `parseInt('19.9')` 会丢掉小数，`parseInt('0.01')` 会得到 0；直接乘 100 在部分小数上会出现 `1989.9999999999998` 一类结果；随后建议先 `Number` 再 `Math.round`。
- **我怎么处理**：采用 `Math.round(Number(raw) * 100)`，同时增加了空字符串和非有限数字的异常处理。
- **怎么确认**：用 Vitest 固化 `0.01 → 1`、`19.9 → 1990`、`12.5 → 1250`、`1 → 100`、`100 → 10000`；`fenToYuan(0)` 返回 `'0.00'`，`formatPrice(0)` 返回 `'¥0.00'`。
- **结论**：采用经过四舍五入的方案，没有使用 `parseInt`，也没有提交未取整的浮点结果。

### 场景 2：统一 API 返回值与 HTTP 错误

- **我想干什么**：让所有页面通过同一层调用接口，并能在调用方用 `try/catch` 显示后端 message。
- **我怎么问的**：要求实现一个统一请求函数，解析 `{ code, message, data }`，并处理 HTTP 非 2xx。
- **它给了什么**：建议集中定义 `API_BASE_URL`，请求后先读取 body，再根据 `response.ok` 和 `payload.code` 分别抛错；HTTP 非 2xx 时优先使用 body 中的 message。
- **我怎么处理**：保留了统一请求函数，API 函数只负责路径、方法和请求体；基础地址只在 `src/api/index.js` 定义一次。
- **怎么确认**：检查了商品、订单、支付相关函数的路径；直接请求已支付订单的支付接口，确认 HTTP 409 与 body message 可被页面按同一逻辑展示。
- **结论**：直接采用，并保持页面对错误 message 的展示逻辑一致。

### 场景 3：检查支付轮询在离开页面后的清理

- **我想干什么**：每秒查询支付状态，最多 10 次；离开订单页后不能继续查询，也不能让旧请求回来修改已销毁组件。
- **我怎么问的**：让 AI 检查轮询实现，重点问“组件卸载时已有请求在途怎么办”“旧定时器回调是否会继续 setState”。
- **它给了什么**：指出只调用 `clearInterval` 不足以处理在途请求；建议增加 `cancelled` 标志、轮询 token、`requestInFlight`，并在 `onUnmounted` 中先标记取消再清理定时器。
- **我怎么处理**：采用 `cancelled + pollToken + clearInterval`，每次异步返回后重新检查页面状态；`processing` 不提前成功，达到 10 次上限提示未确认。
- **怎么确认**：浏览器中发起支付后切换到其他页面，观察 Network，确认 5 秒内没有新的 `GET /api/payments` 请求；实测新增查询为 0。
- **结论**：这是 AI 辅助检查真正有价值的一次；不是让 AI 直接“写一个定时器”，而是让它指出生命周期边界，再由浏览器验证。

### 场景 4：一次被带偏的经历：`{{ }}` 不等于标题内容一定正常

- **它给了什么**：最初实现只保证了标题使用 Vue 的 `{{ }}` 文本插值，认为这样就不会执行脚本。
- **当时为什么信了**：这个判断在安全层面没有错，文本插值确实不会把字符串当作 HTML 执行。
- **怎么发现的**：检查商品列表时发现 `id=24` 的标题显示为 `<script>alert('xss')</script> 二手教材`。虽然没有弹窗，但“奇怪名称”仍然直接展示给了用户，数据质量问题没有解决。
- **最后怎么修的**：新增 `normalizeProductTitle()`，在展示前移除 script/style 内容、HTML 标签、控制字符和零宽字符；列表、订单和详情统一使用该函数。长标题 `id=23` 不删除，仍由 CSS 单行省略。
- **怎么验证的**：重新打开列表和详情，确认页面不弹脚本、标题显示为“二手教材”，同时长标题仍保持省略效果；Vitest 也固化了这些规则。
- **之后怎么改做法**：不再把“没有执行脚本”当作“数据已经正确展示”；安全渲染和数据清洗要分开检查。

### 场景 5：规划上下架、数量下单和正式测试

- **我想干什么**：把此前遗留的商品上下架、购买数量选择、防重复提交和 L2-12 自动化测试补齐。
- **我怎么问的**：先让 AI 对照当前实现和验收项列出未完成项，再按“功能实现 → 单元测试 → 浏览器验证 → 文档同步”的顺序逐步推进。
- **它给了什么**：建议上下架使用按商品 ID 的 `Set` 锁，下单使用全局 `creatingOrder` 锁，数量由卡片传 `{ product, quantity }` 给 `App.vue`，并用 Vitest 先固定金额和标题清洗规则。
- **我怎么处理**：接入 `updateProductStatus()`，增加数量输入和全局下单锁；新增 `money.test.js`、`product.test.js` 与 `npm test` 脚本。
- **怎么确认**：快速连点上下架只产生 1 次 PATCH，快速连点购买只产生 1 次 POST；数量 2 的请求体和订单金额一致；`npm test` 为 2 个文件、15 个用例全部通过。
- **结论**：功能实现和自动化验证分开完成；临时浏览器脚本用于补充交互链路，不伪装成已提交的 E2E 套件。

## 4. 我用 AI 做验证的一次

除了让 AI 写代码，我还让它做实际检查：

- 运行 `npm test`，确认金额和标题清洗规则可重复通过。
- 运行 `npm run build`，确认生产构建没有模板或打包错误。
- 检查 `ProductListView` 的 loading/error/empty/ready 是否互斥。
- 检查订单页轮询是否在 `processing` 时提前成功，以及离开页面后是否停止请求。
- 检查 `/products/1` 直接打开和 `/products/9999` 的异常路径。
- 用浏览器实际点击发布、上下架、数量下单、支付和详情入口，并记录请求次数。

其中最有价值的是支付轮询和防重复请求检查：一个验证卸载后的在途请求不会继续轮询，另一个验证快速连点不会产生重复 PATCH/POST。

## 5. 成本与使用边界

| 问题 | 我的回答 |
|---|---|
| 有没有一次把整个项目或整个文件塞进去？ | 没有把 `node_modules` 或无关文件塞进上下文；读取和修改都集中在当前前端相关文件。 |
| 有没有同一个报错连续问很多次？ | 没有形成同一报错反复多轮的循环；发现问题后优先定位具体文件和边界，再重新验证。 |
| 如果额度只有 10 元，会怎么调整？ | 优先保证金额、API、商品列表、表单、上下架、订单支付主链路和关键单测；样式优化、分页和大范围重构放在后面。 |
| 哪些问题不值得问 AI？ | 已经能通过一次测试、构建或 Network 观察确认的简单语法问题、纯样式微调，以及没有具体错误信息的主观偏好问题。 |
