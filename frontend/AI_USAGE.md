## 2. 模型选型（6 分，重点）

**我全程只用一个模型，这是我做的选择，不是没想过换。**

| 我用它做什么 | 用的模型 | 为什么选这个 |
|---|---|---|
| 起骨架、写 Vue 组件、写 CSS、补注释 | 同一个（Copilot 默认模型） | 这类活是「照着需求翻译」，不需要多强的推理，换更贵的模型省不下时间 |
| 设计表结构 / 校验顺序 / 异常映射 | 同上 | 这个项目只有 1 张表、5 个接口，复杂度没到需要「一次想清因果」的程度，我自己先把约束列在纸上，再让它落成代码 |
| 排查 `mvnw` 失败、8080 端口占用、Vite proxy | 同上 | 这类问题主要靠**读到正确的报错原文**，不是靠模型更强。模型换贵的也读不到我终端里的日志，还是得我自己贴 |

**为什么不换档**：我试过一次把整个 `backend/src` 丢进去让它「整体 review」，结果它给的建议一半是
「可以加 Lombok」「可以用 JPA」——都是换个技术栈的建议，对我当下的问题没用，反而消耗了大量上下文。
那次之后我改成**只贴相关的那 30~50 行**，一个模型反而更稳。项目体量小，换模型的收益被我
「重新组织上下文」的成本吃掉了。

**如果这个项目再大一倍，我会怎么分档**：简单的样式和正则继续用便宜档；
「事务边界 / 并发 / 状态机」这类需要一次想清因果的，会换更强的模型；
「看不懂的长报错」会换长上下文的模型，一次把相关文件全塞进去。

## 3. 挑 4 个场景写下来（5 分）

### 场景 1（成功）：手写 `schema.sql` 并验证约束

- **我想干什么**：按接口约定手写建表语句，字段类型要和「价格存分」对得上，并且能重复执行。
- **用的模型 / 为什么选它**：默认模型。这是一段有明确规范的 DDL，不需要推理。
- **我怎么问的**（精简后）：
  > 「按这个接口约定手写 schema.sql：商品字段 id/title/price/stock/category/description/seller_name/status/created_at。
  > price 单位是分（整数），status 只有 on/off，category 限定 5 类。要求脚本能重复执行。」
- **它给了什么**：`DROP TABLE IF EXISTS` + `CREATE TABLE`，加了 `CHECK` 约束
  （`price >= 0`、`stock BETWEEN 0 AND 999`、`status IN ('on','off')`、`category IN (...)`）和默认值。
- **我改了吗、为什么改**：改了。它给的 `title VARCHAR(255)`，但接口约定里标题上限是 **50 字**，
  我改成 `VARCHAR(50)`。另外它没写 `created_at` 的默认值，我补了 `DEFAULT CURRENT_TIMESTAMP`。
- **怎么确认改对了**：把 `schema.sql` 连续执行两次，第二次不报错；再用 14 条约束用例
  （空标题、负数价格、`stock=1000`、`status='unknown'`、非法分类等）逐条插，全部被拒绝。
- **结论**：改了之后用。

### 场景 2（失败）：`RETURN_GENERATED_KEYS` 在 H2 下炸

- **我想干什么**：`POST /api/products` 插入后要返回自增 id。
- **用的模型 / 为什么选它**：默认模型，因为这是标准 JDBC 写法，我以为一问就完。
- **我怎么问的**：
  > 「Spring JDBC 插入后怎么拿到自增主键？用 GeneratedKeyHolder。」
- **它给了什么**：标准答案——
  ```java
  jdbc.update(con -> {
      PreparedStatement ps = con.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS);
      ...
  }, keyHolder);
  long id = keyHolder.getKey().longValue();
  ```
- **我改了吗、为什么改**：**被迫改了**。这段写法在 H2 上直接抛
  `InvalidDataAccessApiUsageException: The getKey method should only be used when a single key is returned.
  The current key entry contains multiple keys: ...`。
  原因是 H2 在 `RETURN_GENERATED_KEYS` 下会**返回整行所有列**，`keyHolder` 里有 9 个 key，不是一个。
  改成 `con.prepareStatement(sql, new String[]{"id"})`（显式指定只返回 id 列）才正常。
- **怎么确认改对了**：`ProductCreateTests` 里断言 `201` 且 `data.id` 是非空正整数；连发 3 次，id 递增。
- **结论**：**它给的是对的「通用写法」，但在 H2 上是错的**。这个坑教科书里不会写，只有真跑了才知道。
  这也是我后来加 `data.sql` 之后坚持每次重启后端都跑一遍全流程的原因。

### 场景 3（我自己改的）：前端 `sellerName` 补齐

- **我想干什么**：把前端从 mock 切到直连后端。
- **用的模型 / 为什么选它**：默认模型，因为我以为这是「改个地址」的事。
- **我怎么问的**：
  > 「前端现在走 mock 3001，改成直连 8080 的 Spring Boot。」
- **它给了什么**：改了 `vite.config.js` 的 proxy target，其他基本没动，说「这样就通了」。
- **我改了吗、为什么改**：改了，而且发现**根本不止改地址**。切过去后发布商品一直 400，
  看响应体是 `40001 sellerName 不能为空`。对比才发现差异：
  - mock：忽略 `sellerName`，固定返回 `'我'`
  - 后端：`sellerName` **必填**，缺失直接 400

  这个差异光看「接口约定文档」看不出来（文档里两个都写 `string`）。我在 `api/products.js` 里
  加了 `DEFAULT_SELLER_NAME = '我'`，`createProduct` 显式构造 body 补齐这个字段，
  并在 `products.test.js` 里写了断言锁住「请求体字段集合必须精确等于 6 个字段」。
- **怎么确认改对了**：`npm test` 69 条通过（含这次新加的 7 条接口契约测试和 11 条路由测试）；
  浏览器里发布「二手无线鼠标」→ 201 → 列表从 24 变 25 → 刷新后还在。
- **结论**：**它给的方案是对的但不完整**。AI 只会改我明确说的那一处，
  「mock 和后端行为不一致」这种事它不会主动去比对，得我自己拿两边真实响应 diff。

### 场景 4（必答）：我用 AI 做验证的一次

- **我问了什么**：我把 `ProductCreateRequest.parse` 的校验代码和 `ProductService.create` 贴给它，问：
  > 「这是我的发布商品校验和写入。帮我列出这个接口的边界情况，特别是：校验顺序会不会让某些错误
  > 报成别的错？有没有什么输入能让它 500 而不是 400？」
- **它指出了什么**（3 条有用的）：
  1. `parse` 里先取 `title` 再取 `price`，如果请求体里两个都缺，只会报 `title` 的错——
     用户得改两次才能提交成功。建议要么一次收集所有错误，要么在文档里写清「按此顺序报第一个错」。
  2. `price` 如果传 `1.5`（小数），`isIntegralNumber()` 会是 `false`，会走到「价格必须是整数分」——
     这个是对的；但如果传 `1e3`，JSON 解析出来是 `1000.0` 且 `isIntegralNumber()` 可能是 `true`，
     需要实测。
  3. `description` 传 `null` 和传 `""` 要区分：`null` 应该当「没填」处理，不能当非法。
- **我验证后确认它对不对**：
  - 第 1 条：**对**，但我不打算改。收集所有错误会让响应体从 `message: string` 变成
    `message: string[]`，和其余 4 个接口不一致。我选择**把顺序固定下来并写进注释**，
    保证「同样的输入永远报同一个错」（可测、可预期），这比一次报全更适合 L0 的接口约定。
  - 第 2 条：**它猜错了**。我实测 `1e3` 走 Jackson 解析成 `1000.0`（`DoubleNode`），
    `isIntegralNumber()` 返回 `false`，所以会被拒成 400。但这暴露了一个真问题：
    **`1000.0` 这种「整数值但写成浮点」的输入会被拒**，而用户从 JavaScript 发过来很可能就是 `1000.0`。
    我确认前端 `createProduct` 用的是 `Math.round(x*100)` 出来的整数，不会发浮点，所以不修；
    但记进了 `SUBMISSION.md` 的已知问题里。
  - 第 3 条：**对，且我改了**。原来 `description` 缺失时直接 `asText()` 拿到 `""`，
    但如果显式传 `"description": null`，`asText()` 会返回 `"null"` 字符串——
    这是个真 bug。我改成先判断 `isNull()`，`null` 和缺失都归一成 `""`，并补了一条测试。
- **结论**：3 条里 2 条有用、1 条它猜错。**这次让我确信「让 AI 列边界、我自己跑一遍验证」是可用的**，
  但它的结论必须当成假设，不能当成事实——第 2 条如果我直接信了，就会去改一段本来没问题的代码。

### 场景 5（成功）：把单页拆成多页面路由

- **我想干什么**：把已经能用的单页 `App.vue` 拆成 `/products`、`/products/:id`、`/publish`、`/orders`
  四个页面，并且「从列表点进详情 URL 要变、`/products/9999` 要有提示」。
- **用的模型 / 为什么选它**：默认模型。这一步全是「机械搬运 + 补胶水」，没有需要推理的地方。
- **我怎么问的**：我没让它「帮我加路由」，而是先让它**只回答不改代码**：
  > 「Vue 3 + `<script setup>` 的一个单页组件，要拆成 vue-router 4 的多页面。
  > 先别写代码，按顺序列出：哪些状态必须提到模块作用域、哪些可以留在页面里，以及为什么。」
- **它给了什么**：它指出三类必须提出去——toast 列表（渲染点在外壳、调用点在页面）、
  买家手机号（下单页写、订单页读）、以及路由实例本身。
- **我改了吗、为什么改**：它的判断对，但**结论不够用**。它说「用 `provide/inject` 或 Pinia」，
  这两个都要么需要祖先组件要么需要新依赖。我用的是更土的办法：在 `composables/useOrders.js`
  里写一个模块级的 `const sharedBuyerPhone = ref('')`，再导出一个 `rememberBuyerPhone()`。
  模块只会被求值一次，页面组件随路由销毁重建都不影响它——效果和 store 一样，零新依赖。
- **它没提醒、我自己踩到的**：`<script setup>` 里**不能在顶层写 `let seq = 0`**，
  编译器会报「顶层绑定必须可导出」。我原本把 toast 的自增序号写在页面里，构建直接失败。
  把它挪到 `composables/useToasts.js` 的模块作用域就正常了——这也是「状态该提多高」的判据。
- **怎么确认改对了**：`npm test` 69 条通过（新增 11 条路由契约测试，用 `createMemoryHistory()`
  在 `node` 环境里跑，不用装 jsdom）；`npm run build` 通过且每个页面是一个独立 chunk；
  浏览器里逐条走：点标题 URL 变 `/products/1`、新标签页直接开 `/products/1` 正常、
  `/products/9999` 提示「商品不存在」、`/no-such-page` 提示「页面不存在」、
  发布完跳回 `?highlight=25` 且该行高亮、详情页下单后在「我的订单」里查得到。
- **结论**：**「先让它列约束、再自己写」在重构类任务上比「让它直接写」可靠得多**。
  它列的「哪些状态必须提上去」帮我省了返工，但它给的实现方案（Pinia / provide-inject）
  不是这个体量该用的，最后落地的还是我自己那 10 行模块级 ref。

## 4. 一次被 AI 带偏的经历（必答）

- **它给了什么**：上一轮我让它「把前端改成直连 backend」。它改 `vite.config.js` 时，
  在 `resolveApiTarget` 函数里写了一段判断，**少了一个闭合括号**，同时把原来的
  `server.proxy` 配置整段替换掉了，替换后的版本里 `/api` 这条 proxy 规则还漏了 `changeOrigin`。
- **当时为什么信了**：因为它同时在对话里给出了「改好了，现在 proxy 指向 8080」的说明，
  而且那段代码在对话里显示出来时缩进是对的——少括号的地方在函数结尾附近，视觉上很难一眼看出来。
  我当时直接去切终端重启服务了，没回头逐行看 diff。
- **你怎么发现的**：`npm run dev` 直接崩，报
  ```
  failed to load config from vite.config.js
  SyntaxError: Unexpected token '}'
  ```
  我一开始以为是 Node 版本问题（刚装了 Node 26），还去查了 Vite 2.1.9 和 Node 26 的兼容性，
  浪费了十几分钟。最后用 `node --check vite.config.js` 一条命令就定位到具体行号。
- **最后怎么修的**：补上括号，并把 `changeOrigin: true` 加回 proxy 规则。**修完之后我没有立刻相信它**，
  而是先 `node --check` 过了，再 `npm run dev` 起来了，再用 `curl localhost:5173/api/products`
  确认真的是转发到 8080 拿回 24 条——三步都过才继续。
- **之后你改了做法吗**：改了三条：
  1. **不让 AI 一次性重写整个配置文件**。配置文件是「要么全对要么全错」的东西，
     让它给**局部 diff**，我自己贴进去。
  2. **每次它改完配置文件，我先跑 `node --check` / `mvnw -o test` 这种「编译级」的快检查**，
     再谈功能。语法错误应该在第一秒被发现，不该留到运行期。
  3. **它说「改好了」不算改好了**。现在我的验收标准是：命令跑通 + 接口返回对 + 测试通过，
     三者缺一就不算完成。

## 5. 成本（4 分）

| 问题 | 我的回答 |
|---|---|
| 有没有"一次把整个项目/整个文件塞进去"？为什么？ | **有过一次，效果很差**。我把整个 `backend/src` 和 `frontend/src` 一起丢进去让它「整体 review」，它给的是「建议换 JPA」「可以引入 Lombok」「Vue 可以拆更细」——全是换技术栈的建议，对我当下要做的 L0 一点用没有，还烧掉大量上下文，导致后面那次对话明显变慢、开始忘前面说过的话。之后我改成**只贴相关的那一段（30~50 行）**，同一件事反而一次就说对了。 |
| 有没有同一个报错连续问了很多次？后来怎么改的？ | **有，就是 §4 那个 `SyntaxError`**。我先贴报错问，它猜是 Node 版本；我说不是，它又猜是 Vite 版本；我又贴了一次完整日志，它还是没定位到。**第三次之后我停下来自己跑 `node --check`**，5 秒就找到行号了。后来我总结：**报错先自己读一遍原文，能定位到行的就别问了**——AI 看不到我机器上的行号，我只能把行号告诉它。 |
| 如果额度只有 10 元，你会怎么调整？ | ①**先自己读报错**：终端报错、`F12 Network` 的响应体，这些信息我读一遍就够定位的问题，不问 AI。②**把「写文档」和「写代码」分开问**：文档我可以一次让它按结构生成，我再填事实；代码要一小段一小段确认，混在一起问会来回返工。③**用 `curl`/测试代替对话做验证**：现在我有 47 条后端测试 + 69 条前端测试，改完跑一遍就知道对不对，不需要再来一轮「你看这样对吗」。④ 最省的一条：**让 AI 做的第一件事是「列出你要做的步骤」，不是「直接写代码」**——步骤错了后面全白写，步骤对了写代码很快。 |
