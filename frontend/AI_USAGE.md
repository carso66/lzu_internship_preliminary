> 这一项占 **20 分**，是总分里仅次于 L0 的第二大项。  
> 我们不看"你用了多少次"，看**你怎么选模型、怎么提问、有没有用它做验证、钱花得值不值**。  
> 平台有完整调用记录，下面写的内容要和它对得上——**不需要精确到分**。

> 说明：本文记录的模型提问与结论均来自本人账号在平台的真实调用；主体开发由 WorkBuddy 完成，见第 1、2 节。次数与花费为约数，未精确核算；涉及的请求内容均为精简后的代码片段，未包含任何密钥、手机号或他人隐私。

## 2. 模型选型

**主力是 WorkBuddy，模型只用来验证和给思路，最终提交的代码都由 WorkBuddy 写。** 按验证的问题难不难，模型分两档：

| 我用它做什么        | 用的模型                                           | 它干了什么                                                                                                    |
| ------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 整个前端开发    | **WorkBuddy**                                  | 搭好静态服务与 `/api` 代理，写 `money.js` / `api.js` / `app.js`、页面与样式，写 12 条 Vitest、三份提交文档，实拍三张页面截图，自检后提交推送。一条龙做完，不按难度换模型 |
| 复核一句话就能定结论的判断 | `qwen3.8-flash`、`deepseek-v4.1-flash`（Flash 级） | 验证「`textContent` 能否防 XSS」这类小问题，确认结论就收工，不让它写代码                                                                  |
| 复核需要推理的逻辑     | `deepseek-v4-pro`（Pro 级）                       | review 已经跑通的下单 `buy()`（连点 / 失败 / 重渲染三条时序），再逐条核对它指出的边界对不对                                                       |
| 定位「智能体不回复」    | 逐个实测 9 个白名单模型（Flash / Pro 都有）                  | 统计各模型 `content` 与 `reasoning_content` 的字数，找出哪个能出正文、哪个只有思考                                                      |

`glm-5.3` 一开始被当成最强主力，实测发现它把 2.5 万字全放进 `reasoning_content`、正文 `content` 为 0，客户端读不到，于是弃用，换成上表 4 个能直接出正文的模型。**结论：选模型先验证输出格式能不能被客户端读到，再看能力强弱。**

第 3 节的四个场景，是开发过程中把上面几个判断拿到平台做问答 / 复核的真实记录；模型给的是结论或思路，是否采用、怎么落地由 WorkBuddy 判断。

## 3. 挑 4 个场景写下来

最好是：一个成功的、一个失败的、一个你自己改过的、一个你用 AI 做验证的。下面四个场景按这个顺序，**都是真实发生、平台上留有请求记录的**。

### 场景 1：成功、直接用 —— 一句话确认 `textContent` 能否防住商品标题里的脚本

- **我想干什么**：mock 数据里有一条商品标题是 `<script>alert('xss')</script>`，我想确认「全部用 `textContent` 写 DOM」这个做法是否足够，不想为它引入转义库。
- **用的模型 / 为什么选它**：`qwen3.8-flash`（Flash 级）。只要一句判断，不需要推理，Flash 最快最省。
- **我怎么问的**：
  > 商品标题里可能含有 `<script>` 这类字符串，我用 `element.textContent = title` 写入 DOM。只回答一句：这样够不够防止它被执行？为什么？不要给代码、不要展开讲 XSS 分类。
- **它给了什么**：「够，因为 `textContent` 会把整段字符串当作纯文本节点插入，浏览器不会解析其中的标签或脚本，所以无法被执行。」
- **我改了吗、为什么改**：没改代码。但我没有只凭它一句话就收工，回头把 `app.js` 从头到尾搜了一遍 `innerHTML` / `insertAdjacentHTML` / `document.write`，确认所有接口文本都走 `el()` 里的 `node.textContent = String(text)`（第 30~35 行），没有漏网之鱼。
- **怎么确认改对了**：打开页面，那条 `<script>` 标题的商品在列表里**原样显示为文字**，没有弹窗；F12 里该单元格是文本节点而不是元素节点。
- **结论**：**直接用**。这是一次低成本、结论明确的确认，没有让它写任何代码。

### 场景 2：失败、没用它的 —— `toFen()` 的 `Math.round(元*100)` 方案

- **我想干什么**：写一个把用户输入的「元」字符串转成整数「分」的函数，价格最多两位小数。
- **用的模型 / 为什么选它**：`deepseek-v4-pro`。当时觉得金额换算涉及边界，用 Pro 更稳（回头看这一步就该用 Flash，是个不必要的高配）。
- **我怎么问的**：

> 写一个 JS 函数 `toFen(yuan)`，把用户输入的「元」字符串转成「分」整数，价格最多两位小数。要求简单直接，只给函数体，不要写测试、不要解释。

- **它给了什么**：
  ```js
  function toFen(yuan) {
    return Math.round(Number(yuan) * 100);
  }
  ```
- **我改了吗、为什么改**：**没有采用**。我按「先跑最小复现再落地」的习惯，在 Node 里执行 `console.log(19.99 * 100)`，得到 `1998.9999999999998`；再换 `199999.99` 这类大金额复现，同样不稳。展示层按分取整后会差 1 分。
- **怎么确认改对了**：把这段函数单独拿去跑边界值（整数元、一位小数、两位小数、`0.01`、`199999.99`），确认失败不是个别值，而是 IEEE 754 二进制浮点无法精确表示十进制小数导致的系统性问题。
- **结论**：**没用它的**。这次提问也让我把「只给函数体、不要解释」改成了「给函数体 + 列出你会拦哪些非法输入」——不让它解释，等于主动放弃了一次边界提醒。

### 场景 3：自己改过之后才用 —— 浮点修法落地成 `money.js`

- **我想干什么**：拿到一个不依赖 `Math.round` / `toFixed` 的修法。
- **用的模型 / 为什么选它**：仍用 `deepseek-v4-pro`，因为这是同一个问题的**一次**追问，保持上下文连续，不换模型、不重复开新话题。
- **我怎么问的**：
  > 我用你这个方案跑 `19.99` 得到 `1998.9999999999998`，展示时差 1 分；`199999.99` 也不稳。这是 IEEE 754 浮点问题吗？给一个不依赖 `Math.round` / `toFixed` 的修法，只给函数体。
- **它给了什么**：按 `String(yuan).split('.')` 把整数部分和两位小数部分拆开，用 `Number(intPart + (decPart+'00').slice(0,2))` 拼成整数，并带正负号处理。思路对：**全程不碰浮点乘法**。
- **我改了吗、为什么改**：**改了之后才用**。它给的版本只管换算，不拦非法输入：`'19.999'` 会被静默截成 `1999` 分（多一位小数被吞掉），`'0'`、`'-1'`、非数字字符串也没有校验，而题目 L0-2 / L1-9 要求价格 > 0、最多两位小数、错误显示在字段下方。所以我在 `src/money.js` 里补了正则校验与 `throw`，让 `validatePublish()` 能 `catch` 到并显示 `e.message`；`formatYuan()` 也统一改成 `Math.floor(fen/100)` + `fen%100` 的整数拆分，不回退到浮点。
- **怎么确认改对了**：`npm test` → Vitest **12 条用例全过**，覆盖整数元、一位/两位小数、`0.01`、`199999.99`，以及 `19.999`、`0` 等应当被拦下的输入；再用端到端请求确认 `POST /api/products` 的 `price` 是整数分、`POST /api/orders` 的 `totalAmount` 与前端预估一致。
- **结论**：**改了之后用**。核心思路采纳，输入校验和错误处理是它没给、我自己补的。

### 场景 4：**我用 AI 做验证的一次**

不是"让它写"，是"让它检查"。这一次的 `buy()` 是我自己写完并跑通之后，专门贴过去让它挑毛病的。

- **我想干什么**：验证下单函数的三个时序边界，尤其是「成功后列表重渲染把旧按钮换掉，`finally` 里还能不能恢复按钮」。
- **用的模型 / 为什么选它**：`deepseek-v4-pro`（Pro 级）。要同时看住 `try` / `catch` / `finally` 和重渲染的先后，属于需要推理的 review，不是 Flash 能一句话答的。
- **我怎么问的**：
  > 不要帮我改代码，只做 review。逐条给结论，并说明你是从哪一行看出来的；不确定就直接说不确定，不要猜。  
  > ① 用户快速连点「两个不同商品」的购买按钮，会发生什么？第二个点击有没有任何提示？  
  > ② `createOrder` 请求失败（比如后端返回 409 库存不足）时，按钮和 state 能正确恢复吗？  
  > ③ 成功后列表重渲染把原来的 button 换掉了，`finally` 里重新 `querySelector` 还能不能恢复按钮状态？
- **它指出了什么**：
  1. **第二个点击会被静默忽略，没有任何提示** —— 依据是第 2 行 `if (state.pendingOrderId !== null) return;`，命中即 `return`，不 toast、不改按钮。
  2. **请求失败能正确恢复** —— `finally` 里清 `pendingOrderId`、重新 `querySelector` 恢复 `disabled` 和文案；且失败时不执行 `loadProducts()`，旧按钮还在。
  3. **③「不确定」** —— 它说取决于 `loadProducts()` 重渲染后新按钮是否仍带 `data-action="buy"` 和 `data-id`，而它看不到 `renderProducts()` 的实现，所以不能 100% 确定。
- **你验证后确认它对不对**：
  - **① 确认对，而且这正是我要的行为**：`app.js` 第 215 行确实是全局在途锁，L2-11 就要求「连点只产生 1 个订单」。但它顺带暴露了一个**体验缺口**：第二个点击完全没有反馈，用户不知道自己被拦了。我记进了 DESIGN 第 7 节，没有为此改代码（改了反而可能破坏「只产生 1 个订单」的验收）。
  - **② 确认对**：`app.js` 第 239~242 行 `finally` 清标记并重新查按钮恢复；`catch` 第 238 行把后端 `message` 显示到 toast。端到端也实测过 `40901 库存不足` / `40902 商品已下架` 后按钮可再点。
  - **③ 我否掉了它的保守结论**：我打开自己写的 `renderProducts()` / `productRow()`（第 96~99 行），确认重渲染出的购买按钮**仍然带** `data-action="buy"` 和 `data-id`，所以 `finally` 里的 `querySelector` 能找到并恢复。它说"不确定"只是因为**我没把这段渲染代码贴给它**——是我给的上下文不足，不是代码有风险。另外我顺手确认了它没提到的一个边界：若下单后库存变 0，第 81 行的条件不再生成购买按钮，此时 `querySelector` 返回 `null`，而第 242 行有 `if (current)` 保护，不会抛错。**结论：③ 没问题，它高估了风险。**
- **结论**：**用 AI 做验证，而且敢否掉它的建议**。它帮我确认了 ①②、逼我把 ③ 的实现依据翻出来核对一遍，还让我发现「第二个点击无提示」这个之前没注意的体验缺口。这次没有让它写一行代码。

## 4. 一次被 AI 带偏的经历

- **它给了什么**：场景 2 里那个 `function toFen(yuan) { return Math.round(Number(yuan) * 100); }`，以及它看起来非常可信的「简单直接」外观。
- **当时为什么信了**：① 它是我当时配置的最强 Pro 模型给出的答案；② 我自己在提问里写了「要求简单直接，只给函数体，不要写测试、不要解释」，等于主动要求它别提边界，拿到一行干净代码就觉得"这么基础的写法不会错"；③ `Math.round(x*100)` 是到处都能见到的写法，没多想。
- **你怎么发现的**：**金额对不上**。我在把 `money.js` 接进页面前，先在 Node 里跑了 `console.log(19.99 * 100)`，看到原始值 `1998.9999999999998`；再用 `199999.99` 复现，确认不是个别值。如果直接上线，发布 `¥19.99` 的商品会出现差 1 分，L0-2 和 L1-8 会一起翻车。
- **最后怎么修的**：只追问一次，确认是 IEEE 754 问题并要一个不依赖 `Math.round` / `toFixed` 的修法；拿到字符串拆分思路后，自己补上输入校验和错误处理，落地成 `src/money.js`，再用 Vitest 12 条用例把边界固化，端到端核对请求体 `price` 是整数分、`totalAmount` 与预估一致。
- **之后你改了做法吗**：改了两条，都写进了习惯：
  1. **凡是涉及金额、精度、边界的 AI 代码，先写一行最小复现跑原始值，再决定用不用**——不因为"看起来简洁"就落地。
  2. **不再要求"只给函数体、不要解释"**；改成让它同时列出会拦下哪些非法输入。少一句解释，省下的是几秒，赔上的是一次边界遗漏。  
     另外这也直接促成了 L2-12：把这类边界写成测试，下次不用靠记性。

> 顺带说明：还有一次"被带偏"不在 AI 的答案里，而在**我对模型选型的预设**——见第 2 节，我按"最强 Pro"配了 `glm-5.3`，结果 22 次请求全部 0 输出。那次是靠读本地调用记录（`tokens_generated=0`）和逐个实测模型输出格式定位的，不是靠再问 AI 一遍。

## 5. 成本

| 问题                        | 我的回答                                                                                                                                                                                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 有没有"一次把整个项目/整个文件塞进去"？为什么？ | **没有整包贴过**。最长的一次是场景 4，贴了 `buy()` 约 20 行；问 `toFen()` 时甚至没贴现有代码，只描述输入/输出。原因有两个：一是问题切小后它答得更准，整包贴进去容易改到不相关的地方；二是额度按 token 计费，没必要为一句确认付整个文件的钱。**但有一次浪费**：场景 4 那段 1258 字的问题因为第一次遇到空响应，原样重发了一次，等于同一份上下文付了两遍。后来改成「空响应先查原因、换模型，不重发同一句」。                                                                    |
| 有没有同一个报错连续问了很多次？后来怎么改的？   | **有**。早期 `glm-5.3` 配置下，Continue 里一直不回复，我在没搞清楚原因时反复重试了几次。后来不再重试，改成：先读 Continue 的 `devdata.sqlite` 看生成 token 数 → 用 `/v1/chat/completions` 逐个实测 9 个白名单模型的流式输出，统计 `content` 与 `reasoning_content` 的字数 → 一次定位到「正文全在 `reasoning_content`、客户端只读 `content`」→ 换掉配置。**先自己把现象读明白，只贴/只测相关的那一段，比连问快得多，也便宜得多。** |
| 如果额度只有 10 元，你会怎么调整？       | ① 所有一句话确认（XSS、CSS、正则、报错归属）一律走 Flash，Pro 只留给「review 已写好的逻辑」和「排错」各一次；② 提问前先自己把报错原文读一遍，把上下文摘到 20 行以内，一次说清一个问题；③ 把「逐个实测模型」这类批量验证合并成一次脚本跑完，不在聊天里一条条试；④ 遇到空响应立刻停下来查原因，绝不重发同一句；⑤ 像"帮我 clone 一个仓库""这段 CSS 怎么写"这类查文档就能解决的事，不值得问。**额度花得少本身不是目的，省下的次数应该换成"多一次 review"。**                                     |
