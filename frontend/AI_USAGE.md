# AI 使用说明

本项目在开发过程中使用 AI 编程助手辅助完成前端实现、代码检查、测试补充和浏览器验证。用户在本轮明确切换为 DS v4 Pro；调用次数和实际费用没有在本轮对话中提供，因此本文不虚构这些数字，提交前仍应以平台调用记录为准。

| 使用方式 | 让 AI 助手阅读当前代码、提出实现方案、修改文件并运行测试/构建/浏览器检查 |
| 主要场景 | 金额转换、API 封装、页面与组件实现、独立上架页拆分、支付轮询生命周期、商品上下架、数量下单、防重复提交、异常标题修复、文档审计、边界/错误测试、测试与工程化收口 |
| 模型切换 | 用户在本轮明确切换为 DS v4 Pro；具体调用记录仍以平台日志为准 |
| 大致调用次数 | 以平台调用日志为准，提交前补填 |
| 大致费用 | 以平台调用日志为准，提交前补填 |

## 2. 模型选型

在这一轮实现中，我把任务按“确定性实现”和“需要推理的边界问题”分开处理：

| 任务类型 | 我的选择原则 | 实际结果 |
|---|---|---|
| 写页面、组件、CSS 和简单校验 | 优先让助手按现有项目风格直接实现，减少重复劳动 | 商品列表、表单、订单卡片和详情页按现有结构完成 |
| 金额、错误解析、轮询清理 | 先要求解释边界，再检查具体代码和实际行为 | 没有只接受“看起来能跑”的实现，而是检查了整数分、非 2xx 和卸载后的请求 |
| 上下架、数量下单、防重复 | 先明确请求锁的作用范围，再做浏览器请求计数 | 同一商品 PATCH 和快速购买 POST 都通过请求计数验证 |

| 最终验证 | 不只让 AI 写代码，还让它执行静态检查、测试和构建 | `npm run check` 通过：ESLint、Prettier、8 个测试文件 83/83 和 55 modules 的 Vite 构建全部成功 |

## 3. 十个具体场景

### 场景 1：确认元转分为什么不能直接用 `parseInt` 或裸 `* 100`

- **我想干什么**：实现 `yuanToFen(yuan)`，保证 `0.01`、`19.9`、`12.5`、`1`、`100` 等输入都变成整数分。
- **我怎么问的**：要求比较 `parseInt`、直接乘 100 和 `Math.round(Number(x) * 100)` 的差异，并说明浮点误差。
- **它给了什么**：指出 `parseInt('19.9')` 会丢掉小数，`parseInt('0.01')` 会得到 0；直接乘 100 在部分小数上会出现 `1989.9999999999998` 一类结果；随后建议先 `Number` 再 `Math.round`。
- **我怎么处理**：采用 `Math.round(Number(raw) * 100)`，同时增加了空字符串和非有限数字的异常处理。
- **怎么确认**：用 Vitest 固化 `0.01 → 1`、`19.9 → 1990`、`12.5 → 1250`、`1 → 100`、`100 → 10000`；`fenToYuan(0)` 返回 `'0.00'`，`formatPrice(0)` 返回 `'¥0.00'`。
- **结论**：采用经过四舍五入的方案，没有使用 `parseInt`，也没有提交未取整的浮点结果。

### 场景 2：统一 API 返回值与 HTTP 错误

- **我想干什么**：让所有页面通过同一层调用接口，并能在调用方用 `try/catch` 显示后端 message。
- **我怎么问的**：要求实现一个统一请求函数，解析 `{ code, message, data }`，并处理 HTTP 非 2xx。
- **它给了什么**：建议集中定义 `API_BASE_URL`，请求后先读取 body，再根据 `response.ok` 和 `payload.code` 分别抛错；HTTP 非 2xx 时优先使用 body 中的 message。
- **我怎么处理**：保留了统一请求函数，API 函数只负责路径、方法和请求体；基础地址只在 `src/api/index.js` 定义一次。
- **怎么确认**：检查了商品、订单、支付相关函数的路径；直接请求已支付订单的支付接口，确认 HTTP 409 与 body message 可被页面按同一逻辑展示。
- **结论**：直接采用，并保持页面对错误 message 的展示逻辑一致。

### 场景 3：检查支付轮询在离开页面后的清理

- **我想干什么**：每秒查询支付状态，最多 10 次；离开订单页后不能继续查询，也不能让旧请求回来修改已销毁组件。
- **我怎么问的**：让 AI 检查轮询实现，重点问“组件卸载时已有请求在途怎么办”“旧定时器回调是否会继续 setState”。
- **它给了什么**：指出只调用 `clearInterval` 不足以处理在途请求；建议增加 `cancelled` 标志、轮询 token、`requestInFlight`，并在 `onUnmounted` 中先标记取消再清理定时器。
- **我怎么处理**：采用 `cancelled + pollToken + clearInterval`，每次异步返回后重新检查页面状态；`processing` 不提前成功，达到 10 次上限提示未确认。
- **怎么确认**：浏览器中发起支付后切换到其他页面，观察 Network，确认 5 秒内没有新的 `GET /api/payments` 请求；实测新增查询为 0。
- **结论**：这是 AI 辅助检查真正有价值的一次；不是让 AI 直接“写一个定时器”，而是让它指出生命周期边界，再由浏览器验证。

### 场景 4：一次被带偏的经历：`{{ }}` 不等于标题内容一定正常

- **它给了什么**：最初实现只保证了标题使用 Vue 的 `{{ }}` 文本插值，认为这样就不会执行脚本。
- **当时为什么信了**：这个判断在安全层面没有错，文本插值确实不会把字符串当作 HTML 执行。
- **怎么发现的**：检查商品列表时发现 `id=24` 的标题显示为 `<script>alert('xss')</script> 二手教材`。虽然没有弹窗，但“奇怪名称”仍然直接展示给了用户，数据质量问题没有解决。
- **最后怎么修的**：新增 `normalizeProductTitle()`，在展示前移除 script/style 内容、HTML 标签、控制字符和零宽字符；列表、订单和详情统一使用该函数。长标题 `id=23` 不删除，仍由 CSS 单行省略。
- **怎么验证的**：重新打开列表和详情，确认页面不弹脚本、标题显示为“二手教材”，同时长标题仍保持省略效果；Vitest 也固化了这些规则。
- **之后怎么改做法**：不再把“没有执行脚本”当作“数据已经正确展示”；安全渲染和数据清洗要分开检查。

### 场景 5：规划上下架、数量下单和正式测试

- **我想干什么**：把此前遗留的商品上下架、购买数量选择、防重复提交和 L2-12 自动化测试补齐。
- **我怎么问的**：先让 AI 对照当前实现和验收项列出未完成项，再按“功能实现 → 单元测试 → 浏览器验证 → 文档同步”的顺序逐步推进。
- **它给了什么**：建议上下架使用按商品 ID 的 `Set` 锁，下单使用全局 `creatingOrder` 锁，数量由卡片传 `{ product, quantity }` 给 `App.vue`，并用 Vitest 先固定金额和标题清洗规则。
- **我怎么处理**：接入 `updateProductStatus()`，增加数量输入和全局下单锁；新增 `money.test.js`、`product.test.js`、`quantity.test.js` 与 `npm test` / `npm run check` 脚本。
- **怎么确认**：快速连点上下架只产生 1 次 PATCH，快速连点购买只产生 1 次 POST；数量 2 的请求体和订单金额一致。测试后续继续扩充，最终统计见场景 8。
- **结论**：功能实现和自动化验证分开完成；临时浏览器脚本用于补充交互链路，不伪装成已提交的 E2E 套件。

### 场景 6：文档审计后把建议落成代码和验收材料

- **我想干什么**：先检查前端文档与真实代码是否一致，再把高优先级建议直接落地，避免只停留在“建议清单”。
- **我怎么问的**：要求 AI 对照 `README.md`、`constraint.md`、`DESIGN.md`、`SUBMISSION.md` 和 `src/` 中的实现，按正确性、可维护性和工程化风险排序；明确 `mock/` 只读。
- **它给了什么**：建议补齐订单查询上限、数量全局校验、下架禁购、描述字数、404 路由和动态标题；同时把 API 地址环境化，增加请求竞态保护、ESLint、Prettier、`npm run check` 与 CI。
- **我怎么处理**：逐项修改代码，新增 `quantity.js` / `quantity.test.js` 和 `NotFoundView.vue`；保留已有支付轮询和请求锁设计；最后同步 README、接口说明、设计说明、提交说明和本文档。
- **怎么确认**：执行 `npm run check`，确认 ESLint、Prettier、测试和 Vite 生产构建通过；`mock/` 没有改动。测试后续继续扩充，最终统计见场景 8。
- **结论**：文档审计可以转化为具体交付质量改进；但本轮没有重新做浏览器回归，因此不把新增交互写成“已重新浏览器验证”。

### 场景 7：对金额、数量和表单做边界与错误测试

- **我想干什么**：在已有单测基础上，对金额、数量、表单校验和 API 请求封装补一轮边界输入与错误路径测试，避免只验证“正常值”。
- **我怎么问的**：要求把 `quantity.js`、`money.js` 的解析改成严格类型与格式校验，并追问哪些字符串或类型会被 `Number()` 误收。
- **它给了什么**：指出 `Number('1e2')`、`Number('0x10')`、`true`、数组和 `'+1'` 都可能被误当成合法数字；建议用白名单正则拒绝科学计数法、千分位和多余小数位，并限制在安全整数范围。
- **我怎么处理**：数量解析只接受 `>=1` 的安全整数或 `/^[0-9]+$/` 字符串，金额只接受 `>0` 且最多两位小数；新增 `src/utils/productForm.js` 集中表单校验并把字数改成按码点计数，`ProductForm.vue` 改为引用该模块。

- **结论**：边界测试不只验证正常值，也验证脏类型和错误响应；本轮同样没有重新执行浏览器回归。

- **我想干什么**：把原本嵌在商品列表里的发布表单拆成单独的上架页面和导航入口，同时确认页面拆分没有造成路由冲突或权限误解。

### 场景 10：建立商品聚合展示模型并设计权限变化展示

- **我想干什么**：把同名或同一 SPU 的多个 listing 聚合到一张组卡中，同时让用户清楚看到当前角色能管理哪些商品，避免组级摘要掩盖逐条权限差异。
- **我怎么问的**：要求实现一个聚合展示模型，优先按 `spuId` 分组，缺少 `spuId` 时按规范化标题回退；同时说明角色、用户 ID、`sellerId`、上下架状态或筛选结果变化时，页面级、组级和 listing 级权限应如何更新。
- **它给了什么**：建议把 `buildProductGroups(products, session)` 作为纯派生模型，组内始终保留原始 listing；组头只汇总价格、库存、状态和来源，来源身份必须以 `sellerId` 为准；权限摘要分为 `all / partial / none`，但聚合组不能成为权限资源。
- **我怎么处理**：新增 `productGroups.js`、`productGroups.test.js` 和 `ProductGroupCard.vue`，商品列表按 `filteredProducts → buildProductGroups → ProductGroupCard → ProductCard` 渲染。多 listing 组默认折叠、单 listing 组默认展开；页面级摘要使用 `aria-live="polite"`，组头显示“可管理全部 N 条 / 可管理 x/N 条 / 仅浏览”，每条 listing 的按钮仍调用 `canManageProduct()`。
- **怎么确认**：`productGroups.test.js` 覆盖 SPU 优先、标题回退、重复 `id`、无标题独立组、异常价格库存、来源计数和权限三态；`npm test` 实测 8 个测试文件、83 个用例全部通过。完整 `npm run check` 与构建结果在最终验证中复核。
- **结论**：同名商品可以“看起来在一组”，但不能在数据层变成一条，也不能共享卖家、库存或权限。组级摘要只帮助理解，最终操作权限必须逐条判断，并以服务端鉴权结果为准。本轮没有重新执行浏览器回归。

### 场景 11：增加运行时权限演示切换器

- **我想干什么**：不仅说明权限会变化，还要能在页面里实际切换游客、买家、卖家和管理员，观察页面级、组级和 listing 级摘要同步更新。
- **我怎么问的**：追问“所以怎么切换权限演示”，要求把固定管理员会话改成可操作的运行时演示入口，同时不能为了制造 `partial` 而伪造卖家身份。
- **它给了什么**：建议在 `permissions.js` 增加 `createDemoSession(role, sellerId)`，在 `App.vue` 顶部增加角色下拉框和卖家编号输入框，角色变化后通过 computed 重算会话并传给商品页面。
- **我怎么处理**：新增 `createDemoSession()` 及 5 个测试，覆盖默认管理员、角色切换、卖家编号清洗、空编号失败关闭和未知角色降级；`App.vue` 增加游客 / 买家 / 卖家 / 管理员切换器和卖家编号输入，`DEMO_SESSION` 保留为默认管理员会话。卖家模式下明确提示当前 Mock 商品没有 `sellerId`，因此仍显示“仅浏览”，没有用 `sellerName` 或伪造 ID 制造可管理状态。
- **怎么确认**：`permissions.test.js` 14 个用例通过；完整 `npm run check` 通过，ESLint、Prettier、8 个测试文件 83 个用例、55 modules 的 Vite 生产构建全部成功。没有重新执行浏览器回归。
- **结论**：运行时切换解决了“只能改代码看权限”的问题，但演示器仍只是前端体验开关。`partial` 需要在真实数据中同时存在会话 ID 与商品 `sellerId`，最终授权仍必须由服务端完成。

- 检查 `ProductListView` 和 `OrderListView` 的 loading/error/empty/ready 是否互斥，以及请求 ID 是否能阻止旧响应回写。
- 检查订单页轮询是否在 `processing` 时提前成功，以及离开页面后是否停止请求。
- 检查 `/products/1` 直接打开、`/products/9999` 的异常路径和未知路由的 404 页面。
- 核对 README、接口说明、设计说明、提交说明、约束文档和本文档中的测试数量、命令、权限边界与限制是否一致。
- 检查聚合实现是否只做展示分组，组内 listing、来源、库存和权限是否保持独立，组级权限摘要是否没有被当作授权结果。
- 检查权限演示切换器是否按角色即时更新，卖家空编号是否按失败关闭处理，以及是否避免了用 `sellerName` 或伪造 `sellerId` 制造权限。

此前的临时浏览器记录还包括发布、上下架、数量下单、支付和详情入口的点击与请求计数，但其中发布记录属于列表内嵌表单阶段。本轮新增的独立上架页、商品编号与来源展示、身份未核验、前端商品归属判断、商品聚合与组级权限摘要、权限演示切换器、下架禁购、描述字数、全局 404、动态标题和工程化配置只完成了代码检查、单测和构建，没有重新执行浏览器回归。

其中最有价值的是支付轮询和防重复请求检查：一个验证卸载后的在途请求不会继续轮询，另一个验证快速连点不会产生重复 PATCH/POST。

## 5. 成本与使用边界

| 问题 | 我的回答 |
|---|---|
| 有没有一次把整个项目或整个文件塞进去？ | 没有把 `node_modules` 或无关文件塞进上下文；读取和修改都集中在当前前端相关文件。 |
| 有没有同一个报错连续问很多次？ | 没有形成同一报错反复多轮的循环；发现问题后优先定位具体文件和边界，再重新验证。 |
| 如果额度只有 10 元，会怎么调整？ | 优先保证金额、API、商品列表、表单、上下架、订单支付主链路和关键单测；样式优化、分页和大范围重构放在后面。 |
| 哪些问题不值得问 AI？ | 已经能通过一次测试、构建或 Network 观察确认的简单语法问题、纯样式微调，以及没有具体错误信息的主观偏好问题。 |
