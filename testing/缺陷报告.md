# BUG-01：普通用户可以越权查看其他用户的个人资料

- **模块：** 用户认证与个人资料
- **问题类型：** 水平越权（IDOR / BOLA）
- **严重程度：** S2
- **测试环境：** Windows 10 / Python 3.10.22 / CampusMall 1.0 / 8080 端口
- **前置条件：** 使用 Alice（userId=2）成功登录，获得 token `tk_2`。

### 复现步骤

1. 使用 Alice 的账号登录：

```cmd
curl.exe -i -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d "{\"username\":\"alice\",\"password\":\"Alice@123\"}"
```

2. 使用 Alice 的 token 查询 Bob 的个人资料：

```cmd
curl.exe -i http://127.0.0.1:8080/api/users/3 -H "Authorization: Bearer tk_2"
```

### 预期结果

返回 HTTP 403 Forbidden，拒绝 Alice 访问其他用户的个人资料。

### 实际结果

返回 HTTP 200 OK，成功获取 Bob 的个人资料，响应中包含其用户名、真实姓名及手机号等信息。

### 影响分析

普通用户可以通过修改请求 URL 中的用户 ID，访问其他用户的个人资料，导致用户隐私信息泄露。

### 修复建议

在用户资料接口中增加服务端资源级权限校验：

- 普通用户只能访问与当前登录身份对应的 userId。
- 当请求路径中的 userId 与当前登录用户 ID 不一致时，返回 HTTP 403。
- 管理员权限应单独定义和验证，不应直接放开所有用户资料的访问权限。
### 补充验证

| 用例 | 请求身份 | 目标用户 | 实际状态 | 结果 |
|---|---|---|---|---|
| TC-01 | Alice（2） | Alice（2） | 200 | PASS |
| TC-02 | Alice（2） | Bob（3） | 200 | FAIL |
| TC-03 | 未登录 | Bob（3） | 401 | PASS |

结论：身份认证机制正常，但个人资料接口缺少资源归属权限校验。
# BUG-02：普通用户可越权访问管理员订单接口

- **模块：** 用户权限管理 / 订单管理
- **严重程度：** 高
- **环境：** Windows 11，Python 3.10.22，CampusMall SUT，127.0.0.1:8080
- **前置条件：** 使用普通用户 Alice 登录，获得有效 Token `tk_2`。
- **复现步骤：**

```cmd
curl.exe -i http://127.0.0.1:8080/api/admin/orders -H "Authorization: Bearer tk_2"
```

- **预期结果：** 普通用户无权访问管理员订单接口，应返回 HTTP 403，不能获取订单列表。
- **实际结果：** 返回 HTTP 200，`code=0`，成功获取全部订单数据，共 2 条，包含其他用户的订单信息及个人隐私数据。
- **证据：** 2026-11-24 08:04:17，实际 HTTP 响应为 200 OK。
- **影响：** 普通用户可绕过管理员权限控制，批量获取其他用户的订单信息，造成用户隐私泄露。
- **修复建议：** 在管理员订单接口增加角色权限校验，确保只有具有 admin 角色的用户可以访问。

# BUG-03：普通用户可通过修改订单 ID 查看他人订单

- **模块：** 订单管理 / 访问控制
- **严重程度：** 高
- **环境：** Windows 11，Python 3.10.22，CampusMall SUT，127.0.0.1:8080
- **前置条件：** Alice（userId=2）已登录，Bob（userId=3）存在订单 ID=2。
- **复现步骤：**

首先查询 Alice 自己的订单：

```cmd
curl.exe -i http://127.0.0.1:8080/api/orders/1 -H "Authorization: Bearer tk_2"
```

随后修改订单 ID，查询 Bob 的订单：

```cmd
curl.exe -i http://127.0.0.1:8080/api/orders/2 -H "Authorization: Bearer tk_2"
```

- **预期结果：** Alice 只能查看自己的订单。查询 Bob 的订单应返回 HTTP 403，不得返回 Bob 的个人信息。
- **实际结果：** 两次请求均返回 HTTP 200。Alice 成功获取 Bob 的订单详情，包括用户身份、手机号、收货地址、商品及支付状态等信息。
- **证据：** 2026-11-24 08:04:23 和 08:04:30，实际 HTTP 响应均为 200 OK。
- **影响：** 普通用户可以通过遍历订单 ID 获取其他用户的订单信息，存在水平越权及个人隐私泄露风险。
- **修复建议：** 查询订单时增加订单所属用户校验，确保当前登录用户 ID 与订单 user_id 一致；管理员访问应另行按照角色授权。

# BUG-04：支付回调缺少有效性验证，可伪造支付成功

- **模块：** 支付管理 / 支付回调
- **严重程度：** 严重（P0）
- **环境：** Windows 11，Python 3.10.22，CampusMall SUT
- **前置条件：** 订单 ID=1 存在，初始状态为 created，paid_at 为空。
- **复现步骤：**

1. 查询数据库，确认订单初始状态为 created。
2. 不携带 Authorization 和签名信息，发送以下请求：

```http
POST /api/payments/callback
Content-Type: application/json

{"orderId":1,"paymentId":"FAKE-PAY-0001","result":"success"}
```

3. 观察接口响应。
4. 再次查询数据库中的订单状态。

- **预期结果：** 服务端应验证支付回调的真实性及完整性。对于未通过验证的伪造回调，应拒绝处理，不得更新订单状态。
- **实际结果：** 接口返回 HTTP 200，业务响应 code=0，status=paid。数据库中订单状态从 created 变为 paid，paid_at 被写入当前时间。
- **影响：** 攻击者可能通过构造伪造回调绕过真实支付流程，造成未付款订单被错误确认为已付款，进一步引发商品交付、资金对账及业务数据一致性问题。
- **初步原因：** 从实际行为看，支付回调处理未能有效阻止无签名请求。具体是缺少签名验证、验证逻辑失效，还是其他原因，需要结合源码确认。
- **修复建议：**
  1. 对支付网关回调执行严格的签名验证。
  2. 核对订单号、支付金额、商户身份及支付状态。
  3. 使用事务和幂等机制更新订单状态。
  4. 验证失败时不得更新订单状态。
- **测试证据：** 2026-11-24 08:07:50，伪造回调返回 HTTP 200，数据库确认订单状态由 created 变为 paid。

### BUG-04 补充：自动化测试证据

- 测试文件：`testing/自动化/tests/test_payments.py`
- 测试名称：`test_unsigned_fake_callback_must_not_mark_order_paid`
- 测试方式：不提供 Authorization 和签名，发送伪造支付成功请求。
- 实际观察：接口返回 HTTP 200，订单状态被更新为 paid。
- 自动化结果：测试断言失败，确认当前实现未拒绝该伪造回调。
- 说明：本项与 BUG-04 属于同一缺陷，不重复计数。

# BUG-05：创建订单时服务端信任客户端提交的商品价格

- **缺陷模块：** 订单管理
- **测试接口：** `POST /api/orders`
- **严重程度：** 高
- **缺陷类型：** 业务逻辑错误 / 金额完整性
- **测试结果：** Fail

**前置条件：**
- 用户 Alice 已登录，持有有效 Token。
- 商品 ID=1 存在，真实价格为 1990。
- 商品状态为上架。

**测试步骤：**

向订单创建接口发送：

```json
{
  "productId": 1,
  "quantity": 1,
  "unitPrice": 1,
  "totalAmount": 1
}
```

**实际结果：**

HTTP 201 Created，订单创建成功，接口返回 `unitPrice=1`、`totalAmount=1`。

进一步查询 SQLite 数据库，确认订单 ID=3 中的 `unit_price` 和 `total_amount` 均被持久化为 1。

商品数据库中的真实价格为 1990。

**预期结果：**

服务端应根据数据库中商品的真实价格及购买数量计算订单金额，不应信任客户端提交的价格和总金额。非法或不受支持的金额字段应按接口契约处理。

**业务影响：**

攻击者可以通过篡改请求参数，以低于真实价格的金额创建订单，造成订单金额错误、潜在资金损失及后续支付对账异常。

**建议修复：**

服务端根据 `productId` 查询商品真实价格，校验商品状态及库存，使用服务端价格计算订单总额，并在数据库事务中完成订单创建和库存扣减。

**验证证据：**

1. HTTP 201 接口响应。
2. 商品 ID=1 的真实价格为 1990。
3. 订单 ID=3 的数据库记录中 `unit_price=1`、`total_amount=1`。

**结论：** 已通过真实接口调用和数据库查询确认该缺陷。
