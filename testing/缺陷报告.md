# 缺陷报告

> 环境：Windows 11 / Python 3.14 / SUT 默认配置，监听 `http://127.0.0.1:8080`
> 前置约定：`app.py` 启动时会删库重建并写入种子数据，所以**每轮测试前重启一次服务即可回到初始状态**（不需要手动删 `sut.db`，本轮所有数据都是这样取的）。
> 登录命令（下文简写为「先登录」）：
>
> ```bash
> curl -s -X POST http://127.0.0.1:8080/api/auth/login \
>   -H 'Content-Type: application/json' \
>   -d '{"username":"alice","password":"Alice@123"}'
> ```
> 返回 `data.token` 为 `tk_2`（alice，userId=2）。种子数据中的手机号、姓名均为测试数据。

共 11 条。其中 8 条为 S1，3 条为 S2。

**我用的定级标准**（先说清楚，避免「看起来都是大事」）：

| 级别 | 判定条件 | 本轮对应 |
|---|---|---|
| **S1** | 攻击链**闭环**且后果落在资金、身份或批量数据上：能直接造成钱少收/多扣、能伪造身份、能批量拿到他人信息。四个条件缺一不可 | BUG-01~08 |
| **S2** | 有真实缺陷、有可复现证据，但闭环缺一环：或后果限于局部数据、或触发需要额外前提、或当前架构下拿不到实际收益 | BUG-09 存储型 XSS（无凭据可窃）、BUG-10 注入（只能读、不能写）、BUG-11 浮点金额（单笔差异极小） |
| S3 / S4 | 体验问题 / 建议项，本轮未单独立条，收在备选表与「已知问题」里 | X-01、X-05、X-06 等 |

按这条标准，**「能复现」不等于「S1」**：XSS 能复现，但没有可窃取的会话；SQL 注入能复现，但 SQLite 驱动不支持多语句，只能读不能写。这两条都是 S2。

## BUG-01 资源归属校验缺失，登录用户可读取他人资料与订单、操作他人商品、支付他人订单

- **模块**　用户 / 订单 / 商品 / 支付
- **严重程度**　S1
- **前置条件**　SUT 已启动；alice 登录，token 为 `tk_2`
- **复现步骤**

```bash
# 表现 1：读他人用户资料（bob 的 userId 为 3）
curl -s http://127.0.0.1:8080/api/users/3 -H 'Authorization: Bearer tk_2'

# 表现 2：读他人订单（订单 2 属于 bob）
curl -s http://127.0.0.1:8080/api/orders/2 -H 'Authorization: Bearer tk_2'

# 表现 3：下架他人发布的商品（商品 1 的 sellerId 为 1，属 admin）
curl -s -X PATCH http://127.0.0.1:8080/api/products/1/status \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"status":"off"}'

# 表现 4：替他人订单付款（订单 2 属于 bob，金额 129 元）
curl -s -X POST http://127.0.0.1:8080/api/payments \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"orderId":2,"method":"alipay"}'
```

- **预期结果**　四个请求均应返回 HTTP 403，提示无权限。文档承诺「只能看自己，看别人应 403」「只能上下架自己发布的商品，别人的应 403」。
- **实际结果**　四个请求均返回 HTTP 200，成功读取或修改。

```json
{"code":0,"message":"ok","data":{"id":3,"username":"bob","realName":"李波","phone":"13800138003","role":"user","createdAt":"2026-09-01T08:00:00Z"}}
```

```json
{"code":0,"message":"ok","data":{"id":2,"orderNo":"SO202609200002","userId":3,"userName":"bob","productTitle":"机械键盘 87 键","quantity":1,"unitPrice":12900,"totalAmount":12900,"status":"paid","receiverPhone":"13800138003","address":"兰州市安宁区安宁西路88号",...}}
```

```json
{"code":0,"message":"ok","data":{"id":1,"status":"off"}}
```

表现 4 的返回（用 alice 的 token 把 bob 的订单改成了已支付，金额 12900）：

```json
{"code":0,"message":"ok","data":{"paymentId":"PAY202611250002","orderId":2,"amount":12900,"status":"paid","paidAt":"2026-11-25T12:38:36Z"}}
```

- **证据**　上述四条命令及其返回即为证据。第三个请求执行后，用 `GET /api/products/1` 可确认 status 已变为 `off`；第四个请求执行后，`GET /api/orders/2` 的 status 由 `created` 变为 `paid`。
- **影响**　任意登录用户只需遍历自增 ID，即可批量获取全部用户的真实姓名、手机号、收货地址，以及全部订单的收货信息。这构成个人敏感信息批量泄露；同时可由非卖家下架任意商品，破坏商品在售状态。
  表现 4 更严重一层：**可以替别人的订单付款，也可以反过来把自己的订单标记成已支付而不付钱**——订单状态机与资金流水完全由请求方决定。
- **修复建议**　四个处理函数均在「已登录」校验之后补「是否本人」校验：
  - `handle_user_detail`（app.py:306-318）：比对 `user["id"]` 与路径中的 `user_id`，不等返回 403；若需支持管理员查看，额外判断 `role == "admin"`。
  - `handle_order_detail`（app.py:510-522）：查询时加 `AND o.user_id = ?` 条件，查不到即返回 403（不要返回 404，避免与「订单不存在」混淆）。
  - `handle_product_status`（app.py:414-436）：`SELECT` 时一并取出 `seller_id`，与 `user["id"]` 比对，不等返回 403。
  - `handle_create_payment`（app.py:555-593）：查到订单后先判 `order["user_id"] != user["id"]` 则 403，再判订单状态。**这一条要求「先校验归属、再校验状态」**，顺序反了会泄露「该订单是否已支付」这一信息。
- **备注**　四处为同一根因（只校验「已登录」不校验「是谁的资源」），故合并为一条，未拆条计数。四条表现分布在同一套 `current_user()` 之后缺少统一归属层的事实上，说明这不是四处遗漏，而是**缺一层鉴权中间件**。

## BUG-02 垂直越权：普通用户可访问管理端订单接口，获取全站订单与收货信息

- **模块**　管理
- **严重程度**　S1
- **前置条件**　alice 登录（role 为 `user`），token 为 `tk_2`
- **复现步骤**

```bash
curl -s http://127.0.0.1:8080/api/admin/orders -H 'Authorization: Bearer tk_2'
```

- **预期结果**　HTTP 403，提示仅管理员可访问。
- **实际结果**　HTTP 200，返回全站订单列表，含他人手机号与地址。

```json
{"code":0,"message":"ok","data":{"total":2,"items":[{"id":2,"orderNo":"SO202609200002","userId":3,"userName":"bob","productTitle":"机械键盘 87 键","quantity":1,"totalAmount":12900,"status":"paid","receiverPhone":"13800138003","address":"兰州市安宁区安宁西路88号","createdAt":"2026-09-20T13:05:00Z"},{"id":1,"orderNo":"SO202609180001","userId":2,...}]}}
```

- **影响**　与 BUG-01 表现不同：BUG-01 需逐个 ID 遍历，本缺陷一次请求即可拿到全量订单，是更高效的批量泄露入口。普通用户可获得全站交易额、买家姓名手机号与收货地址。
- **修复建议**　`handle_admin_orders`（app.py:540-551）在登录校验后增加 `if user["role"] != "admin": return (403, ...)`。注意不能只依赖前端隐藏入口，必须在服务端拦截。

## BUG-03 令牌机制缺陷：令牌可预测伪造，且登出后不失效

- **模块**　认证
- **严重程度**　S1
- **前置条件**　已知任意一个合法 token（如登录 alice 得到的 `tk_2`）
- **复现步骤**

```bash
# 表现 1：把 tk_2 改成 tk_1，直接以管理员身份读取资料
curl -s http://127.0.0.1:8080/api/users/1 -H 'Authorization: Bearer tk_1'

# 表现 2：登出后原 token 是否失效
curl -s -X POST http://127.0.0.1:8080/api/auth/logout -H 'Authorization: Bearer tk_2'
curl -s http://127.0.0.1:8080/api/users/2 -H 'Authorization: Bearer tk_2'
```

- **预期结果**　表现 1 应返回 401（令牌应不可伪造）；表现 2 文档承诺「登出后原 token 应失效」，应返回 401。
- **实际结果**　表现 1 返回 admin 完整资料；表现 2 登出接口返回成功后，原 token 仍可正常访问。

```json
{"code":0,"message":"ok","data":{"id":1,"username":"admin","realName":"系统管理员","phone":"13800138001","role":"admin","createdAt":"2026-09-01T08:00:00Z"}}
```

```json
{"code":0,"message":"ok","data":{"message":"已退出登录"}}
{"code":0,"message":"ok","data":{"id":2,"username":"alice","realName":"张爱丽","phone":"13800138002","role":"user",...}}
```

- **影响**　令牌格式为固定前缀 `tk_` 拼接用户自增 ID，既无签名也无服务端存储，因此：任何拿到过一个合法 token 的人都能枚举全部身份，包括管理员；登出只是返回一句提示，无法真正终止会话，令牌泄露后在整个有效期内（12 小时）都不可撤销。
- **修复建议**　`parse_token`（app.py:240-252）与 `handle_login`（app.py:271-295）：
  1. 令牌改为服务端生成的高熵随机串（如 `secrets.token_urlsafe(32)`），与会话表或签名机制绑定，不可由用户 ID 推导；
  2. 增加会话存储（内存表或数据库表），登出时删除对应记录，`current_user` 校验时查表；
  3. 若坚持无状态方案，至少对 `userId + 过期时间` 做 HMAC 签名，并在 `handle_logout` 中维护一张吊销表。
- **备注**　两个表现为同一根因（令牌既不可信也不可撤销），合并为一条。

## BUG-04 订单金额由客户端决定，可篡改单价与总额

- **模块**　订单
- **严重程度**　S1
- **前置条件**　alice 登录；商品 1「无线蓝牙耳机」数据库单价为 1990 分（¥19.90）
- **复现步骤**

```bash
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":1,"unitPrice":1}'
```

- **预期结果**　文档承诺「金额由服务端按商品价格 × 数量计算」。请求中携带的 `unitPrice` 应被忽略，返回 `unitPrice: 1990`、`totalAmount: 1990`。
- **实际结果**　服务端直接采信客户端传入的 `unitPrice`，且 `totalAmount` 亦可被 `payload["totalAmount"]` 覆盖。

```json
{"code":0,"message":"ok","data":{"id":3,"orderNo":"SO202611240003","productId":1,"productTitle":"无线蓝牙耳机","quantity":1,"unitPrice":1,"totalAmount":1.0,"status":"created","receiverPhone":"13800138002","address":"兰州市城关区天水南路222号",...}}
```

- **影响**　以 1 分钱买下任意商品。若支付链路按 `total_amount` 发起扣款，则直接造成资金损失；即便下游有对账，也会产生大量异常订单。这是本服务最高危的一条。
- **修复建议**　`handle_create_order`（app.py:472-480）：
  ```python
  # 删除从 payload 取 unitPrice 与 totalAmount 的逻辑，改为
  unit_price = product["price"]        # 只信数据库
  total_amount = unit_price * quantity # 全程整数分运算
  ```
  客户端传来的金额字段一律不读取。如果业务需要支持优惠价，应由服务端根据优惠规则计算，不能接受客户端报价。

## BUG-05 并发下单超卖，库存被扣为负数

- **模块**　订单
- **严重程度**　S1
- **前置条件**　数据重置后，商品 5「轻薄防晒外套」库存为 1；alice 登录
- **复现步骤**　用 10 个线程同时发起下单，每个买 1 件（脚本见 `testing/自动化/并发测试.py`，核心逻辑）：

```python
barrier = threading.Barrier(10)
def buy():
    barrier.wait()                      # 保证 10 个请求同时发出
    POST /api/orders {"productId": 5, "quantity": 1}
```

- **预期结果**　恰好 1 个请求返回 201，其余 9 个返回 409「库存不足」；结束后库存为 0，新增订单 1 条。
- **实际结果**　7 个请求返回 201，3 个返回 409；结束后库存为 **-6**，新增订单 7 条。

```text
商品5 下单前库存 = 1
并发 10 个请求，成功 7 个，失败 3 个
   HTTP 201  code=0  ok
   HTTP 201  code=0  ok
   ...（共 7 条 201）
   HTTP 409  code=40901  库存不足
   ...（共 3 条 409）
商品5 下单后库存 = -6
```

- **对照实验（排除「脚本写错」）**　只用一份并发结果，无法排除「其实是脚本把响应的数量数错了」或「脚本把库存读错了」。所以补了一组**只改并发度、不改其他任何东西**的对照：同样 10 条请求、同一商品、同一接口，但一条一条串行发（脚本 `testing/自动化/串行对照.py`）。

```text
串行实验开始前，商品 5 库存 = 1
  第  1 条：HTTP 201  code=0  ok
  第  2 条：HTTP 409  code=40901  库存不足
  ...（第 3~10 条均为 409 库存不足）
串行 10 条：201 成功 1 个，409 库存不足 9 个
商品 5 结束后库存 = 0，新增订单 = 1 条
结论：串行结果完全正确，库存没有被扣成负数
```

串行 1 个成功、库存归零，并发 7 个成功、库存 -6——两者的唯一差别是并发度。这就把「脚本计数错误」「库存读取错误」「库存校验本身失效」三种解释都排除了，剩下的只能是并发时序问题。

- **复现稳定性（连跑 3 轮）**　每轮开始前把商品 5 库存重置为 1，再跑一次 10 并发：

| 轮次 | 201 成功 | 409 库存不足 | 结束后库存 | 新增订单 |
|---|---|---|---|---|
| 1 | 7 | 3 | -6 | 7 |
| 2 | 7 | 3 | -6 | 7 |
| 3 | 8 | 2 | -7 | 8 |

**「库存变负」三轮全部复现，这是本条的结论依据。** 但成功个数在 7~8 之间波动——`Barrier` 只保证 10 个请求同时发出，不保证服务端同时读到库存快照；落在第一条 `UPDATE` 之后的请求会被正确判为库存不足，落在这之前的都会通过校验。所以**成功数取决于机器调度，不是一个常量，本报告不拿「7」这个具体数字做论证**。同理，在任何一段「先查后写」的代码里，只要并发量足够，卡进窗口的请求数就会波动，不能用「我这台机器上是 7」去反推「影响面有限」。

- **影响**　卖出 7 件而库存只有 1 件，库存账实不符，直接造成超卖与履约失败。这是必须实际构造并发请求才能发现的问题，静态阅读代码只能推测。
- **修复建议**　`handle_create_order`（app.py:466-470、493-494）：
  1. 把「校验库存」改成「原子条件扣减」，用受影响行数判断结果：
     ```python
     cur = conn.execute(
         "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?",
         (quantity, product_id, quantity))
     if cur.rowcount != 1:
         conn.rollback()
         return (409, JSON_TYPE, error_body(40901, "库存不足"))
     ```
  2. 删除 `time.sleep(STOCK_WINDOW_SECONDS)`（app.py:470）。这一行注释写「等待库存服务返回可售数量」，但代码从头到尾没有消费任何外部结果，唯一作用是把手慢时的偶发超卖变成稳定必现。
  3. 扣减与插入订单放在同一事务内，失败整体回滚；SQLite 下可用 `BEGIN IMMEDIATE` 避免写锁中途升级导致的 `database is locked`。

## BUG-06 下单数量未校验，负数使库存反向增加、小数被截断、非数字直接 500

- **模块**　订单
- **严重程度**　S1
- **前置条件**　数据重置；商品 1 库存为 12；alice 登录
- **复现步骤**

```bash
# 表现 1：负数
curl -s http://127.0.0.1:8080/api/products/1 | grep -o '"stock": [0-9]*'
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":-5}'
curl -s http://127.0.0.1:8080/api/products/1 | grep -o '"stock": [0-9]*'

# 表现 2：小数
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":1.5}'

# 表现 3：非数字
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":"两件"}'

# 表现 4：布尔
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":true}'
```

- **预期结果**　`quantity` 必须是正整数。负数、小数、非数字、布尔值均应返回 400 + `40001`。
- **实际结果**　四种情况全部放行，且各自以不同方式出错。

表现 1（负数）：订单生成，库存不减反增。

```json
{"code":0,"message":"ok","data":{"id":5,"orderNo":"SO202611240005","productId":1,"quantity":-5,"unitPrice":1990,"totalAmount":-9950.0,"status":"created",...}}
```

```text
下单前库存：12
下单后库存：17
```

表现 2（小数）：`1.5` 被静默截断成 `1`，用户以为买了 1.5 件，实际只买 1 件，且返回里没有任何提示。

```json
{"code":0,"message":"ok","data":{"id":4,"orderNo":"SO202611250004","quantity":1,"unitPrice":1990,"totalAmount":1989.9999999999998,"status":"created",...}}
```

表现 3（非数字）：抛 `ValueError`，被全局兜底成 500。

```json
{"code":50000,"message":"服务内部错误","data":null}
```

表现 4（布尔）：`int(True)` 得 1，订单按 1 件创建——因为 Python 里 `True` 就是 `int` 的子类。

```json
{"code":0,"message":"ok","data":{"id":5,"quantity":1,"unitPrice":1990,"totalAmount":1989.9999999999998,...}}
```

- **影响**　四个方向：负数让库存被免费刷高，可反复操作制造虚假库存，同时生成 `totalAmount` 为负的订单，若支付链路按该金额发起等于反向资金流出；小数被静默截断，是「用户意图与实际订单不符」的静默错误，比报错更难发现；非数字直接 500，暴露服务端堆栈行为且错误码不符合文档约定（应 400）；布尔被当 1，属于类型混淆。
  四者的共同根因是**只用 `int()` 做转换、不做类型与范围校验**——`int()` 对负数照收、对小数截断、对字符串报异常、对布尔返回 1。
- **修复建议**　`handle_create_order`（app.py:456-457）：当前是 `quantity = 1 if raw_quantity is None else int(raw_quantity)`，需改为显式校验：
  ```python
  raw_quantity = payload.get("quantity")
  if not isinstance(raw_quantity, int) or isinstance(raw_quantity, bool) or raw_quantity < 1:
      return (400, JSON_TYPE, error_body(40001, "quantity 必须为大于 0 的整数"))
  if raw_quantity > 999:
      return (400, JSON_TYPE, error_body(40001, "quantity 超出上限"))
  ```
  注意三点：`isinstance(True, int)` 为真，必须单独排除布尔；`isinstance(1.5, int)` 为假，小数会自然被挡在门外，不要用 `int()` 转换后再判断；对 `productId` 同样处理（当前传 `"1"` 也会被 `int()` 收下）。

## BUG-07 支付回调无验签，任意请求可将订单改为已支付

- **模块**　支付
- **严重程度**　S1
- **前置条件**　存在一笔待支付订单（订单 3，status 为 `created`），无需登录
- **复现步骤**

```bash
curl -s http://127.0.0.1:8080/api/orders/3 -H 'Authorization: Bearer tk_2' | grep -o '"status":"[a-z]*"'
curl -s -X POST http://127.0.0.1:8080/api/payments/callback \
  -H 'Content-Type: application/json' \
  -d '{"orderId":3,"paymentId":"FAKE0001","result":"success"}'
curl -s http://127.0.0.1:8080/api/orders/3 -H 'Authorization: Bearer tk_2' | grep -o '"status":"[a-z]*"'
```

- **预期结果**　文档承诺「回调必须验签（只接受平台签发的 paymentId 与正确签名），伪造请求应被拒绝」。无签名请求应返回 401 或 403，且订单状态不变。
- **实际结果**　请求返回成功，订单由 `created` 变为 `paid`。

```text
回调前状态: created
{"code":0,"message":"ok","data":{"orderId":3,"status":"paid"}}
回调后状态: paid
```

- **影响**　该接口完全公开且不校验来源，任何人构造一个 `result: "success"` 的 POST 即可把任意订单标记为已支付，等于免费下单。这是必须实际构造请求才能确认的问题，属于支付链路最严重的一类缺陷。
- **修复建议**　`handle_payment_callback`（app.py:595-619）：
  1. 增加签名校验：对 `orderId + paymentId + amount + result` 按约定算法生成摘要，与请求中的 `sign` 比对，不一致返回 403；
  2. 校验 `paymentId` 必须存在于 `payments` 表中且属于该订单，未支付记录不允许直接确认；
  3. 校验金额与订单 `total_amount` 一致；
  4. 接口即使公开也必须限流，防重放（记录已处理的 `paymentId`，重复回调直接返回成功幂等结果）。

## BUG-09 评价内容未转义，形成存储型 XSS

- **模块**　评价
- **严重程度**　S2
- **前置条件**　alice 登录；商品 1 已有评价
- **复现步骤**

```bash
curl -s -X POST http://127.0.0.1:8080/api/product-reviews \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"content":"<img src=x onerror=alert(1)>","rating":5}'
curl -s "http://127.0.0.1:8080/api/product-reviews?productId=1" | grep -o '<div class="content"><img[^<]*>'
```

- **预期结果**　文档承诺「用户内容必须做 HTML 转义」。页面中应出现 `&lt;img src=x onerror=alert(1)&gt;`。
- **实际结果**　标签原样输出到 HTML，浏览器会将其作为元素解析并执行 `onerror`。

```html
<div class="content"><img src=x onerror=alert(1)>
```

同时确认两件事：该响应确实是浏览器渲染的页面（`Content-Type: text/html; charset=utf-8`），**且没有任何 `Content-Security-Policy` 响应头**，也就是说既没有输出编码这一层，也没有 CSP 这一层兜底。

- **攻击链评估（为什么定 S2 而不是 S1）**　这条我一开始定的是 S1，理由是「存储型 XSS 可窃取会话」。后来按「攻击链是否闭环」重新过了一遍，发现链子在最后一环断了：
  1. **能注入**：任意登录用户 POST 一条带标签的评价，内容落到 `product_reviews.content`——成立。
  2. **能被渲染**：任何访问 `/api/product-reviews?productId=1` 的浏览器都会执行脚本——成立，已实测。
  3. **能造成实质损失**：**不成立**，但理由不能只写「用的是 Bearer 头所以偷不到」。Bearer 令牌一样可能被同源前端存进 `localStorage`，那样 XSS 照样读得到——所以这一环必须落在「这个服务里浏览器侧到底有没有凭据」这个事实上。我逐项查了三件事：
     - **页面里有没有脚本、有没有读写本地存储**：`grep -n "localStorage\|sessionStorage\|<script\|javascript:" sut/app.py` 零命中；`render_reviews_page`（app.py:627）拼出来的是纯静态 HTML。
     - **服务有没有下发 Cookie**：`grep -n "Set-Cookie" sut/app.py` 零命中，全程不用 Cookie 会话。
     - **有没有同源前端替用户存令牌**：仓库 `frontend/` 是另一方向的 mock 服务，不属 SUT；SUT 自己只托管评价页这一个服务端拼好的静态 HTML，没有前端构建产物。浏览器里不存在 `tk_x` 的副本。

     三者叠加的结论是：**在这一版部署形态下，浏览器侧根本没有可被脚本读到的凭据**，所以脚本能执行、但偷不到会话。这不是「因为用了请求头所以安全」，而是「这一版没有同源前端持有令牌」——差别很重要，前者是永久结论，后者是当前形态的结论。

  当前设计下这条的实际后果是：页面篡改（把评价区改成钓鱼页）、把访问者重定向到外站、在受害者浏览器里做键盘记录（若后续页面加了表单）。
- **影响**　存储型 XSS，影响所有打开该商品评价页的访问者，但当前无凭据可窃，实际损失限于页面篡改与钓鱼跳转，故定 S2。
  **若后续出现以下任一变化，应立即升为 S1**：① 出现同源前端（SPA / 管理后台）并把令牌存进 `localStorage` 或 `sessionStorage`；② 评价页接入登录态或改用 Cookie 承载会话；③ 这篇评价内容被后台管理页 / 客服工单 / 订单详情页消费；④ 增加「评价内容导出为 HTML 报表」这类功能。**定级取决于内容被谁消费、凭据存在哪，不取决于服务端有没有前端。**
- **修复建议**　`render_reviews_page`（app.py:662）：插入前对 `row["content"]` 与 `row["username"]` 做 HTML 转义：
  ```python
  import html
  parts.append('<div class="content">%s</div>' % html.escape(row["content"]))
  ```
  注意 `username` 与 `product_title` 同样来自数据库，应一并转义。若模板中需要保留换行，应先把 `\n` 转成 `<br>` 再转义，不要整体关闭转义。
  另外补一层响应头兜底：给该页面加 `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`，这样即使将来某处漏了转义，脚本也无法执行。

## BUG-10 商品列表 keyword 参数拼接 SQL，可绕过在售状态过滤

- **模块**　商品
- **严重程度**　S2
- **前置条件**　数据重置后在售商品 11 条、已下架 1 条（id=7）
- **复现步骤**

```bash
# 正常查询：默认只返回在售商品
curl -s "http://127.0.0.1:8080/api/products" | grep -o '"total":[0-9]*'

# 注入：闭合 LIKE 的单引号并追加恒真条件
curl -s -G "http://127.0.0.1:8080/api/products" --data-urlencode "keyword=' OR '1'='1" | grep -o '"total":[0-9]*'
```

- **预期结果**　`keyword` 应作为字面量参与模糊匹配，注入串不匹配任何标题，返回 `total` 为 0。
- **实际结果**　注入串使 WHERE 条件变为恒真，已下架商品被一并返回。

```text
正常查询 total = 11
注入后   total = 12，结果中包含 status=off 的 id=7
```

- **影响**　攻击者可绕过业务过滤条件读取本不应展示的数据（下架商品），也可通过构造条件探测表结构。因 SUT 使用的 SQLite 驱动不支持单次执行多条语句，无法执行 DROP/UPDATE 一类破坏性操作，影响限于信息泄露，故定为 S2 而非 S1。
- **修复建议**　`handle_product_list`（app.py:338）：当前为字符串拼接
  ```python
  conditions.append("p.title LIKE '%" + keyword + "%'")
  ```
  改为参数化，把通配符放进参数值而非 SQL 文本：
  ```python
  conditions.append("p.title LIKE ?")
  params.append("%" + keyword + "%")
  ```
  同时建议对该接口的其他字符串参数（`status`、`category`）统一走参数绑定，避免同类问题复发。

## BUG-11 订单总额浮点运算产生小数，金额不符合「分（整数）」约定

- **模块**　订单
- **严重程度**　S2
- **前置条件**　数据重置；商品 1「无线蓝牙耳机」数据库单价为 1990 分
- **复现步骤**

```bash
# 不传 unitPrice，让服务端自己算
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":1}'

curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":2}'
```

- **预期结果**　文档要求金额单位为「分（整数）」。`unitPrice` 为 1990 时，`totalAmount` 应为整数 `1990` 与 `3980`。
- **实际结果**　两笔订单的总额均为非整数。

```text
买 1 件：unitPrice = 1990，totalAmount = 1989.9999999999998
买 2 件：totalAmount = 3979.9999999999995
```

原始 JSON 片段：

```json
"totalAmount": 3979.9999999999995
```

- **证据**　上述字符串为接口返回原文（`grep -o '"totalAmount":[^,]*'` 取出，未经二次处理）。自动化测试 `test_create_order_normal` 的失败信息同样为此值：`assert 1989.9999999999998 == 1990`。
- **影响**　金额以浮点数写入 `total_amount`（NUMERIC 列，SQLite 会存为 REAL）。下游若按整数取整方式处理：截断则每笔少 1 分，四舍五入则偶发多 1 分；若直接把该浮点值传给支付网关，可能因「金额必须为整数分」被拒绝。单笔差异极小，但批量订单累积后会造成对账差异，且这类差异很难在事后定位来源。注意此问题在部分数值组合下不会显现（例如 1990 × 3 恰好得到 5970.0），说明它依赖具体数值，容易在抽测中被漏掉。
- **修复建议**　`handle_create_order`（app.py:477-478）：当前实现为
  ```python
  total = unit_price / 100 * quantity   # 先转元，产生浮点
  total_amount = total * 100            # 再转回分，误差被固定下来
  ```
  改为全程整数运算，不做元与分的来回换算：
  ```python
  total_amount = unit_price * quantity   # 单位已是分，直接相乘
  ```
  同时建议在数据层给 `total_amount` 加 `CHECK (total_amount >= 0)` 与整数校验，把这类问题挡在入库前。
