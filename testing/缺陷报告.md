## BUG-01 普通用户可读取任意用户的真实姓名与手机号

- **模块**　认证 / 用户
- **严重程度**　S1
- **环境**　SUT 默认配置，8080 端口，种子数据
- **前置条件**　alice 已登录，token 为 `tk_2`（userId=2）；bob 的 userId 为 3
- **复现步骤**　用 alice 的 token 请求 `/api/users/3`
- **预期结果**　HTTP 403，`code=40301`，提示无权限（接口文档承诺"只能看自己，看别人应 403"）
- **实际结果**　HTTP 200，返回 bob 的 `realName` 与 `phone`
- **证据**

  ```bash
  curl -s http://127.0.0.1:8080/api/users/3 \
    -H 'Authorization: Bearer tk_2'
  ```

  ```text
  {"code": 0, "message": "ok", "data": {"id": 3, "username": "bob", "realName": "李波", "phone": "13800138003", "role": "user", "createdAt": "2026-09-01T08:00:00Z"}}
  ```

- **影响**　5 个种子用户全部可枚举（ID 连续 1~5）。任意注册用户遍历 `id` 即可批量导出全站用户的真实姓名与手机号，属于个人信息泄露，可直接用于撞库与骚扰。叠加 BUG-02（token 可预测）后，未登录者也能做到。
- **修复建议**　在 `app.py:306` `handle_user_detail` 中，取到 `current_user(auth_header)` 后比对：`if user["id"] != user_id and user["role"] != "admin": return (403, JSON_TYPE, error_body(40301, "无权查看该用户"))`。不要只在路由层做判断，权限校验应放在处理函数内，因为同一数据可能被多个入口访问。

## BUG-02 token 由用户 ID 直接拼接且登出后仍有效

- **模块**　认证
- **严重程度**　S1
- **环境**　SUT 默认配置
- **前置条件**　无（不需要任何账号）
- **复现步骤**　① 直接伪造 `tk_1` 访问 `/api/users/1`；② 用 `tk_2` 登出，再用同一 token 访问 `/api/orders/mine`
- **预期结果**　① 伪造 token 应 401；② 登出后原 token 应失效（文档明确承诺）
- **实际结果**　① 返回 admin 的完整资料；② 登出后仍能正常读取订单
- **证据**

  ```bash
  # ① 不登录，直接拼 token
  curl -s http://127.0.0.1:8080/api/users/1 -H 'Authorization: Bearer tk_1'
  # ② 登出后复用
  curl -s -X POST http://127.0.0.1:8080/api/auth/logout -H 'Authorization: Bearer tk_2'
  curl -s http://127.0.0.1:8080/api/orders/mine -H 'Authorization: Bearer tk_2'
  ```

  ```text
  # ①
  {"code": 0, "message": "ok", "data": {"id": 1, "username": "admin", "realName": "系统管理员", "phone": "13800138001", "role": "admin", "createdAt": "2026-09-01T08:00:00Z"}}
  # ② 登出
  {"code": 0, "message": "ok", "data": {"message": "已退出登录"}}
  # ② 登出后仍可访问
  {"code": 0, "message": "ok", "data": {"total": 1, "items": [{"id": 1, "orderNo": "SO202609180001", "userId": 2, "userName": "alice", "productId": 1, "productTitle": "无线蓝牙耳机", "quantity": 2, "unitPrice": 1990, "totalAmount": 3980, "status": "created", "receiverPhone": "13800138002", "address": "兰州市城关区天水南路222号", "createdAt": "2026-09-18T09:20:00Z", "paidAt": null}]}}
  ```

- **影响**　这是本次作业里危害最大的一条：**认证体系形同虚设**。任何人把 URL 里的数字换一换就能扮演 admin，登出、改密码也不起作用。BUG-01、BUG-03、BUG-11、BUG-14 四条越权缺陷在它的加持下都会升级为"未登录也能利用"。
- **修复建议**　两处同源问题一起改（`app.py:240-302`）：① 换用 `secrets.token_urlsafe(32)` 生成不可预测的随机 token，服务端维护 `token -> userId` 映射并落库；② 登出时删除该映射或在表中标记 `revoked_at`，`current_user` 校验时检查撤销状态。不要把用户 ID 编进凭证。
- **备注**　本条已把"token 可预测"与"登出无效"合并，因为二者根因同为**凭证无服务端状态**，修复方式也是同一处。

## BUG-04 可上下架他人发布的商品

- **模块**　商品
- **严重程度**　S2
- **环境**　SUT 默认配置
- **前置条件**　alice 已登录（token `tk_2`）；商品 1「无线蓝牙耳机」的 `sellerId=1`（admin 发布）
- **复现步骤**　用 alice 的 token PATCH 商品 1 的状态为 `off`，再查商品 1
- **预期结果**　HTTP 403，商品状态不变（文档承诺"只能上下架自己发布的商品，别人的应 403"）
- **实际结果**　HTTP 200，商品 1 的 `status` 变为 `off`
- **证据**

  ```bash
  curl -s -X PATCH http://127.0.0.1:8080/api/products/1/status \
    -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
    -d '{"status":"off"}'
  curl -s http://127.0.0.1:8080/api/products/1
  ```

  ```text
  {"code": 0, "message": "ok", "data": {"id": 1, "status": "off"}}
  {"code": 0, "message": "ok", "data": {"id": 1, "title": "无线蓝牙耳机", "price": 1990, "stock": 12, "category": "数码", "status": "off", "sellerId": 1, "sellerPhone": "13800138001", "createdAt": "2026-09-01T09:00:00Z", "description": "半入耳设计，蓝牙 5.3，单次续航 6 小时。"}}
  ```

- **影响**　恶意用户可批量下架全站商品（ID 1~12 逐个 PATCH），使商城在售商品清零，造成可用性事故；也可把自己不想要的竞品商品下架。
- **修复建议**　`app.py:414` `handle_product_status` 里目前只查了 `SELECT id FROM products WHERE id = ?`。改为把 `seller_id` 一起查出来并比对：`if row["seller_id"] != user["id"] and user["role"] != "admin": return (403, ...)`。同时把 `UPDATE` 的 `WHERE` 加上 `AND seller_id = ?` 做双保险，避免"校验与更新之间被换掉"。

## BUG-05 商品搜索 `keyword` 存在 SQL 注入

- **模块**　商品
- **严重程度**　S1
- **环境**　SUT 默认配置
- **前置条件**　无（该接口不需要登录）
- **复现步骤**　GET `/api/products`，`keyword` 传 `' OR '1'='1`，`status=on`
- **预期结果**　按字面匹配关键词，没有商品标题包含这串字符，`total=0`
- **实际结果**　`total=12`，返回全部商品，条件被注入为恒真
- **证据**

  ```bash
  curl -s -G http://127.0.0.1:8080/api/products \
    --data-urlencode "keyword=' OR '1'='1" -d status=on
  # 对照：正常关键词
  curl -s -G http://127.0.0.1:8080/api/products -d keyword=耳机 -d status=on
  ```

  ```text
  # 注入
  {"code": 0, "message": "ok", "data": {"total": 12, "page": 1, "pageSize": 10, "items": [{"id": 1, "title": "无线蓝牙耳机", "price": 1990, ...}, {"id": 2, "title": "机械键盘 87 键", ...} ...
  # 对照（正常关键词 total=0 说明"耳机"关键词本身确实匹配不到，注入时却返回 12 条）
  {"code": 0, "message": "ok", "data": {"total": 0, "page": 1, "pageSize": 10, "items": []}}
  ```

  传入 `' OR '1'='1` 后 `total` 从 11 变为 12，且第 1 条商品的 `status` 是 `off`——说明 `p.status = 'on'` 这个条件被整体短路掉了，注入生效。

- **影响**　可绕过 `status='on'` 筛出已下架商品；进一步可用 `UNION SELECT` 把 `users` 表的 `phone`、`password` 拼进商品列表返回，配合 BUG-02 可直接拖库。这是不需要登录的**未授权漏洞**，风险最高。
- **修复建议**　`app.py:338` 用了字符串拼接：`conditions.append("p.title LIKE '%" + keyword + "%'")`。改为参数化：`conditions.append("p.title LIKE ?")`、`params.append("%" + keyword + "%")`。注意 `LIMIT/OFFSET` 那行（`app.py:348`）也是 `%d` 拼接，虽然是整数、风险较低，但建议统一改为参数化并先做类型转换。

## BUG-06 `pageSize` 未校验 1~50 范围，负数与 0 被接受

- **模块**　商品
- **严重程度**　S3
- **环境**　SUT 默认配置
- **前置条件**　无
- **复现步骤**　分别请求 `pageSize=0`、`pageSize=51`、`pageSize=-1`
- **预期结果**　三者均返回 HTTP 400，`code=40001`（文档承诺"`pageSize` 范围 1~50，超出应 400"）
- **实际结果**　均返回 HTTP 200，且原样回显非法的 `pageSize`
- **证据**

  ```bash
  for ps in 0 51 -1; do
    echo "pageSize=$ps"
    curl -s "http://127.0.0.1:8080/api/products?pageSize=$ps" | head -c 230; echo
  done
  ```

  ```text
  pageSize=0
  {"code": 0, "message": "ok", "data": {"total": 11, "page": 1, "pageSize": 0, "items": []}}
  pageSize=51
  {"code": 0, "message": "ok", "data": {"total": 11, "page": 1, "pageSize": 51, "items": [{"id": 1, "title": "无线蓝牙耳机", ...
  pageSize=-1
  {"code": 0, "message": "ok", "data": {"total": 11, "page": 1, "pageSize": -1, "items": [{"id": 1, "title": "无线蓝牙耳机", ...
  ```

- **影响**　`pageSize=0` 会让前端收到 `total=11` 但 `items=[]`，分页器算出 0 页却显示有数据，前端容易陷入空白列表；更实际的风险是**分页可被绕过**：`app.py:348` 用 `LIMIT %d` 拼接，而 SQLite 中 `LIMIT -1` 表示"不限制"。我把在售商品造到 71 个后实测：`pageSize=50` 正常返回 50 条，`pageSize=-1` 和 `pageSize=1000` 都返回了全部 71 条 —— 攻击者可一次性拉全表，既是信息收集的便利，也是轻量的资源消耗放大点。
- **修复建议**　`app.py:332-333` 解析后补一段范围校验：`if not (1 <= page_size <= 50): return (400, JSON_TYPE, error_body(40001, "pageSize 需为 1~50"))`；同时对 `page` 也加 `>= 1` 校验。`LIMIT/OFFSET` 改为参数化绑定，别用 `%d` 拼接。

## BUG-07 参数类型非法时返回 500 而非 400

- **模块**　全局
- **严重程度**　S2
- **环境**　SUT 默认配置
- **前置条件**　alice 已登录（部分子项需要）
- **复现步骤**　见下方四个子项的请求
- **预期结果**　均为 HTTP 400 + `code=40001`（文档明确"`id` 不是数字时返回 400，不是 500"）
- **实际结果**　均为 HTTP 500 + `code=50000`，服务端抛 `ValueError` 被兜底捕获
- **证据**

  ```bash
  curl -s http://127.0.0.1:8080/api/products/abc
  curl -s 'http://127.0.0.1:8080/api/products?page=abc'
  curl -s -X POST http://127.0.0.1:8080/api/orders \
    -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
    -d '{"productId":1,"quantity":"两件"}'
  curl -s -X POST http://127.0.0.1:8080/api/product-reviews \
    -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
    -d '{"productId":1,"content":"好","rating":"五星"}'
  ```

  ```text
  {"code": 50000, "message": "服务内部错误", "data": null}
  {"code": 50000, "message": "服务内部错误", "data": null}
  {"code": 50000, "message": "服务内部错误", "data": null}
  {"code": 50000, "message": "服务内部错误", "data": null}
  ```

- **影响**　四处 `int()` 转换都没有包 try（`app.py:309`、`331`、`455/457`、`702`）。后果有三：① 客户端传错类型被报成"服务端故障"，前端无法区分该提示用户还是该报警；② 500 日志会把监控打满，真实故障被噪音淹没；③ 若将来接入告警，一次恶意扫描就能触发大量误报。
- **修复建议**　抽一个公共函数 `def to_int(value): try: return int(value) except (TypeError, ValueError): return None`，在各 handler 里判空后返回 400。不要依赖全局的 `except Exception` 兜底（`app.py:852`），那层只该记录未预期异常。

## BUG-08 下单金额可被客户端篡改，且计算产生浮点误差

- **模块**　订单
- **严重程度**　S1
- **环境**　SUT 默认配置
- **前置条件**　alice 已登录（`tk_2`）；商品 2「机械键盘」价格 12900 分；商品 1 价格 1990 分
- **复现步骤**　① 下单时多传 `unitPrice=1`；② 下单时多传 `totalAmount=1`；③ 正常下单观察金额类型
- **预期结果**　服务端按 `商品价格 × 数量` 计算，忽略客户端传入的金额字段；金额为整数分
- **实际结果**　① `unitPrice` 被采纳，`totalAmount=1.0`；② `totalAmount` 被直接覆盖为 1；③ 正常下单返回 `5970.0`，是浮点数
- **证据**

  ```bash
  # ① 篡改单价
  curl -s -X POST http://127.0.0.1:8080/api/orders \
    -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
    -d '{"productId":2,"quantity":1,"unitPrice":1}'
  # ② 篡改总额
  curl -s -X POST http://127.0.0.1:8080/api/orders \
    -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
    -d '{"productId":2,"quantity":1,"totalAmount":1}'
  # ③ 正常下单，看金额类型
  curl -s -X POST http://127.0.0.1:8080/api/orders \
    -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
    -d '{"productId":1,"quantity":3}'
  ```

  ```text
  # ① 12900 分的键盘，1 分钱买走
  {"code": 0, "message": "ok", "data": {"id": 3, "orderNo": "SO202611250003", "productId": 2, "productTitle": "机械键盘 87 键", "quantity": 1, "unitPrice": 1, "totalAmount": 1.0, "status": "created", ...}}
  # ② 单价正常但总额被改成 1
  {"code": 0, "message": "ok", "data": {"id": 4, "orderNo": "SO202611250004", "productId": 2, "productTitle": "机械键盘 87 键", "quantity": 1, "unitPrice": 12900, "totalAmount": 1, "status": "created", ...}}
  # ③ 1990 × 3 应为 5970（整数），实际返回浮点
  {"code": 0, "message": "ok", "data": {"id": 5, "orderNo": "SO202611250005", "productId": 1, "productTitle": "无线蓝牙耳机", "quantity": 3, "unitPrice": 1990, "totalAmount": 5970.0, "status": "created", ...}}
  ```

- **影响**　接口文档只声明了 `productId` 和 `quantity` 两个字段，但服务端读了 `unitPrice` 和 `totalAmount`——**这是最典型的"多传字段被信任"漏洞**。任何用户都能以 1 分钱下单，再走 BUG-15 伪造回调置为已支付，形成完整的"0 元购"链路。浮点问题则会让 `19.9 元 × 3` 这类计算出现 `59.699999999999996` 的经典误差，金额对账必然出错。
- **修复建议**　`app.py:472-480` 整段删掉对 `unitPrice` / `totalAmount` 的读取，改为 `total_amount = product["price"] * quantity`，全程整数运算（价格本来就是分，不需要 `/100*100` 这层来回换算）。数据库 `total_amount` 列建议由 `NUMERIC` 改为 `INTEGER`，从存储层杜绝小数。

## BUG-12 并发下单导致超卖，库存变为负数

- **模块**　订单
- **严重程度**　S1
- **环境**　SUT 默认配置；商品 5「轻薄防晒外套」库存 1（种子数据专门留作并发测试）
- **前置条件**　alice 已登录
- **复现步骤**　10 个线程用 `threading.Barrier` 对齐起跑点，同时 POST `/api/orders` 买商品 5，各 `quantity=1`

- **证据**

  ```python

  barrier = threading.Barrier(10)
  def worker(i):
      barrier.wait()                      # 10 个请求同时出发
      requests.post(BASE + "/api/orders", json={"productId": 5, "quantity": 1},
                    headers={"Authorization": "Bearer " + token})
  ```

  ```text

  成功下单数 = 8   409 拒绝数 = 2
  并发后 stock = -7
  库存变化 = 1 - 8 = -7
  ------------------------------------------------------------
  库中商品5订单数 = 8
  库中商品5订单 quantity 合计 = 8
  ```

  ```text
  2026-11-25 12:08:33 [auth] 登录请求 username=alice password=<此处为本机实际口令明文，报告中已脱敏>
  ```

- **影响**　违反了"日志不得记录敏感凭据"的基本要求。日志通常会被采集到集中平台、被多人查看、长期留存，一旦泄露等于所有用户口令泄露（用户习惯复用密码，影响会外溢到其他系统）。同时日志里还有 `[access] ... token=Bearer tk_2`（含 token），同样敏感。
- **修复建议**　`app.py:274` 删掉 `password=%s` 部分，只保留 `username`；`app.py:861-862` 的 access 日志把 token 改为只记录前 4 位或 `***`。建议统一走一个 `mask_sensitive()` 函数处理。**另外注意：本条证据涉及真实口令样式，报告中已脱敏，不在 AI 对话中粘贴原文。**
