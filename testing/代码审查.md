## 重点三条的展开说明

### 序号 3：验签形同虚设（`payment_service.py:37`）

```python
def verify_sign(params):
    sign = params.get("sign")
    if sign == params.get("sign"):     # ← sign 就是 params.get("sign")
        return True
```

`sign` 变量就是 `params.get("sign")` 的返回值，这一行等价于 `if x == x`。只要回调里带了 `sign` 字段（哪怕值是 `"1"`），就直接 `return True`，后面真正的 MD5 校验永远走不到。

这不是"薄弱"，是**完全没有验签**。后果：任何人都能构造一个 `result=SUCCESS` 的 POST 请求把订单置为已支付。这与我在 SUT 里实测到的 BUG-15 是同一类问题，说明这类错误在实际项目里确实高频。

修复要点：① 删掉这行；② 校验键必须从参与签名的字段集合里剔除；③ 用 `hmac.compare_digest` 代替 `==` 防时序攻击。

### 序号 9、10：下单的竞态与事务（`order_service.py:43-53`）

```python
order_id = execute("INSERT INTO orders ...")          # ① 先建订单，已提交
for line in lines:
    stock = query_all("SELECT stock ...")[0]["stock"]  # ② 读库存，无锁
    if stock >= line["count"]:
        execute("UPDATE products SET stock = %s ...")  # ③ 写库存，已提交
    # else: 什么也不做，也不报错
```

三个独立问题叠在一起：

1. **`execute()` 每次都 `conn.commit()`**（`db_helper.py:50`），所以订单和库存是**三个独立事务**，中途失败无法回滚。
2. **读库存与写库存之间有窗口**，并发下多个请求读到同一个 `stock`，全部扣减成功 → 超卖。
3. **库存不足时静默跳过**（没有 `else` 分支），订单已经建好了但库存没扣，产生"有订单、没库存"的脏数据。

正确写法是把判断交给数据库并放在同一事务里：

```python
with get_connection() as conn:
    with conn.cursor() as cur:
        cur.execute("INSERT INTO orders (user_id, amount, status) VALUES (%s, %s, 'created')",
                    (user_id, total))
        order_id = cur.lastrowid
        for line in lines:
            cur.execute("UPDATE products SET stock = stock - %s "
                        "WHERE sku = %s AND stock >= %s",
                        (line["count"], line["sku"], line["count"]))
            if cur.rowcount == 0:
                raise StockNotEnough(line["sku"])   # 触发回滚
    # with 块正常退出才 commit，异常自动 rollback
```

### 序号 5：`except Exception: return SUCCESS`（`payment_service.py:54-55`）

```python
except Exception:
    return {"code": "SUCCESS"}
```

这是**最危险的一种"吞异常"**：不是返回错误，而是返回**成功**。

链路推演：回调进来 → `verify_sign` 返回 False（或 `order_no` 拼错导致订单查不到 → `IndexError`）→ 被这里捕获 → 返回 `SUCCESS` → 支付网关认为通知已送达，**不再重试** → 订单永久停留在未支付状态，而用户的钱已经扣了。

而且没有 `logger.exception`，线上只会表现为"偶发订单未到账"，几乎无法定位。

修复：至少记录异常；区分"可重试"与"不可重试"，前者返回 `FAIL` 让网关重试；只捕获具体异常类型，别用裸 `Exception`。
