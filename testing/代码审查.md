## 2. 三个必须优先处理的问题

按「被利用的难度」排序，以下三条不需要任何前置条件：

1. **`payment_service.py:37` 验签恒真** —— 一行代码，任何外部请求都能打通。这不是配置问题，是代码写错了比较对象。
2. **`payment_service.py:54-55` 异常吞成 SUCCESS** —— 就算第 37 行修好，这一条仍会让所有错误静默成功。两条叠加意味着支付链路**既不能拒也不能信**。
3. **`db_helper.py:29-34` 只收裸 SQL** —— 这不是某一处的注入，是**接口设计鼓励注入**。修单点没有意义，必须改签名。

## 3. 验证记录

以下输出来自在临时目录用**最小复刻脚本**验证逻辑（只复制问题函数体，不改动 `testing/legacy/` 原始文件）。

### 3.1 可变默认参数会跨调用污染（对应序列 9）

```python
def get_product(product_id, default={}):
    raw = None          # 模拟缓存未命中
    return default

a = get_product(1)
a["title"] = "被污染的默认值"
b = get_product(999)
print(b, a is b)
```

```text
第二次未命中返回: {'title': '被污染的默认值'}
同一对象? True
```

结论：第一次未命中后往返回值里加字段，**后续每次未命中的调用都会拿到同一个被改过的 dict**。放到 `build_order_lines` 就是把上一单的附加行带到下一单。

### 3.2 验签恒真（对应序列 1）

```python
def verify_sign(params):
    sign = params.get("sign")
    if sign == params.get("sign"):      # 恒真
        return True
    ...
```

```text
sign=None    -> True
sign=forged  -> True
sign=wrong   -> True
```

结论：不传 `sign`（`None == None`）、传 `forged`、传全零，**三种全部通过**。真正的 MD5 分支是死代码。

### 3.3 空值与零值崩溃（对应序列 10）

```text
refund_ratio {'paid_amount': 100} -> raise TypeError unsupported operand type(s) for /: 'NoneType' and 'int'
refund_ratio {'paid_amount': 0, 'refunded_amount': 0} -> raise ZeroDivisionError division by zero
reason=None -> raise AttributeError 'NoneType' object has no attribute 'strip'
```

注意第三行：`apply_refund(order_id, items, reason=None)` 的 **`reason` 默认值就是 `None`**，即「不传理由」这一个正常用法直接崩。

### 3.4 未退款订单让汇总接口崩溃（对应序列 15）

```python
def refund_summary(orders):
    total = 0.0
    for order in orders:
        total += order.get("refunded_amount")   # 缺键返回 None
```

```text
refund_summary 含未退款订单 -> raise TypeError unsupported operand type(s) for +=: 'float' and 'NoneType'
单笔已退款: {'count': 1, 'total': 10.0}
```

结论：**只要列表里有一笔订单从未退过款，整个汇总就 500**。而「从未退款」是绝大多数订单的常态，所以这不是边界，是主路径。

### 3.5 字符串拼接即注入（对应序列 4、5）

```python
query_all("SELECT * FROM orders WHERE order_no = '%s'" % order_no)
```

```text
正常: [(1, 'SO1001', 'created')]
注入: [(1, 'SO1001', 'created'), (2, 'SO1002', 'paid')]
```

结论：`order_no` 传 `x' OR '1'='1` 就返回了全表。因为 `query_all` 没有参数化通道，调用方**没有安全的写法可选**。

### 3.6 浮点累加（对应序列 5 的金额部分）

```text
0.1*3 累加: 800.3
29.9*3 : 889.7
```

`calc_amount` 把 `0.1 * 3` 累加后得 `0.30000000000000004`，加运费后显示 `800.3` 只是 `round` 前的巧合；金额一律用 `float` 累加在多次运算后必然出现分位误差。建议全链路改用「分」为单位的整数，与 SUT 的 BUG-07 同类。

## 4. 审查方法说明

- **为什么只读不跑**：`testing/legacy/` 是历史代码片段，依赖内网 Redis（`10.20.31.16`）、MySQL（`10.20.31.15`）和外部支付网关，本地无法直连；直接运行也只会得到连接超时，验证不了逻辑。
- **怎么保证结论可信**：对每个结论先想清「触发路径」，再把出问题的那几行**原样复制**到独立脚本里跑，用真实输出替代推理。第 3 节的 6 段输出都是这么来的。
- **局限**：静态审查无法发现只在特定时序下出现的问题（如连接池耗尽的具体阈值），也无法评估这些片段在生产中的实际调用频率。因此本文只标注「问题的存在性与触发路径」，不评估发生概率。
