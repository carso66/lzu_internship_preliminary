> 优先级：P0 核心链路 / P1 重要异常 / P2 一般。
> **执行结果**列：通过 = 符合文档承诺；失败 = 与文档承诺不符，关联缺陷编号。

## 统计

| 维度 | 数量 |
|---|---|
| 用例总数 | **56**（提交时的原始设计）+ **3 条事后补充**（TC-057~059，见上） |
| 按类型（原 56 条） | 正常 11 / 异常 18 / 边界 13 / 安全 6 / 权限 6 / 幂等 1 / 并发 1 |
| 三类基础要求 | 正常 11 ≥3 ✅ / 异常 18 ≥3 ✅ / 边界 13 ≥3 ✅ |
| 涉及金额或库存 | 18 条（TC-017、020~023、026~036、041、045） |
| 执行通过 | 32 条 |
| 执行失败（缺陷） | 24 条，关联 17 个缺陷（部分缺陷由多条用例覆盖） |
| 补充用例执行情况 | TC-057 失败（BUG-11）；TC-058 失败（BUG-03）；TC-059 无法执行（接口未实现） |
| 接口覆盖 | 16 / 16，全覆盖 |

> **关于 TC-057~059 的来源，如实说明**：这 3 条不是我一开始想到的。原 56 条用例按"接口逐个枚举"设计，能保证每个接口都摸到，但漏掉了"同一攻击面跨接口"的场景。缺口是在用 AI 做交叉检查时发现的（见 `AI_USAGE.md` 场景 D），我逐条核实后补上并实测。这件事本身暴露了我设计方法上的偏差：**按接口枚举 ≠ 按攻击面枚举**。

> 一条缺陷对应多条失败用例是正常的：例如 BUG-08（金额可篡改）同时被 TC-026（浮点）、TC-027（unitPrice）、TC-028（totalAmount）三条用例命中；BUG-07（类型非法返回 500）被 TC-016、019、036、051 四条命中。缺陷按**根因**合并，用例按**验证点**分开，两者数量不必相等。
