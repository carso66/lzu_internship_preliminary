# 测试用例

> 环境：`http://127.0.0.1:8080`，数据重置后执行。
> 登录凭据：alice / `Alice@123`（userId=2，token `tk_2`）；bob / `Bob@123`（userId=3）。
> 类型分布：正常 6 条、异常 13 条、边界 4 条，共 23 条，覆盖全部 15 个业务接口。
> 第 16 个接口 `/health` 不单独列用例——它是环境自检而不是业务功能，放在自动化里做冒烟（`test_health_ok`），实测 200 且 `status=up`；算上它，题面列出的 16 个接口全部有实测记录。
> 涉及金额或库存的用例 9 条（TC-09、TC-10、TC-12、TC-13、TC-14、TC-15、TC-18、TC-22、TC-23）。

## 执行统计

| 项 | 数量 |
|---|---|
| 设计用例 | 23 条（另有补充执行项 9 条） |
| 通过 | 8 条 |
| 不通过（对应缺陷） | 15 条 |
| 未执行 | 0 条 |
| 执行率 | 100% |
| 关联缺陷 | BUG-01 至 BUG-11，以及备选 X-01、X-02 |

不通过的 15 条全部因 SUT 缺陷导致，非脚本或数据问题。每条的判断依据是接口文档中的明确承诺（如「只能看自己，看别人应 403」「同一订单只能支付一次」「pageSize 范围 1~50」「金额单位为分（整数）」），而非个人主观预期。

其中 TC-12 是执行过程中被推翻的一条：手工执行时只核对了状态码 201 与库存变化，判为通过；后来写自动化断言时把 `totalAmount` 与 `unitPrice` 逐位比对，才暴露出返回值是 `1989.9999999999998`。据此补登 BUG-11，并把本条改判为不通过——**手工「看着差不多」会漏掉精度类问题，这是本轮最直接的一个教训**。

## 用例与缺陷的追溯表

缺陷报告里每一条都能回指到具体用例，反过来也成立——**11 条缺陷没有一条是「凭感觉记下来的」，都有对应的用例在执行**：

| 缺陷 | 关联用例 | 该用例覆盖的表现 |
|---|---|---|
| BUG-01 归属校验缺失 | TC-04、TC-11、TC-16、**TC-23** | 读他人资料 / 改他人商品状态 / 读他人订单 / 替他人付款 |
| BUG-02 垂直越权 | TC-05 | 普通用户读管理端订单 |
| BUG-03 令牌机制缺陷 | TC-03 | 登出后令牌仍可用 |
| BUG-04 金额客户端可控 | 补充执行项（unitPrice=1 实测） | 1 分钱下单 |
| BUG-05 并发超卖 | 补充执行项（10 并发 + 串行对照） | 库存变负 |
| BUG-06 数量未校验 | TC-14、TC-15 | 0 / 负数；另补测小数与布尔（见缺陷报告） |
| BUG-07 回调无验签 | TC-19 | 无签名回调被接受 |
| BUG-08 重复支付 | TC-18 | 两次支付都成功 |
| BUG-09 存储型 XSS | TC-20 | 评价内容未转义 |
| BUG-10 keyword 注入 | TC-22 | 下架商品被重新查出 |
| BUG-11 浮点金额 | TC-12 | 总额 `1989.9999999999998` |

两条走「补充执行项」而不是正式用例的，原因是它们需要特殊环境（并发要重置库存、金额篡改要构造非文档字段），按用例模板写会变成一行放不下的步骤；它们在缺陷报告里有完整的复现命令和脚本，追溯性不受影响。
