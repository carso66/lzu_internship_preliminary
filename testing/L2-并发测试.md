# L2-8 并发测试

> 要求：10 个请求同时购买库存为 1 的商品 id=5，验证库存是否变负，并给出数字结论。
> 取证脚本：`testing/自动化/concurrency_report.py`（可直接重跑）

## 1. 测试目标

验证 `POST /api/orders` 在并发场景下对库存的扣减是否原子。接口文档承诺"**库存永远不能小于 0**"，因此判据很明确：并发结束后库存是否 `< 0`。

## 2. 环境与方法

| 项 | 内容 |
|---|---|
| 被测商品 | id=5「轻薄防晒外套」，种子库存 **1** |
| 并发数 | 10 |
| 轮次 | 3（观察重复性，避免单次偶发） |
| 并发实现 | `threading.Barrier(10)` 让 10 个线程在同一起跑线释放，避免"伪并发"（顺序发请求根本压不出问题） |
| 客户端 | Python `requests`，`timeout=30` |
| 服务端 | `ThreadingHTTPServer`（多线程，天然支持并发） |

关键代码：

```python
barrier = threading.Barrier(CONCURRENCY)

def worker():
    barrier.wait()                       # ← 10 个线程在此对齐，同时往下走
    requests.post(BASE + "/api/orders",
                  json={"productId": 5, "quantity": 1},
                  headers={"Authorization": "Bearer " + token})
```

## 3. 执行与结果

```bash
# 服务需先启动（启动时会重建库，库存回到 1）
python testing/sut/app.py --port 8080
python testing/自动化/concurrency_report.py
```

```text

第 2 轮：成功下单 0　409 拒绝 10　库存 -6 -> -6

商品 id=5 的订单条数：7
这些订单的 quantity 合计：7
当前库存：-6

[结论] 存在超卖：库存被扣成负数，最小 -6。
       文档承诺「库存永远不能小于 0」，应为缺陷。对应 BUG-12。
```

另一次独立运行（重启服务后）结果为：**成功 8 单，409 拒绝 2 单，库存 -7**。

## 4. 数字结论

| 指标 | 数值 |
|---|---|
| 商品初始库存 | 1 |
| 并发请求数 | 10 |
| **实际成功下单数** | **7 ~ 8**（两次运行分别为 7 和 8） |
| 409 拒绝数 | 2 ~ 3 |
| **最终库存** | **-6 ~ -7** |
| **超卖数量** | **7 ~ 8 件** |
| 落库订单条数 | 7（与成功数一致） |
| 订单 quantity 合计 | 7（与库存减少量 1-(-6)=7 完全吻合） |

**结论：存在确定的并发超卖。库存 1 件的商品被成功卖出 7~8 件，库存被扣成负数。**

"落库条数 = quantity 合计 = 库存减少量"三者完全相等，说明这不是统计误差或计数 bug，而是**真的多卖了**——每一单都写进了数据库，库存每一件都真扣了。

## 5. 根因分析

源码 `app.py:459-495`：

```python
conn = get_conn()
try:
    product = conn.execute("SELECT id, title, price, stock FROM products WHERE id = ?",
                           (product_id,)).fetchone()
    if product["stock"] < quantity:                        # ① 检查
        return (409, ...)

    time.sleep(STOCK_WINDOW_SECONDS)                       # ② 等 150ms

    ...
    conn.execute("UPDATE products SET stock = stock - ? WHERE id = ?",
                 (quantity, product_id))                   # ③ 扣减
    conn.commit()
```

问题在 **①→②→③ 之间存在 150ms 的窗口**，且整个过程没有加锁：

1. 10 个请求几乎同时执行 ①，都读到 `stock = 1`，都通过 `1 < 1 == False` 的判断；
2. 全部进入 ② 等待 150ms；
3. 全部执行 ③，`stock = stock - 1` 被连续执行 7~8 次，从 1 一路减到 -6/-7。

`time.sleep(0.15)` 的注释写着"等待库存服务返回可售数量"——**这行代码本身就是把并发窗口放大到必然踩中的设计**。即使去掉 sleep，只要"检查"与"扣减"不在同一原子操作内，高并发下依然会超卖。

## 6. 为什么这条必须动手跑才能发现

静态读代码时：

```python
if product["stock"] < quantity:
    return (409, ...)
```

这一句在单请求视角下**完全正确**，看不出任何毛病。只有把并发压上去，才会发现"检查"与"扣减"之间隔着 sleep，属于典型的 **check-then-act 竞态**（TOCTOU）。

同理，`UPDATE products SET stock = stock - ?` 这条语句本身是原子的，但它执行时**已经不知道库存够不够了**——原子性用错了地方。

## 7. 修复建议

把判断下推到数据库，让"检查 + 扣减"变成一条语句：

```python
cursor = conn.execute(
    "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?",
    (quantity, product_id, quantity),
)
if cursor.rowcount == 0:
    conn.rollback()
    return (409, JSON_TYPE, error_body(40901, "库存不足"))
```

要点：

1. **`WHERE stock >= ?`** 是核心——库存不足时 `rowcount == 0`，天然完成检查。
2. **检查 `rowcount`**，不要用"再查一次库存"来判断。
3. 订单插入与库存扣减放在**同一事务**，`commit` 之前不释放。
4. SQLite 下建议 `BEGIN IMMEDIATE` 显式取写锁，避免 WAL 模式下的 `SQLITE_BUSY`。
5. 顺手删掉 `time.sleep(0.15)`——这行在生产环境里只会放大问题。

修复后重跑 `concurrency_report.py`，预期输出应为：成功下单 1，409 拒绝 9，库存 0。

## 8. 复现注意

- 每次重跑前**必须重启 SUT**（启动时重建库，库存回到 1）。若库存已被扣成负数，第 2、3 轮会全部返回 409，看不到超卖。
- 并发数低于 5 时偶发不超卖（时序碰巧错开）。脚本默认 10 并跑 3 轮，就是为了排除偶发。
- 并发测试会污染数据（库存变负、多出订单），**建议单独跑，不要和功能用例混在一台服务上**。
