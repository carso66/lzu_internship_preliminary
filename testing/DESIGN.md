## 2. 我是怎么拆的

| 顺序 | 我做的事 | 为什么排在这个位置 |
|---|---|---|
| 1 | 先启动 SUT，用 Apifox 做 56 个请求初筛 | 先确认服务可跑、接口真实返回，避免把环境问题当成业务缺陷 |
| 2 | 对失败项用 curl 复现 | Apifox 可能受 query 参数丢失或 HTML 解析影响，curl 才能把状态码和响应固定成缺陷证据 |
| 3 | 沉淀 L0 文档：测试计划、28 条普通用例、15 类缺陷、测试报告 | 先把范围、预期、真实结果和结论稳定，后面自动化才不会把错误预期写进脚本 |
| 4 | 沉淀 pytest 自动化 | L0 文档稳定后，重复执行的正常、异常、边界用例最适合转成回归 |
| 5 | 补安全专项和并发测试 | 越权、注入、金额篡改、伪造回调、XSS 和并发扣库存都需要专门构造，普通 CRUD 用例覆盖不到 |
| 6 | 审查 legacy 代码 | 手工和自动化暴露“现象”，静态审查能定位 SQL 拼接、验签恒真、连接复用、资源泄漏等根因 |
| 7 | 加 CI | 最后把启动、等待健康检查、pytest、报告上传和 SUT 停止固化，保证评审能复现 |

## 4. 一条完整链路

```text
python3 testing/sut/app.py --port 18081
  → GET /health
  → POST /api/auth/login 使用 alice 登录
  → GET /api/products，确认在售商品和分页
  → POST /api/orders { productId: 1, quantity: 2 }
  → 校验 201、totalAmount、unitPrice 和订单状态
  → POST /api/payments { orderId, method: alipay }
  → 复查订单详情，确认 paidAt 和状态
  → POST /api/product-reviews 写入评价
  → GET /api/product-reviews 检查 HTML 转义
  → 全程保留请求、响应和缺陷编号
```

这条链路覆盖认证、商品、订单、支付和评价；金额、越权、重复支付、伪造回调和 XSS 再从这条主链路上做旁路攻击。

## 5. 一个取舍

- **可以在哪两个方案里选**：先补 UI 自动化 / 先补安全专项和并发测试
- **我选了**：安全专项和并发测试
- **因为**：SUT 的主要风险集中在权限、金额、支付状态、HTML 输出和并发扣库存；这些用 requests 就能稳定复现。
- **代价是**：没有用浏览器验证渲染后的交互效果，后续需要 Playwright 补齐。

## 6. 我卡得最久的一个问题

- **现象**：CI 中启动 SUT 并运行 pytest 时，可能出现服务启动策略不一致和数据库竞态。
- **我一开始以为**：只要 CI 里先启动服务，pytest 里再自动启动一次也不会有影响。
- **试过什么**：查看 workflow 启动日志；单独运行 health check；分别验证 conftest 自动启动和外部 `SUT_BASE_URL` 两种模式。
- **最后靠什么定位的**：把“未设置 `SUT_BASE_URL`”和“设置了 `SUT_BASE_URL`”的行为拆开，外部地址只做健康检查，不再自动启动。
- **真正的原因**：本地自动启动逻辑和 CI 外部启动逻辑叠加。第二个 SUT 会先重建数据库，再因同一端口占用退出，可能让正在处理请求的第一个 SUT 访问不到表。

|---|---|---|
