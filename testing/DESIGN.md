# 设计说明（DESIGN）

## 1. 我做到了哪一步

- [x] L0：测试计划、23 条用例、11 条缺陷报告、测试报告，四项全部完成
- [x] L1：代码审查 10 条（覆盖 8 类问题）
- [x] L1：pytest 自动化 23 条（正常 5 / 异常 11 / 边界 7）+ 可复跑的并发验证与串行对照脚本（`testing/自动化/`）
- [x] L2：第 7 项安全专项、第 8 项并发测试

一句话：**我做了一轮针对电商服务的质量检查，能覆盖全部 15 个接口并给出 11 条有复现证据的缺陷，但还不能自动验证数据层的落库结果——23 条脚本断言的都是 HTTP 响应，库存和支付流水对不对仍然要靠手工去查。**

## 2. 我是怎么拆的（最重要）

| 顺序 | 我做的事 | 为什么排在这个位置 |
|---|---|---|
| 1 | 先把 SUT 起起来，用 curl 把 login、products、orders 三个接口各打一遍，看返回结构 | 不先看真实返回，后面写用例时字段名会全靠猜，写出来的步骤别人跑不通 |
| 2 | 通读 `sut/app.py`，按模块列出处理函数和它们各自「应该做但可能没做」的校验 | 纯靠点接口是盲试，16 个接口 × 六类边界能组合出上百种情况，得先缩小范围 |
| 3 | 按「资金 → 身份 → 数据」排序验证怀疑点，先测金额和库存 | 这两类出问题直接是资损，收益最高；而且金额/库存的缺陷最容易拿到真实返回证据 |
| 4 | 再测鉴权与越权，因为要先用 login 拿到 token，依赖第 3 步已经跑通的请求方式 | 依赖关系：越权测试需要两个不同身份的 token，得先确认登录可用 |
| 5 | 最后铺用例表，把已经跑过的验证反过来整理成 23 条 | 先有事实再写文档，避免为了凑用例数量编步骤 |
| 6 | 补并发、XSS、SQL 注入这三类必须构造特殊请求的项 | 这三类成本高，放最后；但它们恰恰是静态看代码只能推测、必须跑才能确认的 |
| 7 | 把接口校验与并发场景固化成 pytest 脚本 | 原本打算放弃，但第 6 步之后发现自己手工判的结论有一条是错的，见第 7 节 |

排这个顺序的核心理由：**先做「能被真实返回证明」的，后做「只能靠推理」的。** 缺陷报告要求可复现证据，所以每一步都优先选那种「跑一下就能拿到证据」的验证方式。

## 3. 我的产出分成哪几块

| 文件 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `测试计划.md` | 范围、不测什么、结束条件 | 它约束后面所有动作。写清「不测什么」比写「测什么」更能防止范围失控 |
| `测试用例.md` | 23 条用例与执行结果 | 和缺陷报告分开：用例记录「我打算验证什么」，缺陷报告记录「实际错在哪」。混在一起会让报告变成流水账 |
| `缺陷报告.md` | 11 条缺陷，含复现命令与真实返回 | 这是唯一会被评审逐条复现的文档，格式必须独立且自足 |
| `测试报告.md` | 汇总、未覆盖项、上线建议 | 面向决策者，结论要独立成立，不能要求读者先看缺陷报告 |
| `代码审查.md` | legacy 五个文件的静态问题 | 对象不同（别人的代码），方法不同（只读不跑），所以分开 |
| `安全专项.md` | 按认证/越权/输入/金额四方向重组 | 同一批缺陷换个视角组织。安全视角关心「防护是否存在」，功能视角关心「行为是否符合预期」 |
| `自动化/test_sut.py` | 23 条 pytest 用例，其中 14 条对照已登记缺陷，用 `@pytest.mark.defect` 标了编号 | 让「修完没有」变成一条命令能回答的事，而不是重新手工敲 23 遍 |
| `自动化/并发测试.py` | 可复跑的并发验证 | 并发缺陷靠手工点不出来，必须固化成脚本才能被复核 |
| `自动化/串行对照.py` | 同样的 10 条请求改成串行发 | 光有「并发下库存变负」证明不了不是脚本写错，得有一组只改并发度的对照 |

**如果再加「退款」和「优惠券」，哪里会最先乱掉？**

会乱在 `缺陷报告.md`。现在它的组织维度是「模块」（认证/商品/订单/支付/评价），一条缺陷只属于一个模块。但退款会横跨订单与支付（要校验订单状态、支付流水、退款金额、重复退款），优惠券会横跨商品与订单（券的适用范围、叠加规则、金额分摊）。届时一条缺陷该记在哪个模块下就说不清了，同根因合并的判断也会变难。

如果真要扩，我会在缺陷报告里加一列「影响链路」，把「模块」从归属维度降级为定位维度，用链路串起跨模块的问题。用例表也要加一列「场景」，因为退款和优惠券的用例天然是场景式的，不是接口式的。

## 4. 一次完整链路是怎么走的

选「下单金额与库存」这条，因为它串起了本服务最严重的三条缺陷（BUG-04、BUG-05、BUG-06）。

```
构造请求 POST /api/orders {productId:1, quantity:1, unitPrice:1}
  → 服务端 current_user() 校验 token
      → token 无效 → 401
      → token 有效（哪怕是我伪造的 tk_1）→ 继续
  → 查商品：SELECT id, title, price, stock WHERE id=1
      → 不存在 → 404
      → 存在（注意：没有查 status，所以下架商品也能走到下一步）
  → 比较 product["stock"] < quantity
      → 不足 → 409「库存不足」
      → 足够 → 继续（此时读到的是快照值）
  → time.sleep(0.15) ← 竞态窗口在这里被放大
  → unit_price = payload.unitPrice（客户端说了算）
  → total = unit_price / 100 * quantity（先换成元）
  → total_amount = total * 100（再换回分，浮点误差被固定下来）
  → INSERT 订单 + UPDATE stock = stock - quantity
      → quantity 为负时，stock 反而变大
  → 201，返回我传进去的 unitPrice 和我算出来的 totalAmount
```

实际验证时的四个断点：

1. 传 `unitPrice:1`，返回 `totalAmount:1.0` —— 证明第 6 步真的采信了客户端
2. 传 `quantity:-5`，库存从 12 变 17 —— 证明第 8 步的减法没有对符号做任何检查
3. 10 个并发买库存 1 的商品，7~8 个成功、库存 -6 ~ -7；同一脚本改成串行发，变成 1 个成功、库存 0 —— 证明第 3 步和第 8 步之间的窗口是真实的，而且「库存变负」只在并发时出现
4. 正常买 1 件，`totalAmount` 返回 `1989.9999999999998` 而不是 `1990` —— 证明第 7 步那次「元 → 分」的往返换算确实留下了误差。这一条是我手工执行时判错、后来被自动化断言抓出来的，详见第 7 节

## 5. 一个取舍：我选了 A，没选 B

- **可以在哪两个方案里选**：先把 15 个接口各铺 1-2 条用例做「广度覆盖」，vs 先在订单与支付两个模块深挖做「深度验证」
- **我选了**：深度优先。订单和支付两个模块花了大约六成时间，商品和评价模块只做了基础用例
- **因为**：这个服务的评分和实际风险都集中在钱上。金额可篡改、并发超卖、回调无验签这三条任意一条都能直接造成资损，而商品列表的排序、分页这类问题最多是体验问题。同样的时间投在订单模块的边际收益明显更高。另一个原因是：金额和库存的缺陷能拿到非常干净的证据（一个响应体、一个库存数字），而 UI 类问题往往需要截图和主观判断，证据强度不足
- **代价是**：商品与评价模块的覆盖偏薄。评价模块只测了提交成功一条正常用例和 XSS 一条异常用例，没有测评分边界之外的场景（比如同一用户重复评价、评价与订单的关联）。商品模块的 `category` 与 `status` 组合筛选也没测全。另外，自动化是全部手工验证做完之后才补的，这意味着深度优先那几轮验证的中间状态没被保留下来——补脚本时我是照着文档里的 curl 重敲一遍，而不是直接复用当时的请求

如果重来一次，我会把取舍改成「先深挖订单，但第一次验证就顺手写成脚本」。现在这个顺序（手工全部跑完再回头补自动化）的代价不是时间，是**证据的可追溯性**：手工阶段的临时数据状态没了，脚本只能重建。

## 6. 我卡得最久的一个问题

- **现象**：10 个并发请求同时买一件库存为 1 的商品，结果 7 个返回 201 成功，结束时库存是 **-6**。但单独发一个请求时，库存扣减完全正常。后来又连跑两轮，是 7、8，库存 -6、-7。
- **我一开始以为**：以为 SQLite 有写锁，多个写操作会自动串行，不会出现超卖。毕竟库级锁听起来应该能兜住这种事。所以第一反应是「是不是我的脚本没真的并发」。
- **试过什么**：
  1. 先单线程跑一遍，库存 1 → 0，完全正确，确认业务逻辑本身没问题
  2. 改成 5 个并发，库存变成 -3；改回 10 个并发，变成 -6。**超卖数量随并发数线性增长**，这个规律说明不是偶发，是必然
  3. 怀疑请求没同时发出，于是用 `threading.Barrier` 让 10 个线程卡在同一起跑线再同时放行。结果不变，排除了脚本因素
  4. 还是不信「是不是我数错了」，于是把同一个脚本改成串行发 10 条：1 条 201、9 条 409、库存归零。**唯一变量只有并发度，串行就对、并发就错**，到这里才彻底排除脚本问题的可能
  5. 最后回去读 `handle_create_order`，把「查库存」到「扣库存」之间的每一行都看了一遍
- **最后靠什么定位的**：读代码时注意到中间有一行 `time.sleep(STOCK_WINDOW_SECONDS)`，注释写「等待库存服务返回可售数量」。但这行前后没有任何变量被它赋值，也没有任何外部调用——它唯一的作用就是让请求停 0.15 秒。顺着这行往上看，发现库存校验用的是 `product["stock"]`，而这个值是在 sleep **之前**查出来的快照；往下看，扣减语句是 `stock = stock - ?`，既没有 `AND stock >= ?` 条件，也不检查影响行数
- **真正的原因**：check-then-act 竞态。判断和写入之间隔了 150 毫秒，这段时间里所有并发请求都基于同一个过期快照做决策，全部通过校验，然后各自执行减法。`ThreadingHTTPServer` 每请求一线程，所以 10 个请求真的在同时跑。SQLite 的写锁只能保证「两次 UPDATE 不会交错」，管不了「读到旧值再据此写入」这种逻辑层的竞态

那次之后我改了一个习惯：**看到「先查询、再根据查询结果写入」的代码，先找这两步之间有没有别的东西。** 有 sleep、有网络调用、有日志 IO，就是高风险的信号。

## 7. 没做的事和已知问题

| 项 | 状态 | 原因 |
|---|---|---|
| pytest 的覆盖范围 | 23 条，到接口层为止 | 23 条手工用例的场景基本都脚本化了，但断言只到 HTTP 响应层，没有查数据库落库结果——库存是不是真的扣了、`payments` 表是不是真的只有一条，仍然靠手工核对。这是下一件该做的事（见第 8 节） |
| 商品模块的组合筛选 | 只测了 keyword 单条件 | 深度优先策略的代价，见第 5 节 |
| 评价模块的重复评价 | 没测 | 文档未约定是否允许同一用户重复评价，缺少判定基准，不做主观推断 |
| 性能与长稳 | 没做 | 48 小时窗口内不具备条件，且题目未要求 |
| 支付金额与订单金额的一致性校验 | 只在缺陷里指出，未构造完整攻击链 | 需要模拟真实支付网关回调，超出本轮范围 |

**一次判错的记录。** TC-12（正常下单）我一开始判的是「通过」。当时的理由看着很充分：状态码 201 对、库存从 12 变 11 对、`totalAmount` 扫一眼是 1990 附近。后来写 pytest 断言时把 `totalAmount` 和 `unitPrice` 逐位比对，才发现实际值是 `1989.9999999999998`——我那一扫把小数点后 13 位当成了显示格式问题。据此补登 BUG-11，并把 TC-12 改判为不通过。

这件事直接改了我对自动化的排序。原先我把它当成「省时间」的加分项，排在所有手工验证之后；判错这一次之后我意识到它的真正作用是**防止人眼把误差当成没误差**——尤其是金额、精度、字段类型这类问题，人眼天然不擅长，脚本天然擅长。所以哪怕当天时间已经很紧，我还是先补了一批，后来又按 P0/P1 补到 23 条。

**已知但未写进缺陷报告的问题**：`GET /api/products/{id}` 对已下架商品仍返回完整信息（含 description），文档未约定下架商品是否应对普通用户可见，属于需求不明确，未按缺陷处理，仅在此记录。

## 8. 如果还有一天

1. **给脚本补上数据库层的断言（排第一）**。现在这 23 条只断言 HTTP 响应：状态码、`code`、返回体字段。但「响应说成功了」和「数据真的落库了」是两件事——比如 BUG-08 重复支付，我手工验证的依据是「`payments` 表里真的多了两条记录、两次金额都对得上」，而脚本里对应的断言只有「第二次应返回 409」。补法是在用例前后各读一次 `sut.db`，比 `orders` / `payments` 的行数和 `products.stock` 的值。这一步的收益比再加 10 条用例大，因为它把「接口行为」和「数据状态」分成两层来看，而越权、超卖、重复支付这类缺陷恰恰会在这两层之间出现分歧。
2. **把并发测试扩成矩阵**。现在是「库存 1 + 10 并发」一个点，应该测「库存 1/5/50 × 并发 5/10/20」，看超卖量与并发数的关系是否稳定线性。如果能画出这条线，缺陷的严重性论证会比一句「库存 -6」有力得多。
3. **补一轮权限矩阵测试**。现在越权是逐个接口试出来的，缺一张「角色 × 接口 × 资源归属」的完整表格。有了矩阵才能确认是「漏了几处」还是「整体缺一层鉴权」——从现有 4 条越权来看，我倾向于是后者，但需要矩阵验证。

排第一的理由是：另外两条是「让结论更可信」，第一条是「让结论真的可被检验」。现在脚本能告诉我「接口返回变了」，但告诉不了我「库存对不对」——而库存和金额恰恰是这轮最严重缺陷所在的层。
