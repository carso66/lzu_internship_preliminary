# 设计说明（DESIGN）

> 方向：测试。以下所有回答都围绕 L0 文档 + L1 自动化与审查的交付过程，不写套话。

---

## 1. 我做到了哪一步

- [x] L0：测试计划、66 条用例、19 条缺陷报告、测试报告 —— 4/4
- [x] L1：pytest 自动化（83 项）、legacy 代码审查（15 条）—— 2/2
- [ ] L2：未做

一句话：**我做了一套能一键复跑的接口测试（83 个测试项、覆盖 16 个接口），它能把 19 个缺陷里的 25 个失败点稳定复现出来，但还做不到在缺陷修好后自动判定「可以上线」——那 25 个 `xfail` 需要逐个摘掉才算数。**

## 2. 我是怎么拆的（最重要）

| 顺序 | 我做的事 | 为什么排在这个位置 |
|---|---|---|
| 1 | 先读 `testing/README.md` 的接口文档，抄下每个接口「承诺了什么」 | 缺陷的判据只有这一份文档。没有判据就写不出断言，写出来的也只是「我看它不爽」 |
| 2 | 起一个 SUT，用 `curl.exe` 把 16 个接口各打一遍，把真实返回抄下来 | 文档写的和实际返回经常不一致（比如 `total` 我一开始以为是 12，实际是 11，因为默认排除下架商品）。**先看真实数据再写用例**，否则一写就错一片 |
| 3 | 定下 6 个测试维度（正常 / 缺参错类型 / 边界 / 权限 / 重复操作 / 并发），逐个接口过一遍 | 只有「接口 × 维度」这张网格才能保证不漏。如果按接口顺序想到哪测到哪，一定会漏掉「越权」这一类——它不属于任何单个接口的职责 |
| 4 | **先建 pytest 骨架并跑通，再写文档** | 这是整个流程最关键的一次顺序调整，见下方说明 |
| 5 | 66 条用例逐条落成断言，缺陷用 `xfail(strict=True)` 标记 | 到这一步每个期望值都已被实跑验证过，写下的断言可信 |
| 6 | 用 `pytest --collect-only` 反查用例数与文档是否对得上 | 人工数 66 条用例、83 个测试项，两边对不上就说明有参数化漏写或重复 |

**第 4 步为什么重要**：我最初打算「先把 66 条用例写在文档里，再照着文档写代码」。写到商品模块就发现文档里已有一批用例的「预期结果」是我猜的——比如我写了「`pageSize=0` 应返回 400」，实际它返回 200 且返回全部数据。如果先写完文档再写代码，我会被迫在文档里改数字来迎合代码，那份文档就失去了作为判据的意义。

改成「先跑代码拿到真实结果 → 再写文档」之后，文档里每个「实测结果」单元格都是复制来的原文，每个「不符 → BUG-xx」都能用一条 curl 复现。代价是文档要写两遍（第一版草稿全废了），但可信度是本质差别。

## 3. 我的程序分成哪几块

| 文件 / 模块 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `conftest.py` | 拉起 SUT、分配端口、提供 token | 端口和 token 一旦写死在 7 个文件里，换台机器全废；集中到 fixture 后，只要 `conftest.py` 能跑，全部用例就能跑 |
| `test_health.py` | 1 项存活检查 | 单独成文件，是为了让它成为「SUT 是否起来」的第一道信号。它挂了，后面的失败全是噪音 |
| `test_auth.py` / `test_authz.py` | 认证（5 项）/ 越权（9 项） | **故意分开**：`auth` 测「你是谁」，`authz` 测「你能干什么」。这两个概念混在一个文件里，写断言时很容易把「没登录」和「登录了但没权限」混成一个 401 |
| `test_products.py` / `test_orders.py` / `test_payments.py` / `test_reviews.py` | 四个业务模块，各 24 / 16 / 12 / 16 项 | 按业务边界拆，和缺陷报告、测试用例文档的章节一一对应，方便交叉核对「这条用例在文档第几节、在代码第几行」 |

**如果再加「退款」和「优惠券」，哪里会最先乱掉？**

先乱的是 `conftest.py` 的夹具作用域，不是业务代码。现在的规则是「每个模块一个新实例」，因为下单会改库存。退款同样改数据（`refunded_amount`），优惠券还要引入「已领取/已使用」状态，那时「模块级隔离」就不够了——`test_refund.py` 内部的前一条用例会污染后一条。

届时要改成**函数级 `db_snapshot` 夹具**：每个用例前把 `sut.db` 复制一份、用例后还原。这个改动会波及全部 7 个文件里所有依赖初始库存的断言（比如「id=5 库存 1」）。所以真正的瓶颈是测试基础设施的作用域设计，业务代码反而好加。

## 4. 一次完整链路是怎么走的

选 **TC-022 正常下单** 这条链路，因为它是「一个请求穿过最多状态」的一条：

```
POST /api/orders {productId: 9, quantity: 3}  + Authorization: Bearer tk_2
  → conftest 已注入 alice 的 token（tk_2）
  → SUT：parse_token("tk_2") → userId=2，无签名，所以任何 tk_<数字> 都成立（BUG-04）
  → 查商品 id=9：中性笔，单价的原始值 1290（分），库存 50
  → 校验 quantity：无正数校验（BUG-08），此处传 3 恰好合法
  → 计算 total = 1290/100*3 = 38.7  →  total_amount = 38.7*100 = 3870.0000000000005（BUG-07）
  → 查库存 50 ≥ 3，扣减为 47，写入 order
  → 201 {code:0, data:{orderNo, totalAmount: 3870.0000000000005, ...}}

断言链：
  ① status == 201                    ← 正常路径
  ② data.totalAmount == 3870         ← 文档承诺「金额单位为分」，实际是 3870.0000000000005
  ③ 重查 /api/products/9 库存 == 47  ← 库存确实扣了
```

这条链路上有三处可以独立失败：**认证**（token 是否被正确解析）、**金额**（是否服务端计算、精度是否正确）、**库存**（是否扣减、是否并发安全）。我把它画出来的收获是发现「断言②不必等①通过才写」——这两个断言验证的是不同层的正确性，一个挂了不代表另一个不能测。

这也是我后来把「金额精度」单独提成 BUG-07、而不是并进「下单功能正常」的原因：**链路上每一跳都是一个独立的判据**，合并了就分不清是哪一跳坏的。

## 5. 一个取舍：我选了 A，没选 B

- **可以在哪两个方案里选**：缺陷在 pytest 里用 `xfail` 标记 / 直接把断言写成「SUT 现在的错误行为」
- **我选了**：`xfail(strict=True)`
- **因为**：如果断言写成 `assert body["totalAmount"] == 3870.0000000000005`，测试是绿的，但这等于**用测试固化了 bug**。将来 SUT 修好了，测试反而变红，维护者会以为是 SUT 退化了。`xfail(strict=True)` 表达的是「按文档应该通过，现在失败，我知道原因」，语义正确。

  更重要的是可验证性：`strict=True` 让「修好一处」立刻体现为「有一项从 xfailed 变 failed」。缺陷修完那一刻，报告会主动报警，不存在「缺陷修了但用例还挂着 xfail」的假绿。这一点写进了测试报告的复测建议里，是这套自动化最实用的一条性质。

- **代价是**：报告上看起来「25 个失败」，第一眼容易被误读成脚本有 bug。所以我在 `SUBMISSION.md` 和测试报告里各写了一段解释 25 个 `xfailed` 的来历，并且坚持 `0 failed / 0 error` 这个门槛——**「预期内失败」和「脚本自己坏了」必须在数字上分得开**，否则整套自动化就失去诊断价值。

  另一个代价：修完缺陷后必须人工把 `xfail` 标记摘掉。如果忘了摘，`strict=True` 会报 failed（这正是设计意图），但需要有人知道「failed 在这里是好事」。

## 6. 我卡得最久的一个问题

- **现象**：pytest 第一次全量跑完，`58 passed, 25 xfailed` 之前有一版是 **4 个 failed**。全都是「正常路径」的用例：`test_product_list_default` 断言 `total == 11` 却得到 10，`test_product_detail` 断言库存 12 却得到 10，另外两条也是类似的数量偏差。诡异之处是**单独跑这几个文件全绿，一起跑才红**。

- **我一开始以为**：
  1. 以为是断言写错了，回去对文档——文档写默认 12 个商品、11 个在售，10 对不上，说明不是断言的事。
  2. 以为是 SUT 有并发 bug，毕竟被测代码里就有个 `time.sleep(0.15)` 的竞态窗口。差点去写 BUG。

- **试过什么**：
  1. 单独跑 `pytest test_products.py -q` → 全绿。说明不是这个文件的问题。
  2. 上面加 `-k test_product_list_default` 单独跑 → 绿。排除了这条用例自身。
  3. 打印 `--collect-only` 看执行顺序 → 发现 `test_orders.py` 排在 `test_products.py` 前面（pytest 默认按文件名排序）。
  4. 在失败的断言里把 `body["data"]["list"]` 的标题打出来 → 看到列表里少了一个商品，少的正是 `test_orders.py` 里下过单的那个。

- **最后靠什么定位的**：**把执行顺序和失败数据对起来。** 看到「少的那条正好是前面模块下过单的商品」时，原因就唯一了：`conftest.py` 里 `base_url` 是 `scope="session"`，整个测试会话只有一个 SUT 实例、一份 `sut.db`。`test_orders.py` 里的用例下单扣了库存、`test_products.py` 里的用例发布了新商品，后面的模块读到的是**被前面污染过的数据**。

  回头看这个结论很浅，但当时代码里同时有「数据库被改」和「SUT 有已知并发 bug」两个嫌疑，是数据比对把我从第二个嫌疑里拉出来的。

- **真正的原因**：夹具作用域太小。修复是把 `base_url` 改成 `scope="module"`——每个测试文件一个新实例、一份干净种子库。改完 `58 passed, 25 xfailed, 0 failed`。

- **副作用**：模块级实例意味着启动 7 次（每次约 0.3 秒），总耗时从 6 秒涨到 10 秒。这个代价可以接受。同时我在 `conftest.py` 顶部写了注释说明「不要在手工跑着 SUT 时执行 pytest，两边会互相重置 `sut.db`」——这是同一类问题的另一种形态，提前写下来省得以后自己再踩。

## 7. 没做的事和已知问题

| 项 | 状态 | 原因 |
|---|---|---|
| L2 加分项（安全专项 / 并发专项 / CI / Playwright） | 没做 | L2 选做。同样的时间投在 L0-3 的证据质量上收益更高：每条缺陷都有可复制的 curl 和真实返回，比多做两个加分项更能体现测试能力 |
| 并发规模只到 10 线程 | 已验证 3 线程与 10 线程两组 | 两组都稳定超卖（3 线程：3 个 201、库存 -2；10 线程：8 个 201 + 2 个 409、库存 -7），结论已成立；但 10 线程时出现了 2 个 409，说明「抢到 8 个成功」这个上限与线程数有关，机制还没说清，属 L2-8 范畴 |
| 压力测试、长稳测试 | 没做 | SUT 是 `ThreadingHTTPServer` + SQLite，测出来的吞吐对真实架构没有参考价值，属无效数字 |
| 权限矩阵穷举（5 用户 × 16 接口 = 80 组） | 只取代表性组合 | 穷举的边际收益低，且已有 4 条越权缺陷（BUG-01/02/03/05）说明这一类整体缺失，补组合不如提一条「缺统一鉴权中间件」的建议 |
| 重复支付 / 重复评价的并发竞态 | 只单线程验证 | BUG-11、BUG-19 串行即可稳定复现；并发放大效应属于 L2-8 的范畴 |
| 缺陷报告里的 S2/S3 判定 | 主观 | 严重程度的分级标准是我自己定的（写在缺陷报告开头），换个人可能把 BUG-16 判成 S3。这是本轮交付里最不客观的部分 |

## 8. 如果还有一天

1. **先做「修复后回归」的闭环。** 现在这套自动化的价值是「发现问题」，还没验证过「确认修好」。挑 BUG-06（金额篡改）和 BUG-09（并发超卖）两条，自己改一版 SUT、把对应的 `xfail` 摘掉、跑一遍看是否转绿。**排第一的原因**：这一步会暴露我所有断言的假设是否可靠——如果修好了测试还红，说明断言里混进了对实现细节的依赖，那 25 个 xfail 的可信度就要打折扣。这是整套交付里唯一没被验证过的环节。

2. **做 L2-8 并发专项，扩到 10 并发 × 3 个商品。** 现在只有「库存 1 被 3 个请求抢」这一个数据点，无法区分「完全没有锁」和「锁粒度太粗偶尔失效」。补上「库存 10 被 10 个请求抢」和「不同商品并发」两组对照，才能说清是不是全局无锁。**排第二的原因**：它能把 BUG-09 的结论从「会超卖」提升到「超卖的机制是什么」，对修复方案（行锁 vs 乐观锁 vs 数据库唯一约束）有直接指导意义。

3. **给 `conftest.py` 加函数级数据库快照。** 现在模块级隔离虽然解决了污染，但因果链很长——第 5 个用例失败时，要先排除前 4 个用例是否改过数据。加一层「用例前复制 `sut.db`、用例后还原」，失败就一定是这条用例自身的问题。**排第三的原因**：这是纯基础设施收益，不加也能交付；但如果要继续往 100+ 条用例扩，不加会越来越难定位失败原因。
