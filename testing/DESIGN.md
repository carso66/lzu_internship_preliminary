| 顺序 | 我做的事 | 为什么排在这个位置 |

| 1 | 读 `testing/sut/app.py` 全文（898 行），先通读一遍源码 | 题目允许看源码。先看一遍能知道"有可能出问题的地方在哪"，避免盲试浪费 48 小时里最宝贵的头 30 分钟。但**看完不写结论**，只列假设 |
| 2 | 按 README 第 2 节的 5 步命令跑一遍 | 这一步就已经能撞出 BUG-01（越权看手机号）。先拿到第一个确定的成果，心态就稳了 |
| 3 | 写一个探测脚本，把 23 个假设一次性打完 | 手工一条条 curl 太慢。脚本一次跑完能立刻看出哪条成立、哪条是我猜错。**猜错的直接丢弃，不写进报告** |
| 4 | 拿真实结果回来对照源码，定位到具体行号 | 只有"返回 200 但应该 403"还不够，修复建议必须能指到 `app.py:306` 这个级别 |
| 5 | 每条缺陷单独重启服务后重新采证 | 这是最关键的一步。`quantity=-5` 会把库存越测越多，前一秒的证据后一秒就对不上。**换个数据库状态，缺陷报告就不可复现了** |
| 6 | 并发和安全专项放在功能测试之后 | 这两个会严重污染数据（库存变负、多出几十条订单）。先做会把后面的功能用例全部带偏 |

排序的核心逻辑：**先拿一个确定的成果 → 再用脚本扩大战果 → 最后才做会污染环境的部分**。第 5 步（每条重启）是我中途才补上的，一开始没做，导致 `quantity=-5` 那条第一次采证时库存数字对不上，白跑了一轮。

## 4. 一次完整链路是怎么走的

以"并发超卖"这条为例，这是我最满意的一条，因为它完整走了"假设 → 实测 → 定位 → 结论"：

```
读源码 app.py:466-494
  → 发现 if stock < quantity 判断之后，隔了 time.sleep(0.15) 才扣库存
  → 假设：并发下 10 个请求会同时通过判断
  → 写 concurrency_report.py，用 threading.Barrier(10) 对齐起跑点
  → 10 个请求同时打到 /api/orders，买商品 5（库存 1）
  → 结果：成功 7 单，库存 1 → -6
  → 落库核对：订单 7 条、quantity 合计 7、库存减少 7
  → 三者相等，证明不是统计误差，是真多卖了
  → 换一轮重跑：成功 8 单，库存 -7（确认可重复，不是偶发）
  → 定位根因：check-then-act 竞态，判断与扣减不在同一原子操作
  → 给出修复：UPDATE ... WHERE stock >= ?  + 检查 rowcount
```

关键是中间那步"**落库核对**"。如果只看接口返回，很容易怀疑是自己统计错了；把"订单条数 = quantity 合计 = 库存减少量"三个数字对上，才能确定是 SUT 真的多写了订单。

## 5. 一个取舍：我选了 A，没选 B

- **可以在哪两个方案里选**：每条缺陷前重启服务 / 一次性跑完所有探测再统一整理
- **我选了**：每条缺陷前重启服务
- **因为**：`quantity=-5`、`pageSize=-1` 这类缺陷会改变数据库状态，后面的证据就不可复现了。评审照着我的 curl 敲一遍，必须得到完全一样的结果，否则这份报告等于没写。
- **代价是**：慢很多。一条缺陷要等 2~3 秒启动，17 条就是一分多钟，而并发测试还要跑 3 轮。我一开始选了 B（图快），结果 `quantity=-5` 那条的库存数字和文档对不上，只能推翻重采。**这个代价我认为值得**——缺陷报告的可复现性比我的时间重要。

另一个小取舍：自动化里我用 `xfail(strict=True)` 而不是直接让用例失败。

- 选 `xfail` 的理由：`pytest -q` 能跑出干净的结果，不会被 23 条红色淹没，同时 `--runxfail` 又能看到真实失败。
- `strict=True` 是关键：SUT 修好后对应用例会变 XPASS 并报错，强迫更新缺陷报告。
- 代价：评审核对时要多敲一个参数。我在 `SUBMISSION.md` 里写清了这个用法。

## 6. 我卡得最久的一个问题

- **现象**：写完第一版自动化，跑出 `23 failed, 28 passed`，但其中一条失败很奇怪——`test_product_list_default_only_on_sale` 报 `assert 30 == 11`。
- **我一开始以为**：SUT 的商品总数计算错了，或者是分页逻辑有 bug。
- **试过什么**：① 手工 curl `/api/products`，返回 `total: 11`，是正常的；② 怀疑是 token 问题，换 admin 重试，还是 30；③ 单独跑这一条用例（`pytest -k test_product_list_default_only_on_sale`），通过了。
- **最后靠什么定位的**：`-k` 单独跑能过、全量跑就挂 —— 这个差异指向"用例之间有依赖"。回头看代码，前面 `test_create_product_success` 等用例各建了商品，累积到 30 个。**我的用例本身没有隔离性**。
- **真正的原因**：我把"种子数据有 11 个在售商品"当成了硬断言。这个数字只在服务刚启动时成立，任何创建商品的用例都会破坏它。
- **怎么修的**：把所有依赖具体总数的断言都改掉。要验证搜索功能，就先建一个带特殊标记的商品再搜它；要验证列表，只断言 `total >= 11` 和"返回项全部 status=on"这两条不变量。**断言不变量，不断言快照数字。**

这件事让我意识到：被测系统的问题是 SUT 的，测试用例的问题是我自己的。**混在一起报出去，等于把 22 条真缺陷的可信度也拖下水了。** README 里那句"提交前应排除脚本自身错误"说的就是这个。

## 8. 如果还有一天

按优先级：

1. **把所有采集证据的过程也脚本化，做成一条命令出全套证据**。现在 17 条缺陷是我逐条重启、逐条 curl 采的，重跑一次要一分多钟且容易漏。做成 `collect_evidence.sh` 一键产出，缺陷报告就是"跑脚本的产物"而不是"我手工拼的文档"，可信度会更高。**这条排第一，因为它直接决定这份作业能不能被别人复现。**

2. **补多商品并发一致性测试**。现在只测了单商品超卖。真实场景是"秒杀时 100 个商品被上千人同时抢"，需要验证的是整个订单表的一致性，而不只是一个商品的库存。

3. **给代码审查补上可运行的复现**。现在 `legacy/` 那 25 条全是静态读出来的，`payment_service.py:37` 那个 `sign == params.get("sign")` 恒为真的问题，如果能写出一个小脚本跑一遍证明它真的放行任意签名，说服力会强很多。这需要 mock 掉 MySQL 和 Redis，工作量不小，所以排在最后。
