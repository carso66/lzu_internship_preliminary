## 2. 模型选型

本项目采用按任务复杂度分配模型的方式，而不是所有任务都使用同一模型。

| 使用场景 | 模型 | 选择原因 |
|---|---|---|
| 接口测试用例设计 | DeepSeek-V4.1-Flash | 任务边界明确，主要是测试场景枚举和结构化输出，使用轻量模型即可 |
| 项目整体分析与测试方案设计 | DeepSeek-V4-Pro | 涉及多个文件、接口关系及任务交付要求，需要较强的上下文分析能力 |
| 支付源码安全审查 | DeepSeek-V4-Pro | 需要分析验签、异常处理、订单状态及支付幂等性之间的逻辑关系 |
| 数据库事务与并发问题分析 | DeepSeek-V4-Pro | 需要结合数据库连接、提交机制和业务调用链分析潜在问题 |

选型原则：简单、明确的任务优先使用 Flash；涉及多文件分析、安全风险和复杂业务逻辑时使用 Pro。

## 3. 四个实际使用场景

### 场景1：接口测试用例设计（成功案例）

- **我想干什么：** 为用户资料接口设计覆盖正常、异常和权限边界的测试用例。
- **使用模型：** DeepSeek-V4.1-Flash。任务相对明确，不需要复杂源码推理。
- **我怎么问的：**

  > 请根据校园电商系统的接口要求，为 GET /api/users/{id} 设计8条测试用例，覆盖正常登录、未登录、无效Token、越权访问、异常用户ID等场景。每条用例包含编号、测试目的、前置条件、请求步骤、预期HTTP状态码和预期结果。对于无法确定的行为请明确标注，不要编造接口实现细节。

- **它给了什么：** 生成了本人信息查询、未登录访问、无效Token、越权访问及异常用户ID等测试场景，并对缺少接口契约支持的预期结果标注待确认。
- **我改了吗：** 后续根据主办方 README 和实际接口行为核对预期结果，没有直接把模型生成的所有判断当成缺陷标准。
- **怎么确认改对了：** 通过实际接口请求及 pytest 自动化测试验证。
- **结论：** 修改和核对后采用。

### 场景2：支付源码审查遇到失败（失败案例）

- **我想干什么：** 审查 payment_service.py 中的支付回调签名验证、异常处理、金额校验和幂等性。
- **使用模型：** DeepSeek-V4-Pro。支付安全问题涉及多个逻辑环节，需要深入分析。
- **我怎么问的：**

  > 请独立审查 payment_service.py，重点检查支付回调签名验证是否正确及是否可绕过、异常处理是否错误确认成功、是否验证订单金额和商户身份、重复回调是否造成状态异常，并给出具体行号和修复建议。

- **它给了什么：** 第一次没有读取到本地源码，因此拒绝给出具体行号，只提供了通用审查清单。
- **我改了吗：** 没有直接采用通用清单作为正式审查结论。随后补充实际源码内容，重新进行针对性分析。
- **怎么确认改对了：** 对照 legacy 源码逐行核实，并结合支付回调黑盒测试结果。
- **结论：** 第一次回答没有直接使用，补充源码后重新审查。

### 场景3：支付回调源码与数据库事务分析（修改后采用）

- **我想干什么：** 进一步分析支付回调缺陷，并确认数据库操作是否存在事务及连接管理问题。
- **使用模型：** DeepSeek-V4-Pro。需要跨文件分析支付服务和数据库工具之间的调用关系。
- **我怎么问的：**

  > 请继续审查 db_helper.py，重点分析 query_all 和 execute 的具体实现、数据库连接是否自动提交、是否支持参数化 SQL、是否提供事务管理机制，并结合 payment_service.py 判断支付回调的查询和更新是否真正处于同一个事务。

- **它给了什么：** 对数据库连接复用、查询和写入封装、事务管理及并发访问风险进行了分析。
- **我改了吗：** 对模型给出的判断进行源码核对，并区分已经确认的问题和需要进一步验证的风险，没有直接照搬全部修复建议。
- **怎么确认改对了：** 对照 db_helper.py 和 payment_service.py 的实际实现，检查连接创建、提交和 SQL 执行逻辑。
- **结论：** 经过人工核对后采用部分审查意见。

### 场景4：使用 AI 检查支付回调分析是否成立（验证案例）

- **我想干什么：** 不只是让 AI 找漏洞，还要检查 legacy 源码能否解释当前 SUT 的黑盒测试结果。
- **使用模型：** DeepSeek-V4-Pro。需要比较不同文件的字段、执行逻辑和业务结果。
- **我怎么问的：**

  > 已经通过黑盒测试确认，不携带签名的伪造支付回调能够将订单状态从 created 修改为 paid。请结合 payment_service.py 审查源码，判断具体原因，并区分黑盒已证实的问题、源码确认的问题和尚待验证的风险。

- **它指出了什么：** legacy 源码中存在签名自比较问题，即 sign 与自身比较，导致校验逻辑可能恒真；异常处理也存在捕获异常后仍返回成功的问题。
- **我如何验证：** 将源码与 SUT 实际接口处理逻辑进行对照，发现两者存在字段差异：legacy 使用 outTradeNo 和大写 SUCCESS，而 SUT 黑盒请求使用 orderId 和小写 success。
- **验证结论：** 黑盒伪造回调能够成功改变订单状态已经得到实际验证，但不能仅凭 legacy 文件认定它就是 SUT 的直接执行路径。需要将两类证据分开记录。
- **结论：** AI 提供分析线索，最终结论由源码和真实接口测试共同确认。

## 4. 一次被 AI 带偏的经历

- **它给了什么：** 在支付回调审查中，AI 一度将 legacy 源码中的验签缺陷与 SUT 黑盒测试现象联系起来，容易让人认为已经找到黑盒问题的直接源码根因。
- **当时为什么信了：** 两边都涉及支付回调，而且 legacy 源码确实存在明显的验签问题，表面上具有较强的关联性。
- **我怎么发现的：** 进一步逐项核对请求字段，发现 legacy 使用 outTradeNo 和 SUCCESS，而 SUT 使用 orderId 和 success，无法直接证明两者调用链一致。
- **最后怎么修的：** 将黑盒测试结论和 legacy 静态审查结论分开记录，对不能确认的调用关系标注待验证。
- **之后改了做法吗：** 后续要求 AI 明确区分事实、推断和待验证事项；涉及源码结论必须提供具体文件和行号，涉及运行结果必须通过实际请求或 pytest 验证。

## 5. 成本与使用效率
