# AI 使用说明（AI_USAGE）

## 1. 概览

| 项 | 内容 |
|---|---|
| 用了哪些模型 | `glm-5.3`（强档）、`glm-5.3-flash`（快档）、`deepseek-v4-pro`、`MiniMax-M3`（后两个用来换厂商做交叉判断） |
| 调用次数 | 本地脚本逐条落盘 60 次：前 53 次全部 `glm-5.3`；后 7 次为 2 次 `glm-5.3` + 2 次 `glm-5.3-flash` + 1 次 `deepseek-v4-pro` + 2 次 `MiniMax-M3`。另有 1 次 `MiniMax-M3` 因客户端读超时（7 分 24 秒）没拿到内容、没有落盘，平台侧应能看到这次请求；此外还有几次在 Cherry Studio 界面里完成，含第 3 节场景 3 那次 |
| 大致花费 | 约 4~7 元 / 额度 40 元（本地记录累计输入 751,636、输出 69,608 token，按四档单价粗估；准确值以平台控制台用量页为准） |
| 主要用在哪些环节 | 阅读 SUT 与 legacy 源码时定位可疑点、判断某条现象算不算缺陷、review 我写好的缺陷报告、核对几份文档之间的数字是否自洽、写 pytest 脚本时确认断言写法、最后请另外两个厂商的模型按评审口径给整份作业扣分并专门挑刺 |

两点先说清楚，后面各节都围绕它们展开：

1. **前 53 次调用完全没有分档**，连「把 JSON 转成表格」这种活都用最强档，这是本轮最直接的浪费。
2. **后 7 次做了分档，但发现分档省的不是 token**——因为这几个模型都带 reasoning，思考过程也计入输出。

## 2. 模型选型（6 分，重点）

### 2.1 前 53 次为什么没分档

原因分三层，一层比一层不体面：

1. **一开始没意识到任务难度有区别。** 在我脑子里「问 AI」是一件统一的事，没想过「把 JSON 转成表格」和「判断并发下会不会超卖」对模型能力的要求差了几个量级。
2. **客户端里只配了这一个模型。** 在 Cherry Studio 里接好 API 之后，直接用默认模型开始问，中间没有切换过。
3. **后来知道了，但当时觉得来不及改。** 读到评分标准时才意识到应该分档，可那时主要结论已经跑完，重新用另一个模型问一遍不产生新结论，只是为了记录好看——那会儿我没做。

### 2.2 后 7 次怎么分的

| 任务 | 用的模型 | 为什么这么选 | 输入 / 输出 token | 耗时 | 结束原因 |
|---|---|---|---|---|---|
| review 并发缺陷（BUG-05） | `glm-5.3` | 要判断「单样本能不能证明竞态」，属于方法论判断 | 280 / 4096 | 85.2s | `length`（被截断） |
| 判定回调缺陷该 S1 还是 S2 | `glm-5.3` | 定级要权衡影响面，是我最不敢自己拍的一类 | 188 / 4224 | 70.9s | `stop` |
| 四份文档的数字是否自洽 | `glm-5.3-flash` | 纯核对，有明确对照物，不需要推理深度 | 388 / 4000 | 61.7s | `length`（被截断） |
| 两张分模块统计表对账 | `glm-5.3-flash` | 同上，只是把范围缩到两张表 | 244 / 4275 | 48.7s | `stop` |
| **整份作业按评审口径打分** | `deepseek-v4-pro` | **第一次换厂商**：前面四次都是同一家模型，我自己看不出它对不对；换一家来评，如果它指出的毛病和 glm 说的重合，那大概率是真问题 | 844 / 10539 | 177.9s | `stop` |
| **改完之后再挑一遍刺** | `MiniMax-M3` | **第二次换厂商**：deepseek 的意见我已经照改了，可「改得对不对」没人评过——让没参与过修改、也没被我引导过的第三家来看，专挑改完之后还虚的地方 | 808 / 6000 | 49.4s | `length`（推理吃满预算，只拿到前四点） |
| **追问它没说完的两点** | `MiniMax-M3` | 上一条断在第五点，把问题拆成两个小问题重问，预算给足 | 419 / 2129 | 20.4s | `stop` |

最后那次是第一次「换模型做交叉判断」。结果值回票价：它给的 84 分和我自己的估计（心里大概 80~85）接近，但它指出的三个点我原先没想到——「测试计划缺风险分级」「用例与缺陷的编号追溯不够」「安全专项和缺陷报告有重叠」。这三条后来都改了。

**为什么换模型有效**：同一家模型对同一份材料容易给同一种评价（还容易顺着我的措辞走）。换一家之后，它对「11 条缺陷里 9 条都是 S1」这件事的第一反应是「定级偏松」，而 glm 前面从没提过这句——因为它一直在回答我问的问题（「这条算不算缺陷」），从没被我要求「整体评价」。**换模型不只是换能力，是换一个没被我引导过的视角。**

这条我采纳了：按「攻击链是否闭环」重过一遍，把存储型 XSS 从 S1 降到 S2，并在缺陷报告里补了一张定级标准表、写了「什么情况下应升回 S1」。现在是 8 条 S1 / 3 条 S2。

**第二次换厂商（MiniMax）抓到的不是结论错，是理由虚。** 它认可 S1→S2 这个降级，但把我给的理由驳了：我说「凭据在 `Authorization` 头里、不在 Cookie 里，所以脚本偷不到」，它指出这句话不成立——Bearer 令牌一样可能被同源前端存进 `localStorage`，那样 XSS 照样读得到。**它说的是对的：我拿一个「通用推论」当成了「本服务的实测结论」。** 于是我回头把三件事逐个查实（`app.py` 里 `localStorage`/`sessionStorage`/`<script>`/`Set-Cookie` 全部零命中；SUT 只托管一个服务端拼好的静态 HTML，没有同源前端），把定级依据从「因为用了请求头」改成「这一版浏览器侧根本没有凭据副本」，并把升级条件补成四条。结论没变，**支撑结论的证据换了一层**——这类修改不会让分数变高，但被追问「你这个 S2 凭什么」时，答得出和答不出是两回事。

它还提了两条我不打算全照做的（见 §3.6），其中一条我采纳了它的纠正、但没采纳它的方案。

### 2.3 分档之后发现的第一个问题：省的是单价，不是 token

看上表最右两列——输入 188~844，输出 2129~10539。**除最后那次追问，输出都是输入的十倍以上**，而我的问题都要求「只回答三行」「最多 3 行」。多出来的全是 reasoning。

那一次追问（419 进 / 2129 出）是唯一说得过去的：问题被压到两个、每个限 300 字，输出立刻掉到 2129。**这不是换模型换来的，是把问题切小换来的。**

所以真正的结论不是「换个便宜模型就省了」，而是：

- **换快档省的是单价**，token 量一点没省，因为三个模型都会长篇推理；
- **真正决定花费的是 `max_tokens` 和「问题有多开放」**：四个判断题输出都在 4000 上下，唯一那道开放题（按评审打分）输出了 10539，是前者的两倍半；
- 我第一版调用脚本没设 `max_tokens`，直接被截断两次（见第 5 节）。

回头看，正确的分配是三层：**先问「这个问题需不需要 AI」→ 再问「需不需要它想」→ 最后才问「用哪一档」。** 只做第三层，只能省单价；做了第一层，能省掉一半调用。

### 2.4 回头看应该怎么分

| 任务 | 应该用 | 我实际用的 |
|---|---|---|
| 把接口返回压成一行、字段列表转表格 | 快档，且设小 `max_tokens` | 前 53 次全用了强档 |
| 改写文档措辞、压缩长句 | 快档 | 同上 |
| 判断「这个现象算不算缺陷」 | 强档，要对照文档承诺做因果判断 | 强档（用对了） |
| 判断两条缺陷是否同根因 | 强档 | 强档（用对了） |
| 审查整个 legacy 文件 | 长上下文档 | 强档（文件都在 55 行以内，够用） |

也就是说：**该用强档的几件事我用对了，不该用强档的十几次小事我也用了强档。** 分档这件事我是在最后 7 次才真正做起来的（前 4 次在 glm 内部换档，后 3 次换厂商），而且做起来之后才发现分档本身也不是省钱的关键——这是我这轮在成本上最大的认知修正。

## 3. 四个场景（5 分）

### 场景 1（成功）：让它 review 并发那条缺陷，它反过来质疑我的证据链

- **我想干什么**：BUG-05（并发超卖）已经写完，我想知道这条的证据够不够硬、定级和修复建议有没有问题。
- **用的模型 / 为什么选它**：`glm-5.3`。这类问题不是「这段代码有没有 bug」，而是「我的验证方法能不能支撑这个结论」，需要方法论层面的判断，不敢用快档。
- **我怎么问的**（精简后）：

  > 帮我 review 一条缺陷记录，只挑问题，不要帮我重写。
  > 背景：库存 1，10 个线程用 `threading.Barrier` 卡在同一起跑线后同时下单，结果 7 个 201、3 个 409，结束后库存 -6，新增订单 7 条。我判断根因是 check-then-act 竞态：先 SELECT 快照，再 `time.sleep(0.15)`，最后 `UPDATE ... SET stock = stock - ? WHERE id = ?`，既没有 `AND stock >= ?` 也不查 `rowcount`。
  > 三点逐条回答，没问题就说没问题：1) 只凭「10 并发成功 7 个」这一个样本，能不能断定是竞态而不是我脚本写错了？如果不能，还差什么证据？2) 定 S1 合不合理，有没有理由降到 S2？3) 修复建议只写「改成原子条件更新 + 查 rowcount」够不够具体？

- **它给了什么**：直接挑了我三个毛病，其中第一个是我完全没想到的——
  1. **单样本不够。** 它说「库存为负」确实是硬性的不变量违反，一个写错的脚本没法让服务端把 1 减成 -6；但要排除「脚本数错了响应」「脚本读错了库存」，还缺三样：跑之前的库存与订单数要有记录、结束后的库存要从数据库直接读而不是走接口、以及**一组串行对照**（同一脚本改成 1 条 1 条发，应该恰好 1 个成功）。
  2. **它指出我解释不了「为什么恰好 7 个」**，说这个数字在你自己的叙述里是悬空的，要么解释是什么把并发卡到了 7，要么就不要拿它当论据。
  3. 定级它认为 S1 站得住，但理由要落在「扣款与扣库存的先后顺序」和「有没有下游兜底」上，而不是笼统说「涉及资金」。
- **我改了吗、为什么改**：改了，而且改的是验证方案不是措辞。
  1. 新写了 `testing/自动化/串行对照.py`：同样 10 条请求、同一商品、同一接口，唯一区别是一条一条发。实测 1 条 201、9 条 409、库存归零、订单 1 条——**串行就对、并发就错，唯一变量只有并发度**，这才把「脚本写错」彻底排除。
  2. 把商品 5 库存重置后又连跑 3 轮并发，成功数是 7 / 7 / 8，库存 -6 / -6 / -7。于是明确写下：**「库存变负」每轮都复现，这是结论依据；成功个数随调度波动，不拿「7」当常量。** 这正是它第 2 点批评要我处理的。
  3. 定级保留 S1，但理由改成具体的链路描述。
- **怎么确认改对了**：串行和并发两组结果放在一起，除并发度外所有条件相同，结论只有一种解释。这是我认为本轮最干净的一个证据。
- **结论**：用了。**这次回答其实是被截断的**（`finish_reason=length`，4096 个 token 全被 reasoning 吃掉，`content` 返回 `null`，我拿到的是思考过程），但三条批评在截断前已经完整，所以照用。这也说明一件事：**它对我的价值不在于给出成品，而在于指出我的证据链缺哪一环。**

### 场景 2（失败）：只贴函数签名，被它当场退回

- **我想干什么**：想省 token，只把函数签名 `def handle_create_order(auth_header, payload):` 贴过去，问「这段并发安全吗」。
- **用的模型 / 为什么选它**：`glm-5.3`。
- **我怎么问的**：就是那一行签名加一句问题。
- **它给了什么**：直接说「你只贴出了函数签名，没有函数体的实现代码，我无法针对具体逻辑做精确分析。请把完整实现（包括涉及的数据库操作、库存扣减逻辑等）贴出来」，然后给了一份通用的并发风险检查清单。
- **我改了吗、为什么改**：改了。把 20 行实现补上去，重新问了一次。
- **怎么确认改对了**：第二次的回答是针对具体行号的，能对上代码。
- **结论**：改了之后用。这次失败让我明白：**上下文给少了不是省钱，是白花一次调用。** 这份「通用检查清单」我一个字都没用上，因为它是任何电商系统都适用的套话。

### 场景 3（我改过，后来发现自己改错了方向）：金额那条缺陷

- **我想干什么**：确认 `totalAmount` 返回 `5970.0` 而不是 `5970` 算不算缺陷。
- **用的模型 / 为什么选它**：`glm-5.3`。
- **我怎么问的**：

  > 商品单价 1990 分，买 3 件，接口返回 `"totalAmount": 5970.0`。文档要求金额单位是「分（整数）」。这算缺陷吗？

- **它给了什么**：说算，理由是「浮点精度误差，1999 分 × 3 会得到 5996.999…，入库金额可能差一分，应该全程用整数分运算」。
- **我改了吗、为什么改**：**当时我改了它的理由，保留结论——但这一步我做得过头了。** 我先按它的思路实算：`1999 / 100 * 3 = 59.97000000000001`，乘 100 得 `5997.000000000001`，不是它说的 5996.999…，它举的例子确实错了。接着我又实测 1990 × 3，返回 `5970.0`，数值干干净净。于是我下了一个判断：**「金额算错」不成立，真正的问题只是类型——文档要整数分，返回了浮点数**。据此把这条从「资金损失」降级为 S2，理由重写成「类型不符合接口约定」。
- **怎么确认改对了**：我把 1990×3 和 1999×3 都在本地算了一遍，再和接口实际返回对比，两边都对得上。
- **后来的反转**：这个「确认」是假的。我写 pytest 断言时写的是 `assert totalAmount == 1990`（买 1 件），跑出来 `assert 1989.9999999999998 == 1990`。也就是说**浮点误差是真的会污染金额值的，只是我当初挑的 1990×3 恰好算得干净**。我拿一个偶然干净的样本去否证了一个正确的方向，等于用一次抽样推翻了结论。据此把 BUG-11 补回来，影响描述里明确写上「该问题在部分数值组合下不显现（如 1990×3 恰好得 5970.0），依赖具体数值，容易在抽测中被漏掉」。
- **结论**：它给的方向是对的，它举的算术例子是错的，而我当时把「例子错」当成了「方向错」。这条现在留在报告里，定级 S2 不变，但理由改成「浮点往返换算会污染金额值，且只在部分数值组合下显现」——比原来的「类型问题」更接近事实。教训是：**要否定一个方向，得覆盖足够多的样本，不能只测一个刚好干净的。**

### 场景 4（用 AI 做验证）：让它给两份文档的数字对账

- **我想干什么**：几份文档里的统计数字是我分别维护的，改完一遍怕还有漏，想让一个没有上下文的东西替我数一遍。
- **用的模型 / 为什么选它**：`glm-5.3-flash`。核对不需要推理深度，只需要不出错地比对，正好拿来做分档对比。
- **我怎么问的**：

  > 只做核对，不写解释。【给了缺陷报告的分模块统计：11 条、S1 9 条、S2 2 条，逐模块列出】
  > 【给了测试报告里同一张表：合计行写 10 条 / S1 9 / S2 1】
  > 问题：两处对不上的是哪几行？只输出对照行，格式「模块: 缺陷报告 a/b，测试报告 c/d」，最多 3 行；完全一致就输出「一致」。

- **它给了什么**：

  > 订单: 缺陷报告 3/1，测试报告 3/0
  > 合计: 缺陷报告 9/2，测试报告 9/1

  两行全中，没有多说一个字。
- **我改了吗、为什么改**：这两处我在改文档时已经手算出来了（订单应为 4 条、合计应为 11 条 9/2）。**这次是拿「已知答案」去测它**，目的是判断以后能不能把这类核对交给快档——所以我故意没说我改过了。
- **怎么确认改对了**：它给出的两行和我手算的完全一致，且没有臆造第三条不存在的矛盾（这一步很关键：如果它为了显得有用而多报一条，我就不会再用它做核对）。
- **结论**：用了，并且确认这类活不需要强档。只花 244 输入 token，48.7 秒。**这是四个场景里唯一一次我主动设计成「已知答案」的测试**，因为核对类任务的失败成本比判断题低，值得先摸清它的可靠性再放手。

### 3.5 AI 产出复核表

四个场景说的是「怎么用」，这张表说的是「用了之后我怎么处理」——**每一条 AI 产出最后都归到三种处理之一：全用、部分用、不用**。

| AI 产出 | 用在哪儿 | 我人工做了什么 | 最终 |
|---|---|---|---|
| 并发缺陷的三点 review（强档）：单样本不足、7/3 分裂无法解释、定级理由要落到扣款时序 | `缺陷报告.md` BUG-05 | 照第 1 点新写 `串行对照.py` 并实跑；照第 2 点连跑 3 轮拿到 7/7/8，把报告里「7 个成功」改成「7~8 个，不拿它当常量」；第 3 点补进影响描述 | **全用** |
| 回调缺陷应定 S1，且与「重复支付」不同根因（缺验签 ≠ 缺幂等） | BUG-07、BUG-08 的定级与合并判断 | 逐条核对我原有定级，结论一致，未改动 | **采用**（确认型，没有产生修改） |
| 浮点误差「1999 分 × 3 会得到 5996.999…，入库可能差一分」 | `缺陷报告.md` BUG-11 | 它举的例子算错了（实际是 5997.000000000001），我换成 1990×1 的实测值 `1989.9999999999998`；但它「浮点会污染金额」的方向是对的，保留 | **部分用**（弃例、留向） |
| 两张分模块统计表的对账结果（快档）：订单行、合计行 | `测试报告.md`、`测试用例.md` 的统计 | 这两处我已手算发现并改过，问它只是交叉验证；它没有多报不存在的矛盾 | **采用**（作为第二双眼睛） |

### 3.6 两条我没照做的建议，和为什么

评分标准里有一句「会否掉它的建议」。这一节是唯一能拿证据说话的地方，所以挑两条我确实否掉的，把理由摆出来。

**第一条：把 14 条对照缺陷的用例改成 `xfail(strict=True)`。**

`MiniMax-M3` 的建议本身很专业：`strict=True` 下，缺陷修好后会变成 XPASS 而不是静默通过，能逼着人去关单，是成熟项目的标准做法。我没改，理由是作业的口径：它要的是「业务预期与实际行为不一致的失败，应在测试结果中如实说明」和「因 SUT 缺陷导致的测试失败，需关联缺陷编号并说明原因」——**要的是真实失败 + 能对上号**。标成 `xfail` 后汇总行会变成 `14 xfailed, 9 passed`，这 14 条不再计入失败统计，和上面那条要求就对不上了。

这里还有个小插曲：我最初给的理由是「xfail 会让人看不出错在哪」，它直接指出这句不准确——`reason` 照样会打印，`xfail` 省掉的只是红色。**这条纠正我接受了**，正式的理由改写成了上面那段（口径问题，不是可读性问题）。最后它自己也认可保留 `failed`，并建议补一句口径说明，我照做了，写在 `自动化/README.md` 和 `SUBMISSION.md` 里。

一句话：**方案否掉，理由被它修好，最后按修好的理由写。**

**第二条：把「替他人订单付款」从 BUG-01 里拆出来单独记一条。**

它的理由值得听：读资料、读订单、改商品状态、替人付款，四件事的资产、后果、修复位置都不同，修复者很可能只补了 `GET` 的归属校验就以为修完了，`POST /api/payments` 还漏着。

但我不能拆，两个原因：

1. 作业的缺陷评分明确写了「同根因问题合并为一条」，还列了「同根因拆多条 −1」的扣分项。这四条的表现全部来自同一个根因——处理函数拿到 `auth_header` 后没有把「当前用户 ID」和「资源归属」比对过，只是漏在了四个入口上。按影响面拆成四条，等于用同一个 bug 刷四次分。
2. 拆开还会让「11 条缺陷」这个数字虚高，而评审要看的恰恰是有几条独立的根因。

它担心的「只修一半」，我用另一种方式解决了：**BUG-01 的修复建议里把四个入口逐个点名**（`handle_get_user`、`handle_get_order`、`handle_update_product_status`、`handle_create_payment`），并注明「先校验归属、再校验状态」；标题也从「可读取他人资料」扩成「可读取他人资料与订单、操作他人商品、支付他人订单」。这样即使只有一条缺陷号，修复清单也是四条，漏一条就会被自己发现。

一句话：**结论否掉，担心被吸收进修复建议。**

## 4. 一次被 AI 带偏的经历（必答）

**它给了什么**：我一开始想让它「逐行审查」下单函数，于是一行一行贴代码过去。它非常配合，每贴一行就分析一行，还不断催我。日志里第 52 条的原话是：

> `createdAt`——响应体最后一个字段。函数完整收官。
> **贴最后的 `}))`，或者直接说"贴完了"——最终审判报告立刻奉上。**

前面还有一条："**就差最后的 `}))` 收尾了——贴完立刻出最终审判报告。**"

**当时为什么信了**：它的语气很确定，而且逐行分析看起来比一次性看整段更细致。我以为这样能得到更精确的结论，加上它一直在推进节奏，就跟着一行一行贴下去了。

**我怎么发现的**：回看调用记录时看到一组数字——**53 次调用集中在 15 分 47 秒内（18:15:48 到 18:31:35），输入累计 748,465 token，最后几条单次输入已经涨到约 2.7 万 token，而最短的一条回复只有 70 个字。** 因为它每轮都要重新读一遍全部历史，我每多贴一行，成本就往上叠一层。而真正有用的那份完整分析，是在我把整个函数一次性贴过去之后才出现的。

**最后怎么修的**：停掉那个会话，重新开一个，把 20 行实现一次性贴进去，只问一个判断题。输入降到两千 token 左右，回答反而比前面几十次加起来都有用。

**之后我改了做法吗**：改了三条：

1. 先想清楚「我要它回答什么」，再决定贴多少代码。不问「有什么问题」这种开放题，改问「这里并发安全吗」这种判断题。
2. 一段代码只贴一次，不重复喂。
3. 换话题就开新会话，不让上一轮上下文继续累加。

代价是多花了大半额度，换来一条经验：**AI 会顺着你的问法走。** 你逐行问，它就逐行答，还会帮你把这种低效包装成「马上就出最终报告」。它不会提醒你「你这样做很浪费」——那是我自己该判断的事。

## 5. 成本（4 分）

| 问题 | 我的回答 |
|---|---|
| 有没有「一次把整个项目/整个文件塞进去」？为什么？ | 没塞过整个项目，但**有过变相的大输入**：逐行贴代码时因为历史累积，单次输入涨到 2.7 万 token。当时没意识到，以为「我没贴大文件就不算大输入」。后来才明白决定成本的是累计上下文，不是单条消息的长度 |
| 有没有同一个报错连续问了很多次？后来怎么改的？ | 没反复问同一个报错，但有反复问同一类问题（逐行分析），本质一样：没想清楚就不停试。后来改成先自己把问题想成一句话，再问 |
| 如果额度只有 10 元，你会怎么调整？ | 砍掉三类：逐行分析这类碎问，改成自己读代码；格式转换，`grep` 或一行 python 就能做；「帮我解释这个报错」，大部分报错原文里已写了原因。只保留两类：判断某条现象是否算缺陷（要对照文档做权衡），以及 review 我已经写完的东西（要外部视角） |

**我判断「不值得问 AI」的标准**：如果这个问题我自己花三分钟能查出来（翻文档、跑一条命令、读十行代码），就不问。因为问的成本不只是钱，还有组织语言和核对答案的时间，反而更慢。

**这一节里最值得记的一次浪费，其实是我自己写脚本时犯的**：第一版调用脚本没设 `max_tokens`，默认值下让模型自由发挥。第一次调用跑了 85 秒、烧掉 4096 个输出 token，`finish_reason` 是 `length`，`content` 字段是空的——**拿到的只有它的思考过程，一个字答案都没有**。我以为是自己解析错了，换快档重试，同样在 4000 个 token 处被截断。两次加起来 8096 个输出 token，换来两段没写完的思考。

后来把 `max_tokens` 显式设到 12000 才稳定拿到答案。教训很具体：**对带 reasoning 的模型，「回答长度」和「输出预算」是两件事，不能靠「我要求它只答三行」来省 token。** 这一点在我前 53 次调用里完全没意识到，因为那时候压根没看 `usage` 字段。
