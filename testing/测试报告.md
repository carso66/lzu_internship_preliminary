## 1. 结论（先看这段）

**不建议上线。** 本次共发现 **17 个缺陷**，其中 **S1 级 11 个**，包含 **3 条完全无需登录即可利用**的漏洞（BUG-02、05、15）和 **4 条直接造成资金损失**的问题（BUG-08、13、14、15）。

最关键的三个问题：

1. **认证体系形同虚设**（BUG-02）——token 就是 `tk_<用户ID>`，不登录就能拼出 admin 的凭证；登出也不失效。它把下面所有越权问题都从"需要注册账号"降到"不需要任何账号"。
2. **存在完整的 0 元购链路**——BUG-08（下单金额可被改成 1 分）+ BUG-15（支付回调可伪造），两步即可白拿任意商品。这两条都必须实际跑才能发现。
3. **并发超卖**（BUG-12）——库存 1 件卖出 8 件，库存变 -7，商家必然无法履约。

如果必须在短期内上线，最低限度要先修 BUG-01/02/03/05/08/09/11/12/14/15 这 10 条，其余可作为下一迭代处理。

## 6. 上线建议

**结论：不通过。**

**主要依据：**

1. 认证可被完全绕过（BUG-02）。这是所有安全措施的前提，不修则其他修复都失去意义。
2. 存在"1 分钱下单 + 伪造回调"的完整白拿链路（BUG-08 + BUG-15），任何用户都能零成本获取商品，属直接资损。
3. 未授权访问可批量导出全站用户姓名、手机号、收货地址（BUG-01 + BUG-03 + BUG-11），有合规风险。
4. 商品搜索存在未授权的 SQL 注入（BUG-05），可进一步拖库。
5. 库存可被刷高、并发可超卖（BUG-09 + BUG-12），运营数据不可信。

**修复优先级建议：**

| 优先级 | 缺陷 | 理由 |
|---|---|---|
| P0（上线前必须） | BUG-02 → BUG-15 → BUG-08 → BUG-05 | 前三条串成完整的攻击链；BUG-05 是未授权入口 |
| P0 | BUG-01 / 03 / 11 / 14 | 隐私与越权，可批量利用 |
| P0 | BUG-13 | 重复支付直接多扣款，且**无退款接口**，资金无法追回 |
| P1（首迭代内） | BUG-09 / 12 | 库存准确性 |
| P1 | BUG-16 / 04 / 10 | 内容安全与业务逻辑 |
| P2（下次迭代） | BUG-07 / 06 / 17 | 健壮性与日志规范 |

**修复后回归建议**：直接跑 `cd testing/自动化 && pytest -q`。当前的 23 条 `xfail` 会因修复转为 XPASS 并报错，正好用来逐条确认缺陷是否真的修好——这是 `strict=True` 带来的额外收益。

## 7. 一点反思

这次测试里我做错了一件事，值得记下来：最初写自动化用例时，我把"商品列表默认返回 11 条"写成了硬断言，结果前面用例新建了商品，这个数字变成 30，用例假失败。**测试用例本身也需要隔离性设计**，后来改成"新建隔离商品 + 只断言属性不断言全站总数"才稳定。

另外，`quantity=-5` 这条我最初差点漏掉——看到 `stock < quantity` 觉得逻辑没问题，是照着 README 里"负数、0、小数、超大值，每个都要试"这句提示才补上的。这也印证了那句话：**只测正常路径的用例，写得再多也没用**。
