- **被测对象**：`testing/sut/app.py`（SUT，校园好物市集），共 898 行、16 个接口
- **版本**：单轮快照（无历史版本可比对）
- **测试周期**：本轮一轮摸底，覆盖设计 → 执行 → 回归 → 文档全流程

## 3. 发现的问题

共 **19 条**有证据的缺陷（详见 `缺陷报告.md`），另有 11 项「经实测确认符合文档」的行为记录在缺陷报告附录，用于说明这些点已覆盖、不是漏测。

### 3.1 按模块 × 严重程度

| 模块 | 数量 | S1 致命 | S2 严重 | S3 一般 | 缺陷编号 |
|---|---|---|---|---|---|
| 认证与权限 | 5 | 4 | 1 | 0 | BUG-01~05 |
| 金额与库存 | 5 | 3 | 2 | 0 | BUG-06~10 |
| 支付 | 2 | 2 | 0 | 0 | BUG-11~12 |
| 注入与输出编码 | 2 | 1 | 1 | 0 | BUG-13~14 |
| 健壮性与数据安全 | 5 | 0 | 3 | 2 | BUG-15~19 |
| **合计** | **19** | **10** | **7** | **2** | |

### 3.2 严重程度分布

| 等级 | 数量 | 占比 | 含义 |
|---|---|---|---|
| S1 致命 | 10 | 53% | 可越权、可篡改金额/库存、可绕过支付，直接造成资金或数据损失，**上线阻断** |
| S2 严重 | 7 | 37% | 安全加固缺失、可用注入面、可达的 5xx，上线前必须修复 |
| S3 一般 | 2 | 10% | 功能约束缺失、参数校验不足，影响体验或数据质量 |

> S1 占比过半不是「全填 S1 凑分」，而是这个 SUT 的缺陷密度本身集中在资金与越权路径上：金额由客户端决定 + 库存可刷成负数 + 支付回调不验签，这三条任意一条被打通就是实际资损。每条 S1 都给出了造成损失的具体路径，可逐条核对。

### 3.3 按「怎么发现的」分类

这个维度更能说明测试设计的有效性：

| 发现方式 | 缺陷 | 说明 |
|---|---|---|
| 照 README 30 分钟路径改个 id 就撞到 | BUG-01 | 第一个 30 分钟内就复现 |
| 顺着「文档承诺」和实现对不上 | BUG-02、03、04、05、10、11、15、16 | 文档写了 403/409/400，实现没做 |
| 输入侧主动构造异常数据 | BUG-06、08、13、14、17、18 | 夹带金额字段、负数、注入串、脚本标签 |
| 用例集之外探索时发现 | BUG-19 | 7 条用例全绿之后继续追问「能不能重复评价」，才发现的业务规则缺失 |
| **必须动手跑才能发现** | BUG-07、09、12 | 见下 |

其中三条是**静态看代码很容易误判、必须实跑才能定论**的：

- **BUG-07**：`total = unit_price / 100 * quantity; total_amount = total * 100` 看起来只是绕了一圈，实际 `1990/100*1*100 = 1989.9999999999998`。只有真下单才看得到这个尾巴。
- **BUG-09**：代码里 `time.sleep(0.15)` 之后才检查库存，是明确的 TOCTOU 窗口。3 个线程同时抢库存为 1 的商品，**3 个请求全部 201，库存被扣成 -2**；扩到 10 线程复现，**8 个 201 + 2 个 409，库存被扣成 -7**。值得注意的是那 2 个 409 **不是**库存保护生效——它们是读到已被扣成负数的库存才拒绝的，也就是说保护只在「已经超卖之后」才触发。
- **BUG-12**：回调接口完全不读签名字段。不带任何身份、用伪造的 `paymentId` 指一条真实订单，直接把 `status` 改成 `paid`。

### 3.4 已确认「不是缺陷」的行为

为避免误报，以下 11 项经实测符合文档，已在缺陷报告附录列表记录：默认只返回 11 个在售商品、`status=on/off` 过滤、库存不足 409、商品不存在 404、未登录 401、发布商品四类字段校验、评价内容 201 字拦截、`rating=0/6` 拦截、支付方式白名单、非法 JSON 落到 401。

> 关于最后一项：登录接口传非法 JSON 或空 body 时返回 401 而不是 400。第一版我记成了缺陷，核对后判定**不是**——请求缺少有效的用户名密码，语义上等价于凭据缺失，文档也没承诺 400。这类「看着像 bug 其实是合理设计」的判断，比多报一条更有价值。因此本轮缺陷数保持 19 条，没有为凑数硬加。

## 5. 上线建议

### 结论：**不建议上线。**

### 主要依据

三条独立的阻断理由，任意一条都足以否决：

1. **资金可直接被盗取。** BUG-06 客户端传 `totalAmount` 即生效，实测 1 分钱买走 2350 分的商品；BUG-12 支付回调零验签，不带任何身份就能把任意订单标成已支付。这两条叠加后，「下单 + 白拿」只需要两条 curl。
2. **库存与金额数据不可信。** BUG-08 下负数数量能让库存反向增加，BUG-09 并发把库存扣成 -2（10 线程时扣到 -7），BUG-07 金额出现 `1989.9999999999998`。库存和金额是电商的两条命脉，任何一条算错都会导致超卖或对账失败。
3. **用户隐私批量泄漏。** BUG-01 改 URL 里的 id 就能拿到任意用户的真实姓名与手机号；BUG-02 普通用户能拉全部订单的收货人、手机、地址；BUG-03 同样问题在订单详情。这已经触及个人信息保护的合规红线，不是「体验问题」。

### 修复优先级

| 批次 | 缺陷 | 理由 |
|---|---|---|
| 第一批（阻断） | BUG-04、BUG-12、BUG-06、BUG-08、BUG-09 | 认证可伪造 / 支付可绕过 / 金额可篡改 / 库存可刷高或超卖 |
| 第一批（阻断） | BUG-01、BUG-02、BUG-03、BUG-05、BUG-11 | 越权读写他人数据、重复扣款，涉及隐私合规与资金 |
| 第二批 | BUG-13、BUG-14、BUG-17、BUG-18 | SQL 注入、XSS、凭据明文，属安全基线 |
| 第二批 | BUG-07、BUG-10、BUG-15 | 金额精度、下架商品可买、5xx 语义错误 |
| 第三批 | BUG-16、BUG-19 | 分页边界与评价规则，影响体验与数据质量 |

### 复测建议

修复后按以下顺序回归，成本最低：

1. `cd testing/自动化 && python -m pytest -q` —— 因为缺陷项都用了 `strict=True`，**修好一处就会有一项从 xfailed 变 failed**，正好当修复确认器用；全部转 passed 即表示 25 个点全部收敛。
2. 对 BUG-07 与 BUG-09 单独复跑：金额精度要覆盖多个商品组合（不是每个单价都有浮点误差），并发要复跑 3 线程抢库存 1。
3. 每批修复后重跑一遍全量，确认没有引入新的 5xx。

## 6. 结论一句话

> 66 条用例覆盖 16 个接口，自动化 83 项全部可重复执行、0 failed 0 error；发现 19 条有证据的缺陷（10 条 S1），其中 3 条必须实跑才能发现（浮点误差、并发超卖、回调伪造）。**当前状态不具备上线条件**，需先完成 10 条 P0 修复并复测。
