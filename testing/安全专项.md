# 安全测试专项

> 依据题目 L2-7 要求：按认证、越权、输入、金额篡改四个方向，各给出至少 1 条实测记录。
> 全部命令在数据重置后执行，环境 `http://127.0.0.1:8080`。种子数据中的姓名与手机号均为测试数据。

## 一、认证

### 1.1 令牌可预测，可枚举冒充任意身份

**原理**：登录返回的 token 为固定前缀 `tk_` 拼接用户自增 ID，无签名、无随机性、服务端不存储。只要知道任一合法 token，就能推导出所有人的 token。

**实测**：

```bash
curl -s http://127.0.0.1:8080/api/users/1 -H 'Authorization: Bearer tk_1'
```

**结果**：返回 200 与管理员完整资料。

```json
{"code":0,"message":"ok","data":{"id":1,"username":"admin","realName":"系统管理员","phone":"13800138001","role":"admin",...}}
```

**结论**：未登录、未持有任何凭据的情况下，直接把 token 写成 `tk_1` 即获得管理员身份。认证环节不成立。

### 1.2 登出后令牌不失效

**文档承诺**：「登出后原 token 应失效」。

**实测**：

```bash
curl -s -X POST http://127.0.0.1:8080/api/auth/logout -H 'Authorization: Bearer tk_2'
curl -s http://127.0.0.1:8080/api/users/2 -H 'Authorization: Bearer tk_2'
```

**结果**：登出接口返回 200，随后用同一 token 请求仍返回 200 与 alice 资料。

**结论**：注销只是返回了一句提示，没有任何服务端状态变更，令牌在 12 小时有效期内不可撤销。

### 1.3 敏感信息落入日志

**实测**：在服务端控制台观察登录请求的日志输出。

```text
2026-11-24 16:44:16 [auth] 登录请求 username=alice password=Alice@123
2026-11-24 16:44:16 [access] POST /api/auth/login 200 3.2ms token=-
```

**结论**：明文密码被完整打印；访问日志还记录了完整 Authorization 头。任何能读日志的人都能获得凭据。

## 二、越权

### 2.1 水平越权：可读取他人资料与订单

**实测**：

```bash
curl -s http://127.0.0.1:8080/api/users/3 -H 'Authorization: Bearer tk_2'
```

**结果**：

```json
{"code":0,"message":"ok","data":{"id":3,"username":"bob","realName":"李波","phone":"13800138003",...}}
```

```bash
curl -s http://127.0.0.1:8080/api/orders/2 -H 'Authorization: Bearer tk_2'
```

**结果**：返回 bob 的订单，含 `receiverPhone: 13800138003` 与完整收货地址。

**结论**：接口只校验「已登录」，不校验「是否本人资源」。用户 ID 与订单 ID 均为自增，遍历即可批量获取。

### 2.2 垂直越权：普通用户可访问管理端

**实测**：

```bash
curl -s http://127.0.0.1:8080/api/admin/orders -H 'Authorization: Bearer tk_2'
```

**结果**：返回 200，`total` 为 2，包含全部用户的订单、姓名、手机号、地址。

**结论**：管理端接口只判断登录状态，未判断 `role == "admin"`。这是效率最高的信息泄露入口，一次请求即拿到全站数据。

### 2.3 越权操作数据：可下架他人商品

**实测**：

```bash
curl -s -X PATCH http://127.0.0.1:8080/api/products/1/status \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"status":"off"}'
```

**结果**：`{"code":0,"data":{"id":1,"status":"off"}}`。商品 1 的 `sellerId` 为 1（admin），alice 无权操作。

**结论**：越权不只泄密，还能篡改业务数据。

## 三、输入

### 3.1 SQL 注入：keyword 参数影响查询逻辑

**实测**：

```bash
curl -s "http://127.0.0.1:8080/api/products" | grep -o '"total":[0-9]*'
curl -s -G "http://127.0.0.1:8080/api/products" --data-urlencode "keyword=' OR '1'='1" | grep -o '"total":[0-9]*'
```

**结果**：

```text
正常查询：total = 11
注入之后：total = 12，结果中出现 status 为 off 的 id=7
```

**结论**：`keyword` 被直接拼进 `LIKE '%...%'`，注入串把 WHERE 变成恒真，绕过了「默认只返回在售商品」的业务规则。受 SQLite 驱动限制（不支持单条语句多命令），无法执行破坏性操作，影响限于信息泄露。

### 3.2 存储型 XSS：评价内容未转义

**实测**：

```bash
curl -s -X POST http://127.0.0.1:8080/api/product-reviews \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"content":"<script>alert(1)</script>","rating":5}'
curl -s "http://127.0.0.1:8080/api/product-reviews?productId=1" | grep -o '<div class="content">.*</div>' | head -1
```

**结果**：

```html
<div class="content"><script>alert(1)</script></div>
```

**结论**：用户内容原样写入 HTML。内容持久化在库中，任何访问该评价页的用户都会执行，属存储型 XSS。

### 3.3 类型输入导致 500

**实测**：

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/api/products/abc
curl -s http://127.0.0.1:8080/api/products/abc
```

**结果**：

```text
500
{"code":50000,"message":"服务内部错误","data":null}
```

**结论**：文档明确承诺非数字 id 应返回 400，实际因 `int()` 抛 ValueError 被全局兜底成 500，暴露了服务端异常处理路径。

## 四、金额篡改

### 4.1 单价与总额均由客户端决定

**实测**：

```bash
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":1,"unitPrice":1}'
```

**结果**：商品 1 数据库单价为 1990 分，返回却为

```json
{"code":0,"data":{"id":3,"productId":1,"quantity":1,"unitPrice":1,"totalAmount":1.0,"status":"created",...}}
```

**结论**：服务端未按数据库价格重算，直接采信请求体。1 分钱即可下单。代码里 `totalAmount` 亦可被 `payload["totalAmount"]` 整体覆盖，等于总额也由客户端说了算。

### 4.2 负数数量使金额为负、库存反向增加

**实测**：

```bash
curl -s -X POST http://127.0.0.1:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"productId":1,"quantity":-5}'
```

**结果**：

```json
{"code":0,"data":{"id":5,"quantity":-5,"unitPrice":1990,"totalAmount":-9950.0,...}}
```

库存由 12 变为 17。

**结论**：金额校验缺失导致可生成负金额订单，同时 `stock - (-5)` 使库存反向增加。若支付链路按订单金额发起，等同资金反向流出。

### 4.3 支付环节不校验金额

**实测**：发起支付时 SUT 直接取订单的 `total_amount` 作为支付金额，不校验与商品价格、数量是否一致。

```bash
curl -s -X POST http://127.0.0.1:8080/api/payments \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer tk_2' \
  -d '{"orderId":1,"method":"alipay"}'
```

**结果**：`{"paymentId":"PAY...","orderId":1,"amount":3980,"status":"paid"}` —— 金额来自订单表，而订单表的金额在上一步已可被客户端控制。

**结论**：金额信任链从下单环节就断了，支付环节只是把错误金额固化下来。金额必须在最靠近数据源的地方（数据库商品价格）重算，且只算一次。

## 五、四个方向汇总

| 方向 | 实测条数 | 对应缺陷 | 最严重的后果 |
|---|---|---|---|
| 认证 | 3 | BUG-03 | 可冒充管理员，认证体系失效 |
| 越权 | 3 | BUG-01、BUG-02 | 批量泄露全站用户手机号与地址 |
| 输入 | 3 | BUG-09、BUG-10、X-02 | 存储型 XSS，所有访问者受影响 |
| 金额篡改 | 3 | BUG-04、BUG-06 | 1 分钱下单、负金额订单 |

四个方向均无「已防护」项：认证可绕过、越权无校验、输入未过滤、金额不可信。这不是单点漏洞，而是缺少统一的鉴权中间件与参数校验层——每个处理函数各写各的，漏一处就等于没做。
