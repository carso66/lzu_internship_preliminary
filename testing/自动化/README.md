# 自动化测试

本目录是被测服务（`testing/sut/app.py`）的自动化回归脚本。

## 文件

| 文件 | 作用 |
|---|---|
| `conftest.py` | pytest 公共夹具：`base_url`（支持用环境变量 `SUT_BASE` 换地址）、`token`、`auth`、`new_order`；并注册 `defect` 标记 |
| `test_sut.py` | 23 条接口用例：正常 5、异常 11、边界 7 |
| `并发测试.py` | 10 线程同时下单，验证超卖，独立脚本，仅用标准库 |
| `串行对照.py` | 同样 10 条请求但串行发，用来排除「脚本写错」，与上者构成唯一变量对照 |
| `requirements.txt` | 依赖清单 |

## 准备

```bash
# 1. 装依赖
python -m pip install -r requirements.txt

# 2. 起被测服务（另开一个终端，在 testing/sut 下）
python app.py --port 8080

# 3. 确认服务活着
curl http://127.0.0.1:8080/health
```

## 运行

```bash
# 接口用例
pytest -q

# 只看对照已知缺陷的那 14 条
pytest -q -m defect

# 换端口跑（验证 SUT_BASE 生效）
SUT_BASE=http://127.0.0.1:8090 pytest -q

# 并发验证
python 并发测试.py
python 并发测试.py --threads 20

# 串行对照（同样 10 条，但一条一条发，用来排除脚本问题）
python 串行对照.py
```

## 预期结果

`pytest -q` 的结果是 **14 failed, 9 passed**。这 14 条失败不是脚本写错，是被测服务确实存在的缺陷：

| 失败用例 | 对应缺陷 | 实际行为 |
|---|---|---|
| `test_create_order_normal` | BUG-11 | 总额返回 `1989.9999999999998`，应为整数 `1990` |
| `test_client_price_ignored` | BUG-04 | 传 `unitPrice:1` 后总额变成 `1.0`，单价由客户端决定 |
| `test_user_detail_other_forbidden` | BUG-01 | 读他人资料返回 200，应为 403 |
| `test_order_detail_other_forbidden` | BUG-01 | 读他人订单返回 200，应为 403 |
| `test_admin_orders_forbidden` | BUG-02 | 普通用户读管理端返回 200，应为 403 |
| `test_logout_invalidates_token` | BUG-03 | 登出后同一 token 仍可访问，应 401 |
| `test_order_off_shelf_product` | X-03 | 已下架商品仍可下单，返回 201，应为 409 |
| `test_duplicate_payment_rejected` | BUG-08 | 同一订单付两次都成功，第二次应 409 |
| `test_callback_requires_signature` | BUG-07 | 无签名回调返回 200，应 400/401/403 |
| `test_product_pagesize_over_limit` | X-01 | `pageSize=999` 返回 200，应为 400 |
| `test_order_quantity_zero` | BUG-06 | `quantity=0` 返回 201，应为 400 |
| `test_order_quantity_negative` | BUG-06 | `quantity=-5` 返回 201，应为 400 |
| `test_order_quantity_float` | BUG-06 | `quantity=1.5` 被截断成 1，应为 400 |
| `test_product_keyword_injection` | BUG-10 | `keyword` 注入让已下架商品 7 重新出现 |

断言依据是接口文档里的承诺，不是服务的实际行为。**测试保持失败状态是正确的**——修好服务后它们会自然转绿，这正是一条可用的回归基线。

## 为什么不用 `xfail` / `skip` 把它们标黄

这是有意的取舍，不是不知道 pytest 有这个功能：

- 作业原文要的是「业务预期与实际行为不一致的失败，应在测试结果中如实说明」「因 SUT 缺陷导致的测试失败，需关联缺陷编号并说明原因」——**它要的是真实失败，且能对上号**。标成 `xfail` 后汇总行会变成 `14 xfailed, 9 passed`，这些用例不再计入失败统计，与这条要求的口径不一致。
- 说明白一点：`xfail` 并**没有**隐藏原因（`reason` 照样会打印），它省掉的只是「红色」。所以理由不能写成「xfail 看不出错在哪」，那样不准确。
- 保留红色在交付场景里更直接：评审看到 `14 failed` 的第一反应是「错在哪」，顺着失败清单能一路走到 `缺陷报告.md`；如果是 14 条黄色，得先理解 `xfail` 的语义才看得懂。
- 还有一个附带好处：**修复进度是可读的**。修好一条，那一条就从 `F` 变成 `.`，剩几条一眼可见，不用再解释「XPASS 等于修好了」。

换到真实项目的 CI 里我会反过来用 `xfail(strict=True)`：那时需要的是「红灯只代表新问题」，已登记缺陷不该天天把流水线打红。这里不这么做，是因为这份交付物本身就是给人看的测试结果，不是给流水线看的。

## 关于「是不是把缺陷写成测试来凑数」

如果要凑通过数，最省事的做法是把断言改成迁就服务的现状（例如把「读他人资料返回 200」也写成断言），那样 23 条会全绿，还更好看。反过来做——**把断言钉在文档承诺上、让它红着**——是更难、也更没好处的那条路。

23 条里 9 条绿、14 条红：绿的 9 条守的是服务本来就做对的行为（登录、商品列表、库存不足 409、分页、评价发布等），红的 14 条是缺陷。**缺陷是靠红的那 14 条被固定住的，不是靠它们充数**——它们在服务修好之后必须变绿，变不绿就说明没修对。

**关于独立性**：会改服务状态的用例（重复支付、回调）都用 `new_order` 夹具现场建单，每条动自己那笔，互不干扰；`test_logout_invalidates_token` 也在用例内部重新登录取 token，因为它一旦「修好」，会话级 token 就会被作废、把后面的用例一起带挂。

`并发测试.py` 的预期结果是「不符合」：库存 1 件、10 个并发请求，实际会成功 7~8 个，库存被扣成 -6 ~ -7。连跑 3 轮的成功数是 7 / 7 / 8，**变的是成功个数，不变的是「库存必然为负」**——结论以后者为准，别拿「7」当常量。

`串行对照.py` 的预期结果是「完全正确」：1 条 201、9 条 409、库存归零、订单 1 条。它和 `并发测试.py` 的唯一差别是并发度，两条一起看才能排除「脚本数错了」这种可能。

## 注意

用例会真实下单、消耗库存。反复跑若干轮后商品 1 的库存会被扣光，`test_create_order_normal` 会提前因 409 失败。完整回归前**重启一次服务**就能回到初始数据——`app.py` 启动时会删库重建，不用手动删 `sut.db`。

`并发测试.py` 与 `串行对照.py` 都要求商品 5（轻薄防晒外套）库存为 1，同样在重启服务后运行。
