# 自动化测试

本目录是被测服务（`testing/sut/app.py`）的自动化回归脚本。

## 文件

| 文件 | 作用 |
|---|---|
| `conftest.py` | pytest 公共夹具：`base_url`（支持用环境变量 `SUT_BASE` 换地址）、`token`、`auth` |
| `test_sut.py` | 8 条接口用例：正常 3、异常 3、边界 2 |
| `并发测试.py` | 10 线程同时下单，验证超卖，独立脚本，仅用标准库 |
| `串行对照.py` | 同样 10 条请求但串行发，用来排除「脚本写错」，与上者构成唯一变量对照 |
| `requirements.txt` | 依赖清单 |

## 准备

```bash
# 1. 装依赖
python -m pip install -r requirements.txt

# 2. 起被测服务（另开一个终端，在 testing/sut 下）
python app.py --port 8080

# 3. 确认服务活着
curl http://127.0.0.1:8080/health
```

## 运行

```bash
# 接口用例
pytest -q

# 换端口跑（验证 SUT_BASE 生效）
SUT_BASE=http://127.0.0.1:8090 pytest -q

# 并发验证
python 并发测试.py
python 并发测试.py --threads 20

# 串行对照（同样 10 条，但一条一条发，用来排除脚本问题）
python 串行对照.py
```

## 预期结果

`pytest -q` 的结果是 **4 failed, 4 passed**。这 4 条失败不是脚本写错，是被测服务确实存在的缺陷：

| 失败用例 | 对应缺陷 | 实际行为 |
|---|---|---|
| `test_create_order_normal` | BUG-11 | 总额返回 `1989.9999999999998`，应为整数 `1990` |
| `test_order_off_shelf_product` | X-03 | 已下架商品仍可下单，返回 201，应为 409 |
| `test_product_pagesize_over_limit` | X-01 | `pageSize=999` 返回 200，应为 400 |
| `test_order_quantity_zero` | BUG-06 | `quantity=0` 返回 201，应为 400 |

断言依据是接口文档里的承诺，不是服务的实际行为。**测试保持失败状态是正确的**——修好服务后它们会自然转绿，这正是一条可用的回归基线。

`并发测试.py` 的预期结果是「不符合」：库存 1 件、10 个并发请求，实际会成功 7~8 个，库存被扣成 -6 ~ -7。连跑 3 轮的成功数是 7 / 7 / 8，**变的是成功个数，不变的是「库存必然为负」**——结论以后者为准，别拿「7」当常量。

`串行对照.py` 的预期结果是「完全正确」：1 条 201、9 条 409、库存归零、订单 1 条。它和 `并发测试.py` 的唯一差别是并发度，两条一起看才能排除「脚本数错了」这种可能。

## 注意

用例会真实下单、消耗库存。反复跑若干轮后商品 1 的库存会被扣光，`test_create_order_normal` 会提前因 409 失败。完整回归前请重置数据库：

```bash
# 停掉服务后
rm testing/sut/sut.db
# 再重新启动
```

`并发测试.py` 需要商品 5（轻薄防晒外套）库存为 1，同样要在重置数据库后运行。
