# 测试计划

被测对象：`testing/sut/app.py`（SUT），一个用 Python 标准库实现的校园好物市集服务，共 16 个接口。
依据：`testing/README.md` 第 5 节的接口文档与「文档承诺」。
本轮为一轮摸底测试，目标是在 48 小时内用有限时间找出**有证据、影响明确**的问题，并交付可重复执行的自动化用例。

---

## 1. 测什么

### 1.1 覆盖范围

16 个接口全部覆盖，按业务模块分五组：

| 模块 | 接口 | 重点测试方面 |
|---|---|---|
| 认证 | `POST /api/auth/login`、`POST /api/auth/logout` | 口令校验、token 生成与**失效**、token 可伪造性 |
| 权限 | `GET /api/users/{id}`、`GET /api/admin/orders`、`GET /api/orders/{id}`、`PATCH /api/products/{id}/status` | 横向越权（读别人的）、纵向越权（普通用户当管理员）、资源属主校验 |
| 商品 | `GET /api/products`、`GET /api/products/{id}`、`POST /api/products`、`PATCH /api/products/{id}/status` | 过滤与分页边界、参数类型、字段校验白名单、SQL 注入 |
| 订单 | `POST /api/orders`、`GET /api/orders/mine`、`GET /api/orders/{id}` | **金额是否由服务端计算**、金额精度、库存扣减正确性与并发安全、已下架商品、quantity 边界 |
| 支付 | `POST /api/payments`、`POST /api/payments/callback` | 重复支付、订单存在性、回调验签、状态机 |
| 评价 | `GET /api/product-reviews`、`POST /api/product-reviews` | 内容长度与评分范围边界、非数字 id、**输出编码（XSS）** |
| 健康检查 | `GET /health` | 存活探针可用性 |

### 1.2 测试方面（每个接口都按这 6 问展开）

1. **正常路径**：合法参数能否走通，返回字段是否与文档一致
2. **缺参与错类型**：少传字段、`id=abc`、`price=19.9`
3. **边界值**：`quantity=0` / `1` / `库存` / `库存+1`，`pageSize=0` / `50` / `51`，`content` 200 / 201 字，`rating` 0 / 1 / 5 / 6
4. **该拦的人拦住了吗**：无 token、他人 token、普通用户 vs 管理员、非属主
5. **重复操作**：同一订单付两次款、同一商品重复评价、重复登出
6. **并发**：库存为 1 的商品被多个请求同时下单

优先级分配：涉及**资金、库存、越权、认证**的为 P0；影响主流程可用性的为 P1；仅影响边界体验的为 P2。

## 2. 不测什么，以及为什么

| 不测项 | 原因 |
|---|---|
| 压力测试 / 长时间稳定性 | 目标是功能与安全摸底，SUT 用 `ThreadingHTTPServer` + SQLite，压测结论对真实架构没有参考价值；且时间预算只有 48 小时 |
| 前端 UI / 浏览器兼容性 | SUT 无前端，评价页只返回裸 HTML |
| 数据库迁移、灾备、备份恢复 | SUT 每次启动重建 `sut.db`，没有迁移逻辑 |
| 真实第三方支付渠道联调 | 支付是模拟实现，无外部依赖；只测回调的身份校验逻辑 |
| 性能指标（响应时间、吞吐） | 同上，`time.sleep(0.15)` 是人为植入的竞态窗口，不代表真实性能 |
| 短信、邮件、推送等通知 | 未实现 |
| 多语言、时区、货币单位换算 | 金额统一为分，无多币种设计 |
| 权限矩阵的完整笛卡尔积 | 只取 5 个用户 × 关键接口的代表性组合，不穷举 |

## 3. 怎么测：方法与工具

| 阶段 | 方法 | 工具 |
|---|---|---|
| 探索 | 手工先跑一遍 README 第 2 节的 30 分钟路径，记录真实响应形态 | `curl.exe`（PowerShell 下 `curl` 被别名为 `Invoke-WebRequest`，必须写 `curl.exe`） |
| 接口用例 | 按 6 问法逐接口设计正/异/边界用例，先用 curl 确认实际行为，再固化为断言 | `curl.exe` + PowerShell |
| 自动化回归 | 把已确认的期望值写进 pytest，`xfail(strict=True)` 标记已确认的缺陷 | `pytest 8.3.4` + `requests 2.32.3` |
| 并发 | 多线程同时下同一件库存为 1 的商品，统计成功数与最终库存 | `threading` + `requests` |
| 静态审查 | 读 `testing/sut/app.py` 定位根因、确认行号（不作为缺陷唯一证据） | 编辑器 |
| legacy 审查 | 只读审查 `testing/legacy/` 五个片段，按行号提意见 | 静态阅读 |

**自动化框架约定**（加分项要求）：

- 端口与 token 全部由 `conftest.py` 的 fixture 管理，不写死。
- 夹具 `base_url` 支持 `SUT_BASE_URL` 环境变量指向外部实例；不设置时自动挑一个空闲端口拉起 SUT 子进程，并轮询 `/health` 等待就绪。
- 夹具作用域为 `module`：SUT 每次启动都会重建数据库，但下单/发商品会改变库存，用 module 级隔离保证每个模块的初始状态可预期。
- 缺陷用 `@pytest.mark.xfail(strict=True, reason="BUG-xx …")` 表达「期望失败」，这样报告里能同时呈现「多少个不符合预期」和「SUT 修好后用例会反过来报警」。

## 4. 结束条件

满足以下全部条件即结束本轮：

1. **范围达成**：16 个接口每个至少 1 条用例，共 ≥15 条（实际 66 条）。
2. **类型分布达成**：正常 ≥3、异常 ≥3、边界 ≥3（实际 18 / 37 / 11）。
3. **缺陷证据充分**：每条缺陷都有可复制执行的 `curl.exe` 命令 + 真实返回原文，且在干净库上复现过（实际 19 条）。
4. **自动化可重复**：在仓库根目录执行 `cd testing/自动化 && pytest -q`，全部结果只剩 `passed` 与 `xfailed`，**没有 error、没有 failed**（即排除环境缺失、服务未启动、脚本自身错误）。
5. **结论可用**：测试报告能给出明确的上线建议，并说明依据。
6. **可复现**：另一台机器按 `SUBMISSION.md` 的环境与启动步骤能从零跑通。

**终止标准（提前结束的条件）**：若剩余时间不足 4 小时且上述 1、3、4 已达成，停止继续扩用例，转入文档整理。
