# 测试计划

> 被测对象：校园好物市集（`testing/sut/app.py`），15 个业务接口 + `/health`
> 窗口：48 小时开卷，我实际可用约 10 小时
> 环境：Windows 11 / Python 3.14 / SQLite / 单进程 `ThreadingHTTPServer`，默认 8080

## 一、测什么

覆盖 SUT 全部 15 个业务接口，按五个模块划分：认证（login/logout/users）、
商品（列表/详情/发布/上下架）、订单（下单/详情/我的订单）、支付（发起/回调）、
评价（列表页/提交）。

测试方面包括：功能正确性、鉴权与越权、输入校验与边界值、金额与库存一致性、
并发安全、异常处理。

**测试点是怎么展开的。** 每个接口先按六个问题过一遍（正常能不能用 / 少传不传 /
类型格式 / 边界值 / 该拦的人拦没拦住 / 重复操作），再按模块合并同类项。展开后是 23 条用例：

| 模块 | 接口数 | 正常 | 少传·类型 | 边界 | 越权 | 重复 | 风险等级 | 落成用例（数量 / 编号） |
|---|---|---|---|---|---|---|---|---|
| 认证 | 3 | ✓ | ✓ | — | ✓ | ✓（登出后令牌应失效） | **高** | 3　TC-01～03 |
| 商品 | 4 | ✓ | ✓ | ✓ | ✓ | — | 中 | 5　TC-06～10、22 |
| 订单 | 3 | ✓ | ✓ | ✓ | ✓ | ✓ | **高** | 7　TC-12～17 |
| 支付 | 2 | — | ✓ | — | ✓ | ✓ | **高** | 3　TC-18、19、23 |
| 评价 | 2 | ✓ | ✓ | ✓ | — | — | 中 | 2　TC-20、21 |
| 合计 | 15 | | | | | | | **23** |

表里带 `✓` 的格子都有对应用例，没有出现的格子是刻意留空的（例如支付不测「正常」：
发起支付的正常路径已在 TC-18 的第一次请求里走过，再单列一条属于重复计数）。
每个格子对应哪个用例号见上表最后一列，逐条展开在 `测试用例.md`。

**为什么这几块排「高」**：钱 > 身份 > 数据 > 体验。订单和支付的缺陷直接是资损，
认证的缺陷会让「我是谁」这件事失效，后面所有基于身份的校验都跟着不成立，所以这三块排最前。
商品和评价的问题多数是数据泄露或体验问题，排第二梯队。这个顺序决定了时间不够时先砍谁。

## 二、暂不测什么，为什么

1. 性能与压测：本轮不具备稳定压测环境，且题目范围未包含响应时间指标。
2. 管理端订单的导出与分页：SUT 未提供该功能。
3. 邮件/短信通知：SUT 无此依赖。
4. 前端交互与兼容性：被测对象是无界面服务。

**这四条的风险由谁承担**（不测不等于没风险，只是明确不在这里兜）：

| 不测项 | 风险落点 | 本轮怎么弥补 |
|---|---|---|
| 性能与压测 | 上线后首波流量 | 无法弥补，属于上线前必须另做的一轮，已写进测试报告的「有条件上线门槛」 |
| 管理端导出/分页 | — | SUT 无此功能，风险为 0 |
| 邮件短信 | — | 依赖不存在，风险为 0 |
| 前端交互 | 浏览器端渲染 | 只验了服务端返回的 HTML（BUG-09 就是这么发现的），未验真实浏览器行为，属于遗留项 |

## 三、用什么方法和工具

- 接口请求：curl（命令行，便于把命令原样写进缺陷报告，评审可直接复现）
- 断言与批量执行：pytest + requests，夹具集中在 `自动化/conftest.py`
- 并发验证：Python threading + urllib，10 线程用 `Barrier` 卡在同一起跑线再放行
- 证据留存：请求命令 + 实际响应原文 + 服务端日志片段

**环境与数据状态**：`app.py` 启动时会删库重建并写入种子数据，所以「回到初始状态」
就是重启一次服务，不需要手动清库。每轮用例执行前重启，保证起点一致。

## 四、什么条件算测完

满足以下任一条即结束本轮：

1. 15 个接口均至少有 1 条正常用例通过，且异常/边界用例覆盖到金额、库存、鉴权三类
   ——**对照实际：23 条用例 15 个接口全覆盖，执行率 100%**；
2. 发现的有效缺陷达到 8 条（题目缺陷项封顶线），继续投入的边际收益下降
   ——**对照实际：确认 11 条，已过封顶线**；
3. 距离截止不足 3 小时，转入文档收尾。

**结束条件的量化口径**（这里改过一次，值得说清楚为什么）：

- **第一版**写的是「`pytest -q` 必须等于 `14 failed, 9 passed`」。这是个坏数字——它把当时的缺陷状态写成了验收标准，服务一旦修好一条，这个条件就永远不可能满足，反而要反过来改计划。
- **现在**改成三条可判定的条件：
  1. 9 条基线用例（不带 `defect` 标记的那批）全部通过——它们守的是服务本来就做对的行为；
  2. 14 条对照缺陷的用例逐条能对上 `缺陷报告.md` 里的编号（`pytest -q -m defect` 可筛出来复核）；
  3. **意外失败为 0**：如果出现第 15 条失败，要么是新缺陷（要登记），要么是脚本自己写错了（要修脚本），两种都必须先查清再收尾。

这样一来，「修好之后」的状态也有定义：14 条全部转绿、0 失败、0 意外，就是可以关单了。

## 五、48 小时怎么切

| 阶段 | 大致时间 | 产出 | 卡点 |
|---|---|---|---|
| 读题 + 起服务 + 摸接口 | 0.5 h | 知道 15 个接口长什么样 | — |
| 通读 `app.py`，按模块列可疑点 | 1 h | 一份怀疑清单 | 容易读着读着陷进细节，靠「只列校验缺失」约束 |
| 按资金→身份→数据顺序验证 | 3 h | 缺陷草稿 + 可复现命令 | 并发那条卡了最久，见 DESIGN 第 6 节 |
| 铺用例表、写缺陷报告 | 2 h | 用例 23 条、缺陷 11 条 | — |
| 代码审查、安全专项 | 1.5 h | L1-6、L2-7 | — |
| 自动化与文档收尾 | 1.5 h | 23 条 pytest + 三份说明文档 | 浮点那条是被断言抓出来的，见 DESIGN 第 7 节 |

这个切法是动手之前定的，合计约 9.5 小时。实际走下来，前四段基本对得上；
最后一段超了时间，因为写 pytest 断言时发现自己手工把金额那条判错了，回头补了一条缺陷（BUG-11）
并重做了复测，过程写在 DESIGN 第 7 节。**计划的用处不是预测准，是时间不够时知道该砍哪一段——
按第一节的风险排序，先砍商品和评价，不砍订单和支付。**
