# 测试计划

## 1. 测试目标
- 对 `testing/sut/app.py` 暴露的 16 个接口做手工接口测试，并沉淀可重复执行的自动化回归。
- 覆盖正常、异常、边界、权限、金额与状态流转。
- 用例分层为 L0 普通手工用例 28 条、L2 安全专项用例 12 条、L2 并发专项用例 4 条，共 44 条。
- 对疑似缺陷用独立请求复现，只记录有真实响应证据的问题。

## 2. 测试范围
- 认证：登录、登出、token 有效性。
- 用户与权限：用户详情、管理端订单。
- 商品：列表、详情、创建、上下架。
- 订单：创建、详情、我的订单。
- 支付：发起支付、支付回调。
- 评价：创建评价、评价页 HTML 输出。
- 系统：健康检查。
- 安全专项：未登录、可预测 token、水平越权、垂直越权、SQL 注入、金额篡改、负数数量下单、商品标题 XSS、paymentId 不匹配回调、伪造支付回调、评价 XSS。
- 并发测试：10 个并发请求购买库存为 1 的商品 `id=5`、同一订单并发重复支付、支付与回调混合竞争。
- Legacy 代码审查：`testing/legacy/` 下 5 个代码片段的硬编码、SQL 拼接、并发、金额精度、异常处理和资源管理问题。
- CI：验证 GitHub Actions 能启动 SUT、执行 pytest、生成并上传测试报告。

## 3. 暂不测试
- 前端页面与后端实现。
- 性能压测和 UI 自动化；CI 只验证测试流水线可用，不做完整平台部署验证。
- 支付回调的有效签名场景；当前文档未给出签名算法，只做伪造回调与异常回调检查。

## 4. 方法与工具
- 使用 Apifox 批量执行 56 个请求作为初筛。
- 对失败项和重点风险用 `curl` 在独立端口 `18081` 上复现。
- 对需要干净数据的用例，重启 SUT 由服务自动重建数据库；运行产生的 `sut.db` 不进入提交。
- 每个缺陷保留可直接执行的 curl 命令、实际状态码和响应片段。

## 5. 结束条件
- 16 个接口至少各执行 1 条用例。
- 正常、异常、边界用例均有记录。
- 至少 4 条缺陷有真实请求证据。
- Apifox 中因工具或导入导致的结果不再作为缺陷结论。
- 未覆盖内容在测试报告中如实说明。
