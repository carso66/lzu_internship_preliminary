### 索引实测结论（P07）

在 H2 2.x、2000 行商品数据下用 `EXPLAIN` 对比：

| 查询 | 是否建 `title` 索引 | 执行计划 |
|---|---|---|
| `title LIKE '%商品1%'` | 否 | `tableScan` |
| `LOWER(title) LIKE LOWER('%商品1%')` | 否 | `tableScan` |
| `title LIKE '%商品1%'` | 是 | `tableScan`（前后通配符用不上索引） |
| `LOWER(title) LIKE …` | 是 | `tableScan` |
| 函数索引 `ON products(LOWER(title))` | — | H2 语法不支持 |

结论：**`LOWER()` 没有额外代价**，当前写法无需修改。若将来要做标题检索加速，方向是全文索引或倒排索引，不是 B-tree。

### 毫秒精度实现要点

用 `SimpleModule` + `addSerializer(LocalDateTime.class, ...)` 注册为容器 bean。
Spring Boot 会把容器里的 `Module` 自动注册到它构建的 `ObjectMapper`，
因此 `spring.jackson.*` 的严格类型配置不受影响。

**反例**（P04 踩过的坑）：手工 `new Jackson2ObjectMapperBuilder().build()`
不会继承 `spring.jackson.*`，会静默关闭严格类型校验。

截断用 `truncatedTo(MILLIS)` 而非四舍五入——时间戳语义是「不晚于真实时刻」，
向上取整会造出未来时间。

## 三、已定技术决策（汇总）

### 分层与依赖

| 项 | 决策 | 理由 |
|---|---|---|
| 持久层 | **JdbcTemplate**，无 ORM | SQL 可控，便于写条件 UPDATE 与展示索引思路 |
| 数据库 | **H2 内存库**，`jdbc:h2:mem:marketplace` | 评审零依赖启动；重启回到干净状态 |
| `schema.sql` | 放在 `backend/` 根（题目 §1 要求），Maven 复制进 classpath | 兼顾题目目录要求与三条启动路径 |
| 测试库 | `application-test.yml` 用 `${random.uuid}` | 每个 Spring 上下文独立库，避免 DROP 互相干扰 |
| 包结构 | 模块化单体：`product/` `order/` `payment/` + `common/` | 按业务分包 |

### 金额与数值

| 项 | 决策 |
|---|---|
| 金额类型 | DB `BIGINT`，Java `long`，单位**分**，全程不用浮点 |
| 乘法 | `Math.multiplyExact`，溢出抛 `ArithmeticException` → 50000 |
| 入参上限 | `price ∈ [1, 999_999_999]`，`quantity ∈ [1, 9999]` |

### 参数校验

| 项 | 决策 |
|---|---|
| JSON 严格类型 | `allow-coercion-of-scalars=false` + `accept-float-as-int=false` |
| DTO 数值字段 | 一律**包装类型** + `@NotNull`（原始类型会把 null 变 0） |
| 查询参数分页 | 包装类型 `Integer`，省略 → 默认值；越界 → **400，不夹断** |
| 空串 | 归一化为 null（视为未传） |

> ⚠️ **Jackson 强转的行为边界（P07 实测）**
>
> `ALLOW_COERCION_OF_SCALARS=false` 只拦截**「非字符串 → 数字」**方向：
>
> | 输入 | 目标类型 | 结果 |
> |---|---|---|
> | `"2"` | `Integer` | ❌ 拒绝 `MismatchedInputException` |
> | `2.5` | `Integer` | ❌ 拒绝 `InvalidFormatException` |
> | `2` | `Integer` | ✅ 接受 |
> | `1` | `String` | ✅ **接受**，变成 `"1"` |
> | `true` | `String` | ✅ **接受**，变成 `"true"` |
>
> 所以字符串字段（如 `status`）收到数字时，**不是类型错误**，而是被后续
> `@Pattern("on|off")` 拒绝。对外结果仍是 400 + 40001，符合题目要求，
> 但排查时不要误以为是 Jackson 拦下的。

### 响应与异常

| 项 | 决策 |
|---|---|
| 响应结构 | `{code, message, data}` 恒定，`data` 无值为 `null` |

| 时间格式 | `yyyy-MM-ddTHH:mm:ss.SSS`（毫秒精度，截断不四舍五入） |
| JSON 字符集 | 显式 `application/json;charset=UTF-8` |

### 商品

## 四、L1/L2 阶段已确认的约束（P09 已实现 L1-6）

| 项 | 约束 |
|---|---|
| 库存扣减 | **悲观行锁**：`SELECT ... FOR UPDATE` 锁行 → 校验 → `UPDATE products SET stock=stock-? WHERE id=? AND stock>=?`；扣减 UPDATE 仍检查影响行数作为第二道防线 |
| 事务 | 锁行 + 校验 + 扣库存 + 算价 + 插订单同一 `@Transactional` 事务，全部写在 `OrderService.create()` 一个 public 方法内 |
| 错误区分 | 锁内按 40401 → 40902 → 40901 顺序判定，与题目 L1-6 叙述顺序一致 |
| 金额 | `unit_price` / `total_amount` 只取锁内读到的 DB 价格；`Math.multiplyExact` 防溢出 |
| 快照 | `product_title` / `unit_price` 落库，后续改价改名不影响历史订单 |
| 支付 | 状态迁移 + 插支付记录同一事务；`payments.order_no` 唯一约束兜底 |
| 单号 | 日期 + UUID(32hex)，`VARCHAR(64)`；**不用 `COUNT(*)+1`** |

> **为什么最终选行锁而不是条件原子 UPDATE**：两者都能杜绝超卖。
> 选定行锁的原因是「读→判→扣」的顺序与题目 L1-6 的错误判定叙述完全同构，
> 评审读代码无需额外翻译；且 H2 上的锁行为已由并发实测验证（下面「并发实测结论」）。
> 代价是多一条 SELECT，以及并发时请求在锁上排队——对本题规模无影响。

### 并发实测结论（P09）

`stock=1` 商品，10 个并发 `POST /api/orders`，每个买 1 件：

| 观测项 | 结果 |
|---|---|
| HTTP 响应 | 1 个 `201`，9 个 `409 + 40901` |
| 最终库存 | `0` |
| 订单数 | 恰好 1 条 |

结论：H2 的 `SELECT ... FOR UPDATE` 在本项目下正常串行化，未出现锁超时导致的 50000。

### 回滚验证方法（P09）

`OrderRollbackTest` 用固定订单号的 `OrderNoGenerator` 替身制造唯一约束冲突，
把故障点精确放在**库存扣减之后、订单插入时**。两个读数构成完整证据：

1. 替身被调用时（事务内、未提交）读库存 = `4` → 证明扣减已生效；
2. 请求结束后从外部读库存 = `5` → 证明回滚发生。

只断言最终值是 5 不够——那也可能因为根本没扣过。

## 五、L1-7 / L1-8 订单查询（P10）

| 项 | 决策 |
|---|---|
| `GET /api/orders/{orderNo}` | `orderNo` 声明为 `String`：格式不对只是「查不到」，走 404 而不是 400 |
| `GET /api/orders` 的 `buyerPhone` | **必填**。缺失或空白 → 400 + 40001，不退化成「查全部买家」 |
| 买家隔离 | `WHERE buyer_phone = ?` 精确匹配，参数绑定；COUNT 与分页查询共用同一 WHERE |
| 排序 | `ORDER BY created_at DESC, id DESC`，与商品列表同一约定 |
| 分页结构 | **复用商品模块的 `PageResult` 与同一套参数规则** |
| 手机号索引 | `idx_orders_buyer_phone_created (buyer_phone, created_at DESC, id DESC)` —— 第三列 id DESC 是 L2-13 时补的（决胜列纳入索引，索引序与查询序完全同构），实测证据见 DESIGN 附录 A |

### 为什么分页结构复用商品模块，而不另起一套

题目 §5 L1-8 只说「支持 page 和 pageSize」，没规定 `data` 的结构；§4 L0-3 则明确要求
`total / page / pageSize / items`。选择沿用商品模块：

1. **前端只需一套翻页逻辑**。商品列表和订单列表如果默认值或越界行为不同，
   前端就要维护两套，出 bug 时也难判断是哪边的问题。
2. **`PageResult` 已是 common 层类**（当时就是为了订单列表预留的），直接复用不需要新代码。
3. **越界一律 400 而不夹断**，与 L0-3 的判罚口径一致——不会出现「商品页传 51 报错、
   订单页传 51 悄悄改成 50」这种前后端认知分裂。

反过来说，`OrderQuery` 与 `ProductQuery` **没有**抽公共基类：两者的筛选条件语义完全不同
（一个是三个可选筛选，一个是必填精确匹配），且默认值将来可能各自调整。
过早抽象会为了迁就差异而加一堆参数，不如各写一份、把约定写在注释里。
这和「复用 `PageResult`」并不矛盾——复用的是**输出形状**，不是**输入校验**。

### 为什么 buyerPhone 必填而不是可选

题目 L1-8 的语义是「查某个手机号的订单列表」。
若允许省略，接口就变成了「查全平台所有订单」——既不符合语义，
也把「看到别人订单」的口子开在了参数缺省上。
`OrderQuery.of` 里显式判空并返回 400，而不是让 `null` 顺着流到 SQL 的 `WHERE buyer_phone = ?`
（那样虽然也不会返回数据，但错误信息会变成「查无此号码」，误导客户端以为自己参数传对了）。

### 排序为什么必须带 id 兜底

`created_at` 是 `TIMESTAMP`，两个订单在同一毫秒创建时值完全相同。
只写 `ORDER BY created_at DESC` 时，并列行的相对次序由数据库决定，
且可能随数据量、执行计划变化——同一个买家翻页时就会出现
「第 2 页重复第 1 页的某条」或「某条在翻页中消失」。
追加 `id DESC` 后，排序在数学上变成全序，翻页结果稳定。

`OrderQueryTest.stableTieBreakBySameTimestamp` 用 3 条完全相同的 `created_at`
验证了这一点：逐页取出的 orderNo 序列既不重复也不遗漏。

### 验证结论（P10）

`OrderQueryTest` 20 个用例全部通过，覆盖：详情存在/不存在、手机号筛选、
多买家隔离、前缀相同号码不互相污染、空结果、空表、缺少/空白手机号、
倒序、同时间戳稳定排序 + 逐页不重不漏、默认分页、total 为筛选后总数、
末页不满、超末页、pageSize 边界、非法分页参数、page 极大不溢出。
另在真实服务上用 curl 复核了同样的场景。

## 六、L2-10 并发不超卖（P11）

### 审查结论：现有事务无需改动

实现并发的测试前，先复核了已有的下单事务，确认三处都成立，因此**没有重写任何业务代码**：

1. **事务边界**：`OrderService.create()` 是 `public` 方法，`@Transactional` 经 Controller
   跨 bean 调用生效；所有步骤（锁行 → 校验 → 扣减 → 算价 → 插订单）都在同一方法内，
   不存在类内自调用绕过代理。
2. **行锁生效条件**：`findByIdForUpdate` 的 `SELECT ... FOR UPDATE` 在 `create()` 事务内执行，
   锁持有到提交/回滚，满足「读→判→扣」串行化的前提。
3. **扣减逻辑**：锁内校验 + `UPDATE ... WHERE stock >= ?` + 检查影响行数，双重防线。

### 测试实现要点

| 项 | 决策 |
|---|---|
| 并发载体 | `RANDOM_PORT` 真实 Tomcat + JDK `HttpClient`，非 MockMvc（MockMvc 默认在调用线程内执行，会掩盖事务/连接池真实行为） |
| 同步机制 | 两级 `CountDownLatch`：`ready` 全部就绪 → `startGate` 统一放行 |
| 线程池 | `Executors.newFixedThreadPool(10)`，10 个独立任务各买 1 件 |
| 数据准备 | 每轮 `@BeforeEach` 清三表 + 插库存为 1 的商品 |
| 断言 | 恰好 1 个 201；9 个 409 + 40901；库存 0；订单恰好 1 条 |
| 防伪 | 不重试、`Future.get()` 传播执行异常、断言数据库最终状态而非只看响应码 |
| 稳定性 | `@RepeatedTest(5)`，每轮重建数据 |

### 实测结果（P11，5 轮全过）

`surefire` 报告里 5 个 testcase 名称为 `tenConcurrentOrdersOnlyOneSucceeds()[1]~[5]`，
耗时分别为 1.263s / 0.020s / 0.015s / 0.017s / 0.021s（首轮含 Tomcat 启动与连接建立，

## 七、L2-9 模拟支付（P12）

### 设计理由

| 决策 | 理由 |
|---|---|
| `POST /api/payments` 成功返回 HTTP 200 | 题目 L2-9 明确要求 200（不是 201——支付不是创建资源的 POST 语义） |
| 响应只含 `paymentId/orderNo/amount/status/paidAt` | 照题目示例，不额外返回 method/createdAt |
| 金额取订单 `total_amount` | 支付结算的是下单时点的金额，不重查商品价格；请求体里传 `amount` 被忽略 |
| 同步返回 `paid`，无中间态 | 题目允许「直接同步返回 paid，不做异步回调」；不新增轮询、不接真实平台 |
| `method` 用 `@NotBlank+@Pattern` | 非法值由可控的 message 说明，非框架枚举反序列化报错 |
| 支付**不碰 `products.stock`** | 库存在 L1-6 下单时已扣，支付只改 orders/payments 两表 |

### 防重复支付的两层设计

1. **应用层**：`PaymentService.pay()` 先 `SELECT ... FOR UPDATE` 锁订单行，
   后到者在锁上排队；先到者提交后、后到者读到 `status='paid'` → 40903。
2. **数据库层**：`payments.order_no` 唯一约束（`uk_payments_order_no`）兜底。
   即便锁失效，第二条支付记录也会因唯一约束插入失败，不会出现
   「同一订单两条成功支付记录」。

### 事务回滚验证（PaymentRollbackTest）

故障点选在「支付记录插入」这一步：用固定 `paymentId` 替身撞 `uk_payments_payment_id`
唯一约束。关键点在于——支付链路里**先插支付记录、后更新订单状态**，
所以故障发生在订单状态更新之前，正好验证「支付记录插不进去时，订单不能先被标成 paid」。

两个读数构成证据：
1. 替身在 `next()`（事务内、未提交）读订单状态 = `created`；
2. 请求结束后从外部读订单状态 = 仍是 `created`，且该订单无支付记录。
