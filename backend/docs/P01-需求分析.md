L1-6 官方给出的固定步骤顺序（题目 §5）：

1. 校验 `quantity` 是 **≥1 的整数**（`0`、`-1`、`"2"` 都要处理 → 400 + `40001`）；
2. 查商品：不存在 → 404 `40401`；`status='off'` → 409 `40902`；
3. 库存检查：`stock < quantity` → 409 `40901`；
4. 扣库存；
5. 插订单，`unit_price`/`total_amount` **由服务端按数据库价格计算**，不接受客户端传价；
6. `order_no` 自生成（日期 + 序号即可，**必须唯一**）。

> 硬性：**扣库存与插订单必须在同一个数据库事务**，插订单失败时已扣库存必须回滚。L1 按单次下单验收；并发场景归 L2-10。

## 2. 接口验收矩阵

> 统一外层（题目 §3 硬性）：所有已实现接口，成功/失败均返回 `{ "code", "message", "data" }`；无数据时 `data` 可为 `null`。金额单位统一「分」（整数），全程不用浮点。

### 2.0 统一业务码（题目 §3，硬性）

| code | HTTP | 场景 |
|---|---|---|
| `0` | 200 / 201 | 成功 |
| `40001` | 400 | 参数不对（缺字段、类型错、**超范围**、枚举非法） |
| 自定（非 0） | 401 | 鉴权失败（仅 L2-11，本项目不涉及） |
| `40401` | 404 | 商品 / 订单不存在 |
| `40901` | 409 | 库存不足 |
| `40902` | 409 | 商品已下架 |
| `40903` | 409 | 订单已支付，不可重复支付 |
| `50000` | 500 | 服务出错（**不把堆栈返回客户端**） |

> 码表共 **8 行，已全部收录**（`0`/`40001`/自定 401/`40401`/`40901`/`40902`/`40903`/`50000`），无遗漏。题目未给「非法 JSON」「接口不存在」的码——前端 mock 用的 `40002`/`40400`/`50300` **不是后端规范**，本项目需自行定义（见 §7 #16）。
>
> `message` 文案由考生决定（题目 §3 明示）；`data` 中题目未明确字段由考生决定。

### 2.1 L0-2 `POST /api/products`

| 项 | 内容 |
|---|---|
| 请求体（示例，题目 §4） | `{"title":"测试商品","price":1990,"stock":10,"category":"文具","description":"备注","sellerName":"校园数码铺"}` |
| 成功 | HTTP 201，`code:0`，`data` = 完整商品对象，含 `id/title/price/stock/status:"on"/…` |
| 失败 | 字段长度/类型不合法 → 400 `40001`，`message` 指明具体字段 |
| 边界 | `title` 空/超长、`price` 非正整数/浮点/字符串、`stock` 负数、`category` 缺/非法、`description` 超长（具体上限自定，见 §7） |
| 待定义 | `sellerName` 是否必填及来源；`status` 默认值（示例返回 `on`，题目未明说）；`category` 是否枚举约束 |

### 2.2 L0-3 `GET /api/products`

| 项 | 内容 |
|---|---|
| 查询参数 | `keyword`（标题模糊匹配）、`status`（`on`/`off`，不传=全部）、`category`（分类精确匹配）、`page`/`pageSize`（默认 1/10，`pageSize` 范围 1~50） |
| 成功 | `data` 必须含 `total`（筛选后总条数）、`page`、`pageSize`、`items`（当前页数组） |
| 边界 | 三筛选可叠加；`pageSize` 超出 1~50 → 400 `40001`（「超范围」依据 §3 码表）；无匹配返回空 `items` |
| 分页规则（关键） | **缺失 → 用默认值（page=1、pageSize=10），不报错**；**显式传非法值 → 400 `40001`**：`pageSize` 非整数/超 1~50、`page` 非整数/`<1` 均属「类型错/超范围」 |
| 待定义 | `status` 非法值（`on`/`off` 之外）→ 400 `40001`（「枚举非法」）；`keyword` 是否大小写不敏感；`category` 非法值返回空列表还是 400 |

> ⚠️ 前端 mock 对 `pageSize` 是 `Math.min(50, …)` **夹断**而非报错，但后端题目 §3 码表明确「超范围 → 40001」，且 L0-3 写明「范围 1~50」。**后端应 400，不能照抄 mock 的夹断行为**——这是容易丢分的一处。

### 2.3 L0-4 `GET /api/products/{id}`

| 项 | 内容 |
|---|---|
| 成功 | 存在 → 200，`data` = 单条商品 |
| 失败 | 不存在 → 404 `40401` |
| 边界 | `{id}` 非数字（路径变量类型不匹配）→ 400 `40001`（需在全局异常处理里统一，避免 Spring 默认 400 裸体返回破坏统一结构） |

### 2.4 L0-5 `PATCH /api/products/{id}/status`

| 项 | 内容 |
|---|---|
| 请求体 | `{"status":"off"}`（或 `"on"`） |
| 成功 | HTTP 200，`data` 示例 `{"id":1,"status":"off"}` |
| 失败 | `status` 非 `on`/`off` → 400 `40001`；商品不存在 → 404 `40401`（题目未明说，按码表「商品不存在」推断） |

### 2.5 L1-6 `POST /api/orders`

| 项 | 内容 |
|---|---|
| 请求体（示例） | `{"productId":3,"quantity":2,"buyerName":"张三","buyerPhone":"13800138000","address":"兰州市城关区天水南路222号"}` |
| 成功 | HTTP 201，`code:0`，`data` = `id/orderNo/productId/productTitle/quantity/unitPrice/totalAmount/status:"created"/buyerPhone/address/createdAt` |
| 校验顺序（硬性） | ① `quantity` ≥1 整数（`0`/`-1`/字符串 `"2"` 均 400 `40001`）② 商品不存在 404 `40401` ③ 商品 `off` → 409 `40902` ④ `stock<quantity` → 409 `40901` ⑤ 扣库存 ⑥ 插订单（服务端算价） |
| 顺序即验收点 | 题目给出**固定步骤顺序**，意味着组合错误时按顺序短路：如 `{productId: 不存在, quantity: 0}` 应先报 400（quantity），**不是** 404；`{productId: 下架商品, quantity: 0}` 也是先 400。测试别写反 |
| 事务（硬性） | 扣库存 + 插订单同一事务，插入失败库存回滚 |
| 边界 | `unit_price`/`total_amount` 服务端算（**客户端传价一律忽略/拒绝**）；`order_no` 唯一 |
| 待定义 | `buyerName`/`buyerPhone`/`address` 是否必填与格式规则；`buyerName` 是否出现在响应（示例省略，可能是省略号）；`totalAmount = unitPrice × quantity` 的溢出上限 |

### 2.6 L1-7 `GET /api/orders/{orderNo}`

| 项 | 内容 |
|---|---|
| 成功 | 存在 → 200，按 `orderNo` 查详情 |
| 失败 | 不存在 → 404 `40401` |
| 注意 | 路径参数是**订单号字符串**（如 `SO202611190001`），不是数字 id（与前端 mock 用数字 id 不同） |

### 2.7 L1-8 `GET /api/orders?buyerPhone=…&page=…&pageSize=…`

| 项 | 内容 |
|---|---|
| 查询参数 | `buyerPhone`、`page`/`pageSize` |
| 成功 | 按创建时间**倒序**的分页列表（`data` 结构题目未明说，推断复用 `total/page/pageSize/items`） |
| 待定义 | `buyerPhone` 是否必填（不传返回全部还是 400）；分页参数规则（推断复用商品规则：默认 1/10、`pageSize` 1~50） |

### 2.8 L2-9 `POST /api/payments`

| 项 | 内容 |
|---|---|
| 请求体 | `{"orderNo":"…","method":"alipay"}`（`method` 仅 `alipay`/`wechat`） |
| 成功 | HTTP 200，`data` = `{"paymentId":"PAY…","orderNo":"…","amount":9980,"status":"paid","paidAt":"…"}` |
| 失败 | 订单不存在 → 404 `40401`；订单已 `paid` → 409 `40903`；`method` 非法 → 400 `40001`（推断，按「枚举非法」码表） |
| 硬性 | ① 支付成功要把订单 `status` 改 `paid` 并写 `paid_at` ② 新增 `payments` 表落库 ③ 幂等：同 `orderNo` 第二次必须 409，不能两条成功记录 ④ 可同步返回 `paid`（不用真异步） |
| 边界 | 并发重复支付（见 §5）；`amount` = 订单 `total_amount`；`paymentId` 自生成唯一 |
| 待定义 | `paymentId` 生成算法；`payments` 表字段结构；`method` 校验位置（先校验 method 还是先查订单，题目未排顺序） |

### 2.9 L2-10 并发不超卖（验收口径，硬性）

| 项 | 内容 |
|---|---|
| 前置 | 自行准备一个已上架且库存 = 1 的商品 |
| 请求 | 同时发起 10 个有效下单请求，每个买 1 件 |
| 响应 | **恰好 1 个成功，其余 9 个 409「库存不足」** |
| 最终数据 | 全部结束后库存**恰好 0**，本轮**恰好新增 1 条订单** |
| 交付 | 可重跑脚本/测试；`SUBMISSION.md` 写明如何准备数据、如何运行、如何核对这两项 |

### 2.10 L2-12 自动化测试（本项目选做）

|---|---|
| 数量 | 3~5 条（JUnit） |
| 必覆盖 | ① 正常下单库存减 1 ② 库存不足 409 ③ `quantity=0` → 400 |

## 4. 商品 / 订单 / 支付依赖关系

### 4.1 实体与引用

```
products(id, title, price, stock, category, description, status, seller_name, created_at)
orders(id, order_no, product_id, product_title, quantity, unit_price, total_amount,
       buyer_name, buyer_phone, address, status, created_at, paid_at)
payments(id, payment_id, order_no, amount, method, status, paid_at, created_at)   ← L2-9 新增
```

- `orders.product_id → products.id`：下单依赖商品存在、在架、库存充足。
- `payments.order_no → orders.order_no`：支付依赖订单存在且未支付。
- 快照冗余：`orders.product_title/unit_price/total_amount` 在下单时从商品价格落库，避免商品后续改名/改价影响历史订单（题目示例结构即隐含此意图，见 §4 L0-1、§5 L1-6）。

### 4.2 状态流转

```
商品 status : (创建默认 on) ⇄ off        —— L0-2 / L0-5
商品 stock  : 初值(发布) → 下单扣减 → 0  —— L0-2 / L1-6
订单 status : created → paid            —— L1-6 / L2-9
支付 status : 落库即 paid（同步返回）       —— L2-9
```

- 库存只在**下单**时扣减；支付不改库存。
- 商品下架（`off`）不影响已生成订单，只阻止新下单。

### 4.3 开发依赖顺序（题目 DESIGN 模板点名）

```
商品(L0) → 订单(L1，依赖商品号/价格/库存) → 支付(L2-9，依赖订单号) → 并发(L2-10，依赖下单) → 测试 → 文档
```

「先做下单再做支付，因为支付依赖订单号」——这是 DESIGN.md 第 2 节最想看到的一句话。

## 5. 风险分析（事务 / 并发 / 金额 / 参数校验）

### 5.1 事务风险

| 风险 | 说明 | 应对（P02 落地） |
|---|---|---|
| 扣库存与插订单非原子 | 插入失败时库存已扣（题目硬性要求回滚） | 下单全程 `@Transactional`，`JdbcTemplate` 复用同一连接 |
| 支付三步非原子 | 幂等检查 → 插支付 → 改订单状态，拆分即产生中间态 | 支付 `@Transactional`；先原子改订单状态，再插支付记录 |
| 事务回滚时机 | 异常类型与回滚边界 | 用 `@Transactional(rollbackFor = Exception.class)`，避免受检异常吞掉回滚 |

### 5.2 并发风险（核心）

| 风险 | 说明 | 应对 |
|---|---|---|
| **超卖**（L2-10） | 「先 SELECT 再 UPDATE」存在读-改-写竞态：两个事务都读到 stock=1，都扣减成功 | 条件原子扣减：`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`，检查 `affectedRows`，为 0 即库存不足 → 409 回滚 |
| **重复支付**（L2-9 幂等） | 两个并发支付同单都通过「未支付」检查 | `payments` 表对 `order_no` 加**唯一约束**；先原子 `UPDATE orders SET status='paid', paid_at=… WHERE order_no=? AND status='created'` 检查行数，或捕获唯一键冲突 → 409 `40903` |
| 测试要真并发 | 顺序发 10 个请求测不出竞态 | L2-10 用线程池/`CountDownLatch` 并发发起，再核对结果 |
| H2 行锁 | 需确认并发下条件 UPDATE 生效 | H2 支持行级锁；测试用独立库实例，勿共享写连接 |

> 方案取舍（DESIGN 素材）：条件 `UPDATE` 的行数判断 **优于** `SELECT … FOR UPDATE`（代码更少、天然原子、无需锁等待），本项目采用前者。

### 5.3 金额风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 浮点精度 | 用 double/float 存算金额必然出分位误差（题目 §3 明示最易翻车点） | 全程 `int`/`long`（分），DB 列用整数类型 |
| 乘法溢出 | `totalAmount = unitPrice × quantity` | 定义 `price` 与 `quantity` 上限并校验，使乘积在 `long` 安全范围内（如 price ≤ 999_999_999 分、quantity ≤ 9999） |
| 客户端传价 | 篡改 `unitPrice/totalAmount` 请求字段 | 服务端忽略客户端价格，一律以 DB 价格重算 |

### 5.4 参数校验风险

| 风险 | 说明 | 应对 |
|---|---|---|
| `quantity="2"`（字符串） | 题目 §5 明示 `"2"` 必须按 400 处理，**不能被转成整数** | ⚠️ Jackson 默认把 JSON 字符串 `"2"` 强转成 int。需关标量强转（`MapperFeature.ALLOW_COERCION_OF_SCALARS=false`，Spring Boot 3 / Jackson 2.12+）或对 DTO 做原始 JSON 校验，否则该用例失分 |
| 字符串数值不只 `quantity` | 题目对「整数」校验的用词同样落在 `price`/`stock`/`productId`：`"1990"`、`"10"`、`"3"` 都应视为**类型错 → 400**，不能被强转 | 与上一条同源：**全局关标量强转**，对所有 `int`/`long` 入参（`productId`、`quantity`、`price`、`stock`、`page`、`pageSize`）统一生效，一处配置覆盖全部 |
| 缺字段/类型错/超范围/枚举非法 | 码表「40001」 | 全局参数校验 + 统一异常处理映射到 400 `40001` |
| 路径变量类型不匹配 | `GET /api/products/abc` 走 Spring 类型转换报 400 裸体 | 全局异常处理兜住，返回统一结构 + 40001 |
| 500 泄漏堆栈 | 码表「50000 不返回堆栈」 | 全局异常处理吞掉堆栈，只回 `message` |
| 未匹配路由/非法 JSON | 题目码表未定义（前端 mock 用 40400/40002，**非后端规范**） | 自定：非法 JSON → 400 `40001`；未匹配路由返回统一结构（Spring 默认 404 无 envelope，建议自定义兜底） |

## 6. 最小可行架构与分阶段开发计划

### 6.1 最小可行架构（MVP）

```
backend/
├── pom.xml                      # Spring Boot 3.x + Web + JDBC + H2 + spring-boot-starter-test
├── schema.sql                   # 手写 DDL（题目硬性要求放这里；通过 spring.sql.init 加载）
├── data.sql                     # 可选：初始商品/订单种子数据（评审启动即有演示数据）
└── src/main/java/…/marketplace/
    ├── controller/              # REST 入口（商品/订单/支付/健康检查）
    ├── service/                 # 业务逻辑 + @Transactional 事务边界
    ├── dao/                     # JdbcTemplate 封装 SQL
    ├── model/                   # 实体 + 请求/响应 DTO + 统一 Result<T>{code,message,data}
    ├── config/                  # Jackson 配置（snake_case、关闭标量强转）、SQL 初始化配置
    └── exception/               # 业务异常 + @RestControllerAdvice 统一映射到码表
```

关键决策（均需写进 DESIGN.md）：

- **持久层 JdbcTemplate**（用户已定）：不下 ORM，SQL 可控、便于写条件 `UPDATE` 和展示索引思路。
- **H2 内存模式** `jdbc:h2:mem:market` + `schema.sql`/`data.sql` 自动执行：评审每次启动从一致初始数据开始、无 `*.db` 提交残留（自检清单明确禁止提交 `*.db`）。
- **统一响应**：`Result<T>` + `@RestControllerAdvice` 把业务异常/校验异常/未匹配路由统一收敛到 `{code,message,data}`，避免每个 Controller 手写。
- **JSON↔DB 命名映射**：DB 用 snake_case（题目 schema 示例），JSON 用 camelCase（题目示例 `sellerName/orderNo/unitPrice/totalAmount/buyerPhone/paidAt`），统一用 Jackson `@JsonNaming(SnakeCaseStrategy.class)` 或显式字段映射，**避免每处手写**。
- **`schema.sql` 位置细节**：题目目录示意把 `schema.sql` 放 `backend/` 根，但 Spring Boot 默认从 classpath 加载。方案二选一：① 放 `src/main/resources` 并同步保留根目录副本；② 配置 `spring.sql.init.schema-locations=file:./schema.sql`（`mvn spring-boot:run`/`mvn test` 均以 `backend/` 为工作目录，可行）。**P02 落地时定并验证**。
- 支付表唯一约束：`payments(order_no UNIQUE)`，幂等与并发双保险。
