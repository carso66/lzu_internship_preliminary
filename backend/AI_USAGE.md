> 开发分布在多个会话中，部分历史我无法逐条调出，所以下面只写有依据的内容：
> 精简提示词一律标注为「摘要」，不是原始逐字记录；具体某次调用的模型归属若无法确认，明确写「待核对」，

## 2. 模型选型

核心原则是**按任务难度分档**，强推理的活给 Pro 级，机械的活给 Flash 级；并额外引入一个「换模型独立审查」的动作。

| 我用它做什么 | 用的模型 | 为什么选这个 |
|---|---|---|
| 订单事务、条件 UPDATE 原子扣库存、金额精度、并发推理、建表与真实联调、集成测试 | `DeepSeek V4 Pro` | 这类活需要一次想清楚因果与边界，Flash 会漏；事务和并发是整个项目出错面最大、也最难靠测试兜住的地方 |
| 工程初始化、常规 CRUD 实现、定向小修正、补测试、DESIGN 整理 | `Qwen3.8 Flash` | Flash 能满足常规任务的需求，本项目中实际平均单次调用成本较低（见第 5 节），适合频繁调用 |
| 对已完成项目做只读、不告知已知 Bug 的独立代码审查 | `GLM 5.3` | 换一个模型、开新会话、从零看同一套代码，避免和「写代码的模型」同源产生盲区；审查类任务值得用一次较强模型 |

本项目主要使用企业平台提供的三款模型完成开发与验证，同时使用 ChatGPT 辅助任务规划、提示词设计、代码审查及分析，使用 Codex 辅助独立冷启动验收、文档整理和 Git 工程交付。

最后阶段（文档成稿与提交准备），`Qwen3.8 Flash` 还承担了提交前文档核对（三份文档与源码、Git 记录的一致性检查）、官方提交规则与 AI 使用条款核实，以及依据独立审查结论执行的定向文档修正。这一阶段在恢复使用企业 AI 后开展，相关调用计入第 5 节最终统计。

两点如实说明：

- 我**没有**全程只用一个模型，但分工不是一开始就想清楚的。早期工程初始化阶段没分档，让 AI 一把抓，结果它重复解压 Maven、还改了用户级 Maven 镜像配置（见第 4、5 节）。后来才固定成上面这张表。
- 上面「用的模型」是主流用法，个别调用的具体归属我现在无法逐条核对，**以平台记录为准，存疑处标注待核对**，不按任务名称倒推猜测。

## 3. 挑 4 个场景写下来

### 场景 1（成功）：订单模块与事务设计

- **我想干什么**：实现 `POST /api/orders`，重点是「扣库存和插订单必须在同一个数据库事务里」，并且不能靠「先查库存、再无条件更新」这种会丢更新的写法。
- **用的模型 / 为什么选它**：`DeepSeek V4 Pro`。事务边界、原子扣库存、金额精度是强推理活，且是 L1 核心区分点，值得用 Pro。
- **我怎么问的**（摘要，非逐字）："实现下单接口：服务端按数据库价格用整数（分）算价、请求体不接受客户端传价；扣库存用带 `stock >= ?` 条件的 UPDATE，和订单插入放在同一个 `@Transactional` 事务内；明确不要用『先 SELECT 判断、再无条件 UPDATE』的写法。"
- **它给了什么**：事务内先查商品（不存在→404、下架→40902）、服务端 `Math.multiplyExact` 算价、带 `WHERE id=? AND status='on' AND stock>=?` 的条件 UPDATE 扣库存、占位订单号先插再回填的实现方案。
- **我改了吗、为什么改**：核心事务和条件 UPDATE 的方案直接采纳。但我没有止步于「代码写完」，而是要求用真实 H2 数据库、事务故障注入和并发 HTTP 请求去验证它（这部分验证设计见 DESIGN 第 9 节，代码由企业 AI 辅助、方案和验收由我定）。
- **怎么确认改对了**：三件事各自独立通过——`OrderIntegrationTest` 用 `TestRestTemplate` 打真实 HTTP 并断言库存/金额/快照落库；`OrderRollbackIntegrationTest` 用 `@MockitoSpyBean` 只把「插订单」桩成抛异常，验证真实事务回滚（响应 500、库存恢复、零残留订单）；`OrderConcurrencyTest` 库存=1 抢 10 单，每轮恰好 1 成功 9 库存不足、最终库存 0、新增 1 条。全量 95 项测试通过。
- **结论**：直接用，但通过真实联调、故障注入和并发把它「坐实」了，而不是只看代码像不像对。

### 场景 2（失败）：商品分页 `LIMIT ? OFFSET ?` 绑定顺序写反

- **我想干什么**：商品列表的分页查询。
- **用的模型 / 为什么选它**：发现问题的不是写代码的模型，而是**换 ChatGPT 做源码审查**；修正交给企业 AI。同一个「写的人」很难自己看出顺序类笔误，换一个从审查视角看的模型更有效。
- **我怎么问的**（摘要，非逐字）：把 `JdbcProductRepository.findPage` 的 SQL 和参数绑定代码贴给 ChatGPT，请它核对「占位符出现的顺序」和「绑定参数的顺序」是否一致。
- **它给了什么**：指出 SQL 写的是 `LIMIT ? OFFSET ?`，JDBC 按出现顺序绑定，第 1 个 `?` 应是每页条数、第 2 个是偏移量，代码却按 (offset, limit) 传——反了。
- **我改了吗、为什么改**：让企业 AI 修正绑定顺序；并**新增 `JdbcProductRepositoryTest`**，直接断言最终传给 JdbcTemplate 的 SQL 文本和绑定参数顺序。当时的 46 项测试全是 Mock 层，不检查绑定参数，所以全绿也拦不住这个错。
- **怎么确认改对了**：新增测试后累计 53 项通过；建表完成后用真实 H2 接口联调复核分页行为，正常。
- **结论**：改对了。教训是 Mock 测试验的是「我以为我会怎么调」，不是「实际传给 JDBC 的是什么」，顺序敏感的调用要么断言到参数层、要么落到真实库验。

### 场景 3（定向修正）：订单号回填没检查影响行数

- **我想干什么**：订单模块初次实现后，做一轮健壮性复查。
- **用的模型 / 为什么选它**：`ChatGPT` 辅助审查 + 企业 AI 做最小范围修正。这个点很细，需要「审查者」视角，且修正必须小，不能顺手重构。
- **我怎么问的**（摘要，非逐字）：请 ChatGPT 审查订单号回填这段——`updateOrderNo` 的返回值（影响行数）有没有被检查，异常情况下会不会返回一个和库内不一致的订单号。
- **它给了什么**：指出影响行数没有被检查，回填 UPDATE 若影响 0 行或多行，代码仍照常返回，可能给出与数据库不一致的订单号。
- **我改了吗、为什么改**：要求企业 AI **最小范围**修正——更新行数不等于 1 时抛运行时异常（让事务回滚），并新增对应测试。没有借机扩大改动。
- **怎么确认改对了**：新增测试后累计 90 项通过，新增单元测试验证订单号回填影响 0 行时会抛出异常。真实 H2 回滚测试的故障注入点为订单插入，回填失败尚未单独进行集成验证。
- **结论**：改了之后用，且刻意压住了改动范围。

### 场景 4：我用 AI 做验证的一次（独立跨模型审查）

- **我想干什么**：换一个模型、开新会话，让 `GLM 5.3` 用高思考强度对**已完成的项目**做只读审查，检查七个接口、SQL、事务、并发、金额、参数校验和测试覆盖，按严重程度给证据和建议。**不提前告诉它此前已经发现的 Bug，也不许它改代码。**
- **它给了什么**：没有发现新的代码级严重缺陷，但指出几处真实风险——真实 SQL 未验证、真实事务回滚缺乏覆盖、H2 多上下文重复初始化。
- **我验证后确认它对不对**：这些风险基本属实，但**我没有照单全收**。例如它建议用 `continue-on-error` 忽略建表重复初始化错误，我没有采纳（那样会把真错误一起吞掉），改用 `CREATE ... IF NOT EXISTS` 的幂等写法从根上解决；「真实 SQL 未验证」用独立测试库 `jdbc:h2:mem:itest` + 加载同一份 `schema.sql` 的真实集成测试解决；「事务回滚缺覆盖」用故障注入测试补上。它的建议里，验证得对的采纳、验证得不合适的换方案。
- **结论**：这次调用不是「让它写」，而是「让它查」；它没帮我写一行代码，但让我把验证面补齐了，而且我学会了否掉它的建议。

**追加：GLM 5.3 最终交付审查（文档成稿后）**。在提交前又用 `GLM 5.3` 开独立只读会话做最终审查。**没有发现需要修改核心业务代码的问题**，但指出了几处文档准确性与可复现性的真实缺陷，典型两条：
① SUBMISSION.md 的接口示例执行顺序矛盾——上下架示例把商品设为 `off` 后，紧接着的下单示例却展示 201 成功（按该顺序照抄实际会得到 409 + `40902`），已补「下单前重新上架」步骤使示例可按顺序执行；
② 并发测试数据准备的描述与源码不符——文档写「每轮开始前清库」，实际是 `@BeforeEach` 只在测试方法开始前清空一次，随后 3 轮各自插入独立库存=1 的商品并按其 ID 核对（测试代码本身正确，未改动）。
同轮还采纳了示例数据改 ASCII（规避 Windows 终端 GBK 编码问题）、未实测环境的表述收口等修正。修正只落在 SUBMISSION.md / DESIGN.md 文档层面，业务代码、测试代码与 `schema.sql` 未动。此次审查未产生新的测试结果。两轮审查的调用及费用计入第 5 节 `glm-5.3` 的最终统计。

## 4. 一次被 AI 带偏的经历

- **它给了什么**：公共异常处理阶段，AI 声称「Jackson 默认拒绝未知 JSON 字段」，也就是请求体里多带字段会被当作参数错误拒绝。
- **当时为什么信了**：这个说法听起来像「严格校验」的自然延伸，符合我当时对「严格反序列化」的想象；而且它说得很有把握，我差点直接照它的话去加配置。
- **我怎么发现的**：我没有直接改代码，而是**先要求补一条测试**验证。`unknownJsonFieldIsIgnoredByDefault` 测试实际通过，证明当前 Spring Boot 配置默认是**忽略**未知字段的——和 AI 说的相反。经我质疑，AI 承认此前说法有误。同一轮还发现两个真问题：未处理的「HTTP 方法不支持」异常、Spring 方法级参数校验异常会错误落进 500 兜底，修正后累计 24 项测试全部通过。
- **最后怎么修的**：对「未知字段」没有改任何代码（默认行为本就符合要求），只修了那两个真异常路径。
- **之后我改了做法吗**：改了。之后凡是「它说得很确定、但会改变行为」的结论，我都先检查、先复现（写测试或跑命令），再决定改不改；**不把模型的自信程度当成结论的正确性**。这条规则在后面几次审查里都起了作用。

## 5. 成本

| 问题 | 我的回答 |
|---|---|
| 有没有「一次把整个项目/整个文件塞进去」？为什么？ | 没有把整个项目或整个文件一次塞进去。但早期吃过「范围太大」的亏：工程初始化时让 AI 一把抓，它重复解压 Maven、还改了用户级 Maven 镜像配置。后来在提示词里写死约束——复用已有环境、只允许改指定文件、禁止无关重构、禁止自动 Git 提交、要求实际执行的测试——并改成按模块切（技术设计/公共/商品/订单/联调/测试/文档），相同模块的定向修正沿用会话，独立审查和新任务另开新会话。 |
| 有没有同一个报错连续问了很多次？后来怎么改的？ | 没有把同一个报错原样反复丢给同一个模型。早期真正的问题不是「反复问」，而是「没约束操作范围」导致它重复做同一件事（重复解压 Maven）。最接近「反复问」的是分页绑定顺序这类**静默错误**：同层 Mock 测试全绿，反复让写代码的模型自查也查不出，后来把审查范围缩小到 SQL 占位符与绑定参数的顺序，才定位到问题（见第 3 节场景 2）。环境类问题（Windows GBK 编码、推送 TLS 报错）不反复问 AI，作为环境插曲自己处理。 |
| 如果额度只有 10 元，你会怎么调整？ | **（假设性预算方案，区别于上面的实际做法）** ① 模型分工收紧：`DeepSeek V4 Pro` 只留给订单事务、并发、表设计这几个关键节点，其余一律 `Qwen3.8 Flash`；独立跨模型审查（一次较强模型调用）可能砍掉，改由我自己读 + Flash 查边界。② 压输入量：不贴整文件，只贴相关几十行，减少重复贴，把多个小问题合并成一次结构化提问。③ 少做验证性重复调用：先自己读报错和代码，判断「值得问」再问。代价是「用 AI 做验证」这类动作变少，需要我本人承担更多自查——核心链路和必要测试在 10 元内仍能完成，但验证的厚度会下降。 |

### 最终费用统计

项目的企业 AI 任务已全部结束。本节的 API 调用次数和费用仅统计企业 AI 平台上的 Qwen3.8 Flash、DeepSeek V4 Pro 和 GLM 5.3。本人于 2026 年 11 月 24 日晚正式提交前查看该平台的 My Call Logs 和 Wallet 页面，取得最终统计数据。

My Call Logs 显示总请求数为 284。恢复使用企业 AI 后只使用了 Qwen3.8 Flash，从总数中减去此前已确认的 DeepSeek V4 Pro 92 次和 GLM 5.3 39 次，得到 Qwen3.8 Flash 的 153 次（284 − 92 − 39）。

| 模型 | API 调用次数 | 调用次数占比 | 分项显示费用（元） | 费用占比 | 平均单次调用成本（元/次） |
|---|---:|---:|---:|---:|---:|
| `qwen3.8-flash` | 153 | 53.87% | 3.2238 | 14.99% | 0.0211 |
| `deepseek-v4-pro` | 92 | 32.39% | 12.0601 | 56.07% | 0.1311 |
| `glm-5.3` | 39 | 13.73% | 6.2236 | 28.94% | 0.1596 |
| **合计** | **284** | **100.00%** | **21.5075** | **100.00%** | **0.0757** |

调用次数占比以 284 次为分母，费用占比以分项显示费用合计 21.5075 元为分母，平均单次调用成本按各行费用除以调用次数计算。调用占比保留两位小数，三项显示值相加为 99.99%，合计行按总次数计算为 100.00%。企业平台的 API 调用记录与人工发送提示词的次数采用不同统计口径。

初始额度为 40 元。Wallet 显示实际余额为 18.492448 元，总消费约为 21.51 元。按初始额度减去余额反推的消费为 21.507552 元，比分项显示费用合计高 0.000052 元，差异来自显示精度。按钱包余额反推的消费计算，预算使用率约为 53.77%。

Qwen 承担初始化、常规开发和定向修正等任务，调用占比为 53.87%，费用占比为 14.99%。DeepSeek 负责订单事务、联调、并发验证等复杂业务开发和测试，费用占比最高，为 56.07%。GLM 用于两轮独立只读审查，费用占比为 28.94%。平均单次费用反映本项目的实际调用，受输入输出 Token 数、上下文缓存命中情况和任务构成影响。比较模型定价需要按各自的计费规则核对。

最后阶段的提交前文档核对及定向修正新增 12 次 Qwen API 调用。按 Qwen 的两次分项显示费用相减（3.2238 − 2.7787），新增费用约 0.4451 元。若直接比较两次总额显示值，差额是 0.4452 元，差出的 0.0001 元来自恢复使用企业 AI 前那次快照的总额与分项加总的显示差异。
