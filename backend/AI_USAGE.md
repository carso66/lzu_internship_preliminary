# AI 使用说明

## 1. 实际使用情况

我此前没有独立搭过 Java 后端环境。这次 AI 参与了环境排查、架构解释、实现代码、文件写入和测试，也帮助整理了这份文档。我没有把这些代码都写成自己独立完成的。

我的做法逐渐变成：先把需求和约束说清楚，让一个模型负责设计，再让另一个模型执行确定的方案。我负责把任务拆到能检查的程度，追问不理解的规则，决定哪些建议采用、哪些暂缓，以及每一轮允许修改的范围。

| 项目 | 记录 |
|---|---|
| 使用模型 | DeepSeek 4 Pro、DeepSeek 4.1 Flash |
| 角色分工 | 4 Pro 作为“架构师”，4.1 Flash 作为“执行者” |
| 调用次数 | 待按调用记录核对，不用聊天轮数代替 API 调用次数。 |
| 额度与花费 | 额度 40 元，实际消费待核对账单。 |
| 主要环节 | 架构设计、L0 接口实现、错误分析、边界检查和验证。 |

## 2. 为什么这样分工，我负责什么

我把 DeepSeek 4 Pro 定位为架构师：先解释模块职责、数据流、校验顺序和方案取舍，不直接展开全部代码。把 DeepSeek 4.1 Flash 定位为执行者：根据确认后的设计，补 DTO、接口方法和 SQL。这样安排是为了把需要讨论的设计问题和重复实现分开，不是因为我做过两个模型的性能排名。

我没有把“架构师说可以”当作最后结论。设计仍要回到题目和现有代码上：题目有没有要求这个限制？现有方法能不能复用？改动会不会覆盖已经测过的行为？这些问题不说明白，我就继续追问，而不是直接进入下一步。

我在项目中的主要作用有三点：

1. **确定顺序和范围。** 先跑环境、建表，再做发布和查询；每轮只推进一个接口。明确要求保留已有方法，避免模型为了补一个功能重写整份文件。
2. **检查规则有没有依据。** 对建表脚本中的 DROP、分页上限和溢出提示提出疑问。不能因为模型给出一个数值或一句“推荐”就把它当成需求。
3. **要求用运行结果说明完成情况。** 编译通过后还要看 HTTP 状态、业务码和数据是否变化；修复新问题时，也要验证旧接口。测试由 AI 辅助执行的部分如实记录，不写成全部由我手工完成。

这种分工也有代价：两个对话需要交接当前目录、已有方法和确定的规则。我的控制办法是把交接缩小到本轮接口，明确哪些文件可以加方法、哪些已经完成不要动。具体节省了多少费用还没有统计，不作量化结论。

## 3. 四个具体场景

### 场景一：先设计整体，再逐项实现

我一开始分不清整体架构和 L0-1 建表方案的关系，也不清楚 H2 是什么。我要求设计模型先不写代码，说明整个项目的分层和流程，再把 L0-1 单独拆开。

提问的核心是：“根据完整任务设计整体架构和流程，不写代码；然后说明这一阶段要改哪些文件。”我还指出题目要求 schema.sql 放在 backend 根目录，不能只按框架习惯放进 resources。

最后采用 Controller → Service → Repository 的结构，建表脚本用显式路径加载。后续商品发布、列表、详情确实复用了同一套实体、响应结构和查询方法，没有每个接口另起一套。

结果：调整文件位置和实施范围后采用。

### 场景二：发布商品返回 500

我把 POST 的 500 响应交给 AI，排查时进一步看服务端异常，而不是只根据客户端“服务出错”猜原因。定位到 H2 的主键回填可能带回多个生成列，原来的 getKey() 按单值读取会失败。

采用的修复很小：prepareStatement 明确指定 new String[]{"id"}。没有因为一次报错就重写整个 Repository。代码写入后，在独立端口发起实际发布请求，验证到 201 和商品 ID。

结果：修复后采用。我的收获是把“编译成功”“服务启动”“接口正确”看作三件不同的事。

### 场景三：没有接受新增十万页上限

超大页码 2147483648 被返回“page 必须是大于等于 1 的整数”。我追问这个提示为什么不对，又追问 MAX_PAGE=100000 的依据。

讨论后明确了两件事：输入本身确实大于 1；失败发生在 Integer.parseInt 的范围限制。十万页不是题目规则，也没有测量结果支持这个具体数字。因此最后只改 catch 中的提示为“page 数值超出范围”，保留原来的分页逻辑，没有新增业务上限。

结果：没有采用加上限的建议，只采用报错文案修复。这里我更在意改动是否对应真正原因，而不只是让某个测试停止报错。

### 场景四：让 AI 实际验证，而不是再次口头认可

L0-5 写入后，我明确要求“你测一下，我也再测”。随后通过 AI 辅助在独立的 18085 端口运行实例，进行了 23 次 HTTP 检查，覆盖上下架、重复设置、空白与非法状态、非法 ID、溢出、商品不存在，以及发布、详情和列表回归。检查均通过。

异常处理调整后，又在 18086 端口做了 18 次检查。未知路径返回 40400，用错方法返回 40500，商品不存在仍返回 40401；非法 JSON 和业务参数错误也分别检查，正常发布、详情、列表、上下架未受影响。测试期间没有预期错误被记录为 ERROR。

这些是 AI 辅助执行的临时 HTTP 检查，不是我手工逐条执行的记录，也不是仓库中的 JUnit 套件。类型绑定异常和未知异常兜底没有通过 HTTP 直接触发，不能把它们写成已经实测通过。

结果：以实际状态码和响应体判断，不以 AI 的“应该能跑”作为验收证据。

## 4. 一次被 AI 建议带偏的经历

建表方案曾带有 DROP TABLE IF EXISTS。我起初把它理解为正常初始化步骤，后来想到：如果每次执行都先删表，刚插入的数据怎么办？于是直接追问，没有照着一路做下去。

当前脚本没有 DROP TABLE。与此同时，我也弄清了另一层原因：项目用的是 H2 内存库，即使不删表，关闭应用进程后数据也不会保留。只删除 DROP 并不能实现持久化。

之后我会先问“这条语句会改变什么、什么时候执行、重复执行会怎样”。AI 给出的启动脚本也一样，不能因为它写了“清端口”就直接结束所有占用该端口的程序。

## 5. 成本和上下文

| 问题 | 我的做法与反思 |
|---|---|
| 是否一次贴整个项目 | 是的，刚开始会将整个项目的readme.md交给整个模型来进行分析，这样子能让我快速掌握这个项目，了解项目的需求；后面就没有了，都是一点点来进行完善。 |
| 是否重复追问同一问题 | 有。初期对目录、启动、SQL 执行位置和分页的理解不够，来回确认较多。后来逐渐改成给当前目录、代码位置、完整报错及期望结果。 |
| 怎样减少不必要的生成 | 已有方法不让模型反复整份重写；先定接口行为，再生成必要方法和 import。这样不仅省上下文，也减少覆盖已有逻辑的风险。 |
| 如果只有 10 元 | 优先把 L0 跑通；常见命令和重复 DTO 用已有模板，集中提问一个接口的规则与边界，把更贵的调用留给难以定位的错误和事务设计。先收集运行证据，再问原因。 |
