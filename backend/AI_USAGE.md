## 2. 模型选型（6 分，重点）

这次开发我主要按照任务类型来选模型。涉及数据库、事务和并发的问题交给 Pro 分析，常规接口和测试代码用 Flash 实现，完成一个阶段后再用 GLM 做独立审查。

| 模型 | 主要用途 | 选择理由 |
|---|---|---|
| DeepSeek-V4-Pro | 数据库表结构、下单事务、库存并发和支付幂等设计 | 这些问题需要考虑多个请求之间的执行顺序，以及发生异常时数据库的状态。相比直接生成代码，我更需要它先比较方案，解释各自的优缺点。 |
| DeepSeek-V4.1-Flash | 商品 CRUD、Controller、DTO、Repository、测试用例和文档 | 题目已经规定了大部分字段、接口和错误码，常规实现不需要太复杂的推理，用 Flash 就能满足需求，也能节省费用。 |
| GLM-5.3 | P08 商品模块验收、P13 全量代码审查 | 我希望换一个没有参与前期实现的模型，重新从题目要求出发检查代码，避免之前的设计假设影响审查。 |

设计方案并不是模型给什么我就用什么。例如 Pro 最初推荐条件原子 UPDATE，我结合题目的错误码要求和 H2 的实际锁行为，最后改用了悲观行锁，具体理由见 `DESIGN.md` 第 5 节。

两次审查都重新开启了会话，没有直接沿用之前的设计和开发对话。这会增加一些重复提供上下文的开销，但也让审查更容易发现之前遗漏的问题，例如文档没有及时更新、Jackson 对字符串字段的类型转换等。

## 3. 挑 4 个场景写下来（5 分）

### 场景 1：商品模块开发（成功案例）

**对应需求：** L0-2 ～ L0-5（`backend/README.md` 第 4 节）  
**使用模型：** DeepSeek-V4.1-Flash

**我怎么问的：** 当时只在做商品模块，所以给模型提供了 `schema.sql` 和题目中 L0 的要求，没有把订单和支付也加进来。主要要求它实现发布、列表、详情和上下架，参数使用 `@Valid` 校验，错误按第 3 节码表返回，列表支持三个筛选条件同时生效以及分页。

**AI 给出的实现及我的处理：** 模型生成了 Controller、Service、Repository 和 DTO，整体结构可以直接沿用。不过第一版对 `pageSize` 超过 50 的情况使用了 `Math.min(50, pageSize)`，也就是直接把参数限制在 50，而不是返回错误。

我之前在 `P01-需求分析.md` 第 2.2 节已经记录过这个差异：前端 mock 可以截断，但后端题目要求超范围返回 40001。因此我改成直接抛出 `BusinessException(BAD_REQUEST)`，并补了 `ProductListTest.pageSizeOverMax` 和 `pageSizeZero` 两个测试。

**验证结果：**

```bash
./mvnw test -Dtest=ProductListTest,ProductCreateTest,ProductDetailAndStatusTest
```

三个测试类分别通过 36、30、21 个用例，共 87 个，之后运行全量 `mvn test` 也通过了。

对应 Commit：`bf0dbfc feat:实现商品发布接口`、`a134588 feat:实现商品列表和商品详情与上下架接口，并修复已知bug`。

### 场景 2：模拟支付（失败案例）

**对应需求：** L2-9（`backend/README.md` 第 6 节）  
**使用模型：** DeepSeek-V4.1-Flash

**我怎么问的：** 支付的整体方案在 P11 阶段由 Pro 辅助设计。这次给 Flash 提供 `orders` 表结构和 L2-9 的原文，让它实现模拟支付，要求重复支付返回 409，并返回 `paymentId/orderNo/amount/status/paidAt`。

**遇到的问题：** 接口虽然能运行，但支付金额直接取自 `request.amount`。另外，`payments` 表没有给 `order_no` 加唯一约束，仅通过先查询、再插入的方式判断是否重复支付。

题目在 L1-6 中明确要求订单金额由服务端计算。支付也应该遵循同样的原则，否则客户端就可以修改实际支付金额。第二个问题在并发时尤其明显，两个请求可能同时通过重复支付检查。

**我做的修改：**

- 支付金额改为锁内读取的 `order.totalAmount()`，请求 DTO 不再定义 `amount`。当前 Jackson 配置会忽略未知字段，即使客户端额外传入金额，也不会影响结算结果。
- 给 `payments.order_no` 增加 `UNIQUE` 约束，配合订单锁防止重复支付。

**验证方式：** `PaymentTest.clientAmountIgnored` 传入 `amount:1`，断言实际支付金额仍为 5970；`PaymentTest.duplicatePayment` 检查重复支付；`ConcurrentPaymentTest` 对同一订单发起 10 个并发支付请求，重复 5 轮，每轮恰好一个 HTTP 200；`SchemaConstraintTest.duplicatePaymentForSameOrderRejected` 直接检查数据库唯一约束。

对应 Commit：`21b2624 feat:实现 L2-9 模拟支付`。

### 场景 3：调整下单事务方案（自行修改 AI 方案）

**对应需求：** L1-6、L2-10  
**使用模型：** DeepSeek-V4-Pro

**我怎么问的：** 让模型从状态与价格一致性、事务原子性、并发超卖、错误区分、失败回滚、H2 兼容性和实现复杂度七个方面，比较条件原子 UPDATE 和悲观行锁。除了给出推荐方案，我还要求它用两个并发事务的执行时序解释原因，并说明 `@Transactional` 可能失效的情况。

**AI 推荐的方案：** 使用 `UPDATE ... WHERE status='on' AND stock>=?` 原子扣减库存。它认为这样可以少一次 SELECT，同时避免依赖 H2 的 `FOR UPDATE` 锁语义。

**我的最终选择：** 我最后采用了悲观行锁，主要有三个原因：

1. 题目对错误判断有明确顺序：商品不存在返回 404、下架返回 40902、库存不足返回 40901。条件 UPDATE 失败后还需要回查商品才能区分这些情况。
2. 行锁方案可以在同一个事务里依次完成商品查询、状态校验、库存扣减和订单写入，代码逻辑与题目的业务流程更接近，也比较容易维护。
3. H2 的锁行为可以通过测试验证。我在 H2 2.3 上实测了 `FOR UPDATE`，确认并发请求能够正常串行化处理。

不过模型对 Spring 事务失效的提醒我保留了，包括类内自调用、捕获异常后不继续抛出，以及受检异常默认不回滚等问题。因此下单步骤统一放在 Service 的 public `create()` 方法内，业务失败抛出继承自 `RuntimeException` 的 `BusinessException`，不在事务内部吞掉异常。

**验证方式：** `OrderRollbackTest` 验证扣减后的库存能够回滚，`ConcurrentOrderTest` 连续进行 5 轮并发测试，均未发生超卖。方案的详细比较见 `DESIGN.md` 第 5 节。

对应 Commit：`0c3abf6 feat:悲观行锁方案实现 L1-6 下单接口`。

### 场景 4：使用 AI 做独立验证

**使用模型：** GLM-5.3

我在商品模块完成后和核心业务全部完成后分别做了一次审查。两次都开启新会话，以官方题目和当前代码为依据，没有把之前的 AI 设计结论直接提供给审查模型。

#### 4.1 L0 独立验收（P08）

当时商品模块的测试已经通过，但测试本身也是按照我对题目的理解编写的。如果理解有偏差，仅靠已有测试不一定能发现。因此我让 GLM 重新对照 L0 的原始要求检查实现。

提示词的主要内容是：

> 根据 backend/README.md 的 L0 要求进行只读审查，检查数据库约束、商品字段和类型、组合筛选、分页 total、详情和上下架异常处理、统一响应结构，以及 SQL、整数转换和分页溢出风险。不要仅根据代码判断通过，给出实际验证结果。

这次审查运行了 `mvn test`（当时共 138 个用例），还启动服务通过 curl 验证了约 40 个场景。其中有几个边界是我之前没有专门测试过的：

- `page=2147483647&pageSize=50`：由于 `offset()` 使用 long 计算，没有发生整数溢出。
- 400、404、405、415 错误响应均保留了 `"data":null`。
- `keyword=%` 只匹配标题中包含 `%` 的商品，不会将 `%` 当作通配符查询全表。

审查还提出了三个问题：

| 发现的问题 | 我的处理 |
|---|---|
| `SUBMISSION.md` 仍是空模板 | 纳入后续文档整理任务。 |
| PATCH 缺少请求体时提示为“请求体字段类型不正确” | 提示语不够准确，但 HTTP 状态码和业务码正确，暂时保留。 |
| COUNT 和 SELECT 分开执行，并发写入时可能出现短暂不一致 | 当前是单机内存库，商品列表允许弱一致性，暂不额外引入快照读，并在设计文档中说明限制。 |

这轮没有修改业务代码，主要是确认边界行为并补充文档待办。

#### 4.2 L1/L2 独立复审（P13）

第二轮审查主要关注事务失效、数据不一致、超卖、重复支付，以及金额溢出、非法 JSON 类型和分页错误。我要求模型给出具体文件位置、违反的要求、触发条件、影响、复现方式和最小修复建议。

这次运行了全量 `mvn test`（231 个用例），并启动服务执行 curl 测试。模型还独立发起了 10 个并发下单请求，库存初始为 1，最终结果为 1 个 HTTP 201、9 个 HTTP 409，库存为 0，与我的并发测试一致。

它发现的问题主要集中在文档：`DESIGN.md` 仍是模板、`SUBMISSION.md` 没有更新 L2-9、`AI_USAGE.md` 尚未填完。另外，它发现 Jackson 会把字符串字段收到的数字转换为字符串，例如 `"buyerName":123` 会被接受为 `"123"`。

我用 curl 重新验证了相关接口，确认这个转换确实存在。但它不影响金额和库存计算，题目也没有明确要求字符串字段拒绝数字，因此我选择保留当前行为，并记录这个边界。

## 4. 一次被 AI 带偏的经历（必答）

**使用模型：** DeepSeek-V4.1-Flash

这个问题出现在配置 Jackson 的时候。当时我想把 `LocalDateTime` 统一输出为毫秒精度的 ISO 时间字符串，模型建议手工使用 `new Jackson2ObjectMapperBuilder().build()` 创建 mapper。第一次试的时候时间格式正常，也没有报错，所以我采用了这个写法。

后来补充严格类型校验测试时，发现请求中的 `price: "1990"` 居然能通过，而我已经在配置中关闭了 `allow-coercion-of-scalars`。当时有些不理解，因为配置看起来是正确的。

我按以下顺序排查：

1. 检查 YAML 配置，确认配置项没有写错。
2. 写了一个只使用 `@RequestBody` 的临时 Controller，绕开业务代码，发现字符串数字依然能通过，因此将问题定位到反序列化环节。
3. 打印 `ObjectMapper.getDeserializationConfig()`，确认被检查的 mapper 上 `ALLOW_COERCION_OF_SCALARS` 为 false，开始怀疑 HTTP 转换器实际使用的是另一个实例。
4. 搜索项目中创建 `ObjectMapper` 的位置，最终找到之前手工调用 `build()` 的代码。这条配置路径没有继承 Spring Boot 的 `spring.jackson.*` 设置。

修复时，我在 `config/JacksonConfig.java` 中改为注册 `SimpleModule` Bean，让 Spring Boot 将其装配到已有的 `ObjectMapper` 上。`WebConfig` 也只调整已有转换器的 charset，不再创建新的 mapper。

之后补充了 `JsonStrictnessTest.ObjectMapperFeaturesApplied`，直接检查配置是否生效，并通过 `OrderCreateTest` 和 `ProductCreateTest` 从 HTTP 层验证 `"2"`、`2.5`、`2.0`、`true` 均返回 400。

这次让我意识到，框架相关的代码不能只看能否运行，还要弄清楚自动装配和实际使用的 Bean 之间的关系。后面讨论 H2 行锁时，我也是先做并发测试再决定方案。相关排查记录见 `DESIGN.md` 第 6 节和 `docs/决策与遗留问题.md`。

## 5. 成本（4 分）

本次官方平台实际花费约 37.70 元，占 40 元额度的大部分。其中 GLM-5.3 消耗约 28.76 元，两款 DeepSeek 模型合计约 8.94 元。审查阶段的消耗明显高于普通开发，这也是下次需要重点控制的部分。

### 有没有一次把整个项目或整个文件塞进去？为什么？

常规开发时没有主动这样做。例如做商品模块时，主要提供 `schema.sql` 中的 products 表和题目第 4 节，不让模型提前处理订单、支付模块。这样可以减少无关上下文，也能避免它顺手修改当前任务之外的文件。

P13 全量审查是例外，因为要检查商品、订单、支付之间的事务和数据一致性，审查时需要读取更完整的项目代码，因此这部分开销比较大。

### 有没有同一个报错连续问很多次？后来怎么改的？

有，就是前面 Jackson 的严格类型问题。最开始我直接问为什么字符串数字仍能通过校验，问了几次，得到的都是不同的猜测，没有解决问题。

后来我先自己写最小 Controller、检查配置和 mapper 状态，把问题缩小到实际使用的 `ObjectMapper` 实例，再带着这些信息进行针对性排查。最后定位到了手工创建 mapper 的位置。相比反复发送同一个报错，先缩小范围再提问更有效，也能减少调用次数。

### 如果额度只有 10 元，会怎么调整？

我仍然会保留设计、实现、审查三个环节，但会缩小强模型的使用范围：Pro 只用于 L1-6 下单事务和 L2-10 库存并发；建表 SQL 和支付模块先用 Flash 生成初稿，再自己核对约束和业务逻辑；GLM 只保留一次最终审查，将 P08 和 P13 合并。

普通的代码解释、框架配置查询和简单报错优先自己查文档。审查时重点检查事务和并发等高风险逻辑，减少重复运行已经验证过的场景，尽量把有限的额度用在确实需要模型帮助的地方。
