# AI 使用说明

> 这份文档回答一个问题：**AI 在这 50 小时的开发里，是"我驾驭它"还是"它带着我走"**。
> 所有数字来自我自己的会话日志统计，不是估的；所有结论都配了我实际跑过的命令或代码位置。

---

## 1. 我用了什么工具、什么模型

| 项 | 实际情况 |
| --- | --- |
| 工具 | Kimi Code CLI（命令行 agent，能读写文件、执行 Maven/curl/脚本、跑后台任务） |
| 模型 | `deepseek-v4.1-flash`（经 xytoken 中转），全程**同一档** |
| 模型调用次数 | **429 次** |
| 我发出的提问轮次 | **23 轮** |
| agent 发起的工具调用 | **482 次**（读写文件、跑命令、跑测试、跑并发脚本） |
| Token 用量 | 输入约 **24.1 M**（其中 22.4 M 是缓存命中），输出约 **0.28 M** |

Token 那个数字值得解释一下：**22.4 M 里有 93% 是缓存命中**，因为 agent 每一轮都要把整个会话上下文重新读一遍。这也是我后来刻意控制上下文的动机（见第 5 节）——不是省钱，是**上下文越长、模型的注意力越散，改错文件、改错断言的次数会变多**。

## 2. 模型选型：哪类问题用哪个档，为什么

我自己定的策略是：**按"错了会不会很难查"分层**。

- **错了肉眼可见的活** → 用最快的档：CRUD 骨架、`RowMapper` 样板、curl 命令、Markdown 措辞。这类产出我 30 秒内能判断对错，模型弱一点无所谓。
- **"看起来对"和"真的对"差很远的活** → 想用强档：表设计、事务边界、并发不超卖、支付幂等、索引列顺序。这类错误不会在编译期暴露，要等并发脚本跑出来或者并发场景真的发生才现形。

**实际情况是我没能按这个策略分层。** 我的平台账号只有 flash 档权限，调 `/v1/models` 只返回 `deepseek-v4.1-flash`；尝试切到 Pro 档返回 `122014 The current credential has no entitlement`。所以全程一个模型。

**补救办法：把"模型分层"换成"验证手段分层"。**

既然模型档位拉不开，我就不靠"AI 说对了"来判定事务和并发正确，而是靠三样**它没法作假**的东西：

1. **`scripts/concurrent_order.py`**：10/20/10 三组并发实测，`Barrier` 同瞬间发包，回查库存和订单行数。AI 说"不会超卖"没有意义，脚本输出 `RESULT: NO OVERSELL` 才有意义。
2. **`mvn test` 的 5 条用例**：其中"重复支付后 `payments` 只有 1 行"是直接 `count` 库表，不是看返回值。
3. **`EXPLAIN` 前后对比**：索引有没有被用上，只看执行计划，不看解释。

结论：**模型不够，就用可验证的证据补。** 这条比"我用了哪个模型"重要得多。

## 3. 提问方式：我怎样切小问题、给多少上下文

### 3.1 一个反例

最开始我想要一份"全项目通读"，就把整个仓库丢过去问"这个项目怎么做后端"。回来的是一份 2000 字的通用建议，三分之一在讲 `frontend/` 和 `testing/` 目录——那两个目录跟我这次提交**一点关系都没有**。那次提问的产出，我一行代码都没用上。

问题不在模型，在**我一次问了太多层**：既要它理解仓库，又要它做技术选型，还要它排期。

### 3.2 一个正例

后来我把它拆成"每一步的产出都能被下一步验证"的链条，实际就是这么走的：

1. **"只读 `backend/README.md`，把 L0/L1/L2 每个条目的必填字段、校验规则、成功状态码、失败码列成表，不要写代码。"**
   → 产出：13 行的得分点对照表。我能直接对着表判断它有没有读错。
2. **"基于上面这张表，给我 `schema.sql`，H2 语法，金额用 INT 存分。"**
   → 产出：三张表的 DDL。我把它跑起来，服务能起就是对的。
3. **"只看 `schema.sql`，指出哪些字段缺约束会导致脏数据，最多说 3 条。"**
   → 产出：建议加 `CHECK (stock >= 0)`、`CHECK (status IN (...))`、`payments.order_id` 唯一。**这三条我全都采纳了**，因为它们能被一条 SQL 验证。

差别在于：**每一步的产出都能被下一步验证，也能被我否掉**。一次问完的方案，我只有"全盘接受"和"全部重来"两个选项。

### 3.3 给上下文的原则

我总结出三条，都很便宜：

- **给文件路径，不给文件全文。** agent 自己能读文件，我把 800 行代码贴进对话里只是浪费上下文，还容易让它盯着我贴的那段、忽略没贴的。
- **贴完整报错，别贴"报错了怎么办"。** 有一次我贴了 30 行 Maven 报错原文，一次命中；换成"我的构建失败了"问三次都没进展。
- **一次只问一个可验证的问题。** "帮我实现支付"是没法验的；"重复支付时 `payments` 表会不会出现两行"是能验的。

## 4. 用 AI 做验证：它帮我抓到了什么、我否掉了什么

四个真实素材，每个都按"让它做什么 → 它给了什么 → 我怎么验 → 结论"写。

### 素材 A：它建议我加 `SELECT ... FOR UPDATE`，我否掉了

我让它检查这条 SQL 有没有并发问题：

```sql
UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?
```

它说"没问题，但建议先 `SELECT ... FOR UPDATE` 把行锁住更保险"。

**我否掉了。** 理由不是感觉：`FOR UPDATE` 和条件 UPDATE 在"判断+扣减不可分割"这点上是等价的，前者多一次数据库往返，还把锁持有时间从"单条语句"拉长到"两条语句之间"。我用并发脚本实测条件 UPDATE 版本：10 并发抢 1 件 → 1 个 `201` + 9 个 `409/40901`，最终 `stock=0`、订单 1 行。

**这是"AI 的建议没错但不是我该选的"，而我能说清为什么。** 对比表写在 `DESIGN.md` 第 4.3 节。

### 素材 B：它答错了参数校验的边界，我用一条 curl 抓到

我问它：`price` 传字符串 `"1990"` 会发生什么。它答"会被 Bean Validation 拦住，返回 400"。

**它答错了。** 实际是 Jackson 在**反序列化阶段**就把字符串转成了整数——请求根本没走到 Controller，`@Valid` 压根没跑。

我怎么确认的：在 Controller 方法体第一行打日志，发那个请求，**日志一条都没有**。于是把怀疑对象从"校验注解"换到"反序列化层"。

修法是 `common/JacksonConfig.java` 把整数类型的 `String`/`Float` 输入设成 `CoercionAction.Fail`。现在实测：

```bash
curl -s -H 'Content-Type: application/json' \
  -d '{"title":"x","price":"1990","stock":5,"category":"books","sellerName":"s"}' \
  http://localhost:8080/api/products
# {"code":40001,"message":"请求体格式错误，请检查字段类型","data":null}
```

**这是它答错、我用一条 curl 抓到并修掉的。** 复盘写在 `DESIGN.md` 第 6 节。

### 素材 C：它写的测试断言是错的，我用 DDL 纠正了它

`OrderFlowTest` 第一条用例，它断言下单后 `status` 是 `"pending"`。跑测试 → 失败。

我没有直接改代码去满足断言，而是先去看**谁是对的**：

```bash
grep -n "status" backend/schema.sql
# 38:    status        VARCHAR(16)  NOT NULL DEFAULT 'created',
# 43:    CONSTRAINT ck_orders_status   CHECK (status IN ('created', 'paid'))
```

`DEFAULT 'created'`、`CHECK` 里只有 `created`/`paid`——**代码是对的，断言是错的**。改断言，`Tests run: 5, Failures: 0`。

这条的价值在于流程：**测试失败时先判断是谁错**。如果当时顺手把 `schema.sql` 的默认值改成 `pending` 去迁就断言，那才是真正的坑。

### 素材 D：它自己写的脚本有 bug，假失败了一次

并发脚本第一版把 `buyerPhone` 写死成 `13800138000`。第一次跑 10 并发，脚本报 `FAIL: orders persisted == 10`——看起来像超卖。

实际原因是：**上一次运行留下的历史订单也被算进了本次统计**（同一个手机号）。修法是每次运行生成唯一手机号：

```python
buyer_phone = "138%08d" % random.randint(0, 99999999)
```

修完再跑，五条断言全 `PASS`。

**这条我特意留着**：AI 写的验证工具本身也需要被验证。如果它给的脚本第一次就全绿，反而要更警惕——**假绿比假红危险**。

## 5. 成本：大概花了多少，哪些问题不值得问

### 5.1 量级

| 项 | 数值 |
| --- | --- |
| 提问轮次 | 23 轮（平均每轮产出约 40 行代码或一份文档小节） |
| 模型调用 | 429 次 |
| 输入 token | 约 24.1 M，其中 **22.4 M 是缓存命中** |
| 输出 token | 约 0.28 M |

**输入是输出的 85 倍**，其中绝大部分是每轮重读上下文。这带来一个反直觉的结论：**省 token 的主要手段不是"少提问"，而是"别让上下文变脏"**——一次跑偏的长对话，后面每一轮都在为它付缓存成本。

### 5.2 哪些问题不值得问

- **最不值**：让 AI 生成 `SUBMISSION.md` 的完整正文。它写得很通顺、格式也对，但**每一条命令我都要自己重跑一遍确认输出**，改的时间比我自己写还长。结论：**文档的"结构"可以让 AI 给，"命令和真实输出"必须自己贴。**
- **次不值**：让它猜环境问题。`python` 在我机器上是个坏 alias（报 `No Python at 'C:\Users\??\...'`），我一开始描述成"python 不能用"，来回两轮没结论；后来直接 `which python3` + 跑一次，10 秒解决。**环境问题先自己看一条命令的输出。**
- **最值**：把完整报错原样贴过去问"这是什么原因"。命中率明显高于描述性提问。
- **次值**：让它 review 我自己写的 SQL 并列出"可能的坑"。它给的三条约束建议我全采纳了，因为每条都能用一条 SQL 验证。

### 5.3 一个真实的时间账

我原本估 B0–B5（8 个提交、含并发脚本和测试）要 4 小时 45 分。实际约 1 小时完成，**省下的 3 个多小时全部投到了 `DESIGN.md` / `SUBMISSION.md` / `AI_USAGE.md` 上**——按题目分值，这三份文档比任何一个 L2 项都贵。

所以我对"AI 提效"的判断是：**它主要省的是打样板代码的时间，不省想清楚的时间。** 表结构、事务边界、放弃哪些得分点，这些该想的一分钟都没省。

## 6. 反思：AI 在哪里带偏了我

四个真实的带偏，按危害排序。

### 6.1 最大的坑：它用 MySQL 语法写 H2 的建表脚本

第一版 `schema.sql` 用了 `AUTO_INCREMENT`（MySQL 语法），在 H2 上直接语法错误。**这类"看起来完全正常"的方言错误是 AI 生成 SQL 最常见的坑**，因为它在语法上是合法的 SQL，只是不属于这个数据库。

现在的做法：只用 `GENERATED BY DEFAULT AS IDENTITY`，并且**每次改完 `schema.sql` 都重启一次服务确认能建表**（不是"读一遍觉得对"）。

### 6.2 它默认用框架的"便利"覆盖题目的"要求"

它建议我用 JPA + `ddl-auto=update` 自动建表，"这样不用手写 SQL"。

听起来省事，但题目**明确要求手写 `schema.sql`**；而且 `ddl-auto` 建出来的表和我手写的会打架（到底哪份生效？），讲索引时也说不清 Hibernate 生成的是什么 SQL。**我按"题目要求优先于框架便利"否掉了。**

教训：**AI 的默认目标是"让代码跑起来"，我的目标是"按题目拿到分"。这两个目标在边界上是冲突的**，冲突时要自己拍板。

### 6.3 它会把"我的环境问题"误判成"代码问题"

有一次我用 `-d` 内联中文 JSON，服务返回 `40001 参数不合法`。第一轮排查方向是"中文校验写错了"，改了校验逻辑——没用。实际原因是 **Git Bash 在中文 Windows 上按 GBK 发字节**，JSON 里的中文变成乱码。

修法是把 body 写进 UTF-8 文件再 `--data-binary @file`，或者在 `SUBMISSION.md` 里干脆用 ASCII 字段值。

教训：**报错信息里的"参数不合法"可能真的是参数不合法，只是不是我以为的那个参数。** 排查顺序应该是"先确认发出去的字节对不对"，再看业务逻辑。

### 6.4 它倾向于"多做一点"

我让它写 `OrderService`，它顺手加了参数默认值、日志、一个没被调用的 `cancel` 方法。这些在真实项目里可能是好习惯，但在这个题目里是**给评审增加阅读负担**——评审只会问"这个方法是干什么的"。

现在的规矩：**没被接口调到的方法不留在代码里**。`grep` 一遍就能确认：`OrderService` 只有 `create`，`PaymentService` 只有 `pay`。

### 6.5 总结一句

AI 在我这个项目里的角色，最准确的描述是**"一个很快但需要 review 的初级同事"**：

- 它写样板代码比我快 10 倍，这部分省下来的时间是真的；
- 它对"这个库/这个版本支持什么语法"经常错，而且错得很自信；
- 它给的方案倾向于"更通用/更保险"，而我要的是"更少代码/更好解释"；
- **所有"不会出问题"的结论，都必须用并发脚本、测试、执行计划去证伪一遍。**

这三份文档（`DESIGN.md` / `SUBMISSION.md` / 这份）里的每一个数字，都是我自己跑出来的。**这是我对"用 AI"这件事的底线。**
