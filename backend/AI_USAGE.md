### 1.1 分工说明（人工 / ChatGPT / Cline）

下面按各轮实际发生的过程区分三种角色，**不把 Cline 在终端里自行定位修复的问题算作人工完成**：

| 角色 | 实际承担的职责 |
|---|---|
| **本人（人工）** | 确定每轮目标与范围；审阅 ChatGPT 给出的方案后决定是否采纳；发现 L2-12 需要 `quantity=1` 的精确测试并要求补充；在人工验收环节逐轮确认 57/57、42/42、10 轮并发结果；执行 Git Commit 与 Push；核对数据库文件完整性；决定保留/删除 AI 的哪些建议 |
| **ChatGPT** | 负责**任务规划与验收标准**：把题目拆成阶段（建表 → L0 → L1 → L2）、给出每阶段验收清单、评审方案（如表约束松紧、并发方案是否成立）、指出提交文档中还缺什么（例如并发测试需要「同步起跑」的证据、接口示例需与真实返回对齐） |
| **Cline** | 负责**代码实现与测试执行**：在仓库里写 Controller/Service/Mapper/DTO/测试类与脚本、执行 `mvn compile` / `mvn clean test` / 真实 HTTP 脚本、读取报错并自行定位修复（Jackson 3 包名、`JsonNode` API 变更、Tomcat 异常分类、JsonPath 泛型推断导致的 `ClassCastException` 等） |

> 说明：上面 Cline 自行定位的那几类问题，均是在终端里读报错、查依赖树、写最小复现后修好的，**不应记为本人独立排查**；本人对这些修复的贡献是审阅结论、决定是否采纳，并通过验收环节确认修复有效。

**工作方式**：分阶段推进——每个阶段先做一小块（建表 → L0 → L1 → L2），每阶段结束用真实 HTTP 脚本 + `mvn clean test` 自验，再独立验收；发现问题就回到代码修，然后只提交这一阶段。五次 Git Commit 与里程碑一一对应：

| Commit | 内容 |
|---|---|
| `feat: initialize Spring Boot marketplace project` | 工程骨架 |
| `feat: configure H2 and initialize database schema` | L0-1 建表与运行配置 |
| `feat: implement and verify L0 product management APIs` | L0-2 ~ L0-5 + 57 条真实 HTTP 验收 |
| `feat: implement L1 order management and automated tests` | L1-6 ~ L1-8 + 自动化测试 |
| `test: verify concurrent orders without overselling` | L2-10 并发验证 |

## 2. 模型选型（6 分，重点）

| 我用它做什么 | 用的模型 | 为什么选这个 |
|---|---|---|
| 建表语句、约束草稿，字段与索引建议 | `GLM-5.3` | 表结构是全项目地基，错一次要连带改代码；需要一次把「下单 → 扣库存 → 事务 → 金额」的因果链走完 |
| 下单事务与并发方案设计、审查 | `GLM-5.3` | 超卖与金额精度属于「出错就要推翻重来」的问题，Flash 容易只给到「用事务就行」这种不落地的答案 |
| 复杂报错定位（Jackson 3 API、异常分类） | `GLM-5.3` | 需要结合依赖版本、异常继承链推导，属于需要推理的排查 |
| L0 增删改查接口、参数校验样板、测试用例草稿 | `DeepSeek-V4.1-Flash` | 照着已定的分层和格式填代码，属重复性工作，快且便宜 |
| 文档整理（三份 md 的结构与措辞） | `DeepSeek-V4.1-Flash` | 属于「按已有事实改写」的活，不需要长推理 |
| 起骨架、写配置、补注释 | `DeepSeek-V4.1-Flash` | 改动小、错了改一行就好 |

**分档思路**：凡是「错了要推翻重来」的（表结构、事务、并发、金额）用 `GLM-5.3`；凡是「照着已有模式填」的（CRUD、测试样板、文档整理）用 `Flash`。项目很小，没有再引入第三个模型——换模型省不了多少，反而多一份上下文切换成本。

## 3. 挑 4 个场景写下来（5 分）

### 场景 1：用 `GLM-5.3` 设计两张表（成功的）

- **我想干什么**：在写任何接口前，把 `products` / `orders` 的字段、类型、约束定下来，并顺带想清「并发扣库存」和「金额溢出」怎么处理。
- **用的模型 / 为什么选它**：`GLM-5.3`。表设计是后面所有接口的输入，属于高杠杆任务。
- **我怎么问的**（精简后）：背景是校园好物市集、商品 + 订单、金额单位为分；要求给出 H2 2.x 可执行的 DDL，金额一律整数存储，说明并发扣库存写法与金额乘法溢出的处理方式；约束：不要浮点金额、不要多余字段。
- **它给了什么**：两张表完整 DDL（含 `CHECK`、唯一约束、外键、索引），并给出「用带 `stock >= ?` 条件的 `UPDATE` 扣库存」和「用 `Math.multiplyExact` 算总额」的思路。
- **我改了吗、为什么改**：人工审阅后否掉了 4 处——① `price` 下限从「允许 0」收紧为 `> 0`（本期无赠品/优惠券，0 元商品无业务意义）；② 删掉订单状态里的 `cancelled`（本期没有取消接口，留着就是永不产生的僵尸状态）；③ 补上 `CHECK (total_amount = unit_price * quantity)` 和 `UNIQUE (order_no)`，把「服务端算价」「订单号唯一」变成库层不变量；④ 索引改为 `(buyer_phone, created_at)`，直接对上 L1-8 的查询。具体改动由 Cline 落到 `schema.sql`。
- **怎么确认改对了**：Cline 把脚本录入 `schema.sql` 并启动服务，由 `spring.sql.init` 执行；在 H2 控制台确认两表与约束都在，插入测试数据后重启确认数据仍在；后来由 `SchemaInitTests` 自动断言两表、列顺序、关键 CHECK/UQ/FK 与索引。
- **结论**：**改了之后用**。骨架可用，但约束松紧必须按本期真实范围自己再收一遍。

### 场景 2：Spring Boot 4 / Jackson 3 的编译失败（失败的，由 Cline 在终端自行定位）

- **我想干什么**：用 `RequestBodyParser` 逐字段解析 JSON，以便对 `price: 19.9`、`price: "1990"` 给出「精确到字段」的 400。
- **用的模型 / 为什么选它**：`DeepSeek-V4.1-Flash` 起草解析器（写起来机械，不需要推理）。
- **我怎么问的**（精简后）：给出请求体字段清单与「整数只接受 JSON 整数、字符串只接受 JSON 字符串」的规则，要求用 `ObjectMapper` 逐字段读取，非法类型抛业务异常并指名字段。
- **它给了什么**：使用 `com.fasterxml.jackson.databind.ObjectMapper`、`JsonNode.fieldNames()`、`catch (JsonProcessingException)` 的一段解析器代码。
- **我改了吗、为什么改**：**编译就失败**——`程序包 com.fasterxml.jackson.core 不存在`。这里**没有去问 AI**，而是由 Cline 直接执行 `mvn dependency:tree`，看到本项目实际依赖是 **`tools.jackson.core:jackson-databind:3.1.8`**（Spring Boot 4 默认 Jackson 3，包名从 `com.fasterxml` 变成 `tools.jackson`）。据此把 import 改为 `tools.jackson.databind.ObjectMapper` / `tools.jackson.core.JacksonException`；随后又撞到 `fieldNames()` / `fields()` 在 Jackson 3 已被移除，用 `javap` 查该类后改成 `propertyNames()` / `properties()`。
- **怎么确认改对了**：Cline 执行 `mvn clean compile` 通过；随后 `L02CreateProductApiTest` 的 30 条用例（含小数、字符串、布尔、科学计数 `1e400`、超长数字）全部按预期返回 `40001` 并指名字段，本人在验收时确认这一组结果。
- **结论**：**AI 的代码方向对、API 版本错**。教训是：AI 很可能按训练数据里的旧版本写 API，必须先确认依赖版本再往下写。

### 场景 3：用 AI 审查「全局异常处理会不会把客户端错误误判成 500」（用 AI 做验证）

- **我想干什么**：真实 HTTP 验收时发现，把未 URL 编码的 GBK 字节塞进查询串，接口返回了 **500 / 50000**，我认为这是客户端参数问题，应该是 400。
- **用的模型 / 为什么选它**：`GLM-5.3`，需要顺着异常继承链推断「该在哪一层捕获」。
- **我怎么问的**（精简后）：贴出服务端日志里的异常类型与首行（`org.apache.tomcat.util.http.InvalidParameterException: Character decoding failed ...`）、我的 `@RestControllerAdvice` 里的捕获清单，问：这个异常属于客户端错误还是服务端错误？为什么我的 `IllegalArgumentException` 处理器没接住它？
- **它指出了什么**：`InvalidParameterException` 继承自 `IllegalStateException`（→ `RuntimeException`），**不是** `IllegalArgumentException`，所以我的处理器接不住，落到了兜底 `Exception` 分支变成 500。建议把它归为客户端错误。
- **我改了吗、为什么改**：没有为这个 Tomcat 内部异常直接 import 依赖，而是按建议做**最小归因**：在 `RuntimeException` 这一层判断异常消息是否以稳定的 `Character decoding failed` 开头，是则返回 `400 / 40001`，否则仍走 500；同时把 `GlobalExceptionHandler` 里这段的注释改成准确的继承链描述（原注释写反了）。另外顺带修复了客户端非法 ID `/api/products/abc` 曾因处理器类型不匹配落到 500 的问题，改用父类 `TypeMismatchException` 捕获。**这两处代码改动由 Cline 执行。**
- **怎么确认它对不对**：Cline 把三种情况写成测试（`HttpEndToEndTest.realHttpBrokenEncodingIsClientError`、`L03`/`L04` 的非法参数用例），并在真实服务上重跑 `scripts/verify-l0.ps1`（其中 L0-3-22「非法 URL 编码 → 400 而非 500」），本人验收时确认 57/57 通过。
- **结论**：**采纳，但每条都验证过**。它给的「把 Tomcat 异常 import 进来」的做法我没有用（会耦合容器实现），只借用了它的归因。

### 场景 4：**我用 AI 做验证的一次**（必答）

- **我问了什么**：在写 L2-10 并发测试前，把 `OrderService.create()` 的下单流程和 `ProductMapper` 的原子 UPDATE 一起贴给 `GLM-5.3`，问：这 10 个并发请求同时买最后 1 件，会不会超卖？我的实现有没有漏掉的边界？
- **它指出了什么**：① `SELECT ... FOR UPDATE` 与带条件的原子 UPDATE 都能防超卖，但我的写法更短、锁持有时间更短，没有竞态窗口；② 它提醒「受影响行数为 0 时不要猜原因」，应在回查后区分「已下架」和「库存不足」——这一点实现里已经做了（`40902` / `40901`）；③ 它提醒订单号生成必须有唯一性兜底，否则并发下可能重复。
- **我验证后确认它对不对**：对照源码逐条确认——扣库存确实是 `WHERE stock >= ? AND status = 'on'` 单条 UPDATE；0 行时确实回查商品区分两种错误；`order_no` 确实是 `SO+时间戳+AtomicLong 序号` 且有 `UNIQUE` 约束。随后由 Cline 写并执行 `L210ConcurrentOrderTest`（真实随机端口 + 10 线程 + `CountDownLatch` 起跑门），**10 轮独立实验各 10 个并发请求，每轮恰好 1 个 201、9 个 409/40901，库存归 0、恰好新增 1 条订单**，本人在验收时逐轮核对。
- **诚实说明**：AI 只给了「这个方案应该没问题」的判断，**真正的结论是 Cline 执行 `mvn test -Dtest=L210ConcurrentOrderTest` 跑出来的**，不是 AI 说的，也不是我推演出来的。

> **另一个人工发现的问题**：L2-12 最初只覆盖了 `quantity=2` / `quantity=3` 的下单场景，**官方要求是「正常下单后库存减 1」**。这是本人对照官方要求时发现并明确要求补充的，随后补了独立用例 `normalOrderDecreasesStockByOne()`（库存 10 → 9、订单金额等于单价）。这一条属于人工查漏，不是 AI 主动提出的。

## 4. 一次被 AI 带偏的经历（必答）

- **它给了什么**：`GLM-5.3` 的第一版订单表里，状态枚举是 `created` / `paid` / `cancelled`，并且 `price` / `unit_price` 的约束写的是 `CHECK (price >= 0)`。整体看起来「更完整、更像真实电商系统」。
- **当时为什么信了**：它写的 DDL 语法正确、约束齐全，`cancelled` 也确实在真实业务里存在；「多留一个状态以后能用」这种直觉很顺。
- **你怎么发现的**：回头对照 README 的接口清单时发现——本期没有任何取消订单接口，L2-9 支付只判「已支付不可重复支付（`40903`）」，`cancelled` 永远不会被写入；同时 `price >= 0` 会让 0 元商品能落库，而支付金额 0 元的场景题目里没有定义。这两个「完整性」反而制造了**表和接口对不上的缝隙**。
- **最后怎么修的**：把状态收紧为 `CHECK (status IN ('created','paid'))` 并删掉 `cancelled`；价格/单价改为 `> 0`；在 `DESIGN.md` 中写清「为什么放弃退款/取消状态的扩展位」。改动由 Cline 落到 `schema.sql`，本人验收时确认。
- **之后你改了做法吗**：改了。现在让 AI 出 DDL 时会先说明「本期只有哪些接口、哪些状态会产生」，而不是直接说「设计一个电商表」。**约束的松紧必须由我对本期范围的理解来定，AI 默认按「完整业务」生成，往往超纲。**

> 另有一次不算「被带偏」但同类的问题：AI 起草的 JSON 解析器按 Jackson 2 的 API 写，在 Spring Boot 4（Jackson 3）下直接编译不过（见场景 2）。之后形成的习惯是：**凡是 AI 给的 API 用法，先由 Cline 在本地 `mvn compile` / `javap` 验证版本，再往下写**。

## 5. 成本（4 分）

| 问题 | 我的回答 |
|---|---|
| 有没有「一次把整个项目/整个文件塞进去」？为什么？ | 没有整包塞。设计表时只给 README 里的字段参考 + 本期接口范围；写接口时按「一个接口 + 相关表定义 + 相关分层文件」提问；排查报错时只贴异常首行、关键堆栈和相关的那段代码。原因很实际：项目里真正相关的文件就那么几个，多贴只会让 AI 去改不相关的地方，反而多花轮次。 |
| 有没有同一个报错连续问了很多次？后来怎么改的？ | 没有。H2 认证失败只问了 1 次——提问前先读完启动日志、找到第一个 `Caused by`，确认是「认证失败」而不是 SQL 语法错，再贴出去，一次就拿到方向。Jackson 3 的编译错误**没有问 AI**，由 Cline 直接 `mvn dependency:tree` 看实际依赖版本解决；这类「版本/环境」问题自己查比问更快。 |
| 如果额度只有 10 元，你会怎么调整？ | ① 表设计、事务、并发这类高杠杆任务仍然只问一次、问清楚；② CRUD 样板、文档措辞交给 Flash 或不问；③ 编译/依赖/配置类问题先查（`dependency:tree`、读第一个异常），不问 AI；④ 测试用例边界先自己列，让 AI 只做「我漏了什么」的补充检查，而不是从零设计。 |
| 有没有让 AI 重复做同一件事？ | 有一次：让两个模型分别写过一版参数校验，比对后只保留了更严格的那版，另一版直接丢弃。事后看，先想清楚校验规则再问一次会更省。 |

> 体会：最费钱的不是「问得多」，而是「问得模糊导致改好几轮」。把本期范围（哪些接口、哪些状态会产生、哪些字段必填）先写清楚再问，一轮就能定下来。
