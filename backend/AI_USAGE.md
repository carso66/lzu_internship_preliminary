## 3. 挑 4 个场景写下来（5 分）

### 场景 1：按指定技术栈初始化后端（成功）

- **我想干什么**：按已确定的 Java 17、Spring Boot 3.x、Maven、JDBC、H2、Flyway 技术栈搭建可启动的后端，不改已有文档和其他目录。
- **用的模型 / 为什么选它**：`deepseek-v4.1-flash`。技术栈和修改范围已经由我明确，主要是执行初始化、配置依赖和检查环境，使用日常的 Flash 模型。
- **我怎么问的**："请检查环境，用 curl 调用 Spring Initializr API 完成后端初始化；不引入 JPA、Redis、消息队列、鉴权或微服务，不改 backend 外的目录及已有四个 Markdown 文档。"
- **它给了什么**：生成 Maven 工程、依赖与配置、统一响应、健康接口、Flyway 初始迁移和基础测试。遇到 Initializr 拒绝指定的 3.x 版本后，先生成工程，再将 `pom.xml` 固定为 Spring Boot 3.5.16；本机使用 JDK 21 编译，目标版本设为 17。
- **我改了吗、为什么改**：工程骨架沿用；之后我优化了数据库 schema，并明确要求提交这部分改动。表结构需要按业务约束检查，不能把脚手架生成结果直接当作最终设计。
- **怎么确认改对了**：该会话记录了 `mvn clean test` 的 4 项测试全部通过，实际启动后 `GET /api/health` 返回 HTTP 200 和统一 JSON；编译产物 major version 为 61。这证明编译目标是 Java 17，不等同于已经在独立 JDK 17 环境运行过。
- **结论**：改了之后用，初始化成功，后续表结构由我调整。
- **历史依据**：schema 调整记录，提交 `0849103`。

### 场景 2：建议删除锁等待配置，但理由不足（未采用）

- **我想干什么**：在订单模块实现后，请 AI 检查事务、并发测试和配置是否合理。
- **用的模型 / 为什么选它**：`kimi-k3.1-pro`。用于补充审阅事务和并发方面的实现。
- **我怎么问的**："审阅当前工作区的修改和实现，判断是否存在不合理的情况。" 后来继续问："评估当前实现，确定是否需要修改，并告诉我下一步做什么。"
- **它给了什么**：第一次建议生产配置移除 `LOCK_TIMEOUT=10000`，理由是全局延长锁等待会让请求最多等待 10 秒，而并发测试已经单独配置了该值。后续复查时，它明确承认这个建议过于绝对：等待时间与并发容忍度之间需要取舍，10 秒本身不是正确性缺陷。
- **我改了吗、为什么改**：没有按该建议删除配置，当前主配置仍保留该值。仅凭等待时间较长，不能认定事务或库存保护有错；反过来，配置较长也不代表不会发生锁超时。
- **怎么确认改对了**：后续审阅记录中 `mvn test` 的 115 项测试通过，包含真实 HTTP 并发和库存回滚测试，且 AI 撤回了“应移除”的绝对化建议。测试只支持已有场景通过，不能证明任意负载下都不会超时。
- **结论**：没用它的删除建议。失败的是审阅判断过于绝对，并非已经发生了库存错误。

### 场景 3：我指出并发测试没有覆盖实际 HTTP 响应（人工修正）

- **我想干什么**：验证库存为 1 时，10 个并发下单请求只有 1 个成功，其余请求实际返回 HTTP 409 和业务码 `40901`。
- **用的模型 / 为什么选它**：`deepseek-v4.1-flash`。订单契约和并发保护要求已明确，让日常模型按这些要求实现并补充测试，再由我检查验收范围。
- **我怎么问的**：不要把先查库存当作并发保护；回滚测试不能被外层事务包住；请求必须真正并发，全部完成后再查最终结果。随后明确指出：修正：并发测试没有验证实际 HTTP 响应。
- **它给了什么**：第一版自动化并发测试直接调用 `OrderService`，能检查业务异常和数据库结果，但没有覆盖 HTTP 状态码。收到纠正后，它改成 `@SpringBootTest(webEnvironment = RANDOM_PORT)`，用 `HttpClient` 发出 10 个真实请求，并用两个 `CountDownLatch` 同步放行。
- **我改了吗、为什么改**：我提出验收缺口并要求重做，具体测试代码由 AI 修改。Service 抛出正确业务异常，还不足以证明 Controller 和统一异常处理最终返回了正确 HTTP 响应。
- **怎么确认改对了**：修改后断言恰好 1 个 HTTP 201、9 个 HTTP 409/`40901`，核对成功和失败响应体；所有请求完成后，再查库存为 0、订单数为 1、总额为 1000 分。当时完整测试为 115 项全部通过，我随后回复"已验证，提交当前部分改动吧"。
- **结论**：改了之后用。人工检查决定了测试需要覆盖到哪一层，不能只看测试是否为绿色。

### 场景 4：用 AI 独立审查，发现原测试未覆盖的 406 响应（验证）

- **我想干什么**：在商品、订单和支付实现后，对照两份 README 检查可用性、可靠性及文档一致性，尤其确认“完整测试通过”之外是否还有遗漏。
- **用的模型 / 为什么选它**：`kimi-k3.1-pro`。这次需要同时阅读契约、实现、数据库和文档，并设计额外验证，符合我把 Kimi 用于最终审查的分工。
- **我怎么问的**："你是专业的测试审查工程师，请检查 README 和 backend/README 的要求，审查后端代码、数据库的可用性、可靠性及文档一致性。运行完整测试并对并发做额外测试，给我完整审阅报告。"
- **它给了什么**：确认原有 137 项测试全部通过，并补充多轮并发、重复支付和文件库重启验证；同时指出 `GET /api/products` 携带 `Accept: application/xml` 时会返回 HTTP 406 空响应体，不符合失败也应包含 `code/message/data` 的约定。报告还列出锁超时等风险，并注明这些风险未在本轮复现。
- **我改了吗、为什么改**：该次工作是审查，没有直接修改业务实现；额外审查测试放在项目外的临时目录。406 被保留为已确认的待修问题，不能因为原有测试全过就写成“所有失败响应均已验证正确”。
- **怎么确认它说得对不对**：历史工具输出明确记录 `AUDIT_ACCEPT status=406 contentType=null body=`，对应额外测试为 1 项失败，确认了这条发现。原有 137 项通过与这条补充测试失败是两个独立结果；锁超时等静态风险则不写成已发生故障。当前异常处理代码也尚未补充该响应协商场景的专门处理。
- **结论**：采用它的验证发现，406 问题尚未修复。AI 审查的价值在于补充能暴露遗漏的请求，并保留失败证据。

## 4. 一次被 AI 带偏的经历（必答）

- **它给了什么**：`deepseek-v4.1-flash` 实现订单模块时，给了一份直接并发调用 `OrderService` 的自动化测试，并报告完整测试 115 项全部通过。该测试能检查一个成功、九个库存不足及最终数据库结果，但没有验证实际 HTTP 状态码，容易把“服务层并发逻辑通过”理解为“接口并发验收已经完成”。
- **当时为什么信了**：它提供了具体测试数量、业务码、库存和订单数等检查结果，也使用了同步放行机制，看起来已经覆盖并发要求。这些证据有价值，但不足以证明 HTTP 层也符合契约，我对这层差别的检查不够及时。
- **你怎么发现的**：、审阅发现测试直接调用 Service，未经过真实 HTTP 请求。对照 L2-10 要求后，我明确回复：“修正：并发测试没有验证实际 HTTP 响应。” 
- **最后怎么修的**：要求 AI 改为随机端口启动真实服务，用 `HttpClient` 并发发送 10 个下单请求。断言恰好 1 个 HTTP 201、9 个 HTTP 409 且业务码为 `40901`，检查统一响应体；全部请求结束后再确认库存为 0、订单数为 1。修改后当时的完整测试仍为 115 项全部通过，我验证后才要求提交。
- **之后你改了做法吗**：后续审查明确要求对照 README、运行完整测试并额外验证并发，不再只接受“测试全部通过”的总结。我会检查请求经过哪一层、断言是否对应验收要求，以及最终数据库状态是否一致。支付实现也补充了真实 HTTP 并发和事务回滚测试。
