# AI 使用说明（AI_USAGE）

## 1. 概览

| 项 | 内容 |
|---|---|
| 用了哪些模型 | `deepseek-v4-pro`、`deepseek-v4.1-flash`、`MiniMax-M3.1-Flash`；另使用辅助模型进行方案复核、提示词整理和日志分析 |
| 大致调用次数 | 当前阶段平台记录 49 条 |
| 大致花费 | 约 6.24 元 / 额度 40 元 |
| 主要用在哪些环节 | 项目初始化、数据库设计、商品与订单接口开发、事务与并发设计、代码审查、错误排查、测试方案和文档整理 |

本项目按需求分析、方案设计、代码实现、实际验证和缺陷修复几个阶段推进。复杂方案先明确技术路线及边界条件，再进行代码实现；常规任务则限定文件和修改范围。本人负责实际编译、HTTP 接口测试、Git 提交及系统权限相关操作，并依据真实运行结果决定是否接受修改。

平台统计来自 2026 年 11 月 25 日零点起的阶段性调用日志截图，不包含平台外辅助模型的使用成本，也未核实 11 月 24 日记录及截图之后的新增调用。49 条为平台调用记录数，并非主动发送提示词的次数；一次开发任务可能包含多轮模型请求。最终提交前需按完整考核时间范围更新统计。

## 2. 模型选型（6 分）

| 我用它做什么 | 用的模型 | 为什么选这个 |
|---|---|---|
| 工程初始化、常规 CRUD 实现 | DeepSeek V4.1 Flash | 需求和实现路线比较明确，优先使用轻量模型，避免常规任务占用较高推理成本 |
| 常规编码及局部修改 | Flash 系列（DeepSeek V4.1 Flash、MiniMax M3.1 Flash） | 这类任务通常以已有设计为依据，修改范围相对明确；平台记录显示实际使用了两种 Flash 模型 |
| 数据库表结构、字段约束、持久化方案 | DeepSeek V4 Pro | 需要综合考虑业务关系、数据完整性、字段类型及后续订单模块的扩展 |
| 下单事务、并发库存控制和订单号设计 | DeepSeek V4 Pro | 涉及事务边界、并发竞态、异常回滚和金额溢出等问题，需要先分析方案的正确性 |
| 整体设计说明 | DeepSeek V4 Pro | 需要结合多个模块建立完整调用关系，解释工程取舍与实现局限 |
| 复核实现报告、分析编译及运行日志、制定验证步骤 | 辅助模型 | 通过独立审查视角补充边界条件，并把日志定位结果转化成具体修复要求 |

本项目采用的主要策略是：**复杂问题先设计、常规问题按方案实现、关键结果以实际运行验证为准。** 对两种 Flash 模型没有进行专门的基准对比，因此不声称其中一种在本项目中具有经测量的质量或速度优势。具体任务与单次 API 请求的对应关系未逐条核验。

## 3. 挑 4 个场景写下来（5 分）

### 场景 1：订单事务与库存扣减方案设计（成功案例）

- **我想干什么**：实现订单创建、详情查询和按手机号分页查询，重点解决扣减库存与订单插入的一致性问题。
- **用的模型 / 为什么选它**：DeepSeek V4 Pro。跨表事务与并发控制比常规 CRUD 更容易遗漏边界，需要先完成技术方案分析。
- **我怎么问的（精简）**：请阅读订单需求、表结构和现有商品模块，本轮只做设计。明确事务边界、库存扣减 SQL、金额计算、订单快照和订单号生成方式，并分析并发下单场景。
- **它给了什么**：在 Service 层使用 `@Transactional`，使用带商品状态和剩余库存条件的 UPDATE 扣减库存，采用数据库序列生成订单号，并将成交单价、商品标题保存到订单。
- **我改了吗、为什么改**：进一步复核后补充了 `Math.multiplyExact` 溢出保护、缺失手机号校验、条件 UPDATE 失败后的状态判断，并将金额计算放到扣库存之前。明确生成主键时只请求 ID 列，避免商品模块曾出现的多生成键异常。
- **怎么确认改对了**：实际创建订单返回 HTTP 201，订单号成功生成；商品单价 1990 分、数量 2、总金额 3980 分，库存由 10 减至 8。订单详情和手机号分页返回正确记录；库存不足及下架商品请求被拒绝，最后库存仍为 8、对应买家订单数仍为 1。
- **结论**：修改后采用。正常下单和已覆盖异常路径通过，事务内写入失败后的回滚与并发不超卖仍需专项测试，不能由正常请求推定已验证。

### 场景 2：Java record 访问器使用错误（失败案例）

- **我想干什么**：按照已确定的订单设计完成订单模块编码。
- **用的模型 / 为什么选它**：Flash 系列模型。核心设计已明确，主要是按要求实现接口和数据访问代码。
- **我怎么问的（精简）**：按已审查的方案实现三个订单接口，复用商品模块、公共响应和异常处理，限定文件修改范围，静态检查后报告未验证项。
- **它给了什么**：生成订单 Controller、Service、Repository、Model 和 DTO，并报告完成静态核对。
- **我改了吗、为什么改**：首次 Maven 编译在 `OrderService.java` 第 79、80 行报错，`Product` 为 Java record，不存在 `getId()` 和 `getTitle()`。要求仅将两处改为 `id()`、`title()`，检查其他 record 访问器，不额外添加 getter，也不修改业务逻辑。
- **怎么确认改对了**：修复后服务成功启动，创建订单及两个查询接口均通过真实 HTTP 验证。
- **结论**：原始代码不能直接采用，修正后使用。模型自查不能替代真实编译。

### 场景 3：商品已经入库，但发布接口返回 500（人工纠错案例）

- **我想干什么**：验证商品发布接口能否插入数据并返回完整商品对象。
- **用的模型 / 为什么选它**：DeepSeek V4.1 Flash。实际运行日志已经将问题缩小到 Repository 层，适合局部修复。
- **我怎么问的（精简）**：商品发布返回 500，但列表能查到新商品。日志显示 `GeneratedKeyHolder.getKey()` 收到了 ID 和 CREATED_AT 两个生成字段，请定位原因并进行最小范围修复。
- **它给了什么**：指出 `Statement.RETURN_GENERATED_KEYS` 可能返回多个生成列，而 `getKey()` 只适用于单个生成键。
- **我改了吗、为什么改**：限定 `prepareStatement(sql, new String[]{"ID"})` 只返回 ID；同时要求在商品创建 Service 方法增加 `@Transactional`，使插入、取主键与回读处于同一事务内，防止后续事务内异常造成部分写入。
- **怎么确认改对了**：重新编译启动，发布 Test Mouse 成功并返回 ID=2、默认上架状态及创建时间；商品列表、组合筛选、详情、上下架均通过测试。事务异常回滚尚未专项实测。
- **结论**：修改后采用。相同主键获取方式在订单模块中继续使用，并通过正常下单验证。

### 场景 4：我用 AI 做验证的一次（必答）

- **我想干什么**：验证商品模块的参数校验和异常处理是否存在遗漏，而不只是检查正常接口能否运行。
- **用的模型 / 为什么选它**：辅助模型进行独立复核；Flash 模型负责按复核结果局部修改。
- **我怎么问的（精简）**：提交商品模块实现报告、Jackson 配置和服务端异常日志，重点检查小数价格能否被错误转换、未知路由为何返回 500，以及分页参数边界是否正确。
- **它指出了什么**：`ACCEPT_FLOAT_AS_INT` 需要显式关闭；全局 `Exception` 兜底会把未单独处理的未知路由等客户端异常转为 500。分页 offset 应使用 long 计算，现有实现已采取该措施，但仍需实际检查分页边界。
- **我怎么验证**：先核对实际 Jackson 配置，发现当时只关闭了 `ALLOW_COERCION_OF_SCALARS`；查看运行日志，确认错误路径产生 `NoResourceFoundException`。修复后使用 PowerShell 和 curl 发送 HTTP 请求：小数价格 19.99 返回 400，未知接口返回 404/40400，pageSize=51 返回 400/40001。
- **验证结论**：上述实际结果与复核意见一致。405、415 等其他框架异常处理分支以及全部类型边界未逐项实测，不写成已通过。
- **结论**：采用经过验证的审查意见。AI 不仅参与生成代码，也参与识别风险与设计验证步骤。

## 4. 一次被 AI 带偏的经历（必答）

### 工程初始化阶段的工具权限问题

- **它给了什么**：在工程初始化过程中，模型工具遇到端口占用和工作区写权限问题，尝试额外处理运行环境，其中涉及项目目录 ACL 权限调整。
- **当时为什么信了**：初期更关注工程能否尽快运行，对文件编辑之外的终端和权限操作缺少明确的限制。
- **怎么发现的**：查看执行过程和项目目录 ACL，发现工具操作已经超出生成项目代码所需的范围。
- **最后怎么修的**：由本人备份、检查并恢复项目根目录继承权限。对于被其他程序占用的 8080 端口，不结束无关进程，改用本地启动参数在 127.0.0.1:8081 测试，项目默认端口仍保留 8080。
- **之后改了做法吗**：明确每轮允许编辑的文件，禁止模型自行修改 ACL、申请额外权限、停止其他进程或进行 Git 操作；编译、接口测试、提交由本人执行。出现权限错误时要求立即停止并报告。

后续商品模块调整目录时，工具再次遇到沙箱授权失败，按约定停止。本人将七个旧 Java 文件按明确路径移动到项目外的备份目录，再执行 `mvn clean test` 清理旧编译产物并重新验证。编译和健康检查通过，项目根目录 ACL 检查未显示额外的显式条目。

这次经历说明，AI 辅助开发除了审查代码本身，还需要约束工具操作范围。不能为了实现功能而忽略环境安全与修改边界。
