# AI 使用说明（AI_USAGE）

## 1. 概览

| 项 | 内容 |
|---|---|
| 用了哪些模型 | 指定平台经 Chatbox 使用 `deepseek-v4-pro`、`MiniMax-M3`、`glm-5.3`、`deepseek-v4.1-flash`；另尝试 `Kimi-K3.1-Pro`、`Qwen3.8-Max`，这两者在备份中只有错误响应。开发中还使用了 Codex，协助情况单独注明。 |
| 大致调用次数 | 备份中有 63 条带模型 ID 的助手记录，其中含 9 条错误响应、2 条输出上限终止；另有 2 条无模型字段的交接摘要。此为客户端记录数，实际计费调用次数以平台记录为准。 |
| 大致花费 | **8.82 元 / 额度 40 元** |
| 主要用在哪些环节 | 工程初始化与报错解释、表结构讨论、商品和订单代码建议、事务与并发审查、测试及报告导出、文档整理。 |

本说明依据 Chatbox 备份及实际开发协作记录整理。模型名取自每条消息的 modelId，日志见 [ai-evidence](ai-evidence/README.md)。指定平台模型主要提供建议和静态审查；Codex 还参与文件修改、依赖核验、测试执行和报告整理，不能将这些工作写成指定平台模型或本人独立完成。

最终提交为 L0、L1，以及 **L2-11 最简鉴权、L2-12 自动化测试**。当前精简版本的 **11 项 JUnit、41 项 HTTP 检查**在本人本机完成。

## 2. 模型选型（6 分，重点）

| 我用它做什么 | 用的模型 | 为什么选这个 |
|---|---|---|
| 表结构、项目步骤、商品与订单实现方案 | `deepseek-v4-pro` | 需要结合字段、业务码、金额和事务讨论；前期也沿用它生成普通 CRUD，没有严格做到简单任务全部换快模型。 |
| 阶段规划、摘要与上下文交接 | `deepseek-v4.1-flash` | 已有材料的整理较明确，适合先用快模型处理；实际记录包括阶段规划与总结。 |
| SQL、L0/L1 审查与定向修订 | `MiniMax-M3` | 用另一模型复核已有方案，再围绕确认的问题修订，避免只让最初写代码的模型自我确认。 |
| 业务源码、测试断言、输出与文档的分批审查 | `glm-5.3` | 这一阶段需要对照多类证据，检查事务、回滚、并发和需求是否一致，而非继续生成普通接口。 |
| 本地文件与依赖检查、排错、代码落地及测试 | Codex（开发工具） | 能结合本地文件和终端结果定位问题；其协助与指定平台调用分开说明，不推测底层模型 ID。 |

`Kimi-K3.1-Pro`、`Qwen3.8-Max` 虽有尝试，但没有取得有效审查答复，不将其列为完成任务的模型。以上是实际任务分布；不能据此声称从一开始就完成了严格的强、快模型分工。

## 3. 挑 4 个场景写下来（5 分）

### 场景 1：检查表结构，筛选适合当前需求的建议

- **我想干什么**：检查 H2 的商品、订单两表设计，再继续开发接口。
- **用的模型 / 为什么选它**：`deepseek-v4-pro`，需要把字段、金额单位、快照和约束一起考虑。
- **我怎么问的**（精简）：提供已有 SQL 和校园集市场景，请检查表设计是否合理、哪些字段需要补充。
- **它给了什么**：确认已有订单快照和金额约束的方向，建议补更新时间、图片、备注，也建议增加用户表并改为用户 ID 关联。
- **我改了吗、为什么改**：采纳当前业务所需字段；没有采用用户表。我在后续提问中明确说明题目没有完整的“我的商品”等用户功能，先完成核心流程。
- **怎么确认改对了**：最终 schema 保留 products、orders 两表；商品字段与订单快照能正常写入、返回，当前订单集成测试通过。L2 登录使用题目允许的固定演示账号，没有引入用户表。
- **结论**：改了之后用，未采纳用户表建议。对应 Chatbox M006～M009，见 [对话摘录](ai-evidence/key-scenes.txt)。

### 场景 2：测试报告导出报错，先区分测试失败和导出失败

- **我想干什么**：运行本地测试，导出结果后上传给指定平台模型审查。
- **用的模型 / 为什么选它**：Codex，报告脚本与本地文件需要一起检查。
- **我怎么问的**（精简）：贴出运行脚本后的终端报错，请检查原因。
- **它给了什么**：最初提供的导出脚本在读取 Surefire XML 时发生解码、解析问题；随后核对原始 Maven 日志和 XML，确认是报告导出失败，而不是据此认定业务测试失败。
- **我改了吗、为什么改**：在 Codex 协助下调整读取方式，使用 XML 文档加载器按文件声明读取，恢复原报告；没有仅因导出报错就改业务实现。
- **怎么确认改对了**：原运行日志有 BUILD SUCCESS，恢复的 5 份报告合计 18 项、0 失败、0 错误；恢复时未重跑测试。原进程退出码未保存，没有补写为 0。该案例属于当时的全量原型，不是当前 11 项测试的报告。
- **结论**：最初的脚本不能直接用，修复后使用。AI 提供的验证工具本身也要检查。

### 场景 3：把 L1 总体方案改为明确的修订清单

- **我想干什么**：实现事务下单、订单详情和手机号分页，检查库存及金额边界。
- **用的模型 / 为什么选它**：`deepseek-v4-pro` 提供初版，`MiniMax-M3` 复核并修订；把实现与检查分开推进。
- **我怎么问的**（精简）：先提供当前方案审查，再明确列出采纳的修改，要求按文件给修订代码及真实插入失败的回滚测试，不要重新换一套方案。
- **它给了什么**：指出订单号碰撞风险、手机号保存与查询规范化不一致，并讨论金额溢出、行锁和条件扣库存。
- **我改了吗、为什么改**：明确采用完整 UUID；手机号保存、查询统一 strip；扣库存前 multiplyExact，溢出返回 40001；事务内锁商品行；保留 stock>=quantity 的条件更新。订单号最终为 SO＋日期＋32 位 UUID，不是只用 SO＋32 位字符。
- **怎么确认改对了**：Codex 参与落地与测试适配；OrderIntegrationTest 检查服务端价格、快照、参数异常不写库、真实 INSERT 失败后库存恢复，以及 10 抢 1 后库存为 0、订单恰好 1 条。当前 [订单测试报告](test-evidence/com.example.demo.OrderIntegrationTest.txt)为 5 项通过。
- **结论**：改了之后用。对应 Chatbox M055～M068，尤其 M065 的修订清单。

### 场景 4：我用 AI 做验证的一次——分批 review 源码和测试证据

- **我想干什么**：让模型检查实现、断言、真实输出和提交文档能否互相对应。
- **用的模型 / 为什么选它**：`glm-5.3`，用于跨文件审查事务、鉴权、并发和回滚的依据。
- **我怎么问的**（精简）：先确认附件正文可读；按基线、鉴权、交易与回滚、索引、文档分五批检查。区分确定缺陷、待验证风险和可选增强；未执行测试就明确说明，问题须给位置、触发条件和最小修复。
- **它给了什么**：对当时全量原型未发现确定的 P1/P2 业务问题；指出配置注释和证据端口说明需要收尾，逐项核对了 401 统一响应、拒绝后数据不变、SQL 失败回滚及并发终态断言。
- **我改了吗、为什么改**：核对后修正注释、补充证据运行来源。没有直接照搬“脚本固定 8081”的推断：脚本默认实际为 8080，证据那次通过参数使用 8081，无须修改默认端口。
- **怎么确认改对了**：用源码和实际报告逐条对照，静态审查不当成测试执行。模型当时审查的是 18/46 项全量原型；后来最终只保留鉴权与测试。
- **结论**：采用核对成立的建议，对推断先查证。对应 Chatbox M117～M128；最终版本报告见 test-evidence。

## 4. 一次被 AI 带偏的经历（必答）

- **它给了什么**：已说明 Spring Boot 4.2.0、Jackson 3.1.8 后，`MiniMax-M3` 仍建议使用 `tools.jackson.databind.JsonMappingException`、`getFieldName()` 处理字段类型错误（M049～M050）。
- **当时为什么信了**：答复明确声称适用于当前版本，包名也写成 tools.jackson，看起来已经考虑版本；我起初没有先核验具体类和方法。
- **你怎么发现的**：借助 Codex 检查本地依赖与实际 API，发现这套类型、方法不适配；改包名前缀不能保证旧 API 可用。
- **最后怎么修的**：GlobalExceptionHandler 改用当前支持的 DatabindException，通过异常路径的 getPropertyName 提取字段；无法定位字段时保留通用提示。字符串 stock、小数 price 等请求验证为 HTTP 400、code=40001，字段提示与当前脚本输出一致。
- **之后你改了做法吗**：给 AI 同时提供依赖版本、当前类和最小失败输入；先核验 API、编译与请求结果，再接受兼容性结论。此处平台给建议、Codex 协助核验和修改，不能归为平台模型亲自执行验证。

## 5. 成本（4 分）

| 问题 | 我的回答 |
|---|---|
| 有没有“一次把整个项目/整个文件塞进去”？为什么？ | 上传过整份 Java 文件和多文件集合，方便核对签名、SQL、事务和断言；也发生过原文件与汇总重复提供。后来按模块分批，公共约定先传一次，源码、测试、文档分别审查，减少重复上下文。 |
| 有没有同一个报错连续问了很多次？后来怎么改的？ | 有。MiniMax-M3 两次达到输出上限没有可读正文，中间只发“继续生成”仍未解决；阶段总结也重复问过。后来先确认附件可读，缩小问题，限制输出范围，按“已有证据、仍缺证据、可选增强”回答，保存阶段记录再交接。两次 length 记录见 M076～M079。 |
| 如果额度只有 10 元，你会怎么调整？ | 先固定两个最终选做项。已有模式的解释、摘要和格式整理先用快模型；强模型集中用于表约束、事务、并发及一次明确范围的审查。报错提供最小复现和版本，已验证且未变化的部分不反复生成，多用本地编译、curl 和测试确认。 |
