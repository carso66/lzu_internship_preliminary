## 开发与设计补充说明

### 项目实现摘要

本项目是一个使用 Spring Boot、MyBatis 和 H2 实现的商品交易后端，覆盖商品发布与查询、商品上下架、下单扣库存、订单查询以及模拟支付。接口金额统一使用整数分；订单保存成交时的商品标题和单价快照；支付记录通过订单外键和唯一约束保证一笔订单最多对应一笔支付。H2 使用内存数据库，进程重启后数据会清空。

模块拆分、完整下单链路和金额取舍详见 `DESIGN.md` 第 3–5 节，本节只补充评审时需要快速查看的接口与关键实现信息。

### 接口清单

所有业务接口使用 JSON 请求和响应。除健康检查外，业务接口的统一响应结构为 `{"code":0,"message":"ok","data":...}`。

| 方法 | 路径 | 用途 | 主要成功响应 | 主要失败场景 |
|---|---|---|---|---|
| GET | `/api/health` | 检查服务和数据库是否可用 | 200 | 500：数据库不可用 |
| POST | `/api/products` | 发布商品 | 201 | 400：字段缺失或格式错误 |
| GET | `/api/products` | 分页查询商品，可按关键词、状态和分类过滤 | 200 | 400：分页或状态参数不合法 |
| GET | `/api/products/{id}` | 查询商品详情 | 200 | 404：商品不存在 |
| PATCH | `/api/products/{id}/status` | 将商品上架或下架 | 200 | 400：状态不合法；404：商品不存在 |
| POST | `/api/orders` | 创建订单并扣减库存 | 201 | 400：请求参数不合法；404：商品不存在；409：商品下架或库存不足 |
| GET | `/api/orders/{orderNo}` | 按订单号查询订单详情 | 200 | 404：订单不存在 |
| GET | `/api/orders?buyerPhone=...` | 按买家手机号分页查询订单 | 200 | 400：手机号或分页参数不合法 |
| POST | `/api/payments` | 为已创建订单创建模拟支付 | 200 | 400：支付方式不合法；404：订单不存在；409：订单已支付 |
| GET | `/api/payments/{paymentId}` | 按支付号查询支付详情 | 200 | 404：支付记录不存在 |

### 统一响应与错误码

- 成功响应：`code` 为 `0`，`message` 为 `ok`，业务数据放在 `data` 中。
- `40001`：请求参数或 JSON 字段格式错误，对应 HTTP 400。
- `40401`：商品、订单或支付记录不存在，对应 HTTP 404。
- `40901`：库存不足，对应 HTTP 409。
- `40902`：商品已下架，对应 HTTP 409。
- `40903`：订单已支付，对应 HTTP 409。
- `50000`：未预期的服务端错误，对应 HTTP 500；响应不返回异常堆栈或敏感信息。

### 关键实现说明

- **库存扣减**：`ProductMapper.decreaseStockIfAvailable` 在同一条 SQL 中约束商品已上架且库存足够。条件更新影响 0 行时，服务层再查询商品，以区分商品不存在、商品下架和库存不足。
- **下单事务**：扣库存和写订单位于同一个事务中。写订单失败会回滚库存扣减，避免出现库存减少但没有订单的情况。
- **支付幂等与防重复**：`OrderMapper.markPaidIfCreated` 只允许订单从 `created` 迁移到 `paid`；数据库对 `payments.order_id` 建立唯一约束，保证一笔订单最多写入一条支付记录。
- **异常映射**：`ApiExceptionHandler` 将业务异常、参数错误和未知异常统一转换为固定 JSON 结构，并为不同业务失败返回稳定的业务码。
- **并发控制**：库存和订单状态更新都使用带条件的 SQL，由数据库以原子更新完成并发竞争判断，不依赖先查询再修改的检查方式。
