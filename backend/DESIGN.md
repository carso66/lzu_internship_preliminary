## 2. 我是怎么拆的（最重要）

| 顺序 | 我做的事 | 为什么排在这个位置 |
|---|---|---|
| 1 | 先确定表、金额整数分、时间 UTC、统一响应和错误码 | 后续商品和订单都依赖这些约束，先统一可避免接口各自返回一套结构 |
| 2 | 接入 H2 和 Flyway，先写 `products` / `orders`，预留 `payments` | 订单依赖商品主键和商品价格快照，表关系必须先稳定 |
| 3 | 完成商品发布、列表、详情和上下架，再补商品参数及筛选测试 | 下单需要真实商品数据；先验证商品链路可减少联调时的不确定因素 |
| 4 | 实现下单事务，再实现订单详情和买家订单列表 | 下单同时改商品和订单，是最容易产生数据不一致的链路，应先解决 |
| 5 | 增加数据库订单号序列、条件扣库存和行锁 | 订单号要并发唯一，库存检查和扣减也不能只靠应用层的“先查再改” |
| 6 | 最后做无外层事务的回滚测试和真实 HTTP 并发测试 | 普通 MockMvc 用例不足以证明提交、回滚和竞争条件下的最终状态 |

## 3. 我的程序分成哪几块

| 文件 / 模块 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `common/` | 统一响应、业务码、业务异常、全局异常转换、严格 JSON 类型配置 | Controller 只处理 HTTP 映射，所有成功和失败响应使用同一出口 |
| `product/ProductController` | 商品接口的路径、参数绑定及 HTTP 状态 | 不把 SQL 和事务放进 Web 层 |
| `product/ProductService` | 商品创建、查询和上下架业务操作 | 隔离 Web 与持久化，便于服务层事务管理 |
| `product/ProductRepository` | 商品 SQL、组合筛选、行锁查询、条件扣库存 | 商品写入规则集中，订单服务可以复用同一套库存操作 |
| `order/OrderController` | 下单、订单详情和订单列表接口 | 下单返回 201，查询返回 200，错误交给全局处理器 |
| `order/OrderService` | 锁商品、校验状态与库存、服务端算价、扣库存、写订单 | 这是核心事务边界；任何运行时异常都会回滚库存和订单 |
| `order/OrderRepository` | 订单插入、按订单号查询、手机号计数和分页查询 | 订单 SQL 与事务流程分开，列表始终使用参数绑定 |
| `order/OrderNumberGenerator` | 通过数据库序列生成 `SO + UTC 日期 + 序号` | 不用 `MAX(id)+1`，避免并发请求拿到相同订单号 |
| `resources/db/migration/` | Flyway 版本化建表及序列迁移 | 启动时自动升级数据库，保留可追踪的结构变更历史 |
| `schema.sql` | 当前完整结构的手写 SQL 快照，适用于空库一次性初始化 | 满足结构审阅和手工建库需要；应用启动不重复执行它 |

金额使用 `BIGINT` 和 Java `long`，库存、数量使用整数，不使用浮点数。订单保存 `product_title`、`unit_price` 和 `total_amount` 快照，因此后续商品改价或改名不会改变历史订单。外键保留商品关联；状态、非负库存、正购买数量和金额计算关系也有数据库 `CHECK` 兜底。

## 4. 一次完整链路是怎么走的

以下以两个请求同时购买库存为 1 的同一商品为例：

```text
POST /api/orders { productId, quantity, buyerName, buyerPhone, address }
  → DTO 校验正整数、必填字段和长度
  → 开启 OrderService.create 的数据库事务
  → SELECT ... FROM products WHERE id = ? FOR UPDATE
      ├─ 商品不存在：404 / 40401，事务回滚
      ├─ 商品已下架：409 / 40902，事务回滚
      └─ 库存不足：409 / 40901，事务回滚
  → 使用锁定商品的 price 计算 unitPrice 和 totalAmount
  → UPDATE products SET stock = stock - ?
    WHERE id = ? AND status = 'on' AND stock >= ?
  → 受影响行数不是 1 时不插入订单；重读状态/库存分类，无法解释则回滚并报错
  → 数据库序列生成唯一订单号
  → INSERT orders（保存商品标题、价格、总额等快照）
  → 事务提交后返回 201；任一步抛出运行时异常则库存与订单一起回滚
```

第二个并发事务会等待第一个事务释放商品行锁，再读取已提交的最新库存。库存已经变成 0 时，第二个请求返回 409 / 40901，不会扣成负数，也不会多写订单。条件更新仍保留为数据库层面的第二道保护，而不是把“提前查库存”误当成并发控制。

## 5. 一个取舍：库存采用双冗余设计（确认修改量 + 事务行锁）

- **可以在哪两个方案里选**：只使用条件扣库存并检查受影响行数，或在此基础上增加事务行锁。
- **我选了**：保留两层保护，即“条件扣减后确认受影响行数 + 事务内锁定商品行”。这里的“修改量”指 SQL 实际更新的行数，预期为 1。
- **确认修改量怎么做**：扣库存的 SQL 同时限制 `id`、`status = 'on'` 和 `stock >= quantity`，使用 `stock = stock - quantity` 更新库存。Service 检查返回的受影响行数，只有等于 1 才继续插入订单；否则抛出异常并回滚事务。这样即使后续某条调用路径遗漏了提前加锁，条件扣减仍能阻止库存被扣成负数。
- **事务行锁怎么做**：在 `@Transactional` 方法中先用 `SELECT ... FOR UPDATE` 锁定商品行，再检查状态、库存并读取价格，随后扣库存、写订单。行锁一直持有到事务提交或回滚，使同一商品的下单按顺序处理；订单插入失败时，已经扣减的库存也会回滚。
- **为什么接受冗余**：行锁用于保证商品状态、价格和库存的检查与后续写入衔接一致，条件更新及行数检查用于确认扣库存确实成功。在当前持锁流程中，校验通过后扣减正常应当成功；保留第二层检查，是为了在代码变更或出现异常路径时及时发现问题，避免库存未扣减却写入订单。
- **代价是**：代码多了一次更新结果判断，同一商品的并发下单需要等待行锁，竞争激烈时可能锁等待超时。当前作业规模下，我接受这部分冗余和等待，换取更明确的库存保护与失败处理。

## 6. 我卡得最久的一个问题

- **现象**：下单在单次调用时库存和订单都正确，但“库存为 1 时并发买 10 次”不能只靠普通接口测试说明不会超卖；回滚测试如果加了测试类事务，也无法证明真实回滚。
- **我一开始以为**：先查 `stock >= quantity` 再更新就足够；在测试类加 `@Transactional` 后查到的库存就是 service 回滚后的结果。
- **试过什么**：比较单纯条件更新与商品行锁；把库存更新结果和插入订单放在同一 service 事务；分别用 MockMvc 和随机端口真实 HTTP 请求验证并发。
- **最后靠什么定位的**：回到数据库隔离与事务边界分析，并用强制订单插入异常、并发闩锁和最终 SQL 计数验证，而不是只看某个响应或某个中间状态。
- **真正的原因**：库存检查不是锁；测试类外层事务会包住 service 事务并改变可见结果。最终回滚测试不加 `@Transactional`，并发测试等 10 个真实 HTTP 请求全部结束后才检查库存和订单数。
