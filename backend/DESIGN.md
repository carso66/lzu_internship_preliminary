# 校园好物市集后端设计

## 完成范围

我选了后端方向，实现了商品发布、查询和上下架。下单时服务端计算金额并扣库存，买家可以按订单号查详情，也可以按手机号分页查订单。两项选做题是 L2-9 同步模拟支付和 L2-10 并发下单。支付结果写入本地数据库，没有接入收款渠道。

## 实现顺序

我先定了表和字段约束，把商品现价留在商品表，把成交单价记进订单。这样，商品以后调价也不会改变旧订单的金额。接着做商品接口，让测试可以自己发布商品、设置库存。下单跑通后，测试就能用实际生成的订单号和金额发起支付，所以我把支付放在最后。

## 表和代码

| 位置 | 用途及取舍 |
|---|---|
| `schema.sql` | `products` 保存现价和可售库存。`orders` 保留成交时的商品名、单价、件数和总额，外键指回商品。`payments` 保存支付方式、金额和时间，订单号有唯一约束。金额按整数分存储。 |
| `main.go`、`server.go` | 注册路由、打开数据库、解析 JSON、校验分页参数，统一输出响应。评审只需指定监听地址和数据库文件。 |
| `products.go` | 负责发布和上下架。商品列表的总数与当前页共用一组筛选条件，在同一事务中读取。 |
| `orders.go` | 接收商品编号和件数，按成交价建单并查询。买家订单先按创建时间倒序，再按主键倒序，同一毫秒生成的订单也有固定顺序。 |
| `payments.go` | 在同一个事务中更新订单状态并写支付流水。重复请求有独立的业务码，调用方可以据此查原订单。 |
| `transaction.go` | 在事务结束前保留原连接。若 SQLite 在提交时返回错误，在同一连接上清理事务，避免下一次请求读到未提交的数据。 |
| `market_test.go`、`commit_test.go` | 从 HTTP 入口发请求，再核对库内记录。后者专门在事务提交时制造错误，检查下一笔订单还能否成交。 |

## 买最后一件商品时发生什么

1. `POST /api/orders` 先校验商品编号、件数和收货信息。件数必须是 JSON 正整数。
2. 开事务，用一条带条件的 `UPDATE` 扣库存。只有商品已上架且剩余库存足够时，数据库才会更新并返回商品名和单价。
3. 如果没有更新到行，在同一事务内查询商品状态，分别返回商品不存在、已下架或库存不足。
4. 用数据库返回的单价乘以件数，写入订单。订单插入失败，扣掉的库存随事务一起回滚。提交成功才返回 HTTP 201。
5. 支付时只更新状态为 `created` 的订单，并把同一个付款时间写进订单和流水。后续支付返回 HTTP 409，业务码 `40903`。

## 为什么用一个数据库连接

SQLite 文件随服务启动创建，评审重启后还能查到原订单。我把连接池上限设为 1，同一进程的请求在数据库入口排队。另一个进程打开同一文件时，写事务会先取得 SQLite 写锁。库存条件仍写在更新语句里，订单号和支付流水的唯一性也由数据库约束。代价是长查询会推迟后面的下单；如果要服务更多用户，先测排队时间再决定是否更换数据库。

## 实际遇到的问题

我最初只测了插入订单失败，看到库存能回滚。复核时我用了延迟外键，让订单先插入，到提交时才失败。接口按预期返回了 500，但同一连接随后的查询读到库存 0、订单数 1；再下一单还会报已有事务。问题出在 Go 和 SQLite 对这次失败的处理不同：Go 已经结束了这个事务对象，SQLite 连接上仍可能留有未提交的事务。

我把这段逻辑改为从连接池借出一条连接，直到事务结束才归还。提交失败时在这条连接上执行回滚；清理也失败就丢弃该连接。用同一个故障场景复测，库存恢复到 1、订单数为 0，下一笔有效订单返回 201。

## 已知边界

- 接口默认只监听本机。没有做登录或买家身份绑定，手机号只用作查询条件。
- 同一个订单号最多产生一笔成功支付。创建订单接口没有客户端请求号，重复发两次有效下单请求会被视为买两次。
- 商品按标题做子串匹配。商品量很大时，这类查询需要重新评估。

## 如果多一天

1. 我会先加买家身份校验。订单详情里有收件信息，仅凭手机号或订单号不适合开放给其他用户访问。
2. 给下单接口加客户端请求号和唯一约束。买家遇到网络超时后重试，可以收到已有的订单号。
3. 测同时浏览和下单时的等待时间，区分慢查询和写入排队，再决定是否拆读连接。
