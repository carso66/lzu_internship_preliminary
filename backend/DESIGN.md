- L0：建表、商品发布、列表、详情、上下架全部实现。

这个后端能完成商品发布、购买和模拟支付，数据保存在H2内存中，暂不接真实支付。

## 3. 我的程序分成哪几块

| 文件/模块 | 职责 | 单独拆分原因 |
|---|---|---|
| controller | 路径、请求绑定、HTTP状态、统一响应 | 不把SQL和事务混入HTTP处理 |
| product | 商品请求/查询对象、服务、SQL | 复用同一行映射，管理商品库存和状态 |
| order | 校验商品、锁行、算价、扣库存、存订单和查询 | 集中表达下单事务边界 |
| payment | 锁订单、写支付、更新订单状态 | 防止重复支付和部分成功 |
| common | 业务异常、统一异常处理、响应结构 | 不让各接口各写一套错误格式 |
| config | JSON严格类型转换 | 避免"2"、1.5等被静默当成整数 |
| schema.sql | 显式建表与约束 | 能直接复核字段和SQL，不依赖ORM自动建表 |
| src/test | 数据库、接口、事务、并发测试 | 用实际结果验证实现 |

record用于请求和响应对象，字段含义直接对应JSON；数据库字段映射集中在Repository。
新增退款或优惠券时，订单状态流转、金额计算需要先扩展成明确的业务规则。

## 4. 一次完整链路

```text
POST /api/orders
 → JSON类型检查、字段校验
 → 进入OrderService的Spring事务
 → SELECT商品 FOR UPDATE（查不到404；off返回40902）
 → 检查库存（不足40901）
 → Math.multiplyExact计算整数分金额（溢出400）
 → 带stock>=quantity条件扣库存
 → 插入唯一订单号和标题、单价快照
 → 提交并返回201
任何写入异常 → 整体回滚 → 库存和订单保持一致
```

行锁直到事务结束才释放。上下架更新同样需要该行的锁，因此不会在持锁下单中间改变商品状态。
支付锁订单，检查已支付状态后写payments和更新orders，二者同一事务提交。
payments.order_no还有唯一约束，禁止同一订单有两条成功记录。

## 5. 技术取舍

选择H2内存模式，目的是一条命令启动，评审每次从空数据开始；代价是重启丢失数据。
后续可以改文件模式或外部数据库，并管理schema迁移。
选择JDBC、显式SQL和数据库行锁，便于直接说明扣库存及回滚机制；代价是需要手动写映射和SQL。
金额使用long/BIGINT表示分，并检查乘法溢出，不使用浮点数。
订单号用UUID并有数据库唯一约束，省去维护日期流水号计数器。

## 6. 实际排错案例

本对话记录中出现过：java -version为17，但mvn -v仍使用Java8和Maven3.6.0。
排查JAVA_HOME、MAVEN_HOME和Path后，发现旧目录仍在生效；统一变量、调整顺序并刷新终端后，
java、javac、Maven所用Java都变为17，Maven变为3.9.16。

另一个问题是混入另一套ProductController和异常处理代码，出现请求类型不匹配、调用不存在的ApiResponse.error。
编译日志明确定位了文件和调用点，后续当前工程已去除重复实现，全部测试可编译通过。
