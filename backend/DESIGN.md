# 设计说明

## 1. 我做到了哪一步

目前完成 L0 的五项：商品表和订单表、发布商品、筛选分页、商品详情、上下架。另外补了全局异常中的 404/405 处理。L1、L2 尚未实现，订单目前只有表，没有下单接口。

我做的是一个能运行和验证的商品管理后端，还不能完成购买、扣库存和支付。没有把“表建好了”算作“订单功能做完了”。

## 2. 我是怎么拆任务的

| 顺序 | 做的事 | 为什么这样安排 |
|---|---|---|
| 1 | 检查 Java、Maven，再启动最小 Spring Boot 工程 | 我此前没有后端环境，先确认程序能运行，避免把环境问题和业务代码问题混在一起。 |
| 2 | 按题目把两张表写在 backend/schema.sql，并配置启动时加载 | 后面的发布和查询都依赖数据库。先确认表和约束，再写接口。 |
| 3 | 实现发布商品，验证参数、插入和主键返回 | 查询前要有数据，这一步也能把 Controller、Service、Repository 整条链路跑通。 |
| 4 | 实现列表，再实现详情 | 列表需要理解筛选后的总数和分页；详情可以复用发布时已经写好的 findById。 |
| 5 | 增加上下架 | 在已有查询基础上增加更新，先检查商品存在，再修改状态。 |
| 6 | 单独整理框架异常，再做回归检查 | 业务接口能返回 400，不代表不存在的路径也能正确返回 404。需要把这两件事分开验证。 |

我先让 AI 解释整体结构，再按一个接口一轮进行设计、实现和验证。已经验收过的方法尽量不整份替换，这样出问题时更容易找到是哪次新增引入的。

### 我在推进过程中把关的地方

我没有一开始就让模型生成整个项目，而是先弄清每个阶段的输入、输出和完成条件。比如做列表时，我先追问 total 和 items 的区别，理解“有三件商品”和“当前页能查到几件”不是同一个问题，再继续讨论页码边界。

对于 AI 给的实现，我反复强调保留已验收的发布逻辑，只新增当前功能。另一个重点是要求解释修改依据：超大页码提示不准确，应该先修提示，不能顺便加一个题目没有规定的十万页上限。我负责提出这些问题和决定改动范围，具体实现与测试借助 AI 完成。

## 3. 程序分成哪几块

| 文件 / 模块 | 职责 | 拆开的理由 |
|---|---|---|
| controller/ProductController | 接收 HTTP 请求，调用 Service，返回统一响应 | 不把 SQL 和参数规则都挤在接口方法里。 |
| service/ProductService | 参数校验、商品存在性判断、组织查询和更新 | 同一类规则集中处理，业务错误在这里说明白。 |
| repository/ProductRepository | JdbcTemplate 与参数化 SQL、结果映射 | SQL 可以直接阅读；Java 的 sellerName 与数据库的 seller_name 在这里对应。 |
| model/Product | 表示完整商品 | 发布回查、详情、列表共用，减少重复定义。 |
| dto/ | 请求体、分页结果、上下架响应 | 上下架只返回 id 和 status，不用构造一个其他字段全为空的 Product。 |
| common/ | ApiResponse、BusinessException、GlobalExceptionHandler | 统一 code/message/data，集中决定异常对应的 HTTP 状态。 |
| schema.sql、application.properties | 建表与数据源初始化 | 建表脚本按题目放根目录，用 file:./schema.sql 显式加载。 |

没有增加 ORM、缓存或通用 BaseService。当前只有商品这一条业务线，直接写 SQL 更容易看清每次请求做了什么。以后做订单，事务和金额计算应放在订单 Service，而不是加进 ProductController。

### 表结构的考虑

products 用自增 BIGINT 作主键，金额以 INT 保存，单位为分。数据库限制价格、库存不能为负，状态只能是 on/off；Service 再提前校验，给出能看懂的报错。created_at 由数据库产生。

orders 预先保留了商品标题、单价和总金额字段，用来保存下单时的信息，避免以后商品改名或改价影响历史订单。order_no 有唯一约束，quantity 至少为 1。product_id 当前是逻辑关联，没有外键，代价是数据库不会替应用检查商品是否存在。订单接口尚未实现，这部分校验与事务不能算已经完成。

## 4. 一次完整链路

以上下架为例：

```text
PATCH /api/products/1/status，body = {"status":"off"}
  → Controller 用 String 接收 id，DTO 接收 status
  → Service 检查 id 是正整数且未超 long 范围
  → 检查 status，去首尾空格后只能是 on/off
  → findById 查询商品；没有则返回 404 + 40401
  → UPDATE products SET status = ? WHERE id = ?
  → 返回 200，data 为 {"id":1,"status":"off"}
  → 再查详情和列表，确认状态确实变了
```

参数有错时先返回 400，查不到合法 ID 对应的商品才返回 404。重复设置 off 仍然成功，因为请求的目标状态已经满足。

列表则先按同一组条件查 total，再查当前页。total 是筛选后的总数，不是当前页数组长度；items 没查到数据时才为空。排序固定为 id 升序。偏移量用 long 计算，当前实现超过 int 最大值时直接返回空列表，没有额外设置“最多十万页”的规则。

## 5. 我做过的取舍

### H2 内存库，而不是先装 MySQL

我先保证评审能够启动项目，不想把有限时间花在数据库账号、端口和安装上。H2 随应用启动，代价是进程结束后数据丢失。DB_CLOSE_DELAY=-1 只保证当前进程内最后一个连接关闭时数据库仍保留，不能让数据跨重启保存。若换成文件数据库，需要同时重新考虑建表脚本的重复执行，不能只改连接地址。

### 先查存在，再更新状态

这次选了容易理解的做法：查不到返回 404，查到再 UPDATE。代价是多一次查询，并且两步之间存在并发窗口：如果未来支持删除，可能查到后被其他操作删除，而更新方法没有检查影响行数。当前没有删除接口，先记录边界，没有把这段实现描述成并发安全方案。

### 字符串接收参数，手动说明错误原因

ID、分页参数用 String 接收，可以把“不是整数”和“超出存储范围”分开报错。发布请求的 price/stock 也采用 String 字段，因此当前允许纯数字字符串，并非严格只接受 JSON number。数字不去空格，文本字段按现有规则 trim。这是当前实际行为，后续若收紧类型，需要明确规则并补回归。

## 6. 排查印象最深的问题

发布商品曾经返回 500，响应只有“服务出错”。我最初连 SQL 应该在 PowerShell 还是数据库控制台执行都没有分清，所以后来先把“命令在哪运行”“服务端报了什么”分开看。

这次发布失败的关键是主键回填。原先用了 RETURN_GENERATED_KEYS，H2 返回的生成列可能不止 id，还包含带默认值的 created_at，随后 keyHolder.getKey() 无法按单个值读取。修复时明确指定 new String[]{"id"}，只取主键。修改后用真实 POST 请求确认返回 201 和商品 ID，不能只凭编译通过判断修好了。

这让我开始要求 AI 根据具体异常解释原因，不接受只看最后一行 BUILD FAILURE 就断定是环境或某个文件的问题。

| 项目 | 现状与边界 |
|---|---|
| 下单、订单查询、支付、鉴权 | 未实现；也未验证扣库存事务、金额乘法溢出和并发不超卖。 |

| keyword 的 % 和 _ | 通过参数化 SQL 传入，但未转义 LIKE 通配符，仍按通配符解释。 |
| 列表一致性 | total 和 items 是两次查询，并发修改时不保证来自同一个数据快照。 |
| 订单约束 | total_amount 尚无非负或与数量、单价一致的约束；后续下单必须服务端计算并检查范围。 |

新增的 40400 表示接口路径不存在，40500 表示方法不允许；原有商品不存在仍用 40401。预期错误不记 error 日志，未知异常保留日志且不把堆栈返回客户端。
