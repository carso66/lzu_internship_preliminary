## 3. 我的程序分成哪几块

| 文件 / 模块 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `controller`、`dto` | 接收 HTTP 请求、校验参数、转换返回值和统一错误响应 | 请求格式和 HTTP 状态码留在接口层，业务逻辑集中在服务层。 |
| `service` | 下单算价、扣库存、更新支付状态，管理事务边界 | 扣库存与插订单由同一个事务方法管理，支付状态与支付记录也一起提交或回滚。 |
| `mapper`、`resources/mapper` | 用 MyBatis 执行条件更新、插入和分页查询 | 库存条件和查询排序集中在 SQL 中，便于直接检查更新和查询规则。 |
| `schema.sql`、`domain` | 定义表、约束和数据对象 | `products` 保存当前价和库存，`orders` 保存标题与成交价快照，`payments` 通过订单外键关联，并用 `UNIQUE(order_id)` 限制每个订单只能有一条支付记录。 |

## 4. 一次完整链路是怎么走的

```text
POST /api/orders
  → 校验商品 ID、购买数量和收货信息，参数不合法时返回 400
  → 开启事务，执行条件扣库存，要求商品已上架且库存足够
     └─ 更新 0 行 → 查商品，区分不存在（404）、下架或库存不足（409）
  → 读取商品标题和单价，按数据库单价 × 数量计算总额，金额单位为分
  → 生成订单号，写入订单并读取结果
     └─ 写订单失败 → 回滚事务，恢复本次扣减的库存
  → 提交事务，返回 HTTP 201 和订单数据
```

## 5. 一个取舍：我选了 A，没选 B

- **可以在哪两个方案里选**　用 Java `long` 和数据库 `BIGINT` 按整数分存储和计算，或用 Java `BigDecimal` 和数据库 `DECIMAL` 按元存储和计算。
- **我选了**　接口、Java 代码和数据库统一用整数分。下单时用 `Math.multiplyExact` 计算单价乘件数，并检查结果是否溢出。
- **因为**　题目规定接口金额用整数分，当前订单总额只需要用整数分单价乘整数件数。例如 4990 分买 2 件就是 9980 分，计算结果仍是整数分。`BigDecimal` 也能精确计算，按元存算则要在接口边界来回转换元和分。统一用分，接口、算价和落库都用同一个单位，也省去了这一步转换。
- **代价是**　整数分能表示的最小金额是 1 分。以后如果按比例打折、计税或分摊金额，计算中可能出现不足 1 分的部分。这时 `BigDecimal` 更适合保留中间精度，最后再按业务规则舍入到分。

## 6. 我卡得最久的一个问题

- **现象**　本地一直用 JDK 19 构建，题目给出的 Java 起步版本是 17，需要确认评审能否直接启动。
- **我一开始以为**　最初确认的是本机 JDK 19 可以构建和启动，随后才核对评审使用 JDK 17 时的兼容性。
- **试过什么**　先核对题目和 POM，之后用 JDK 19 按 Java 17 目标重新打包并用 `javap` 查字节码版本，最后安装 JDK 17 重跑构建和健康检查。
- **最后靠什么定位的**　看 POM 的 `java.version`，并用 `mvn -v`、`javap -verbose` 核对实际编译环境和 class 文件版本。
- **真正的原因**　POM 原先把编译目标设为 19。改用 `--release 17` 后，JDK 19 也能生成 Java 17 字节码。用 JDK 17 实测 76 项测试通过，健康检查返回 HTTP 200。
