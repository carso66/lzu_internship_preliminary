# 设计说明

## 1. 表结构设计
- **金额字段（price, unit_price, total_amount）**：统一使用 `INT` 存储“分”（如 1990 表示 19.90 元），坚决不用浮点数，避免精度丢失。计算时提前强转 `long` 防止乘法溢出。
- **订单快照**：在 `orders` 表中冗余了 `product_title` 和 `unit_price`。因为商品后续可能会被改价或下架，订单必须保留下单那一刻的快照，这是电商系统对账和追溯的基本要求。
- **状态枚举**：商品状态 `status` 使用 `VARCHAR` 存储 `on`/`off`，比 `BOOLEAN` 语义更清晰，且未来扩展为 `sold_out` 等状态时不需要改表结构。

## 2. 核心技术实现
- **事务控制（L1 核心）**：下单接口使用了 `@Transactional` 注解。在同一个事务内，先查询商品（并使用 `FOR UPDATE` 加上行锁防超卖），校验库存，扣减库存，最后插入订单。如果插入订单抛出异常，库存扣减会自动回滚。
- **统一响应与全局异常**：封装了 `ApiResponse<T>` 和 `BizException`，配合 `@RestControllerAdvice` 全局拦截。业务代码只管抛出错误（如 40001 参数错、40401 不存在、40901 库存不足），拦截器统一包装成 JSON 并设置对应的 HTTP 状态码。
- **参数严格校验**：为了应对形如 `"price": "1000"` 的非法类型，Controller 入参使用了 `Object` 接收（或 `String` 接收分页参数），手动判断类型后再转换，避免了 Spring 自带的默认类型转换导致绕过统一异常体系。

## 3. 取舍与放弃
- **放弃了 L2 挑战**：在有限时间内，优先保证了 L0 和 L1 接口的健壮性（如处理了 H2 主键返回的坑、金额溢出、订单号生成），而不是盲目堆砌高级功能。
- **没有引入 ORM**：使用原生 `JdbcTemplate`，虽然写 SQL 代码量略大，但可以完全掌控 SQL 执行过程和参数绑定，防止 SQL 注入，也减轻了项目的依赖负担。
