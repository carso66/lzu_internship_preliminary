## 3. 我的程序分成哪几块

### 3.1 技术选型

| 选型 | 选择 | 理由 | 放弃了什么 |
|---|---|---|---|
| 语言 | Java 17 | README 推荐的基线（`start.spring.io` / Maven / Java 17）；LTS；`record` 让 DTO 和领域对象一个声明搞定 | — |
| 框架 | Spring Boot 3.5.4 | 官方题目给出的最快起步路线；Web/JDBC/Validation 三个 starter 自动装配就能干活，48 小时里配置成本最低 | 没上 Security、Actuator 等非必需依赖 |
| 数据访问 | **JdbcTemplate**，不引 ORM | 见下段 | 手写了 4 个 RowMapper，样板代码变多 |
| 数据库 | H2 内存库 | 「评审一条命令起服务」的硬要求；`jdbc:h2:mem:marketplace;DB_CLOSE_DELAY=-1`，每次启动由 `schema.sql` 重建 | 重启丢数据（取舍见第 5 节） |
| 金额 | `BIGINT` 存「分」，全链路整数 | README 明示的最易出错点；`long × int` 用 `Math.multiplyExact` 兜溢出 | 没用 `BigDecimal`——题目规定单位是分，小数场景不存在 |

**为什么用 JdbcTemplate、不引 JPA / MyBatis**：工程只有两张表、查询全是单表 CRUD 加一条条件 UPDATE，实体关系和脏检查都没有需求，ORM 的核心能力在这里没有用武之地。选择的实际理由是：**在当前项目规模下少一层框架抽象，让每条进入数据库的 SQL 显式、可检查、可单独测试**（Repository 单测直接断言 SQL 文本和占位符绑定顺序，见第 9 节）。两点常被夸大的说法如实澄清：JPA 并非必然自动建表——自动 DDL 可以关闭，但引入它意味着实体注解和 `schema.sql` 成为同一份结构的两个来源，需要人工保持同步，多一个漂移点；MyBatis 是 SQL 映射框架而非 ORM——它不接管 SQL，只是在这个规模仍多出 mapper XML/接口一层。后两者在本项目见不到收益，复杂度是确定的。**代价如实说**：`RowMapper` 逐字段手写，改表要同步三处（schema / mapper / 领域 record），这是把表结构写进 Repository javadoc 注释的原因——让漂移可见。

### 3.2 分层与各层职责

```
HTTP 请求 → Controller → Service → Repository(接口) → JdbcTemplate → H2
                │            │            │
                │            └─ 业务规则、事务边界、DTO↔model 翻译
                └─ 参数接收(@Valid)、HTTP 状态码(201/200)、ApiResponse 包装
错误路径：任何一层抛异常 → GlobalExceptionHandler(@RestControllerAdvice)
          → 统一收敛为 {code, message, data} + 对应 HTTP 状态
```

| 包 | 负责什么 | 为什么单独拆出来 |
|---|---|---|
| `controller/` | 路由、`@Valid` 接参、成功时的 HTTP 状态（创建类 201，其余 200） | 让「HTTP 语义」只出现在一层里；业务判断一条都不许有 |
| `service/` | 业务规则（不存在→40401、下架→40902、库存不足→40901）、事务边界、服务端算价、订单号生成、DTO/model 翻译 | 下单将来要接支付（改订单状态）、鉴权，逻辑放 Controller 会和参数校验缠死；`OrderNoGenerator` 单独成类是因为它是纯函数策略，可以不启 Spring 单测 |
| `repository/` | 接口 + `Jdbc*` 实现，唯一允许出现 SQL 的地方 | Service 面向接口编程，测试里可以整体换成 Mockito 桩；SQL 相关问题集中在两个实现类里查 |
| `common/` | `ApiResponse` / `ErrorCode` / `BusinessException` / `GlobalExceptionHandler` | 接口约定是跨模块合同，集中在一个包里，评审看错误规则只需看这一处 |
| `dto/` | 请求/响应 record，携带校验注解 | 请求体形状和领域模型不是一回事（如 `CreateOrderRequest` 没有价格字段——**故意不接受**客户端传价），分开后各自演化 |
| `model/` | `Product` / `Order` / `PageResult` 领域记录 | Repository 返回的就是它，Service 在中间只加规则不加字段 |
| `config/` | Jackson 严格整数反序列化 | 只影响 JSON 请求体的一个开关，隔离出来避免误伤其它序列化行为 |

**事务边界为什么画在 `OrderServiceImpl.create` 上**：扣库存和插订单必须同生共死，这是**业务一致性**概念而不是 SQL 概念。画在 Repository 上就是两个事务（L1-6 明令禁止的情形）；画在 Controller 上会把参数校验甚至 JSON 解析的时间也圈进事务和连接占用里。`@Transactional` 只加在这一个方法上，其余读接口不开事务——单条 SELECT 没有原子性需求，不为此付连接开销。

### 3.3 表设计（`schema.sql`）

两表即 README 示例的两表，字段命名 snake_case，对应 JSON 的 camelCase 由 DTO 层承担。这里只讲**为什么这么定**：

| 决定 | 理由 |
|---|---|
| 金额三列 `price / unit_price / total_amount` 用 BIGINT | 分单位整数；`total_amount` 不落库现算也行，但订单是历史凭证，金额必须固化，见快照条目 |
| CHECK 约束（价格/库存 ≥0、quantity >0、status 枚举） | 与 Java 校验**双轨对齐**：应用层报错给用户看，DB 约束是最后防线——直连数据库或将来别的应用写入时，脏数据进不来。表里有 CHECK 而代码不测它，不丢人；代码有规则而表里没有，才危险 |
| `orders.product_id` 外键指向 `products.id` | 引用完整性。没有「删除商品」接口，所以暂不触发级联问题；测试清库按先 orders 后 products 的顺序删 |
| `product_title / unit_price / total_amount` 是**下单时刻的快照** | 订单记录的是「当时的交易事实」，不是「商品的当前指针」。商品改名、调价、下架都不能让历史订单变形。副作用（好的那种）：查订单详情不需要 JOIN products |
| `order_no VARCHAR(48) UNIQUE` | 48 是量出来的，不是拍的：占位号 33 字符 + 正式号 16~29 字符（推导写在 schema.sql 和 `JdbcOrderRepository` 注释里）。UNIQUE 是订单号唯一性的最终兜底，见第 4 节 |
| 索引只有 `idx_orders_buyer_phone` 一条 | 对应唯一有非主键过滤 + 排序需求的查询（L1-8）。`order_no` 的 UNIQUE 已隐式建索引，不重复建；products 一条不加——没有做过性能测量，也没有证据支持加索引在当前规模（测试数据为百行级）下的收益，不做无依据的设计。L2-13 要求的 EXPLAIN 前后对比没做，所以不声称索引优化了什么，只说明放置理由（判断：按 phone 等值过滤是列表的主要查询条件；排序列 created_at 不在索引内，小规模下影响有限） |
| `created_at` 由应用写入（`LocalDateTime.now()`） | 统一由应用生成时间。H2 `TIMESTAMP` 回读为微秒精度，创建响应与查询响应可能存在亚微秒差异 |
| `paid_at` 为预留列 | 服务于尚未实现的支付功能（L2-9），当前业务不写入、恒为 null；现在建好列，是为了避免将来为加一列重写建表脚本 |
| 全部 `CREATE TABLE/INDEX IF NOT EXISTS` | 幂等。多个 `@SpringBootTest` 上下文共享同一个 H2 内存库时会重复执行脚本；用 `continue-on-error` 吞「表已存在」会把真错误一起吞掉，幂等写法从根上避免 |

### 3.4 统一响应、错误码与严格校验

`ApiResponse<T>` 是 `{code, message, data}` 三字段 record，成功/失败同构，`data` 无内容时为 null——这是 README 第 3 节的硬要求。

**错误码用枚举把「码 + HTTP 状态 + 默认文案」三元组锁死**（`ErrorCode`）：代码里抛的是语义（`STOCK_INSUFFICIENT`），不可能出现「库存不足却返回 200」这类码/状态错配，映射表只此一份。README 码表（0/40001/40401/40901/40902/40903/50000）全部照抄；另自定两个码 `40501`（方法不支持→405）、`41501`（Content-Type 不支持→415），按 HTTP 标准语义补位、不复用已有码含义——**这两个自定码需要在 SUBMISSION.md 向评审说明**，文档已预留。

**整数参数的「严格」做了三层防线**，对应 README「0、-1、`"2"` 都要处理」：

```
第1层 Jackson 反序列化   JacksonConfig: Integer 逻辑类型对 String/Float/空串一律 Fail
                         → "1990"、1990.5、"" 进不来（默认行为会静默转换，这是坑）
第2层 Bean Validation    @NotNull/@Min/@Max/@Size/@Pattern，查询参数走 @Validated 方法校验
                         → 缺失、0/负数、超长、status 非 on/off
第3层 数据库 CHECK       兜住一切绕过前两层的路径（直连 DB、后续新入口）
```

每层失败都有对应的异常处理器接住（共 12 个 `@ExceptionHandler`），message 精确到字段名；**兜底 `Exception` 一律 500 + 50000 + 固定文案「服务内部错误」，堆栈只进日志不下发客户端**——README 明确要求，也避免泄露内部结构。查询参数本来就是字符串，不走 Jackson 那层，非法值由类型转换异常接住，两层各管各的入口，注释里写明了。

### 3.5 商品组合筛选、分页与转义

`GET /api/products` 的 SQL 在 `JdbcProductRepository.findPage` 里动态拼装：

- **组合**：keyword（标题模糊）/ status（精确）/ category（精确）三个条件各自独立开关，任意叠加；**空白值处理并不相同**——keyword/category 的空白串按「未提供」忽略（Repository 层 `isBlank` 判断），而 status 的空串会被 Controller 的 `@Pattern(regexp = "on|off")` 先行拦下返回 400 + 40001（空串不匹配模式），Repository 里的 `isBlank` 只是冗余防护。
- **注入防线**：拼的只是**条件片段的有无**，值一律走 `?` 占位符绑定，参数按 WHERE 子句出现顺序进列表。全工程没有一处字符串拼接用户输入进 SQL。
- **LIKE 转义**：keyword 用 `LIKE ? ESCAPE '\'`，绑定前先 `escapeLike`——顺序必须是**先转义 `\` 本身，再转义 `%` 和 `_`**，反了会把刚插入的转义符再加工一遍。效果：搜 `100%` 匹配字面「100%」，而不是把 `%` 当通配符把全表捞出来；搜 `_` 同理。
- **count 与 items 共用 WHERE**：两条 SQL 使用同一份条件字符串和前缀参数，筛选口径一致；但它们是两条独立查询（列表接口未开事务），两次执行之间若有并发写入，`total` 与页内容可能来自略有差异的快照。对只读列表接受这一一致性边界，不做额外处理。
- **分页**：`page` 默认 1、`pageSize` 默认 10 上限 50（README 要求）。两个细节：① offset 用 `(long)(page-1) * size` 算——`page=2147483647` 时 int 乘法会溢出成**负数** offset，SQL 直接报错，long 之后大 page 只是自然翻到空页；② README 没给 page 上界，我定的是**大 page 返回空列表（200）而不是报错**，理由：翻过头是正常用户行为不是非法输入。排序 products 用 `id DESC`（题目未规定，自定：近似最新在前，唯一键使排序确定）；但确定排序 ≠ 翻页绝不重复/遗漏——OFFSET 分页在两次翻页请求之间有新数据插入时，记录会整体位移，仍可能出现跨页重复或漏项；彻底的做法是 keyset 分页（记录上次看到的 id，改用 `WHERE id < ?` 定位），本项目未做。`LIMIT ? OFFSET ?` 的占位符绑定顺序是 limit 在前 offset 在后，这是 JDBC 按出现顺序绑定的规矩，专门在注释和单测里钉死了（见第 9 节）。

## 4. 一次完整链路：下单

选我最有把握的一条——`POST /api/orders`（L1-6 核心，7 分）：

```
POST /api/orders {productId:3, quantity:2, buyerName, buyerPhone, address}
  → Jackson 严格整数 + @Valid：quantity 必须是 ≥1 的真整数（"2"/2.5/0/-1/缺失 → 400+40001，到此为止）
  ── 以下 @Transactional，任一步失败整单回滚 ──
  1. findById(productId)   不存在 → 404+40401；status=off → 409+40902
  2. 服务端算价            unitPrice×quantity（Math.multiplyExact，溢出→400）
                           ★ 请求体里根本没有价格字段，客户端传价无处可传
  3. 原子扣库存            UPDATE products SET stock = stock - ?
                           WHERE id = ? AND status = 'on' AND stock >= ?
     ├─ 影响 1 行 → 扣减成功
     └─ 影响 0 行 → 重读商品区分真实原因（下架 40902 / 不足 40901）→ 抛异常 → 回滚
  4. 插订单                INSERT orders（占位订单号 "P"+UUID，快照 title/价格）→ 取自增 id
  5. 回填订单号            "SO"+yyyyMMdd+id(%06d) UPDATE 回写；影响行数≠1 → 抛异常 → 回滚
  ── commit ──
  → 201 + {code:0, data:{orderNo, totalAmount, 商品快照…}}
```

### 4.1 为什么第 3 步能防超卖

关键是把「判断够不够」和「扣」合并进**同一条 SQL**。两种反面写法后果不同，不能混为一谈：**(a) 读取旧值再覆盖写**——`SELECT stock` 判断后执行 `UPDATE SET stock = 本事务算出的剩余量`，覆盖写会造成**丢失更新**：两个事务都读到 stock=1、都判断通过、都写回 0，实际卖出 2 件而库存只减 1，直接超卖；**(b) 无条件原子扣减**——`UPDATE SET stock = stock - ?` 不带库存检查，扣减本身原子、不会丢失更新，但库存**可以扣成负数**；表上有 CHECK 约束时会被拒绝，代价是下单事务以数据库约束错误失败，而不是拿到明确的业务码。条件 UPDATE 同时治掉两者：`stock = stock - ?` 按增量写、不丢失更新，`stock >= ?` 在库内挡住不足量、不产生负库存。并发下数据库对同一行的 UPDATE 以行锁排队串行：第一个事务把 1 扣成 0，后九个的 WHERE 在锁释放后重查已不成立，影响 0 行 → 业务码 40901。**不超卖的保证落在数据库语句级，不依赖 Java 侧的锁。**

一个容易忽略的细节：0 行 ≠ 一定是库存不足（也可能是并发的下架操作把 `status='on'` 改掉了）。所以失败后**重读一次商品**区分真实原因，避免并发下把 40902 误报成 40901。前置第 1 步查到的状态到第 3 步之间永远存在窗口，这是「读时判定、写时防御」的正常形态。

### 4.2 订单编号：为什么「先插再回填」

序号要取 orders 自增主键，而主键**只有插入之后才存在**——所以流程必然是：先用占位号 `P`+UUID（满足 NOT NULL+UNIQUE）插入，拿到 id 后在**同一事务内**用正式号覆盖。占位号不对外可见：事务提交前它只存在于当前事务的未提交状态，常规隔离级别下其他读者看不到，提交时已被正式号覆盖；接口返回值取回填后的结果，并断言回填影响行数必须为 1，否则抛异常回滚，避免返回与库内不一致的订单号。

唯一性的适用范围（如实限定，不说无条件的「全局唯一」）：自增主键保证的是**当前数据库实例生命周期内**唯一，同一实例生成的订单号因此互不重复，DB 侧 `UNIQUE(order_no)` 兜底。H2 内存库重启后由 `schema.sql` 重建，自增计数从头开始。同日重启空库时，日期和自增序号可能同时重复，因而可能重新生成相同的订单号。订单查询使用下单响应实际返回的订单号。若需要跨独立数据库实例的持久唯一性，需要相应的持久化与编号设计。日期段仅供阅读，跨天序号不重置（`%06d` 超 6 位自然进位不截断）。**代价**：每单多一条 UPDATE；**备选**：独立日期序号表可以做出「每天从 001 开始」的编号，但引入一个多实例下需要单独防竞争的状态，这里判定不值得。

## 5. 三个取舍：我选了 A，没选 B

**取舍一：JdbcTemplate，没选 JPA/MyBatis**
- 因为：两张表、全单表操作的规模下，显式控制 SQL、少一层框架的价值高于 ORM 的便利（论证见第 3.1 节，这里不重复）。
- 代价是：RowMapper 样板代码；schema、mapper、领域 record 三处需人工同步（缓解：三处互相引用注释 + 加载同一份 schema.sql 的集成测试）。

**取舍二：H2 内存库，没选文件库/MySQL**
- 因为：评审零依赖一条命令起服务，每次启动数据状态完全一致（由 `schema.sql` 重建）；测试与运行共用同一份建表脚本，行为可复现。
- 代价是：**重启即清空**，测试中新建的商品下次启动就不存在——接受，本项目的定位是可重跑的服务而不是数据持久。若换 MySQL，README 要求附 `docker-compose.yml`，评审环境依赖变重。另外迁移**不是换一个 JDBC URL**：需要增加 MySQL 驱动依赖、改数据源配置，并重验 DDL（IDENTITY 语法）、`LIMIT/OFFSET` 及各 SQL 的方言兼容——这些都未实测（见第 7 节）。

**取舍三：条件 UPDATE 防超卖，没选 `SELECT FOR UPDATE` 或版本号乐观锁**
- 因为：一条语句同时完成检查与扣减，没有锁的获取/释放时机问题，没有版本号冲突后「重试几次」的策略问题，代码量和出错面都最小。
- 代价是：失败原因被「影响 0 行」掩盖，需要重读一次商品区分 40901/40902（多一次读，换来业务码准确）；且它依赖**同一个数据库实例**的行锁语义：多个应用实例共享同一个库时，行锁照样跨连接串行，条件更新依然成立；一旦跨库/分库，单库锁不再构成全局保证，需要额外的一致性设计。

## 6. 我卡得最久的一个问题

**主线：商品分页 SQL 的 LIMIT/OFFSET 绑定顺序写反——Mock 测试全绿，靠源码审查暴露。**

- **现象**：`JdbcProductRepository.findPage` 的 SQL 写的是 `LIMIT ? OFFSET ?`，JDBC 占位符按**出现顺序**绑定，第 1 个 `?` 是每页条数、第 2 个是偏移量；代码里参数却按 (offset, limit) 顺序传——两者反了。这个错误完全静默：两个值都是合法整数，数据库不会报错，换序只是「翻到的页不对」，属于语义错误而非语法错误。当时已有的是 Service/Web 层 Mock 测试，它们不检查传给 JdbcTemplate 的 SQL 文本和绑定参数，全部通过；**Repository 层当时还没有任何专项测试**。
- **我一开始以为**：分页代码写法常规，上层测试都过，这一层应该没问题。
- **怎么发现的**：在**建表之前的源码审查阶段**（schema.sql 尚未落地，真实数据库联调还没开始），借助 ChatGPT 逐段审查 Repository 代码时发现占位符顺序与绑定顺序不一致。定位靠的是代码审查，不是任何一层测试——这是本节最值得记录的地方。
- **修复与补强（分工如实写）**：代码修正由企业 AI 完成；修正之后，我要求补充**直接断言最终传给 JdbcTemplate 的 SQL 文本和参数绑定顺序**的测试——用 `mockingDetails(...).getInvocations()` 读取真实调用记录（varargs 已展开），避开 Mockito 对变长参数捕获的匹配歧义。`JdbcProductRepositoryTest` / `JdbcOrderRepositoryTest` 是这次事故**新增**的直接产物（见第 9 节），不是对既有测试的升级。建表完成后，真实 H2 联调时用真实 SQL 执行复核了分页行为，结果正常。
- **真正的原因 / 教训**：Mock 测试验证的是「我以为我会怎么调用」，不是「实际传给 JDBC 的是什么」。排序、分页参数这类**顺序敏感的调用**，要么断言到 SQL 文本和绑定参数层，要么落到真实数据库里验——两层在事故之后都补上了，缺一层这类错误就能一直潜伏。

**两个如实记录的次要插曲**（均发生在联调/提交阶段，排查成果主要属于 AI，不是我的个人战绩）：其一，真实联调时发现 Windows 平台编码问题——curl 直接 `-d` 发含中文的 JSON 会因 GBK 字节流导致 400「JSON 格式错误」，**该问题主要由 AI 定位并解决**：`application.yml` 显式配置 `spring.sql.init.encoding: UTF-8`，测试请求改走 `--data-binary @UTF-8文件`，不依赖平台默认编码。其二，GitHub 推送过程中 TLS 连接报错反复出现过，最终未留下持续问题，此处不展开。

**故障注入为什么可信**：spy 只替换插订单这一步，库存扣减由未被 mock 的真实 Repository 对真实 H2 执行；异常沿真实 `@Transactional` AOP 代理上抛。断言「响应 500+50000 + 库存恢复为 3 + 零残留订单」+ `verify(insert)` 证明流程确实走过了扣减——回滚是生产代码里那个事务干的，不是测试方法自带事务顺手掩盖的。**覆盖范围如实说明**：故障只注入在「订单插入」这一个点，未覆盖订单号回填 UPDATE 失败等其他写失败路径——验证的是「回滚机制真实有效」，不是「所有故障都已穷举」。

**并发测试的严格口径**：每轮独立准备一个库存=1 的商品；10 个响应逐一分类计数，**超时/500/其它错误一律记为「其它」，不许混进「库存不足」**；断言恰好 1 成功 + 9 个 409/40901 + 0 个其它 + 最终库存 0 + 恰好 1 条新订单。脚本可用 `mvn -Dtest=OrderConcurrencyTest test` 单独重跑。
