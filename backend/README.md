## 3. 接口约定

**必遵守**：所有已实现的接口，无论成功还是失败，响应体都用统一的 JSON 结构，包含 `code`、`message`、`data`。HTTP 状态和业务码按下表及各接口的明确要求返回。没有数据时，`data` 可以是 `null`。

```json
{ "code": 0, "message": "ok", "data": { } }
```

| code      | HTTP      | 场景                     |
| --------- | --------- | ---------------------- |
| `0`       | 200 / 201 | 成功                     |
| `40001`   | 400       | 参数不对（缺字段、类型错、超范围、枚举非法） |
| 自定（非 `0`） | 401       | 鉴权失败（仅选做 L2-11 时适用）    |
| `40401`   | 404       | 商品 / 订单不存在             |
| `40901`   | 409       | 库存不足                   |
| `40902`   | 409       | 商品已下架                  |
| `40903`   | 409       | 订单已支付，不可重复支付           |
| `50000`   | 500       | 服务出错（**不把堆栈返回给客户端**）   |

**由考生决定**：`message` 的具体文案，以及 `data` 中题目未明确要求的字段。标注「仅展示 `data`」的示例省略了统一外层，实际响应仍需包含三个顶层字段。

**金额单位统一是"分"（整数）**。`1990` 表示 ¥19.90。**全程不要用浮点数存/算金额**，这是本方向最容易翻车的地方。

## 4. L0 基础（40 分，必做）

### L0-1 建表（手写 `schema.sql`）

表和字段仅做示例参考，具体字段名称，格式，以及是否需要增加其他表可以自行决定

```sql
products(id, title, price, stock, category, description, status, seller_name, created_at)
orders(id, order_no, product_id, product_title, quantity, unit_price, total_amount,
       buyer_name, buyer_phone, address, status, created_at, paid_at)
```

### L0-2 `POST /api/products` 发布商品

```json
{ "title": "测试商品", "price": 1990, "stock": 10, "category": "文具", "description": "备注", "sellerName": "校园数码铺" }
// 201
{ "code": 0, "message": "ok", "data": { "id": 13, "title": "测试商品", "price": 1990, "stock": 10, "status": "on", ... } }
```

校验：字段长度，类型等基础问题  
不合法 → 400 + `40001`，`message` 说清哪个字段错了。

### L0-3 `GET /api/products` 商品列表

不使用筛选条件时，省略 `keyword`、`status` 和 `category`：

```text
GET /api/products?page=1&pageSize=10
```

| 参数                  | 说明                               |
| ------------------- | -------------------------------- |
| `keyword`           | 标题模糊匹配                           |
| `status`            | `on` / `off`，不传表示全部              |
| `category`          | 分类精确匹配                           |
| `page` / `pageSize` | 默认 1 / 10，`pageSize` 范围 **1~50** |

成功时 `data` 必须包含 `total`（筛选后的总条数）、`page`、`pageSize` 和 `items`（当前页的商品数组）。示例（仅展示 `data`）：`{"total":0,"page":1,"pageSize":10,"items":[]}`。**三个筛选条件可以叠加。**

### L0-4 `GET /api/products/{id}`

存在返回单条；不存在 → 404 + `40401`。

### L0-5 `PATCH /api/products/{id}/status`

请求 `{ "status": "off" }`，成功返回 HTTP 200。示例（仅展示 `data`）：`{"id":1,"status":"off"}`。请求中的 `status` 只能是 `on`/`off`，否则 400 + `40001`。

## 5. L1 进阶（15 分）

### L1-6 `POST /api/orders` 下单（核心，7 分）

```json
{ "productId": 3, "quantity": 2, "buyerName": "张三", "buyerPhone": "13800138000", "address": "兰州市城关区天水南路222号" }
// 201
{ "code": 0, "message": "ok", "data": {
  "id": 1, "orderNo": "SO202611190001", "productId": 3, "productTitle": "考研数学复习全书",
  "quantity": 2, "unitPrice": 4990, "totalAmount": 9980, "status": "created",
  "buyerPhone": "13800138000", "address": "…", "createdAt": "…" } }
```

要做的事，顺序想清楚：

1. 校验 `quantity` 是 **≥1 的整数**（0、-1、`"2"` 都要处理）
2. 查商品：不存在 → 404；`status = 'off'` → 409 `40902`「商品已下架」
3. 检查库存：`stock < quantity` → 409 `40901`「库存不足」
4. **扣库存**
5. **插订单**，`unit_price` 和 `total_amount` **由服务端根据数据库里的价格计算**，不接受客户端传的价格
6. `order_no` 自己生成（日期 + 序号即可，要唯一）

**扣库存和插入订单必须在同一个数据库事务中。** 下单成功时库存减少、订单写入；插入订单失败时，已扣的库存必须回滚。L1 按单次下单验收，并发场景见 L2-10，具体实现由考生决定。

### L1-7 `GET /api/orders/{orderNo}`

按订单号查详情；不存在 → 404 + `40401`。

### L1-8 `GET `



查某个手机号的订单列表，按创建时间倒序。

## 6. L2 挑战（10 分，任选 1~2 个，每个 6 分，两个封顶 10）

**L2-9 支付链路（推荐）**

`POST /api/payments` 请求包含 `orderNo` 和 `method`，其中 `method` 为 `alipay` 或 `wechat`。  
成功返回 HTTP 200。示例（仅展示 `data`）：`{"paymentId":"PAY…","orderNo":"…","amount":9980,"status":"paid","paidAt":"…"}`。

要求：

- 订单不存在 → 404；订单已 `paid` → 409 + `40903`
- 支付成功要\*\*把订单 `status` 改成 `paid` 并写 `paid_at`
- 新增 `payments` 表并落库
- **幂等**：同一个 `orderNo` 重复支付，第二次必须返回 409，不能生成两条成功记录
- 可以直接同步返回 `paid`（不用真的做异步回调）

**L2-10 并发不超卖**

自行准备一个已上架且库存为 1 的商品，同时发起 10 个有效下单请求，每个请求买 1 件。

- **响应**：恰好 1 个请求成功，其余 9 个返回 409「库存不足」。
- **最终数据**：等待所有请求结束后，商品库存恰好为 0，本轮恰好新增 1 条订单。

提交可重跑的脚本或测试，在 `SUBMISSION.md` 写明如何准备数据、如何运行，以及如何核对这两项结果。并发控制方案和验证工具自选。

**L2-11 最简鉴权**  
`POST /api/auth/login`（账号写死），成功时在 `data` 中返回随机 token。`POST /api/products`、`PATCH /api/products/{id}/status` 必须带有效的 `Authorization: Bearer <token>`。  
缺少或无效的 token 返回 HTTP 401，响应体仍使用统一结构；业务码由考生自定（非 `0`），在 `SUBMISSION.md` 或其中链接的接口文档里说明。  
不要求 JWT、不要求过期、不要求角色。

**L2-12 自动化测试**  
编写 3~5 条自动化测试（Java 用 JUnit，Go 用 `testing`），覆盖：正常下单库存减 1、库存不足返回 409、`quantity=0` 返回 400。  
在 `backend/` 目录下用一条命令运行全部测试：Java 项目运行 `mvn test`，Go 项目运行 `go test ./...`。把实际使用的命令写进 `SUBMISSION.md`。

**L2-13 索引 + 说明**

从已实现的商品或订单查询中选一条 SQL，自行设计并添加索引。在 `DESIGN.md` 写明查询和典型参数、选择索引列的理由，以及评审如何复核你的结论。

使用同一份数据和查询参数，对比加索引前后的执行计划（如 `EXPLAIN`）或其他可复核的查询证据，解释扫描、排序或查询耗时的变化。如果差异不明显，也可以说明原因；满分看证据和解释，无需达到指定的提速比例。
